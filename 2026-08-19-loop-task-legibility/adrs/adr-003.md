# ADR-003: Run-bound live DAG enters scope (reverses graph-eng deferral)

## Status

Accepted

## Date

2026-08-19

## Context

The graph-eng spec (2026-08-19, archived) explicitly deferred "live run-topology visualization" to its own effort; its run page kept the timeline as the run view. Today the only DAG in the product is the static spine on the loop detail page (`loop-body-dag.tsx`), never bound to a run. Operators cannot see the shape of executing work: which node is running, per-node progress, errors, retries — the run page lists exception nodes only. BUG-20260719 (P1, re-found 6×) documents operators concluding "stalled" while real progress happened.

## Decision

This spec is that deferred effort. Ship a run-bound live DAG in the operator register of the run page: the loop's authored topology rendered with live per-node state (status, attempt, error class, fan-out rollup, links to session/cell record), bound to the per-run node×generation read model this spec introduces. The plain register derives its step progress from the same read model — one source, two projections.

## Alternatives Considered

### Alternative 1: Keep the deferral (node roster table only)

- **Description**: Ship a tabular all-nodes view; leave topology static.
- **Pros**: Cheaper; table answers "what state is node X in".
- **Cons**: Cannot answer shape questions (where the run is in the graph, what's parallel, what's downstream-blocked); leaves the static DAG lying by omission next to live data.
- **Why rejected**: Owner: the executing-DAG view is "extremely necessary" and the highest-value redesign target.

### Alternative 2: Reuse the editor canvas for run rendering

- **Description**: Bind run state onto the authoring canvas.
- **Pros**: One graph renderer.
- **Cons**: Authoring affordances (drag, edit, palette) contaminate an observability surface; editor is fork/edit-oriented.
- **Why rejected as the surface**: run view is read-only observability; whether renderer internals are shared is a Part II implementation choice, not a surface decision.

## Consequences

### Positive

- Operators read execution shape at a glance; node roster, steps, and DAG share one read model (no derived-state drift).

### Negative

- Largest UI lift in the spec; the visual contract is the landed set at `docs/design/opendesign/loop-legibility/` (`loop-legibility-run-dag.html`, `loop-legibility-run-roster.html`, `DESIGN-NOTES.md`).

### Risks

- Live-binding fidelity (SSE gaps) → the read model must be poll-consistent, stream-accelerated (Part II).
- Fan-out scale (wide generations) → rollup grammar per node (count chips), never one element per item.
