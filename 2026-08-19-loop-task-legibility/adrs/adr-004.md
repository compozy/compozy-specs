# ADR-004: Classification rides existing provenance columns — no tasks schema change

## Status

Accepted

## Date

2026-08-19

## Context

Front 1 needs every task listing surface to exclude loop execution records by default and reveal them via a typed filter with structured provenance. The `tasks` table already carries the discriminators: `created_by_kind/ref` (loop records are `daemon`/`loop-coordinator`, covered by `idx_tasks_created_by`), cell `metadata_json` (loop_run_id, generation, node_id, item_index — `internal/loop/coordinator_metadata.go:20-32`), and `task_runs.run_kind`/`loop_run_id` (the one ADR-acknowledged correlation column). Only the coordinator task lacks metadata. The kernel must stay loop-noun-free (archived loops-refac ADR-006).

## Decision

No new column on `tasks`. Classification and filtering ride what exists:

1. Default exclusion = SQL predicate on `created_by` (`internal/task` gains a **neutral** `CatalogQuery.ExcludeCreatedBy []ActorRef`; the api/core handler owns the mapping `include_loop=false → exclude {daemon, loop-coordinator}`). The kernel never sees the word "loop" in the query model except the acknowledged `LoopRunID` correlation field.
2. Run scoping (`loop_run_id=`) = a correlated `EXISTS` semi-join against `task_runs.loop_run_id` (indexed): one row per task regardless of attempt-run count, applied before ordering and pagination (never post-pagination `DISTINCT`); covers cells and the coordinator.
3. Display provenance = project cell `metadata_json` into the catalog item's optional `loop` object; the coordinator seed gains the same metadata keys (data change, not schema).
4. The web id-regex contract is deleted; provenance is fields end-to-end.

## Alternatives Considered

### Alternative 1: New `tasks.kind`/`source` column

- **Description**: Goose migration adding a typed classification column mirroring `task_runs.run_kind`.
- **Pros**: single-column predicate; no join for run scoping; self-documenting schema.
- **Cons**: schema migration + atlas + sqlc churn; a second classification source of truth beside `created_by`; naming it without loop nouns gets contorted.
- **Why rejected**: everything the surfaces need is already columnar and indexed. Recorded fallback: if the `task_runs` join proves awkward or slow in implementation, promote to a generated column on `metadata_json.loop_run_id` (Temporal visibility-schema pattern) — still no semantic kind column.

### Alternative 2: Filter by id prefix (`LIKE 'loop.%'`)

- **Description**: reuse the id grammar in SQL.
- **Pros**: zero changes.
- **Cons**: string-matching is the contract being killed; collides with user-created ids; unindexable semantics.
- **Why rejected**: classification is by provenance, never by name (Part I business rule).

## Consequences

### Positive

- Zero `tasks` migrations; `idx_tasks_created_by` already serves the hot predicate; kernel neutrality preserved by construction.

### Negative

- Run scoping costs a join; provenance projection requires adding `metadata_json` to catalog columns for included-loop queries.

### Risks

- Join performance on large workspaces → run-scoped queries are small by nature; fallback recorded above.
- Pre-existing coordinator tasks lack metadata → a dedicated **provenance backfill pass** repairs them (metadata-only, idempotent, relational via `task_runs.loop_run_id → loop_runs`, covers coordinators of ACTIVE runs too — it is not lifecycle settlement; see ADR-006). Rows whose run is gone and unreconstructible render a truthful degraded `loop` object from relational facts (`run_id`, `role` from `run_kind`) — never id/title parsing.
