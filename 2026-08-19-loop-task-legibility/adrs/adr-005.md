# ADR-005: Run reads are computed projections — on-demand roster, pure briefing, durable paged timeline; SSE accelerates, never narrates alone

## Status

Accepted

## Date

2026-08-19

## Context

Front 2 needs a per-run node×generation read (roster), a plain-language verdict (briefing), and a full-history timeline — powering the live DAG, the node roster, the steps progress, and the narrated story, with CLI/HTTP parity. Today the web derives the story from a client-side SSE buffer capped at 500 frames with no durable backfill except `generation_started`, and per-node state exists only for exceptions. The loop tables already hold everything (`loop_generations`, `loop_generation_outputs`, `loop_node_controls`, `loop_node_waits`, `loop_node_attempts`, `loop_run_events` — all indexed by run).

## Decision

1. **Roster = computed on demand** from the existing loop tables + the pinned definition snapshot. The projection enum is closed and the source→projection mapping total: the 14 persisted output states (with controls/waits/retry-schedule precedence) plus derived `not_taken` — which projects **only from durable route evidence** (`route_taken` electing another arm, `branch_pruned`, recorded route causes); a reachable node with no output row projects `pending`, never `not_taken`. No materialized projection table. Fan-out pages under a cursor; rollups always present. Attempt history reads `loop_node_attempts` (first public exposure); nodes carry `next_retry_at`, `child_loop_run_id`, and structured cancellation disposition/actor.
2. **Briefing = pure function** in `internal/loop` over roster + requests/gates + run status + usage — a deterministic triage cascade (`approval > quarantine > request > failure > backoff/quota > running > terminal`), returning `{tone, headline, detail, blockers[+unblocker command], progress, usage}`. Served by the handler; the web renders the served verdict — no client re-derivation.
3. **Timeline = durable paged read over `loop_run_events`** with two deliberately distinct position types: the HTTP page cursor is an opaque token binding run identity + sequence (replay against a different history returns `409 timeline_branch_changed`); the CLI `--after` is a plain per-run sequence scoped by the command's run argument (beyond-head → deterministic error; no cross-run token exists at the CLI). A `notable | activity | chatter` classification map (authored in Go, exhaustive over the event-kind CHECK list, test-enforced) powers the views; public `all` = ordered union of the three tiers; heartbeat-class kinds coalesce server-side at read, and a coalesced entry's `seq` (and the cursor) advance to its last raw sequence. The first page is a newest window carrying `head_seq` (0 for empty runs); older pages are snapshot-fenced (cursor binds `{run_id, view, fixed_head_seq, before_seq}`, immune to concurrent appends). Live readers take one first page, then attach SSE with `after_sequence=head_seq`, de-duping by monotonic seq — going live never requires reading full history.
4. **SSE is an accelerator, not a narrator**: the existing per-run stream invalidates/appends; every rendered state reconciles against the paged reads. The web story's dependence on the 500-frame buffer as sole history is a delete target.
5. **Live DAG renders through a read-only renderer** in the loops system, reusing pure layout/geometry utilities from the editor canvas where free — zero authoring chrome (surface decision in ADR-003; this fixes the implementation lane).

## Alternatives Considered

### Alternative 1: Materialized roster projection table

- **Pros**: cheap reads at any scale; cross-run queries later.
- **Cons**: second state to reconcile (the exact bug class front 3 fixes); migration + projector; rebuild tooling.
- **Why rejected**: roster is run-scoped and the source tables are indexed by run; Temporal's describe-vs-list split shows computed live reads are the right consistency model. Materialization returns only if a cross-run read (non-goal today) demands it.

### Alternative 2: Keep SSE as the story's source with bigger buffers

- **Pros**: no new read path.
- **Cons**: any cap loses history; reload/return still truncates; agents get nothing.
- **Why rejected**: US-009 requires durable full history; `loop_run_events` already is it.

## Consequences

### Positive

- One source, several projections — DAG, roster, steps progress, and story cannot drift from each other; agents read the same truth (`loop nodes/why/events`).

### Negative

- Roster assembly touches several tables per request (bounded by run size + pagination).

### Risks

- Wide fan-out roster cost → cursor pagination + rollups (agents need not fetch items); indexes exist.
- Verdict cascade correctness → table-driven unit suite over every tone/blocker combination.
