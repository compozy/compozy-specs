# ADR-006: Terminal settlement is part of the transition; an idempotent sweep converges the rest

## Status

Accepted

## Date

2026-08-19

## Context

Run↔task reconciliation exists only on the coordinator plan's happy path (`global_db_task_coordinator_settlement.go:16`). Terminal transitions reached any other way — crash, cancel, kill, child-loop stop — leave coordinator and cell records live forever; no reverse sweep exists (`ListLoopRunsMissingActiveCoordinator` only revives `status='running'` runs). Two orphaned coordinators exist in the owner's workspace today (runs crashed 2026-08-19 ~17:03:58/17:04:09, coordinators QUEUED since). The existing rollup can also force-complete a coordinator while children stay live.

## Decision

1. **One cause-aware settlement primitive.** `settleLoopRunTerminal(tx, runID, cause)` is the single authority for settling a run's execution records. Every transition that sets a loop run terminal — plan-driven, cancel, kill, crash-recovery classification, child-stop (`applyCoordinatorRunStopsWithExecutor`), node-cancel finalization, sweep repair — calls it **in the same store transaction**. It applies the cause→status matrix (done/no-op → coordinator completed; failed/exhausted/stalled → coordinator failed; canceled/killed/run_missing → canceled; live cells → canceled with a reason detail carrying the run outcome; already-terminal cells untouched), settles children before the coordinator, and appends the structured reason (`loop_run_terminal` inline, `reconciled_run_terminal` from the sweep, `run_missing` for retention orphans). A transition-path coverage test fails when any terminal mutation bypasses the primitive. The completion-oriented rollup helper is no longer called directly by loop terminal paths — the primitive wraps it where its semantics fit (done) and replaces it elsewhere.
2. **Boot barrier, then sweep as the safety net.** `RunReconciler.NeutralizeOrphans` runs synchronously in daemon boot **before** `loopActionRuntime.Recover`, the coordinator backstop, or any claim traffic (L-003: boot recovery precedes wake/claim): one transaction removes work-eligibility of every execution record owned by a terminal or missing loop run, so `ClaimNextRun` can never hand out stale terminal-run work (race-tested on real SQLite). `SweepOnce` then runs on `[loops] reconcile_interval` (default `1m`) as the ongoing safety net — idempotent (status-guarded), lifecycle-mutation-free for non-terminal runs, serialized with live settlement through the store transaction (single winner). Remaining repair work (audit backlog) may finish across the first cycles without blocking readiness. **The barrier fails closed**: if `NeutralizeOrphans` errors, the daemon does not report readiness and starts no recovery/backstop/ticker/claimer — it surfaces a structured startup error; log-and-retry-next-tick applies only to interval sweeps, never to the boot barrier.
3. **Provenance repair is separate from lifecycle settlement.** `BackfillProvenance` is a metadata-only, idempotent, relational pass (`task_runs.loop_run_id → loop_runs`) that also covers coordinators of ACTIVE runs — the non-terminal rule binds lifecycle mutation, not provenance repair. Rows whose run is gone and unreconstructible get the truthful degraded provenance shape (relational facts only; never id/title parsing).
4. **Rollup honesty.** A terminal run settling its hierarchy settles children first, then the coordinator — no completed-parent-with-live-children window beyond the transaction, and no live record recorded as "completed" when the cause was cancel/kill/failure.
5. **Wiring.** Barrier, sweep, and backfill are composed in `internal/daemon` (composition-root discipline) as one owned goroutine with stop-and-join shutdown and non-overlapping cycles; the reconciler observes and settles via the primitive — it claims nothing (L-005).

## Alternatives Considered

### Alternative 1: Sweep-only (no inline settlement)

- **Pros**: one code path.
- **Cons**: every terminal run leaves a divergence window up to the interval; QA and agents observe live records after terminal — violates the invariant as stated.
- **Why rejected**: the invariant is "same transition"; the sweep exists for crash windows, not as the primary path.

### Alternative 2: Kernel-side generic orphan GC

- **Pros**: generalizes beyond loops.
- **Cons**: the kernel cannot know loop-run terminality without learning loop state (violates kernel neutrality); no other producer of this record class exists.
- **Why rejected**: the loop domain owns loop lifecycle truth; the kernel stays neutral.

### Alternative 3: Manual repair command for existing orphans

- **Pros**: no automatic writes at boot.
- **Cons**: leaves known-bad state to human memory; contradicts zero-legacy posture.
- **Why rejected**: owner decision (grill Q7) — automatic, idempotent, audited.

## Consequences

### Positive

- "Run terminal ⇒ zero live records" becomes checkable on any surface; the two known orphans disappear on first boot with an audit trail; crash windows converge within one cycle.

### Negative

- Every terminal path gains a settlement call (small, transactional); one new config key.

### Risks

- Sweep vs live settlement race → single winner via `BEGIN IMMEDIATE` store transaction + status guards (safety invariants in Part II).
- Sweep vs `ClaimNextRun` race → eliminated by ordering: neutralization completes before claimers start; proven by a dedicated real-SQLite race test.
- Large orphan backlog at first boot → neutralization is one bounded transaction (eligibility flip), so the barrier stays fast; the heavier repair (events, provenance) finishes across the first cycles without blocking readiness.
