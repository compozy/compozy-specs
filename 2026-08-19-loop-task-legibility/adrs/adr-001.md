# ADR-001: Loop execution records leave the Tasks surfaces by default

## Status

Accepted

## Date

2026-08-19

## Context

Every loop run materializes kernel tasks: one coordinator task (`loop.<run>.coordinator`) plus one cell task per action node × fan-out item × generation (`loop.<run>.g<N>.node.<id>.<item>`). This is deliberate (archived loops ADR-002: Loop is an aggregator over the autonomy kernel, never a second executor) and stays unchanged. But the records flood every task listing surface — web list/kanban/dashboard/inbox, `compozy task list`, HTTP/UDS, the native task tool — as near-identical, semantically thin rows ("Loop <name> node <id>", mono ids in primary position). The shipped client-side mitigation (`buildTaskListTree` nesting) only groups cells when the coordinator is on the same loaded page, so active runs degrade back to the flood; group counts go incoherent; the scenario guarding it (`TA-web-task-list-loop-subtask-nesting`) was never walked. The owner's verdict: the loop rows in Tasks "serve para nada" — the Tasks surface is for human-facing work items.

Market precedent: Temporal's list UI hides child workflows by default behind a reveal control; Kubernetes/Argo derive trees from ownership and treat unfindable children as a bug (argo-cd#2798) — hiding must remain reversible.

## Decision

All task listing surfaces exclude loop-origin execution records (coordinator tasks and loop cells) **by default**. A structured, explicitly-requested filter reveals them: hidden-by-default filter control in the web Tasks surface; explicit flag/query param on CLI, HTTP, UDS, and the native task tool (4-surface parity). Loop observability lives entirely in Loop-owned surfaces (loop run page, node inventory, attention bell lane). Loop escalations route through the loop attention lane, not the Tasks needs-attention bucket.

Exclusion is default-filtering, never erasure: the records keep full provenance in the read model, remain queryable through the opt-in filter, and remain reachable via links from the loop run page. When revealed, they render visually distinguished as loop-origin work (L-004: distinguish, don't erase).

## Alternatives Considered

### Alternative 1: One grouped row per loop run in Tasks (server-backed nesting)

- **Description**: The coordinator renders as a single collapsible row per run; cells expand in place (Temporal "N activities → one line with a count" pattern).
- **Pros**: Loop work stays visible in the person's work list; escalation counts stay in Tasks buckets.
- **Cons**: Still injects mechanical rows into a human work surface; duplicates the loop run page's job with a weaker view; keeps Tasks coupled to loop presentation.
- **Why rejected**: Owner decision — even one grouped row is noise; loop runs belong to the Loops area. The run page (ADR-002) is the observability home.

### Alternative 2: Keep status-quo client-side nesting

- **Description**: Ship `buildTaskListTree` as-is.
- **Pros**: Zero work.
- **Cons**: Pagination fragility (flood returns during active runs), incoherent group counts, no CLI/HTTP story, unverified scenario.
- **Why rejected**: It is the documented failure being fixed.

### Alternative 3: Stop materializing kernel tasks for loop work

- **Description**: Loop stops creating coordinator/cell tasks; runs live only in loop tables.
- **Pros**: No records to filter.
- **Cons**: Loses kernel retry/recovery/claim/HITL machinery; reverses archived loops ADR-002 and violates L-003/L-004/L-005 (single durable queue, converged primitives, exclusive authorities).
- **Why rejected**: The execution architecture is correct; the problem is read-model/presentation only.

## Consequences

### Positive

- Calm Tasks surface: only human-facing work items by default, on every surface with one shared contract.
- Deletes the web id-regex (`task-formatters.ts`) once provenance is structured.
- Dashboard/inbox aggregates stop counting mechanical loop cells.

### Negative

- Loop escalations must be fully owned by loop surfaces (bell probe, run page needs-you, node inventory) — the Tasks bucket no longer backstops them.
- Agents/operators must learn the opt-in filter for forensic listing.

### Risks

- Discoverability of the hidden filter → mitigated by documenting the agent path in the official Compozy skill and linking cell records from the run page.
- Any consumer currently depending on default listings including loop tasks breaks → greenfield alpha; delete-and-update in the same change (delete targets enumerated in the spec).

## Implementation Notes

Classification must be structural (provenance columns/fields in the catalog read model), not id-string matching. Kernel stays loop-noun-free per archived loops-refac ADR-006; the discriminators already exist (`created_by_ref`, `task_runs.run_kind`, `task_runs.loop_run_id`, cell metadata). Exact schema/filter shape is Part II scope.
