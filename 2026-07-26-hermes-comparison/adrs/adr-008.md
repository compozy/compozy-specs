# ADR-008: `agh mcp serve` re-projects the extension host API as an MCP server

## Status

Accepted

## Date

2026-07-04

## Context

External MCP-speaking agents cannot drive AGH today: AGH consumes MCP servers
(`internal/mcp/`) but never serves one, despite the extension host API already exposing the
needed session/task/network/memory methods (slice 08 §3.8, gap P3). Hermes ships `mcp_serve.py`
publishing its capabilities over MCP. Serving AGH over MCP directly fulfills the product premise
that every capability must be agent-manageable through structured surfaces (SD-011) — any MCP
client (Claude Code, IDEs, other daemons) becomes an AGH operator without bespoke integration.

## Decision

1. **`agh mcp serve`:** publish sessions/tasks/network/memory/resources as MCP tools by
   re-projecting the existing host API methods — no new business logic in the façade.
2. **No new native IDs:** the MCP façade must NOT mint new `agh__*` native tool IDs; MCP stays a
   separate projection so descriptors/digests of the native registry are untouched (slice 08 §5.4).
3. **Auth:** stdio transport may run unauthenticated for local spawn (Hermes' model); any non-stdio
   transport requires token auth.
4. **Isolation:** the served surface scopes to the operator's daemon/home and enforces the same
   workspace isolation the host API already enforces — no cross-workspace session/task/network
   data exposure.
