# ADR-002: Extensions contribute palette commands, views, and default shortcuts

## Status

Accepted

## Date

2026-08-17

## Context

The herdr-parity program (archived ADR-003) deliberately deferred extension-contributed palette views: "an explicit non-goal for v1 … the registry design must not preclude it." The extension manifest today has a closed 10-family resource set with no palette, view, or shortcut surface; the CLI command projection (`resources.tools.<handler>.command` + `command_groups`) exists with full CLI/HTTP/UDS parity but is never read by the web. Twelve wiring gaps were mapped (no manifest family, no ResourceKind/codec, no hook events, no SSE invalidation, no namespaced action ids, no agent control plane). The user's brief explicitly asks for extension-contributed commands, views, and shortcut handling.

## Decision

This spec opens all three contribution surfaces to extensions:

1. **Palette commands** — declared in the manifest, executed through existing gated infrastructure (tool invocation and peers); namespaced ids (`ext.<name>.<command>`).
2. **Palette views** — list-shaped, keyboard-navigable, data-driven views whose content crosses the daemon boundary as serializable data (no extension JS in the host renderer by default); the exact view-contract technology is a Stage 2 decision (research in flight).
3. **Default shortcuts** — extensions may declare default chords for their commands; all remain user-rebindable through the daemon-owned keymap, with namespaced action ids and collision rules against core bindings.

This supersedes the herdr-parity deferral while honoring its constraint: the registry design left the door open, and this spec walks through it.

## Alternatives Considered

### Alternative 1: Commands only

- **Description**: Extensions expose invokable commands backed by their tools; no views, no shortcuts.
- **Pros**: Smallest surface; no view-serialization contract; no chord-collision policy needed.
- **Cons**: Extension UX dead-ends at fire-and-close commands; list-shaped results (the palette's core interaction) stay built-in-only; shortcut story unresolved.
- **Why rejected**: User decision 2026-08-17: full scope requested; commands-only re-defers the same design one more cycle.

### Alternative 2: Commands + shortcuts, keep view deferral

- **Description**: Open commands and default chords; views remain built-in-only.
- **Pros**: Avoids the serializable-view contract and its security review.
- **Cons**: "Views become registrations, not redesigns" (herdr ADR-003 consequence) stays theoretical; extension list UX (e.g. a notes extension listing its notes) is impossible.
- **Why rejected**: Views are the differentiating half of the contribution model; the JSON-view contract is bounded work.

## Consequences

### Positive

- Extensions become first-class palette citizens: commands, live list views, and sensible default keys.
- The palette family ships as a **storage-free live projection** (the CLI `command_groups` pattern) — *not* a ResourceKind: no Surface-table row, codec, reconcile pass, or `allowed_kinds` entry (implementation decision refined 2026-08-17 after the channel research; see `_spec.md` § Extensibility Integration Plan — the user-settled contribution decision itself is unchanged).
- Closes the "web ignores /api/extensions/commands" gap with a real consumer.

### Negative

- A serializable view contract must be designed, versioned, and security-reviewed (no arbitrary extension UI).
- Chord namespace and collision policy (core vs extension) becomes part of the daemon keymap contract.

### Risks

- View vocabulary creep toward "mini-apps" — mitigated by the settled fixed-vocabulary rule: views compose only the four host-rendered kinds (List/Detail/Form/Grid — ADR-004/ADR-007); adding a kind requires a new ADR.
- Malicious/broken extension content in a trusted surface — mitigated by daemon-side validation, existing tool policy/risk gates on execution, and no renderer code execution.

## Implementation Notes

View-contract technology is settled by the later accepted ADRs: ADR-007 (Go-owned typed vocabulary + JSON Patch), ADR-008 (programmable view programs in the extension subprocess), ADR-009 (two composable tiers; TS-only programs this cycle). Extension content remains data-only in the renderer.
