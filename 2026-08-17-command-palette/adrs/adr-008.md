# ADR-008: Programmable palette views run in the extension subprocess over a `view.provider` capability

## Status

Accepted (amends ADR-002/ADR-007: extends "data-only" from static payloads to live programs; the renderer remains extension-code-free)

## Date

2026-08-17

## Context

The user judged the data-only view design (manifest + tool returning a static payload) insufficient: extensions must run **live programs** that react to search text, filter chips, selection, form input, and actions — Raycast-grade interactivity. Four research reports (analysis/05–08) mapped the solution space: Raycast/Vicinae's event loop (function props → stable opaque handler ids; one host→extension event kind; batched dirty-tree updates), the cross-host wire patterns (Slack ack-then-update + hash staleness, LSP `isIncomplete` + `$/cancelRequest`, A2UI tree/data split, MCP Apps two-way teardown), supercmd's serializable-vs-in-process split, and CompozyOS's own channel: the extension subprocess already speaks bidirectional concurrent JSON-RPC, the provides table is the extension seam, and `clarify/ask` is the per-invocation correlation template. Fork-exec hook executors and open/close-per-call MCP are structurally disqualified for keystroke-rate events.

## Decision

1. **Channel**: new `view.provider` capability in the provides table (`internal/extensionprotocol/capabilities.go`) with service methods `view/open`, `view/event`, `view/close` — served by the extension's existing warm subprocess through the standard service-call gate; `make codegen` propagates the capability to both SDK contract tables.
2. **Event loop** (Raycast/Vicinae model): function-valued view props become **stable opaque handler ids**; the host sends one event kind (`view/event` carrying handler id + args + `{view_session, revision, seq}`); disposed handlers are quarantined for two frames (in-flight events drop silently). **Event counters on every controlled value** (host increments per local edit; program echoes; host discards stale echoes).
3. **Updates**: the program returns frames/patches from `view/open`/`view/event`, and may push mid-stream via a new **host-API method `view/patch`** that the daemon fans out to the palette SSE stream (chosen over enabling JSON-RPC notifications: zero transport change). Batching on a frame clock with content-hash dedupe; revision-fenced application with full resync on gap.
4. **Declared ownership**: the frame declares who answers what — host-local events never round-trip (keystroke echo, selection, scroll, chips visual, ESC); `onSearchTextChange` presence flips filtering ownership; result sets carry `complete: bool` (LSP) for local-filter handoff; form values bind host-side with full-snapshot delivery on events and submit-time dispatch by default.
5. **Budgets and failure**: three-band latency budget (0 ms host-local · ~150 ms soft busy-with-previous-rows · 3 s hard ack then unbounded streamed updates); circuit-break after 3 consecutive Band-2 misses (view `degraded`, last-good render + retry); program crash → `unavailable` frame; **two-way teardown** (`view/close` reason ↔ program-requested close).
6. **Sessions**: **per-client view sessions** (user decision) — each attached client opening a view gets its own session in the program; daemon holds a session registry generalizing the `clarify/ask` runtime (opaque id, owner check on re-entrant host calls, cancel propagation, `OnceFunc` release). Extension restart destroys sessions; the host reopens.
7. **Protocol additions** (exact seams in analysis/08): cancel frames + per-request `context.Context` (Go SDK) / `AbortSignal` (TS SDK); negotiated `default_view_timeout_ms`; a view-class rate limiter distinct from the 10 rps host-API bucket; per-extension in-flight caps; host-enforced resource caps (components/view, rows/patch, patch bytes, ≤1 in-flight coalescing event per view).

## Alternatives Considered

### Alternative 1: Extension code in the renderer (iframe/worker)

- **Pros**: No daemon round trip for events.
- **Cons**: Reverses the ADR-002/007 security posture; cross-document keyboard/focus is the hardest version of the problem; Stripe bans arbitrary markup even inside full sandboxing; Figma's sandbox-escape history.
- **Why rejected**: The renderer stays extension-code-free — non-negotiable.

### Alternative 2: Fork-exec per event (hook-executor shape)

- **Why rejected**: Process spawn per keystroke; 5 s one-shot semantics; no state between invocations (analysis/08 F11).

### Alternative 3: One process per view (bridge-control shape)

- **Why rejected for v1**: Full launch + handshake per view open kills latency; right only for a future untrusted-heavy "rich view" tier. The warm shared subprocess with concurrent requests is the fit.

## Consequences

### Positive

- Raycast-grade interactive views with zero extension code in the renderer; the channel, supervision, health, dev-reload, and permission machinery are inherited.
- The event vocabulary is host-answerable-by-default: typing feels local because it is local.

### Negative

- Real protocol work: cancellation, push, timeouts, rate class, session registry — all currently absent (seams mapped).
- A slow TypeScript view handler can starve the extension's own `health_check` (single event loop) and crash-loop the extension — the SDK must ship a starvation guard (yield contract or internal worker isolation) and the contract must cap handler work.

### Risks

- Multi-client fan-out cost (N sessions) — bounded: palette views are momentary surfaces; sessions close with the palette.
- Patch/ordering bugs — mitigated by revision fencing + full resync + property tests (inherited from ADR-007).

## Implementation Notes

Daemon: `view_source.go` (~40 lines via the service gate), capability table entry, session registry, `view/patch` host-API method + SSE fan-out, DescribePayload static-view-metadata field (daemon lands first — strict describe decoding). SDK seams per language in analysis/08 appendix. The dead `execute_hook` daemon-request seam is deleted under the greenfield rule (decided here: delete — `view/event` is the interactive path).
