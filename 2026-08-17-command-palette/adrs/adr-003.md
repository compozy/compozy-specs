# ADR-003: Ranking is frecency plus adaptive query learning, persisted by the daemon per workspace

## Status

Accepted

## Date

2026-08-17

## Context

Today's palette has zero personalization: substring match over hand-authored value strings, `localeCompare` ordering, no recents, no usage history. Research shows frecency is now table stakes (PowerToys Command Palette: 3-day half-life; cmdk-engine: `count * 2^(-Δt/halfLife)`), and supercmd's differentiator is per-query adaptive learning — every launch records the normalized query that produced it (14-day half-life), so a stored prefix match contributes more than any tier boost ("gh" learns to mean *your* GitHub). supercmd ships this as pure, DOM-free functions, directly portable. localStorage-based state would fracture across tabs and machines; CompozyOS has a daemon with SQLite.

## Decision

- Rank results with a two-part personal signal on top of textual match scoring: **frecency** (time-decayed usage with a tuned half-life) and **adaptive query history** (normalized query→command associations with a shorter half-life, prefix-matched at query time).
- Show a **Recents group** when the query is empty.
- Persist all personalization **in the daemon, scoped per workspace** (multi-tab/multi-device coherent, agent-inspectable), never in browser storage.
- Keep the scoring pipeline pure and testable (headless), with score components exposed for debuggability.

## Alternatives Considered

### Alternative 1: MRU recents only (legacy compozy-code model)

- **Description**: Last-20 list, deduped; search order stays purely textual.
- **Pros**: Trivial; easy to explain.
- **Cons**: No frequency signal; heavy commands never rise; cold search stays dumb.
- **Why rejected**: Below 2026 table stakes; the research handed us a proven better engine.

### Alternative 2: Plain frecency without query learning

- **Description**: Time-decayed usage score only.
- **Pros**: Simpler storage; fewer tuning knobs.
- **Cons**: Cannot learn user vocabulary ("gh" → GitHub-equivalent); supercmd evidence says query learning is the biggest perceived-quality jump.
- **Why rejected**: User decision 2026-08-17 picked the full model; the increment over plain frecency is one small table and one score term.

### Alternative 3: No personalization

- **Description**: Static deterministic order.
- **Pros**: Zero state.
- **Cons**: Unusable at full-OS catalog scale (ADR-001); every competitor ranks.
- **Why rejected**: Incompatible with full coverage.

## Consequences

### Positive

- Perceived quality scales with catalog size; frequent flows become one keystroke.
- Daemon persistence gives coherence across tabs/devices and lets agents inspect/reset ranking state.

### Negative

- New daemon storage (schema migration) and new API surface for recording/reading usage.
- Ranking becomes stateful — tests must pin decay math and stay clock-injected.

### Risks

- Non-transitive comparators corrupt ordering at scale (documented supercmd production bug) — mitigated by fixed group precedence, score deadband, and shipping the transitivity test.
- Score tuning drift — mitigated by hoisting all weights into one named, versioned config (avoid supercmd's scattered magic numbers).

## Implementation Notes

Half-life constants and weights live in one versioned table, owned and served by the daemon. Exact storage schema and API are Part II decisions.

**Amendment (2026-08-18, round-2 incorporation):** the decision — frecency + adaptive query learning, daemon-persisted per workspace — stands unchanged; the scoring **execution site** is refined: scoring runs as **one TypeScript implementation** client-side (`web/src/systems/os/lib/ranking/`, pure and headless-testable), because the keystroke path cannot round-trip and a Go scorer would have no executable path in the browser. The daemon remains the sole authority for persisted signals and the versioned `Weights` it serves; golden cross-fixtures pin the algorithm; no Go scorer ships and no dual implementation is maintained. CLI/agent listings use deterministic catalog order — personalized ranking exists only where typing does.
