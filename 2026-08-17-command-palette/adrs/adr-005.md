# ADR-005: The domain identifier is `cmd_palette`

## Status

Accepted

## Date

2026-08-17

## Context

The overhaul introduces new public identifiers across every surface: an extension-manifest resource family, a config.toml section, CLI verb group, HTTP/UDS route prefix, native-tool prefix, and SSE event family. "Palette" alone is ambiguous against future palettes (color palettes) and undersells the domain; "command(s)" collides with the existing CLI-projection vocabulary (`resources.tools.<handler>.command`, `resources.command_groups`, `compozy extension commands`). The repo convention is unabbreviated domain identifiers (`window_manager`, `command_groups`).

## Decision

The domain identifier is **`cmd_palette`** (snake) / **`cmd-palette`** (kebab), chosen by the user for explicitness with brevity:

- Manifest family: `resources.cmd_palette.{commands,views}`
- Config section: `[cmd_palette]`
- CLI verb group: `compozy cmd-palette …`
- Routes: `/api/cmd-palette/*`
- Native tools: `compozy__cmd_palette_*`
- SSE events: `cmd_palette.*`

The product name in prose stays **Command palette** (herdr ADR-003, glossary); `cmd_palette` is the machine identifier, mirroring the CompozyOS/`compozy` product-vs-identifier split. Established action ids (`palette.open`, `palette.view.sessions`) keep their `palette.*` family — they are command ids inside the keymap, not domain identifiers, and renaming shipped bindings would break user overrides for zero gain.

## Alternatives Considered

### Alternative 1: `command_palette` (unabbreviated)

- **Description**: Full two-word identifier per repo convention.
- **Pros**: No abbreviation precedent introduced; matches `window_manager` style.
- **Cons**: Longer everywhere (`compozy command-palette list`, `compozy__command_palette_invoke`); the user judged `cmd` universally readable.
- **Why rejected**: User decision 2026-08-17 (surface grill round 2) after seeing both mapped across all surfaces.

### Alternative 2: `palette` everywhere

- **Description**: Single-word identifier.
- **Pros**: Shortest; matches the existing `palette.*` action-id family.
- **Cons**: Under-specific as a domain name; future collision surface (any other palette concept).
- **Why rejected**: User wanted the explicit `cmd` qualifier.

### Alternative 3: `command(s)` domain naming

- **Description**: `compozy command list`, `/api/commands/*`, `resources.commands`.
- **Pros**: Semantically broadest (registry powers keyboard/menubar too).
- **Cons**: Direct overload of the shipped CLI-command vocabulary in the same manifest; permanent ambiguity in docs and prompts.
- **Why rejected**: Collision is structural, not stylistic.

## Consequences

### Positive

- Zero collision with existing vocabulary; instantly greppable; one identifier across all six surfaces.

### Negative

- First abbreviated domain identifier in the repo — a one-off precedent future naming reviews must not generalize from.

### Risks

- Prose drift ("cmd palette" leaking into copy) — mitigated: glossary entry pins **Command palette** (prose) vs `cmd_palette` (identifier); COPY.md register applies.

## Implementation Notes

Glossary edit ships with this spec: add `cmd_palette` under OS Shell, cross-referencing Menubar's palette entry. All `_dx.md` surfaces already use the final names.
