# ADR-004: One runtime self-update mechanism, consumed by both the app and the CLI

## Status

Accepted

## Date

2026-08-15

## Context

Two runtime update tracks exist today. (1) The shell updates the runtime it owns: `runtime.json` feed derived as a sibling of the app updater endpoint, staged download with integrity verification, rollback journal, quiesce, recovery (`desktop/src-tauri/src/update/runtime_update.rs` and peers). (2) Standalone CLI installs self-update through a separate track (QA scenario `REL-beta-self-update`, status pass). ADR-002 already relocates track (1) to the runtime side, which puts both tracks in the same codebase with overlapping responsibilities.

## Decision

Unify: the runtime side owns a single self-update mechanism. The desktop app and the standalone CLI are two consumers of the same mechanism — the app orchestrates and displays it; the CLI invokes it directly. Runtime updates work headless, with no desktop app installed.

## Alternatives Considered

### Alternative 1: Keep two tracks

- **Description**: Relocate the app-owned track as-is; leave the CLI self-update untouched; declare unification a Non-Goal.
- **Pros**: Smaller relocation scope; no changes to a passing QA surface.
- **Cons**: Two implementations of download/verify/swap/rollback in one codebase; divergent behavior between "runtime installed by app" and "runtime installed standalone"; permanent duplication contradicting zero-legacy.
- **Why rejected**: The relocation (ADR-002) already forces both tracks into the same house; keeping them separate there is the worst of both worlds (user decision Q7, 2026-08-15).

## Consequences

### Positive

- One download/verify/swap/rollback implementation to test and trust.
- Headless runtime updates become a first-class agent-manageable path (no app required).
- The app's runtime-update UX becomes a view over the same mechanism the CLI uses — manual and app-driven paths converge on the same primitive.

### Negative

- The relocation phase must absorb and reconcile the semantics of both existing tracks (feed shape, channel selection, integrity format) before the shell swap.
- `REL-beta-self-update` (currently pass) resets to untested when its mechanism changes and must re-walk.

### Risks

- Semantic drift between what the app-owned track guaranteed (staging, rollback journal, schema-heads gate) and what the CLI track guaranteed — Part II must enumerate the union as invariants; the release gate (real beta N→N+1 cycle) exercises the unified path end to end.

## Implementation Notes

Part II decides the mechanism's home, the feed contract, and which existing surfaces (`compozy app update --apply runtime`, CLI self-update verb) map onto it. Strict parity governs the app-visible behavior. _Note (2026-08-15, post-ADR-005): the `compozy app update` surface named here was subsequently deleted — ADR-005 folds both consumers into the single `compozy update` command; ADR-009 defines the operation primitive they converge on._
