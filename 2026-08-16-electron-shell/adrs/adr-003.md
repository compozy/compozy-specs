# ADR-003: No migration bridge for the installed base; hard-cut the old channel feed; preserve app identity

## Status

Accepted

## Date

2026-08-15

## Context

CompozyOS is greenfield alpha; the desktop channel policy publishes `beta` only (`stable` is reserved and refuses to publish). The installed Tauri base is effectively zero. A bridge would require either a final Tauri release that installs the new app through the old updater (cross-format updater gymnastics, the riskiest possible use of the updater) or a prompt-only bridge release (cheap but still one more Tauri release to build, sign, and publish). The old channel feed (`latest.json` in the old updater's format) is polled every 6 hours by any installed app.

## Decision

No bridge of any kind. The cutover is announced (release notes / site changelog); existing installs are replaced manually by downloading the new artifacts. The old channel feed objects are deleted, not frozen. App identity is preserved exactly — product name `CompozyOS`, bundle id `com.compozy.os`, deep-link scheme `compozyos://` — so new installers replace the old install in place and the `compozy app` platform-detection contract keeps working unchanged.

## Alternatives Considered

### Alternative 1: Bridge release with in-app prompt

- **Description**: One last Tauri release that shows "download the new app" and disables auto-update.
- **Pros**: Installed users get an in-app signpost.
- **Cons**: Builds/signs/publishes one more Tauri release for a ~zero base; keeps Tauri CI alive one cycle longer.
- **Why rejected**: Cost exceeds benefit at current install count (user decision, Q3 2026-08-15).

### Alternative 2: Automatic bridge through the old updater

- **Description**: Publish the new app as the old updater's payload.
- **Pros**: Ideal UX.
- **Cons**: Cross-framework updater install is the highest-risk maneuver available, for near-zero beneficiaries.
- **Why rejected**: Risk concentrated in the subsystem that must not fail, benefit ~zero.

### Alternative 3: Freeze the old feed instead of deleting

- **Description**: Leave the last old-format `latest.json` in place forever; old apps see eternal silence instead of check errors.
- **Pros**: No error logs on abandoned installs.
- **Cons**: A permanent legacy artifact contradicting zero-legacy posture, for cosmetic benefit on installs already declared abandoned.
- **Why rejected**: Zero-legacy: delete the old thing.

## Consequences

### Positive

- Zero Tauri releases remain in the pipeline; delete targets are clean and immediate.
- Same-identity installers give in-place replacement on macOS (bundle id) and deb; QA scenarios and `compozy app status/open` need no identity changes.

### Negative

- Abandoned installs log a failed update check every 6 hours until manually replaced or removed.
- AppImage users may end up with both old and new files side by side; the announcement instructs deletion.

### Risks

- A forgotten real user stuck on the old app — mitigated by the announcement and by `compozy app status` continuing to detect the old install (platform probe is identity-based, not shell-based).

## Implementation Notes

Delete targets include the old-format feed objects under the channel prefix and every Tauri-format publisher input. The announcement content is a task-level deliverable, not a spec artifact.
