# ADR-007: App-track updates ship from GitHub Releases; releases.compozy.com is retired

## Status

Accepted

## Date

2026-08-15

## Context

The CLI/runtime already updates from GitHub Releases with sigstore-verified checksums (`internal/update/`: TUF trusted root, cert-identity policy pinned to the release workflow, artifact-size policy, 24h cache). The Tauri desktop feed lives on `releases.compozy.com` (R2/CDN) with its own generator (`cmd/compozy-desktop-release`), publisher scripts, and a repair workflow — and its old-format objects are deleted regardless (ADR-003). Keeping the custom origin only for the new app track would preserve a second distribution system forever.

## Decision

The Electron app's update artifacts and channel manifests publish to the same GitHub Release as the CLI/runtime archives — one tag, one release train, lockstep versions. The app updater consumes the GitHub provider. `releases.compozy.com` is fully retired: bucket/CDN wiring, publish and verify scripts, the feed generator's channel-config path, and the `desktop-feed-repair.yml` workflow are delete targets. Feed repair becomes ordinary release-asset management on GitHub.

## Alternatives Considered

### Alternative 1: Keep releases.compozy.com for the app track

- **Description**: Publish new-format app manifests to the owned origin; CLI stays on GitHub.
- **Pros**: CDN control, custom domain, existing repair tooling.
- **Cons**: Two distribution systems, two verification families, two publish paths to keep consistent; the feed generator is rewritten for the new format either way; the repair workflow only exists because the custom origin does.
- **Why rejected**: Permanent double infrastructure for no user-observable benefit (user decision T1, 2026-08-15).

## Consequences

### Positive

- One publish job, one ordering guarantee (payloads-before-manifests applies to release-asset upload order), one place to audit.
- Deletes an entire infrastructure surface (origin, scripts, secrets, repair workflow).
- Update checks for both tracks read one release — the lockstep version and the one-truth promise (`_dx.md`) fall out structurally.

### Negative

- Distribution couples to GitHub availability and rate limits (mitigated: the CLI track already accepts this; checks are cached).
- The public repo is a hard requirement (already true).

### Risks

- GitHub Releases asset-name collisions between CLI and app artifacts — mitigated by the inventory assertion pattern (exact-set match) carried over from `internal/desktoprelease/inventory.go`.

## Implementation Notes

Delete targets: `scripts/publish-desktop-release.sh`, `scripts/repair-desktop-feed.sh`, `.github/workflows/desktop-feed-repair.yml`, `internal/desktoprelease/channel_config.go` (+ its Tauri-shaped subcommands), minisign key tooling (`scripts/generate-desktop-update-key.sh`, `scripts/verify-desktop-signature.sh`), `TAURI_SIGNING_*` secrets, and the `DistributionOrigin` constant. DNS/bucket teardown is an ops follow-through recorded in the cutover task.

_Note (2026-08-16, post peer-review round 3, B-024): the app-updater feed mechanics are pinned to what the dependencies actually implement. The GitHub **release-list provider cannot express a channel pointer** (it resolves prereleases from the repo feed, and `make_latest` excludes prereleases), so the app updater uses the **generic provider** pointed at raw channel-manifest URLs on a dedicated `channel-beta` git branch. The channel switch is a **git ref update with an expected-old-SHA compare-and-swap** — one commit atomically replaces every platform manifest, the ref CAS is the real linearization point, history is the immutable audit trail, and known-good selection is a commit lookup. Payload assets still live in immutable versioned GitHub Releases._
