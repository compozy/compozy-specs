# ADR-006: Update offers live in the web UI (daemon truth); the boot overlay becomes non-interactive-only

## Status

Accepted

## Date

2026-08-15

## Context

Today the only update UX is the shell's boot-window overlay: when an update is ready, "CompozyOS is ready" with an "Update app"/"Update runtime" button is re-shown **on top of the running product**; the product web UI never learns about updates from the shell. Meanwhile the web UI already renders runtime update state from the daemon (`GET /api/settings/update` → Settings → General "Updates" section, `web/src/routes/_app/settings/-general-update-section.tsx`). With ADR-002/ADR-004 relocating update intelligence to the runtime side, the daemon becomes the single source of update truth for both tracks — which makes the web UI able to present updates without any shell bridge. During the surface grill the user chose to surface update state in the web UI (Settings extension + a discreet menubar indicator) and to remove the overlay's interactive offer.

## Decision

Update state for both tracks (runtime and app) is daemon-owned truth exposed through the existing settings surface. The web UI presents it in two places: the extended Settings → General "Updates" section (both tracks, with an apply action where self-apply is possible) and a discreet OS-menubar indicator shown only while an update is available, which navigates to that section. The SPA gains **zero desktop-awareness**: it reads the daemon like any browser client, so the same UI works identically in the app and in a plain browser. The shell's boot overlay is reduced to non-interactive phases — boot progress, update-in-progress progress, version skew, and error — and its interactive update offer is deleted. Overlay strings for the remaining phases stay frozen as today.

## Alternatives Considered

### Alternative 1: Shell-injected bridge (desktop-aware SPA)

- **Description**: The shell injects a bridge object; the SPA detects it and renders desktop-only update UI.
- **Pros**: Shell-local state without daemon involvement.
- **Cons**: First desktop-awareness in the SPA (today it has none — a deliberate asset); browser surface diverges from app surface; bridge becomes a second contract to test.
- **Why rejected**: Daemon truth achieves the same UX with zero new coupling and works in the browser too.

### Alternative 2: Keep the overlay offer alongside the web UI

- **Description**: Both the overlay and Settings offer the update.
- **Pros**: No behavior removed.
- **Cons**: Two surfaces for one decision; states can visibly diverge; doubles QA states.
- **Why rejected**: User decision (N3): one decision surface; the overlay keeps only phases where the web UI is unusable.

### Alternative 3: Settings only, no menubar indicator

- **Description**: Update state discoverable only inside Settings.
- **Pros**: Calmer chrome (matches the product's calm-defaults posture).
- **Cons**: Updates go unnoticed until the operator visits Settings.
- **Why rejected**: User decision (N2): include the discreet indicator; it is truthful (bound to daemon state) and appears only when actionable.

## Consequences

### Positive

- One decision surface, one truth, identical in browser and app; the SPA stays shell-agnostic.
- The daemon's update state becomes inspectable by every client (web, CLI, HTTP) symmetrically.
- Browser-only operators gain update visibility they never had.

### Negative

- The feature becomes UI-bearing: `_uiux.md`, a design pass, and browser E2E enter the program scope.
- The daemon must model app-track state it previously ignored (internals in Part II).
- Overlay update-offer strings and their QA expectations are retired (scenario resets).

### Risks

- A stale daemon view of app state could render an untruthful offer — mitigated by SD-007 discipline: unknown renders as unknown, and the indicator binds to daemon-confirmed state only.

## Implementation Notes

Surfaces, states, and component plan: `_uiux.md`. The settings surface extension keeps the existing section as its home (`-general-update-section.tsx`); the indicator lands in the OS menubar composite (`web/src/systems/os/components/menubar/os-menubar.tsx`).
