# ADR-009: A durable per-home Update Operation owns every install mutation, executed by a detached coordinator

## Status

Accepted

## Date

2026-08-15

## Context

Peer review round 1 (B-002, B-003, B-006) proved three related unsoundnesses in the first Part II draft: (1) a daemon-side runtime apply cannot own restart/rollback of its own process — `context.WithoutCancel` survives request cancellation, not process exit, so once the old daemon dies nothing can health-check the replacement or restore the backup; (2) "wait for `update.lock` to be free" before the app-track apply is check-then-act — a runtime updater can acquire the lock right after the check, and any flock held by the Electron process vanishes when Electron quits to install; (3) a minimal intent file loses the only record of an app apply on crash and does not bind the apply to the release the Go side verified.

## Decision

One durable **Update Operation** record per home is the exclusivity primitive and the journal for both tracks. Acquisition is atomic creation (`O_EXCL`) of `~/.compozy/update-operation.json`; the record — not any process lifetime — carries ownership: operation id, requester surface, targets and a **compatibility-aware dependency plan**, per-target phases, verified release identity (tag, asset names, digests), backup path, watchdog deadlines, failure counts, and last error. A detached **coordinator** (the `compozy` binary re-executed with the operation id, disowned from its parent) is the sole executor of runtime mutations: verify → swap → restart daemon → health-check → finalize or restore — across daemon generations. Every surface converges on this primitive: `compozy update` creates the operation and runs the coordinator in the foreground; the daemon's apply endpoint creates the operation, spawns the coordinator detached, and returns `accepted` with the operation id; the shell's app-track consumer *transitions phases inside the same record* (staged → applying → verified/failed) under the record's discipline, bound to the recorded asset digest. Terminal operations append to `~/.compozy/logs/update-history.jsonl` and the live record is removed.

Refinements from peer-review rounds 2 and 3 are part of this decision:

- **Ordering is fixed runtime-first; compatibility is a publication invariant** (B-011 → B-020): the operation always executes runtime-first, preserving the frozen closed-app outcome (runtime updates now, app stages). The compatibility-bump deadlock is prevented **at publish time**: the channel authority refuses any release whose runtime `min_app_version` exceeds the app version of the previous channel generation — a runtime must always accept the app generation that can still stage its companion. Requiring a newer app therefore takes two releases by construction. The coordinator's pre-mutation gate remains as a backstop refusal for runtime-only requests against an incompatible release. The round-2 "app-first plan / deferred runtime phase" is deleted.
- **Transitions are serialized, fenced, and single-implemented** (B-012 → B-021): a stable companion lock file (`~/.compozy/update-operation.lock`, never renamed) serializes every writer, including acquisition — create-if-absent happens under the lock with an fsynced temp record atomically published at the final path, so no reader ever observes a partial record. All mutations go through **one Go transition API** requiring `operation_id` + executor fence + **expected record `revision`** (a monotonic counter covering both tracks — unambiguous where per-target phases are not); stale writers are refused with evidence. The shell never writes or flocks the journal: its transitions execute through the same Go API by invoking the installed `compozy` binary (one implementation, no cross-language peer authority — L-005).
- **Ownership is a fenced lease with an explicit dormant state** (B-013 → B-022): the holder is **nullable** and, when live, records `{pid, pid_start_time, surface, executor_generation, lease_expires_at}` with a bounded renewal cadence; the generation fence plus expected revision are checked before every transition **and every irreversible side effect**, so an expired-then-resumed executor cannot act after a replacement takes over. `waiting-for-app` is dormant (holder null, blocks nothing) — a new acquisition for the same target **resumes** it (single-winner resume transition). The app installer handoff (`quitAndInstall` → external installer) is a **non-cancelable phase** that blocks all other mutation until post-restart verification or its phase watchdog decides; cancel applies to dormant records only. A complete per-phase recovery/cancel matrix (resume / wait / restore / fail / cancel-allowed) is part of the record contract.

## Alternatives Considered

### Alternative 1: Request-detached goroutine inside the daemon

- **Description**: `ApplyUpdate("runtime")` runs in the daemon with `context.WithoutCancel`.
- **Pros**: No new process; simple wiring.
- **Cons**: The executor dies with the process it is replacing; no owner exists for post-restart health-check, restore, or finalize; violates the restated lesson behind L-001 (detach from the request is not detach from the process).
- **Why rejected**: Structurally cannot satisfy rollback rules 14/17 (B-002).

### Alternative 2: flock-only single-flight + separate intent file

- **Description**: Keep `update.lock` as the only mutual exclusion; app applies watch for lock release; a thin intent file requests app updates.
- **Pros**: Fewer moving parts; closest to the pre-review draft.
- **Cons**: Observe-then-act race (B-003); lock lifetime tied to a process that must exit mid-apply; intent file carries no verified identity, attempt history, or recovery state (B-006).
- **Why rejected**: Both failure modes are exactly what the review demonstrated.

## Consequences

### Positive

- One primitive, every surface: manual CLI, daemon HTTP/UDS, web apply, and the shell's app consumer converge (manual = autonomous on the same primitive).
- Ownership survives every process exit involved in an update — including the daemon being replaced and Electron quitting to install.
- `blocked` gets a truthful holder from the record on every surface; recovery is a deterministic function of the journaled phase.
- The app apply is cryptographically bound to the release the Go side verified (digest recorded at acquisition, enforced at install).

### Negative

- A new lifecycle component (coordinator + journal + recovery paths) to build and test — the concentration point of the program's test budget.
- The operation record becomes a versioned on-disk contract (schema_version, recovery semantics).

### Risks

- Journal corruption or partial writes — mitigated by atomic temp+rename writes, schema validation on read, and refuse-with-diagnostics on unknown versions.
- Orphaned non-terminal records — mitigated by watchdog deadlines in the record plus daemon-boot and shell-launch recovery sweeps.

## Implementation Notes

`update.lock` remains as the short-critical-section flock *inside* the coordinator's swap step; the operation record is the long-lived ownership layer above it. The intent-file concept from the pre-review draft is deleted — the operation record's app section replaces it.
