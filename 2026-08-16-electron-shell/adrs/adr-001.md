# ADR-001: Replace the Tauri desktop shell with an Electron shell

## Status

Accepted

## Date

2026-08-15

## Context

The CompozyOS desktop app is a Tauri 2 shell (`desktop/src-tauri/`, ~12.3k lines of Rust) whose main window renders the daemon-served web UI at `http://localhost:<port>`. Tauri uses the OS webview: WKWebView on macOS, WebKitGTK on Linux, WebView2 on Windows. Every automated quality surface (Vite dev, Playwright E2E `Desktop Chrome`, daemon-served browser access) runs Chromium, while the shipped app — which docs call "the primary interactive way to run CompozyOS" — renders WebKit with zero automated UI coverage. The two active release targets (macOS, Linux) are exactly the two non-Chromium engines; Windows (the one Chromium Tauri target) is paused on a broken Azure Trusted Signing account. 11 of 14 `APP-*` QA scenarios sit `blocked-verify` largely because `tauri-driver` does not work on macOS. The design system's glass/blur depth carve-out hits a class of upstream WebKitGTK compositing bugs (backdrop-filter on transparent windows, blur during CSS animations, DMABUF/NVIDIA blank windows) that Tauri documents but cannot fix. Market research (2026-08-15): Tauri's consistent-engine options (Verso/Servo, CEF) are experimental with no ETA; OpenCode Desktop — an AI coding agent app, same category — migrated Tauri→Electron in April 2026 citing the same WebKit inconsistency; Electron remains the norm for AI dev tools.

## Decision

Replace the Tauri shell with an Electron shell. The desktop app renders the daemon-served web UI in Chromium on every platform, pinned to an exact Electron version, with behavioral parity as the migration contract (ADR-003 covers the installed base; the spec's Non-Goals freeze feature scope).

## Alternatives Considered

### Alternative 1: Stay on Tauri and wait for a consistent engine (Verso/CEF)

- **Description**: Keep the current shell; adopt Tauri's Chromium-class engine when it ships.
- **Pros**: Zero migration cost; keeps ~15 MB installers and OS-managed webview security updates.
- **Cons**: Verso integration is an under-resourced proof-of-concept ("no time to migrate", May 2026); CEF integration has not started; multi-year horizon at best. WebKitGTK glass/blur bugs are upstream and unresolved. The macOS test gap (`tauri-driver` unsupported) stays permanent.
- **Why rejected**: Waiting is not a plan; the engine gap is the product problem today.

### Alternative 2: Stay on Tauri and invest in WebKit-matrix testing

- **Description**: Keep the shell; build WKWebView/WebKitGTK test coverage and fix rendering divergences per-engine.
- **Pros**: No shell rewrite; browser-surface Safari users benefit.
- **Cons**: No viable macOS WebDriver path for WKWebView app testing; WebKitGTK bugs are upstream (unfixable locally); permanent 3-engine matrix cost for a small team; dev (Chromium) vs prod (WebKit) divergence remains structural.
- **Why rejected**: Highest recurring cost, does not remove the root cause.

## Consequences

### Positive

- Dev, browser E2E, and the shipped app converge on one engine; the existing Playwright suite can drive the real packaged app.
- Unblocks the 11 `blocked-verify` `APP-*` scenarios (Playwright `_electron` works on macOS and Linux).
- Deletes the Rust toolchain from the repo and CI; the monorepo becomes Go + TS.
- WebKitGTK troubleshooting surface (env-var workarounds in ops docs) is deleted.

### Negative

- Installer grows ~15 MB → ~100+ MB; higher baseline RAM (accepted norm in the dev-tool market).
- The team owns the Chromium security treadmill: Electron majors every 8 weeks, 3 supported (~24 weeks each) — plan roughly one bump per quarter.
- App-update artifact/signing infrastructure is rebuilt (feed format, keys, CI).

### Risks

- Update-track regression during the swap — mitigated by ADR-002 (relocation shrinks the shell) and the release gate (full `APP-*` pass + one real beta N→N+1 auto-update cycle).
