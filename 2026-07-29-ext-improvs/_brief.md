# Extension DX: installing is 5 commands, authoring is 45 concepts, the SDK grades B−/C−/C — bring the experience to the bar set by eve, flue, and pi

## Problem

CompozyOS v0.3 shipped the core engine. Extensions are the growth surface, and the question this brief answers is not "does the extension system work?" but "**is it easy?**" — measured on three axes the team cares about, against three reference systems considered best-in-class that are vendored in this repo (`.resources/eve`, `.resources/flue`, `.resources/pi`).

### 1. How easy is installing and updating? — *Uneven: one good path, everything else is heavy*

- Installing a **curated marketplace** extension is genuinely good: 3 commands, and official-tier trust short-circuits every gate. This is the only flow near the one-command bar that all three references hit (`eve add extension/x` / `flue add sandbox daytona | claude` / `pi install npm:@foo/bar`).
- Installing **your own local directory** — the flow every author repeats dozens of times — is **5 commands + a prompt + a global policy flip**, because a local path is routed through *marketplace* trust policy (`internal/daemon/extensions.go:94` → `internal/extension/marketplace_trust.go:152-173`). Four separate trust affordances (config `registry`, config `allow_unverified`, flag `--allow-unverified`, flag `--yes`) guard one decision.
- Installing from the **GitHub registry** is 6 commands + `GITHUB_TOKEN` in the daemon environment (likely a daemon restart).
- **Update discovery is pull-only.** The daemon computes `update_available` (`internal/api/core/marketplace_list.go:401`) and every surface then drops it: `extension list` has no update column (`internal/cli/extension_output.go:16-35`), `marketplace search` omits it (`internal/cli/marketplace.go:180-218`), and the web counts updates only under the `installed` scope so the landing count is structurally zero (`web/src/systems/marketplace/hooks/use-marketplace-kind-page.ts:200,256`). A user must know to run `compozy extension update --all --check`.
- **The error renderer throws away the help.** Human-mode output degrades every diagnostic to `error: %v` (`internal/cli/root.go:216,284-330`): the authored remediation for the most common failure — *"Enable it in Settings › Extensions…"* plus a ready-to-paste `compozy config set` suggestion (`marketplace_trust.go:216-221`) — is visible only with `-o json`. CLI output has zero color, no success glyph, no next-step hint anywhere (`internal/cli/format.go` is plain tabwriter); a successful install renders byte-identically to a plain `status` read.

### 2. Is the SDK simple, complete, current? — *Simple: B−. Complete: C−. Current: C. TypeScript is a real SDK; Go is a thin JSON-RPC shim*

- **Simple (B−).** A one-tool extension is 4 files/122 lines (TS) or 3 files/86 lines (Go) with one line of real logic — ceremony:logic ≈ 12:1 (TS) and 50:1 (Go). The author confronts three meanings of "capability" in one manifest literal, hand-writes JSON Schema **twice** (manifest `input_schema` + code, reconciled by digest — `internal/extension/tool_reconciliation.go:85`), and re-declares name/version/capabilities in code. Go's `Tool[TInput]` free function collides with an identically-named method that silently degrades to `json.RawMessage`.
- **Complete (C−).** First-class support exists for **2 of 5** provide-capabilities per SDK; `model.source` is absent from both required-method maps and `bridge.adapter` is wrong in both (missing `bridges/targets/snapshot` — `sdk/go/types.go:406-411`, `sdk/typescript/src/capabilities.ts:8-13`). TS types 87/87 Host API methods and 90/90 hook payloads; Go names 44/87 methods, types none, and has **0/90** typed hook events. Neither SDK offers config access, state/storage, HTTP helpers, or schema builders; Go has no testing utilities (TS ships a real `TestHarness`). Two daemon signals never reach handler code in either SDK: `trusted_workspace` (the authenticated workspace root — parsed away by both) and, in TS only, `clarify/ask` (its required `invocation_id` is dropped at parse).
- **Current (C).** The TS generated contract layer is exemplary — regenerated by `compozy-codegen`, byte-checked by `make codegen-check`, gated by `make verify`. Everything outside the generator has rotted: the handwritten Go SDK lags by 43 host-method constants, 3 of 5 capability constants, and all 90 hook events; the capability→required-methods map is hand-duplicated and wrong in *both* SDKs; the **default** scaffold template, the flagship example, and the docs' Practical Example all teach `prompt.provider` — a capability the daemon does not implement; and 2 of the 3 scoped `sdk/examples/` import `internal/*` (unimportable outside the repo) — they are daemon E2E fixtures shelved as SDK examples. Protocol `"1"` strict equality means every evolution is a coordinated hard cut.

### 3. How easy is creating, contributing, installing your own? — *1/5. This is the broken promise*

- **No scaffold exists**: no `init`/`create` verb (`internal/cli/extension.go:55-63`), and the documented scaffolder is frozen with "no v0.3 registry successor" (`develop.mdx:399-401`). Every concept is paid up-front, by hand.
- **45 concepts before first success, 32 of them (71%) ceremony** — packaging, trust, and config plumbing rather than the thing the author set out to build: dual manifest formats, dual metadata placement, resource *families* vs *kinds*, `actions.requires` + `security.capabilities` as two hand-maintained lists that must agree (then a third declaration in code), two near-identically-named checksums, four orthogonal status axes, two config sections for one mental model, a daemon required even to flip a local enable bit. The references: **pi needs 2 concepts** (default-export a function, drop it in a directory), eve 5, flue 4.
- **~12 hand actions** from empty dir to first success, ending in the 5-command install chain — and the docs' only end-to-end walkthrough is annotated "It cannot be managed-installed as written" (`develop.mdx:488`).
- **No inner loop**: no reload verb, no logs verb, no dev-install concept; iteration is rebuild → the trust-gated reinstall (or disable/enable). pi hot-reloads extensions+skills+prompts+themes live via `/reload`; eve rebuilds only the changed extension and keeps the last good generation running on a broken edit.
- **Contributing to others**: publishing requires a PR to `compozy/compozy`'s own `catalog/` (no publish verb — `cmd/compozy-catalog/main.go:47-51`); the whole marketplace holds 3 items. All three references let anyone ship without a gatekeeper (npm/git/URL for pi, npm/workspace/self-hosted registry for eve, open blueprint contributions for flue).
- **The agent-OS irony**: pi's extension docs open with *"pi can create extensions. Ask it to build one for your use case."* Compozy is an agent OS whose own bundled skill (`skills/compozy/`) teaches agents to *operate* extensions but contains zero authoring knowledge — Compozy's agents cannot build Compozy extensions.

### Prerequisite correctness blockers (cataloged in round 1, still true, compressed)

These make the DX questions moot for an outsider until fixed, and they are the receiver's floor, not the headline: both npm SDK packages are `"private": true/UNLICENSED` with no v0.3 successor; the Go template pins unresolvable `github.com/compozy/compozy v0.0.0`; 17–18 manifests (all templates, examples, docs snippets, in-tree bridges) declare `min_compozy_version = "0.5.0"` which a release-stamped v0.3 daemon rejects (`internal/extension/manifest_compatibility.go:28-35`; masked in dev builds where `Version = "dev"` short-circuits at `:15-17`); capability strings are validated by shape, not membership, so the phantom capabilities the templates teach load as silent no-ops (`manifest_compatibility.go:73-84`); reinstall over the same name 409s because replace semantics never reach the CLI (`internal/extension/registry_types.go:55-59`); `git_url` provenance is a constant implemented nowhere (`internal/extension/provenance.go:17`); `extensiontest` is `internal/` and bridge-only; bridges are self-declared closed to third parties (`internal/bridges/ADDING_A_BRIDGE.md:9-11`); native tools cover 7 of 9 verbs (no search/provenance) and `-o jsonl` fails on single-item commands the docs advertise.

### The SDK as an API

TypeScript entry (good bones): `new Extension({...}, options)` + chainable `tool<TInput>(name, opts, handler)` with result normalization (`ToolResult | JSONValue | string | void` all accepted), typed hook payloads (`ExecuteHookParams<"prompt.post_assemble">` → typed `PromptPatch`), fully-typed `request<TMethod>` over the 87-method `HostAPIMethodMap` (47 with namespaced sugar), and a `TestHarness` with `mockHostAPI`. Weaknesses: `ExecuteHookParams<HookEvent>` is not a discriminated union (multi-event extensions must cast), capability constants exist but aren't exported from the index or used by templates (authors type raw strings), and no `AbortSignal` reaches tool handlers.

Go entry (thin shim): `compozysdk.Tool[TInput](extension, handler, opts, fn)` is the one ergonomic signature (plus `TextResult`/`StructuredResult` helpers and `ToolRequest.AskClarification` — the sole Go-only feature). Everything else is untyped: `Request(ctx, method, params any, result any)`, `SupportedHookEvents []string`, raw `json.RawMessage` handlers, per-registration `if err != nil` ceremony, no testing utilities, no generated anything.

Both SDKs: no config access, no state/storage (the memory-backend template uses `new Map()`), no HTTP/retry helpers (the flagship example hand-rolls `sessionsListWithRetry` around an initialization race), no schema builders, no event emission/subscription (request/response only), and the dropped `trusted_workspace`/`invocation_id` fields described above.

### Creating the first extension — the journey and the concept bill

Journey (~12 hand actions): choose resource-vs-subprocess → hand-create the tree → write `extension.toml` (6 sections, 15 assignments in the flagship example) → write `actions.requires` and `security.capabilities` as two agreeing lists → hand-write ~88 lines implementing a dual-mode entrypoint that re-declares name/version/capabilities → build (docs show only repo-internal commands) → vendor dependencies inside the root (no tooling documented; symlink escapes rejected) → run the 5-command install chain → verify via `status` + `hooks list --source config`.

Concept inventory: **45 total, 13 essential (29%), 32 ceremony (71%)**. The ceremony clusters: dual manifest format + dual metadata placement; families-vs-kinds; the triple capability declaration (`actions.requires` + `security.capabilities` + in-code); derived subprocess `type` with implicit inference; two checksums (`ChecksumSHA256` extracted-tree vs `ArchiveDigestSHA256` feed) rendered side by side in `provenance` with no explanation; four orthogonal status axes (`enabled` × 5-value `state` × 3-value `health` × `type`); trust tiers + trust decisions + policy key + consent flag + `--yes`; two config sections (`marketplace.catalog.*` vs `extensions.marketplace.*`) for one mental model; registry `slug` vs installed `name`; `config reload` reconciliation; daemon-required for nearly every verb.

## Requirements

What must be true when this lands. Each is stated as an observable outcome with its measurement; mechanism, sequencing, and architecture belong to the receiver.

**R1 — Time-to-first-extension collapses.** A newcomer reaches a working, installed extension holding **≤10 concepts** (today: 45) and **≤4 actions** (today: ~12 + 5-command install), starting from one scaffold entry point that exists and is discoverable. Ceremony is a ladder: the minimal extension requires no hand-written manifest boilerplate, no duplicated schema, no capability triple-declaration; packaging/trust concepts arrive only when the author distributes. Measured by walking the documented path and counting.

**R2 — Installing your own code is trivial and never marketed.** A local-directory install by its author is at most one command plus at most one consent, with no global policy flip and no marketplace vocabulary in the flow or its errors. Trust affordances collapse to at most two (a policy and a consent). Reinstall-in-place during iteration works (same name, no remove round-trip, no 409). Each install source (curated, GitHub, git, local) is a single command once its one-time setup is done, and web install parity covers what the API contract already exposes (local path install; the built-but-unrendered update affordance).

**R3 — Updates announce themselves.** `update_available` — already computed — is passively visible wherever installed extensions are listed (CLI list, marketplace search, web cards/landing, status), and applying is one command with batch partial-progress reporting. Update discovery requires zero prior knowledge of a `--check` flag.

**R4 — The inner loop is edit → reload → observe.** An author can apply a code change to a running extension without the uninstall/reinstall/re-consent cycle; can watch extension logs/stderr live through a supported surface; can validate a manifest pre-install with file/line/column errors; and can see crash-loop state honestly (`consecutive_failures`/`restart_backoff` surfaced, not hidden). Dev installs are distinguishable from published ones in list/status.

**R5 — SDK: simple.** One declaration: tool identity, schemas, and capabilities are declared once, in code or in manifest, never both (digest-drift class of failure becomes impossible or loudly fatal at a defined point). Templates and docs use exported capability constants, not raw strings. Go and TS reach ergonomic parity on registration (typed handler in one call, no free-function/method collision, no silent `json.RawMessage` degradation, error ceremony proportional to risk). Handler results accept the natural return shape in both languages.

**R6 — SDK: complete.** All 5 provide-capabilities have first-class, correct support in both SDKs (required-method maps single-sourced from the daemon — the `bridge.adapter`/`model.source` map bug class cannot recur). Hook payloads are typed in both languages, with event-discriminated narrowing. Host API methods are all nameable and typed in both languages. `trusted_workspace` and clarification (`invocation_id`) reach handler code in both. A recorded decision exists on the batteries tier (config access, state/storage, HTTP/retry, schema builders, testing utilities in Go) — each present or an explicit non-goal.

**R7 — SDK: current, structurally.** No handwritten mirror of daemon contracts remains unguarded: whatever the daemon defines (methods, events, capabilities, required-method maps), both SDKs track it through a mechanism enforced by `make verify` — drift is a CI failure, not an archaeology find. Every `sdk/examples/*` entry imports only the public SDK (the two `internal/*`-importing fixtures move or are replaced). The protocol-version evolution story (hard-cut vs negotiation window) is an explicit recorded decision.

**R8 — Errors help; output confirms.** Human-mode CLI output renders authored diagnostics: suggested commands and remediation text reach the terminal (11 sites exist today; a human sees zero). Success output confirms the action and names the next step. The most common failures (wrong path, unknown name, no marketplace configured, update on local install, subprocess crash) each say what/why/what-next. `status` answers "is it working?" without requiring the user to mentally join four status axes.

**R9 — The concept bill shrinks by design.** Recorded decisions (resolve or explicitly keep, with rationale) on each ceremony cluster: dual manifest formats; dual metadata placement; families-vs-kinds naming; the three "capability" meanings (glossary-owned disambiguation); two checksums with near-identical names; four orthogonal status axes; two config sections governing one mental model; daemon-required reads for local state; slug-vs-name. Success metric: the concept inventory recount lands ≤20 with essential:ceremony inverted.

**R10 — Contribution has no gatekeeper; agents are first-class on both sides.** A third party ships an extension to other users without a PR to `compozy/compozy` (npm/git/URL-class sources are inherently open per the reference systems; whatever the chosen mechanism, discovery reflects it). The examples corpus becomes the documentation (reference bar: 43–78 examples; Compozy has 3, two of them unimportable). `skills/compozy/` gains authoring knowledge so a Compozy agent can build a Compozy extension on request — the agent-OS analogue of pi's opening line — and the CLI's structured output plus native tools cover the full loop (search and provenance included, `jsonl` parity where advertised) so agent callers are first-class, as flue treats them.

**R11 — Prerequisites (correctness floor).** The round-1 blockers are fixed as a precondition to everything above: published, version-matched SDKs for both languages; template/example/docs manifests compatible with the shipping daemon (with a CI gate keying them to the daemon version); closed-set validation for `capabilities.provides`/`security.capabilities`; replace-in-place install; the phantom-capability templates corrected; a public conformance harness covering all provide-capabilities; a recorded position (supported path or explicit non-goal) for each closed surface — third-party bridges above all, since Slack/Jira/Notion-class integrations are where traction lives.

## Constraints & Non-goals

- **Greenfield Alpha**: no backward compatibility, no migration shims; obsolete code is deleted; renames cut hard across code/storage/APIs/CLI/extensions/specs/`.compozy/tasks/*` in one change. Breaking-change techspecs list delete targets.
- **Core premise**: every resulting capability must be runtime-extensible AND agent-manageable via CLI/HTTP/UDS with structured output.
- **Process**: significant changes go through TechSpec (`cy-spec-preflight` → `cy-create-techspec`), honoring `docs/_memory/standing_directives.md`. The install/trust path has absorbed multiple patches — two-touch rule applies: further change there is structural redesign, not a third patch. Every spec carries extensibility/agent-manageability/config-lifecycle analysis and `Web/Docs Impact`; every change carries the Compozy Impact Audit.
- **Storage**: SQLite changes follow `eng-schema-migration` (declarative source + append-only Goose migration + `make codegen`).
- **Gates**: `make verify`; zero-tolerance lint; 500-line production-file cap; no `_`-discarded errors.
- **Vocabulary**: `capability` is the canonical artifact name (`COPY.md`/glossary); resolving the three-way overload is in scope for naming decisions, entrenchment is not.
- **Prior art**: the marketplace program's declared non-goals (feed signing, DCR, community registry sources, bulk updates, background auto-update, in-product publishing) were non-goals *of that program*; R3/R10 touch several — reopening any is a deliberate techspec decision. `.compozy/tasks/marketplace/state.yaml` is stale; don't trust it as a shipped-state map.
- **Truthful UI**: no surface renders controls/metrics the runtime doesn't support; daemon truth wins.
- **Reference systems are a bar, not a blueprint**: eve/flue/pi properties are measurements to meet or consciously decline, not designs to copy — Compozy's subprocess JSON-RPC model and digest-pinned curated trust are not identified as problems and are not up for replacement here.
- **Non-goals**: implementation designs and sequencing; Compozy Network federation; ACP protocol redesign; marketplace monetization; executing the backlog of 50 untested QA scenarios (next QA cycle's scope — new/changed behavior still flags scenarios per the tracker rule).
