# ADR-003: Uniform SDK architecture — thin transport + generated contracts + minimal ergonomics, both languages published

## Status

Accepted

## Date

2026-07-28

## Context

The two SDKs have divergent architectures. TypeScript = transport + a **generated** contract layer (`sdk/typescript/src/generated/contracts.ts`, emitted by `compozy-codegen sdk-contracts` from `internal/extension/contract` specs, byte-checked by `make codegen-check`) + thin sugar. Go = the same transport with a **handwritten partial mirror**: 44/87 host-method constants, 0/90 typed hook events, and a hand-duplicated capability→required-methods map that is wrong in *both* SDKs (`bridge.adapter` missing `bridges/targets/snapshot`, `model.source` absent — `sdk/go/types.go:406-411`, `sdk/typescript/src/capabilities.ts:8-13`). The audit graded the SDK Simple B− / Complete C− / Current C and found the only healthy layer is the generated one. Neither package is obtainable: npm is `private: true`, and `sdk/go` has no `go.mod` (import drags the whole daemon module; scaffold pins unresolvable `v0.0.0`). Two of three scoped examples import `internal/*`.

## Decision

Both SDKs converge on one three-layer architecture:

1. **Transport** (handwritten, small, stable): JSON-RPC over stdio + lifecycle handshake.
2. **Contracts** (generated, zero-maintenance): a new `compozy-codegen sdk-contracts-go` target emits Go contracts from the same `internal/extension/contract` specs that feed TS — all host-method constants + typed params/results, all hook events with typed payloads/patches, the capability→required-methods map (single-sourced; the TS hand map in `capabilities.ts` is replaced by generated output too), mirror types including `TrustedWorkspace` and `invocation_id`, **and the describe-mode payload schema** (the code-first build handshake, ADR-001): its authoritative definition lives in `internal/extension/contract`, both SDK representations plus conformance fixtures are generated from it, and `make codegen-check` gates every one of these outputs in both languages — the central authoring handshake is never a handwritten cross-package mirror.
3. **Ergonomics** (handwritten, minimal): registration only — `defineExtension`/`NewExtension`, `tool`, `onHook`, `watchSource`, describe mode (ADR-001), result normalization. No broad namespaced sugar for the 87 methods.

Both are published: `@compozy/extension-sdk` goes public on npm (real license), and `sdk/go` gets its own `go.mod` (module `github.com/compozy/compozy/sdk/go`) so `go get` resolves without the daemon module. `sdk/examples/*` may import only the public SDKs; the two `internal/*`-importing examples move to internal test fixtures. Protocol stays the strict single version `"1"`; a negotiation-window decision is explicitly deferred to GA (revisit trigger: first release with external extension authors on a prior SDK line).

## Alternatives Considered

### Alternative 1: Both SDKs raw-RPC, untyped

- **Description**: Shrink TS to Go's current level — transport + minimal registration only, no generated types.
- **Pros**: Least shipped code.
- **Cons**: Deletes the layer that maintains itself and keeps the layers that rot; authors lose typed hook payloads (the audit's best-rated DX feature; pi's standout is per-event typing); code-first manifest generation (ADR-001) still requires a registration API, so the "pure transport" floor doesn't exist.
- **Why rejected**: The maintenance burden lives in handwritten mirrors, not in generated types — this optimizes the wrong term.

### Alternative 2: TS-blessed, Go minimal

- **Description**: Declare TS the primary authoring path; document Go as an advanced raw-RPC shim.
- **Pros**: Half the generator work.
- **Cons**: The flagship first-party extension (`extensions/dev-cycle`) is Go; the team is a Go shop; a "blessed vs tolerated" split reintroduces the exact asymmetry that rotted.
- **Why rejected**: Parity through generation costs one codegen target and removes the asymmetry permanently.

### Alternative 3: Rich sugar in both languages

- **Description**: Full namespaced helpers for all 87 methods in both SDKs.
- **Pros**: Maximum discoverability.
- **Cons**: Large handwritten surface unless the sugar is also generated; generated sugar is feasible later without an architecture change.
- **Why rejected**: Not needed to fix completeness/currency; deferred as an additive follow-up.

## Consequences

### Positive

- Drift becomes a CI failure in both languages; the wrong-map bug class is structurally dead; `model.source` and `bridge.adapter` get correct coverage for free.
- A third-party can `npm install` / `go get` a version-matched SDK — the adoption wall falls.

### Negative

- `sdk/go` as a nested module needs release automation (tag `sdk/go/vX.Y.Z`) and a same-repo `replace` for internal consumers.
- Generated Go adds build surface to `make codegen`/`codegen-check` (marginal).

### Risks

- Nested-module version skew vs daemon → the SDK carries a compat floor constant stamped into manifests at build (ADR-001) and CI tests SDK-against-daemon at head.
- npm publish cadence → wired into the existing release workflow (`release.yml`), not manual.

## Implementation Notes

New generator package `internal/codegen/sdkgo` (mirrors `sdkts` structure: collect `HostAPIMethodSpecs()`, `BuildHookContracts()`, `SDKRootTypes()` → emit files). `cmd/compozy-codegen` gains `sdk-contracts-go` target + check. Generated files land under `sdk/go/contracts/` (package `contracts`), consumed by the handwritten layer.
