# ADR-003: Metric-gated ratchet with best-generation seeding and queryable machine verdicts

## Status

Accepted

## Date

2026-08-01

## Context

The Drive synthesis note's core mechanism (gap H1) is a ratchet: a scalar metric with a direction,
baseline retention of the best result, and revert-to-best — "never build on a regression".
Validation against current code (2026-08-01) confirmed the gap is stronger than claimed:

- `Verdict` has no score; `VerdictOutcome` is a closed 7-value enum; aggregation is priority-ordered
  enum precedence (`gate/types.go:130-146,213-227`, `evaluator.go:208-231`).
- The only float in the gate plane, `CriterionResult.Confidence`, never participates in outcome
  aggregation or routing — but it IS consumed downstream (correction from peer-review B-006): the
  store event builder copies it into the existing `gate_verdict` SSE event
  (`global_db_loop_event_boundaries.go:109-146`) and the web reducer renders it
  (`web/src/systems/loops/lib/loop-events.ts`). Replacing it with `Score` is therefore an event
  payload MIGRATION with enumerated consumer delete targets, not a write-only field removal.
- `GateCriterion` has no numeric field; `CriterionType` is closed to
  `command|agent-judge|human|extension` (`dsl/gate_start.go:4-30`).
- Machine verdicts are not queryable anywhere — `loop_gate_decisions` stores human approvals only
  (`service_gate_decisions.go:17-47`); gate verdicts survive only as inline JSON in the gate node's
  `output_ref` (`control_gate.go:246-252`).
- No best-so-far marking or restore path exists — but generation outputs are already
  content-addressed and durable (`loop_output_blobs`, `50_loops.sql:270-276`), so the raw material
  for restore exists.

## Decision

1. **Metric criteria (opt-in per gate).** `GateCriterion` gains an optional `Metric` block:
   direction (`maximize|minimize`) and optional `min_delta` (default 0 = any strict improvement).
   All three machine criterion types can emit the score: `command` (typed JSON output contract),
   `agent-judge` (rubric score field), `extension` (response field). **At most one metric criterion
   per loop definition** (blocking lint) — v1 is single-objective by design.
2. **Ratchet acceptance semantics.** On a metric gate, the criterion fails when the score does not
   improve on the best-so-far by `min_delta` (direction-aware, `min_delta` finite and non-negative
   by lint). Failure flows through the existing outcome/routing machinery (`rejected` →
   `revise`/`next_generation`/`halt` per `on_result`). Boolean gates are entirely unchanged.
3. **Best eligibility and seeding (tightened per peer-review B-004).** Best advances only when the
   score is finite AND the metric gate's aggregate verdict is `approved` AND the improvement is
   strict ≥ `min_delta`; the first score obeys the same rule (an approved finite first score
   becomes the baseline; a rejected/invalid one does not). A metric-gate rejection with an
   existing baseline seeds the next generation from the **best** generation (origin
   `ratchet_restore`, `parent_generation = best`); a rejection with NO baseline seeds from the
   last generation (origin `gate_revise`/`gate_next_generation`) — best is never fabricated.
   `previous.*` always exposes the rejected generation for diagnosis (ADR-001). `exhausted`/
   `stalled` terminals on runs with a recorded best reference the best generation as the run's
   final outputs.
4. **Queryable machine verdicts via the authoritative transaction (per peer-review B-001).** New
   side table `loop_gate_verdicts` (one row per gate evaluation per generation: outcome, score,
   `route_cause_rank`, matchable columns; sanitized criteria/blocking-issue JSON). Best tracking
   lives on `loop_runs` (`best_generation`, `best_score`). Mutations travel as typed intents on
   `GenerationSnapshotPayload`/`CoordinatorCompletionPlan` and are applied by the store finalizer
   inside `CompleteCoordinatorAndEnqueueNext` (`BEGIN IMMEDIATE`, claim-token fenced); the gate
   node `output_ref` is a projection of the same sanitized record written in that transaction —
   one authority, no standalone writer, no peer mutation path (L-005).

## Alternatives Considered

### Alternative 1: Advisory scores (telemetry only)

- **Description**: Persist scores and mark best, but outcomes stay boolean; routing ignores scores.
- **Pros**: Zero routing-semantics risk; smaller change.
- **Cons**: No anti-regression guarantee — the ratchet's entire point; agents keep building on
  regressions; "best" becomes a dashboard fact, not a behavior.
- **Why rejected**: Delivers the cost of scoring without its value. The synthesis note's mechanism
  is acceptance-coupled by definition.

### Alternative 2: Seed from last (regression rejects, but next generation builds on the rejected one)

- **Description**: Score decides outcome, carry-forward still comes from the last generation.
- **Pros**: Minimal seeding change.
- **Cons**: Regressions accumulate as the working base; best is reachable only via namespace
  citation; weak ratchet.
- **Why rejected**: "Never build on a regression" is the invariant that makes the ratchet
  monotone; per-gate opt-in keeps the paper's repair pattern (build on last + verdict) available on
  boolean gates.

### Alternative 3: Extend `loop_gate_decisions` with machine rows

- **Description**: Reuse the human-decision table with `actor_kind = machine`.
- **Pros**: One table.
- **Cons**: That table is criterion-grained and approval-shaped (`decision/actor/origin/note`);
  verdicts are gate-grained with score + outcome + diagnostics; mixing collapses two lifecycles
  (human approvals are awaited, machine verdicts are computed) into one schema.
- **Why rejected**: Side-table-per-entity discipline — matchable machine-verdict state gets its own
  typed table; the playbook forbids JSON bags for matchable state and this is the inverse case
  (don't overload an approval table either).

### Alternative 4: New `RouteAction` `revert_to_best`

- **Description**: Expose restore as an explicit route verb.
- **Pros**: Author-visible control.
- **Cons**: `RouteAction` is a closed vocabulary wired through routing, linter, docs, web, and
  hooks; seeding-from-best on rejection + best-referencing terminals cover the behavior without a
  new verb.
- **Why rejected**: No behavior gap left for the verb to express in v1; can be revisited if
  multi-objective ratchets land.

## Consequences

### Positive

- Optimization-shaped loops (perf tuning, eval-score climbing, size reduction) become expressible
  with a monotone guarantee; exhaustion returns the best work, not the last attempt.
- Machine verdicts become queryable history — also the raw data the deferred eval-harness spec
  (H4) needs.

### Negative

- One migration (new table + two `loop_runs` columns + `loop_generations`, ADR-004) with sqlc/Atlas
  regen; contract/CLI/web/docs surfaces gain score/best fields (co-shipped).
- Single-metric limit constrains multi-objective use until a follow-up.

### Risks

- Score-source contract abuse (command emitting garbage) — typed parse with deterministic
  `invalid_output` verdict on violation (existing outcome).
- Float comparison pitfalls (NaN, ±Inf) — reject non-finite scores as `invalid_output`; comparisons
  are direction-normalized deltas against `min_delta`.
- Seed-from-best interacting with `ChildLoopRunID` carry rules — explicit re-attempt matrix in
  `_tests.md`.
