# ADR-004: Generation provenance (lineage-lite) instead of a lineage DAG

## Status

Accepted

## Date

2026-08-01

## Context

Gap H2 proposed generations as a lineage DAG: branch from any ancestor, keep alternative branches
alive, possibly run sibling candidates concurrently. A dedicated feasibility exploration
(2026-08-01) sized two levels against current code:

- **Level A (tree history, one active leaf)**: ~20-30 non-test Go files + ~8-12 web files, one
  migration — but three semantically heavy problems: stall/no-progress/circuit-breaker arithmetic
  (`generation - offset` scans in `coordinator_terminal_helpers.go:76-212`) is undefined on a tree
  (false-stall on legitimate branch resets); `iteration_cap` and `gate.Revision` must become path
  depth instead of generation number; the session-binding CAS actively forbids going backwards
  (`adopted_generation` monotonic guard, `global_db_goal_bindings.go:136-195`).
- **Level B (parallel live candidates)**: everything in A plus three structural blockers — one
  coordinator in flight per run is an invariant (the `ListLoopRunsMissingActiveCoordinator`
  reconciler treats a second state as broken); managed session bindings collide by construction
  (partial unique index on `(loop_run_id, handle) WHERE state='active'`); run status,
  `active_gate_id`, inactivity clock, and budget are single-valued scalars. ~60-80 files.
- **Tournament best-of-N already exists** at the run level: a body of
  `fan-out → run-loop(variant) → collect → judge gate` runs full child runs as arms
  (`action_runloop.go:41-52`, `ParentLoopRunID`), lacking only shared budget and lineage queries.
- The accepted ratchet (ADR-003) already delivers queryable per-generation verdicts, best-so-far
  marking, and restore-from-best — ~80% of H2's practical payoff without touching succession.

## Decision

1. **Adopt lineage-lite provenance.** New side table `loop_generations` — one row per generation:
   `(loop_run_id, generation, parent_generation, origin, created_at)`. Generation numbering stays
   strictly monotonic `+1` with a single live leaf; `parent_generation` records derivation only:
   normal succession writes `N-1`; ratchet seeding (ADR-003) writes the best generation. `origin`
   is a closed enum: `initial | stop_when | reattempt | gate_revise | gate_next_generation |
   dod_retry | ratchet_restore` (in-body next_generation distinguished per peer-review B-002).
   Rows are written by the loop-start transaction (generation 1) or the coordinator completion
   plan (B-001) — the `COUNT(loop_generations) == loop_runs.generation` invariant holds from the
   first post-migration open because the migration hard-cuts pre-change run history (B-005; see
   TechSpec Delete Targets). The table also replaces the counted
   `for generation := 1..run.Generation` payload loop in `daemon/loop_api_runs.go:303-321` with a
   real query.
2. **Reject Level B (parallel live candidates)** — the three structural blockers reopen the
   coordinator concurrency model and session-binding identity simultaneously, and the run-loop
   tournament already serves best-of-N.
3. **Defer Level A (true tree, one active leaf)** until a concrete demand the child-run tournament
   cannot serve; `loop_generations.parent_generation` is deliberately the schema seed a future
   Level A would extend (no rework).

## Alternatives Considered

### Alternative 1: Level A now

- **Description**: Real branching with one active leaf; allocate generation ids, walk parent
  pointers everywhere.
- **Pros**: Genuine branch-from-ancestor; lineage queries.
- **Cons**: Redefines stall/breaker/cap/revision semantics; replaces the adopted-generation CAS;
  touches ~30 Go + ~12 web files; the ratchet already covers non-regression, leaving provenance as
  the marginal value.
- **Why rejected (for now)**: Marginal value over ratchet + provenance does not pay for redefining
  four safety semantics; deferred, not forbidden.

### Alternative 2: Level B now

- **Description**: Concurrent sibling generations with judge selection.
- **Pros**: True tournament inside one run/budget.
- **Cons**: Violates one-coordinator-per-run, collides session bindings by construction,
  single-valued run status/gate context/clock/budget; ~60-80 files.
- **Why rejected**: Structural rewrite, and `fan-out → run-loop → collect → gate` already delivers
  the user value with today's invariants intact.

### Alternative 3: No provenance at all

- **Description**: Ship the ratchet without recording where a generation was seeded from.
- **Pros**: One less table.
- **Cons**: Ratchet restores become invisible in audit/UI ("generation 7 suddenly matches
  generation 4's outputs" with no recorded reason); the API payload keeps the counted-loop hack;
  future Level A starts from zero.
- **Why rejected**: Provenance is one column + a tiny table, makes restores auditable, and is the
  honest foundation for any future lineage work.

## Consequences

### Positive

- Every generation records its derivation and origin — restores are auditable in events, API, UI.
- Generation payload assembly becomes a real query; contract gains `parent_generation`/`origin`.
- Future Level A extends this schema instead of migrating into it.

### Negative

- One more table in the loop stream (same migration as ADR-003 artifacts).
- UI/docs must explain `parent ≠ N-1` on ratchet restores (a small, honest complexity).

### Risks

- Writers forgetting the row on a new succession path — invariant: every generation-creating plan
  writes its `loop_generations` row in the same transaction; equivalence test asserts row count ==
  max generation.

## Implementation Notes

Row writes happen where generations are created: initial plan, `buildStopWhenNextGenerationPlan`,
`buildNextGenerationCoordinatorPlan` (re-attempt), DoD retry (ADR-002), ratchet restore (ADR-003).
Single migration co-ships with ADR-003 schema work.
