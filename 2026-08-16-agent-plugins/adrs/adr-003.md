# ADR-003: Conformance diagnostics are first-class product output, not logs

## Status

Accepted

## Date

2026-08-15

## Context

The standard mandates component-level failure isolation (a bad skill or MCP entry is skipped; siblings keep loading) and says clients SHOULD report such failures. The two reference implementations studied both bury the report: Codex writes manifest/MCP failures to tracing logs only — a package with an invalid name silently disappears with zero user feedback — and Hermes surfaces exactly one fatal install-time message, with every per-component diagnostic going to `logger.warning`. Both were flagged in their own analyses as the weakest part of the implementation. Compozy's posture (SD-011, "agent-manageable by default") requires structured, discoverable state for agents, and its QA culture treats invisible degradation as a bug.

## Decision

Every outcome of the conformance fatality ladder is user-visible product output:

- **Install** reports, in human and structured form, the package identity, each ingested component, and each skipped component with its reason.
- **Validate** runs the same ladder against a package directory and reports fatal errors and per-component diagnostics with deterministic exit behavior.
- **Status/inventory surfaces** expose a degraded state per component with the recorded reason, queryable by operators and agents alike.
- Diagnostics carry a stable component scope (which skill, which server) so agents can act on them programmatically.

## Alternatives Considered

### Alternative 1: Log-only diagnostics (Codex model)

- **Description**: Ladder outcomes go to daemon logs; surfaces show only success/absence.
- **Pros**: Least implementation surface.
- **Cons**: Silent disappearance of invalid packages; un-debuggable for users, invisible to agents; contradicts SD-011.
- **Why rejected**: It is the documented weakness of both competitors and the clearest gap to beat them on.

### Alternative 2: Fatal-only reporting (Hermes model)

- **Description**: One install-time fatal message; per-component skips logged.
- **Pros**: Small; covers the worst case.
- **Cons**: Partial ingestion (the standard's required behavior) becomes invisible: a package that installed with 3 of 5 skills looks identical to a fully healthy one.
- **Why rejected**: Partial states are exactly where users need visibility.

## Consequences

### Positive

- A degraded package is diagnosable from the CLI, the API, and the web without reading logs.
- Agents can detect, report, and repair broken installs autonomously.
- Competitive differentiator documented against both reference clients.

### Negative

- Diagnostic shapes become part of the public contract — they must be versioned with the same care as any structured output.
- More assertion surface in tests (every ladder branch needs its visible outcome covered).

### Risks

- Diagnostic copy drift across surfaces; mitigated by deriving all surfaces from one recorded diagnostic set (Stage 2 design constraint).

## Implementation Notes

Exact copy, exit codes, output shapes, and where diagnostics persist are Stage 2 decisions (`_dx.md` first, then Part II). The Hermes two-class model (fatal error vs scoped diagnostic `{scope, message}`) is the reference pattern for the recorded set.
