# ADR-001: Ingest Agent Plugins packages as a third install layout of the existing extension system

## Status

Accepted

## Date

2026-08-15

## Context

The Agent Plugins standard (agent-plugins.org, v1.0.0, launched 2026-08-06) defines a portable package: `plugin.json` at the root, `skills/<name>/SKILL.md` (non-recursive discovery), and `mcp.json` (transports `stdio` | `streamable-http` | `sse`). Two of the three ACP providers Compozy spawns (OpenClaw fully; Hermes via a compatibility adapter) already consume it, and AWS/Google/Vercel ship plugin content. Compozy owns native implementations of both standardized component types — `SKILL.md` parsing and MCP server configuration including remote HTTP transport — and a hardened shared archive installer that already accepts two root layouts (`extension.toml`, `SKILL.md`). The standard deliberately ships no distribution, trust, signing, or permission model; those remain each host's business — which is exactly the layer Compozy already has.

Verification (2026-08-15, repo @ d5ff8005) confirmed all load-bearing facts: session-level `MCPServer` supports `stdio`+`http`, `internal/config/mcpjson.go` already parses `mcp.json` documents, resource-only extensions fit every trust tier, and zero third-party-format compat code exists today.

## Decision

Consume Agent Plugins packages by making `plugin.json` the **third accepted root layout** of `compozy extension install`. A conformant reader validates the package per the standard (fatality ladder, closed schemas, non-recursive skill discovery, path containment) and synthesizes a **resource-only** extension — no subprocess, no Host API permissions. One product concept ("extension") with the plugin format as interchange: no new noun in CLI verbs, UI, or docs; at most a read-only format indicator in inventory/list surfaces. Delivery stays entirely daemon-side, so an ingested package works uniformly across Claude Code, OpenClaw, and Hermes sessions.

Scope of this spec: Phase 1 (ingestion, stdio + streamable-http, full 8-item minimum conformance) plus the Phase 2 compatible-clients listing PR as a trailing task. Phase 3 (export/dual-target under a `com.compozy/` namespace) and a Claude Code plugin adapter are explicitly out of scope. Legacy `sse` entries are skipped with a diagnostic (spec-optional for clients). When a directory carries both manifests, `extension.toml` wins. No new `config.toml` keys: format detection is not policy, and trust reuses the existing provenance/consent pipeline.

## Alternatives Considered

### Alternative 1: Re-platform the Compozy manifest onto `plugin.json`

- **Description**: Make `plugin.json` + an `extensions["com.compozy"]` namespace the canonical Compozy manifest.
- **Pros**: Single manifest format; maximal alignment with the standard.
- **Cons**: The standard is a week-old Working Draft with a frozen-but-untagged spec repo; Compozy's manifest carries provides/permissions/hooks/loops the portable format cannot express; churn across every surface for zero user value.
- **Why rejected**: `extension.toml` stays canonical; revisit only if the standard exits draft and gains durable traction.

### Alternative 2: Provider pass-through

- **Description**: Let OpenClaw/Hermes load plugin packages themselves instead of Compozy ingesting them.
- **Pros**: Zero ingestion code.
- **Cons**: Breaks uniformity (Claude Code is not a conformant client); moves resource governance — workspace scoping, trust, consent, prompt-injection scanning — out of the daemon; contradicts the daemon-side delivery architecture.
- **Why rejected**: Daemon-side delivery is the whole point: one ingest, three providers.

### Alternative 3: A separate "plugin" product concept

- **Description**: New noun, new verbs (`compozy plugin install …`), separate registry.
- **Pros**: Mirrors the standard's vocabulary.
- **Cons**: Two overlapping concepts for one capability; duplicated lifecycle surfaces; permanent naming debt in CLI/UI/docs.
- **Why rejected**: Confusing next to extensions; the format is interchange, not identity.

## Consequences

### Positive

- Ingested packages inherit the full extension lifecycle (install/enable/disable/update/remove/logs, trust tiers, provenance, secret bindings) with zero new policy surface.
- Resource-only synthesis means a *smaller* risk surface than a normal extension — no subprocess, no Host API grants.
- Compozy gives plugin content guarantees the standard lacks (trust gate, prompt-injection scan, checksum, provenance).

### Negative

- A conformance layer must be maintained against a standard whose spec repo is frozen but untagged (pin by schema id/SHA).
- The real-world catalog is messier than the standard: flagship vendors (AWS) ship client-specific layouts (`.claude-plugin/`, `.codex-plugin/`) that this spec deliberately rejects with a diagnostic.

### Risks

- Standard abandonment: cost already sunk is small (adapter + detection); removal is a hard cut of one package plus detection arms.
- Spec drift after the draft: schema ids are versioned constants; a new version is a new deliberate mapping, never a silent widening.

## Implementation Notes

Deliberate schema change in Phase 1: extend the extension-manifest MCP declaration (today stdio-only) to carry `transport`/`url`, aligning it with the canonical session-level `MCPServer`. The adapter synthesizes explicit per-skill paths (our extension skill walker is recursive; the standard mandates non-recursive immediate children). This is an additive feature — **no delete targets**.
