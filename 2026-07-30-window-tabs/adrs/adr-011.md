# ADR-011: Durable per-window navigation stacks via navigate modes

## Status

Accepted

## Date

2026-07-30

## Context

Product rule D2/BR-4: each tab owns an independent navigation stack; drill-in never spawns windows/tabs; back pops only the active tab; stacks survive restarts (ADR-003) and travel with reopen (US-008) and layout export (BR-18). Today `Window.Route` is a single replaceable `RouteIntent` — `window.navigate` overwrites it, breadcrumbs are ephemeral TopbarSlot publications, and nothing durable records where a tab has been. `window.navigate` is already history-exempt (`service_execute.go:127`) and undo/redo re-applies live routes over restored states (`restoreStatePreservingRoutes`).

## Decision

Add a bounded, durable navigation stack to the window and express stack discipline through the existing navigate command:

```go
// Window gains:
NavStack []RouteIntent `json:"nav_stack,omitempty"` // ancestors, oldest first; Route stays the current leaf

// NavigateWindowCommand gains:
Mode NavigateMode `json:"mode,omitempty"` // "replace" (default) | "push" | "pop"
```

- `push`: appends the current `Route` to `NavStack` (capped by config `nav_stack_limit`, oldest dropped) and sets `Route` to the payload route.
- `pop`: discards the payload route, sets `Route` to the last `NavStack` entry and shrinks the stack; empty stack → no-op success (PRD US-011 EC-1).
- `replace` (default, today's behavior): overwrites `Route`, stack untouched — deep links, route-pop reconciliation, and non-hierarchical route changes keep current semantics without callers changing.

`window.navigate` stays history-exempt and hook-free; undo/redo preserves live `NavStack` alongside `Route`. The web maps drill-in `<Link>` navigations to `push`, breadcrumb/back (⌘[) to `pop`, and everything else to `replace`.

## Alternatives Considered

### Alternative 1: Client-local navigation history

- **Description**: Keep stacks in browser memory keyed by window ID.
- **Pros**: No domain/wire change.
- **Cons**: Violates ADR-003 (stacks are durable), dies on reload, invisible to agents/export/reopen.
- **Why rejected**: Contradicts accepted product persistence contract.

### Alternative 2: Separate `window.back` command + daemon-inferred pushes

- **Description**: The daemon decides push-vs-replace by comparing route prefixes; a new command pops.
- **Pros**: Callers unchanged.
- **Cons**: Route hierarchy is app knowledge (`/agents/x/sessions/y` is not a child of `/agents` textually); inference guesses wrong exactly where it matters; a second command duplicates navigate's validation and follow rules.
- **Why rejected**: Hierarchy intent belongs to the navigator; explicit mode is one field.

## Consequences

### Positive

- Stacks restore across restarts, ride reopen entries and layout export for free (they live on `Window`), and are visible to agents via every listing surface.
- Zero behavior change for existing callers (`replace` default).

### Negative

- Wire `Window` grows; `nav_stack_limit` config key needs full lifecycle (struct, default, validation, docs, tests).
- Web must classify navigations (push/pop/replace) at the routing-coordinator boundary — a small but real policy layer.

### Risks

- Runaway stacks from cyclic drill-ins → capped by `nav_stack_limit` (default 50, 1..200) with oldest-entry eviction.

## Implementation Notes

Breadcrumb rendering stays a TopbarSlot publication (presentation); the durable stack is the source for restore/reopen, not for live crumb labels. `restoreStatePreservingRoutes` extends to preserve `NavStack` with `Route`.
