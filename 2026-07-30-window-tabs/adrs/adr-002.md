# ADR-002: Apps become multi-instance

## Status

Accepted

## Date

2026-07-30

## Context

Today every app except sessions is a singleton in the OS shell: at most one Tasks window, one Agents window, and so on, enforced purely by web-side window identity (the daemon never enforced it). With tabs as grouped windows (ADR-001), users can express "Tasks in two places" — e.g., a List view filtered one way in one tab and a Kanban view in another tab or group. Keeping the singleton would make such groupings silently collapse into focusing the existing instance.

## Decision

Any app can have **multiple simultaneous windows/tabs** in a workspace. Each instance keeps its own view state (route position, filters, navigation stack). Sessions keep their existing multi-instance behavior. Opening an app from launch surfaces (dock, palette) focuses an existing instance by default; creating an additional instance is an explicit action (e.g., context-menu "open new window/tab" — see ADR-005). Dock indicators aggregate per app: the app lights while any instance exists, and repeated activation cycles through instances.

## Alternatives Considered

### Alternative 1: Keep the per-app singleton

- **Description**: One window/tab per app per workspace; re-opening focuses the existing one.
- **Pros**: No identity changes; no duplicate-tab clutter; simplest mapping between apps, dock, and browser URL.
- **Cons**: "Two views of the same app side by side" — a core multiplexing payoff — is impossible; grouping flows would need special-casing to reject or merge same-app windows.
- **Why rejected**: The user explicitly chose the more powerful model; a tabs feature that cannot hold two views of the busiest app (Tasks) undercuts its own purpose.

### Alternative 2: Multi-instance for a whitelisted subset

- **Description**: Only "content-heavy" apps (Tasks, Sessions) may duplicate.
- **Pros**: Bounded scope.
- **Cons**: Asymmetric rules users must memorize; the inconsistent-support-across-surfaces pitfall from market research.
- **Why rejected**: Arbitrary asymmetry; the uniform rule is simpler to learn and manage.

## Consequences

### Positive

- Two-views-of-one-app workflows (compare filters, watch one run while browsing the catalog) become first-class.
- Grouping any windows is total — no "cannot merge, app already present" edge cases.

### Negative

- Window identity, deep links, and launch surfaces must distinguish instances; the URL can only reflect one focused instance at a time.
- Duplicate-looking tabs become possible; labels must disambiguate beyond the app name (view/leaf-derived labels, per reference rule D2).

### Risks

- Accidental instance proliferation ("Tasks ×5") — mitigated by default-focus-existing on launch surfaces (creation is explicit), ⌘K tab search, and derived labels that expose each instance's current leaf.

## Implementation Notes

Instance identity, URL mapping, and dock cycling order are TechSpec concerns. The product commitments are: uniform multi-instance for all apps, default-focus with explicit duplication, per-instance view state, and aggregate dock signaling.
