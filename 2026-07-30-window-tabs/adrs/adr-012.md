# ADR-012: Snapshot v3 hard cut — boot discards stale-version snapshots; no upgrade path

## Status

Accepted

## Date

2026-07-30

## Context

Window tabs add fields across the aggregate (`Desktop.FloatingStacks`, `Window.NavStack`, `Window.Pinned`, `Snapshot.ClosedEntries`, ClientView projections). The persisted snapshot is version-gated and reject-only: `ValidateSnapshot` fails any version ≠ current (`validate.go:51-53`), the repository decodes with `DisallowUnknownFields` (`window_manager_repository.go:212-244`), and there is no upgrade path — today a stale snapshot **bricks the workspace's window manager** until the clientstate row is deleted by hand. Layout profile documents embed the same version (`resource_codec.go:174-179`). Greenfield policy (SD-002/L-006) forbids compat shims; the user chose discard over a one-pass upgrade.

## Decision

1. `SnapshotVersion` bumps 2 → 3 with all new fields.
2. **Boot/load discard replaces the brick:** when the repository loads a snapshot whose version ≠ `SnapshotVersion` **or whose payload fails strict decode (malformed/unknown fields)**, it logs a warning with the stored version/reason, **deletes the clientstate row, and reinitializes** the workspace with `initialSnapshot` — one-time loss of window/desktop arrangement only; sessions, tasks, and all runtime data are untouched. Discardable classes are exactly those two. **Workspace-ID mismatch and current-version topology validation failures remain hard errors** that preserve the stored blob for forensics — they indicate real corruption, not staleness. This policy is permanent for future bumps, not a one-shot script.
3. **Layout profiles are not converted:** `window_layout` resources whose document version ≠ 3 fail validate/apply with the existing deterministic error surface (`topology.unsupported_version` diagnostics); users re-export. No converter ships.
4. Delete targets: the load-error brick path for version mismatch (replaced by discard), and every test asserting version-2 acceptance (updated to version-3 + discard coverage).

## Alternatives Considered

### Alternative 1: One-pass v2→v3 upgrade

- **Description**: On load, decode v2 leniently, fill new fields with defaults, rewrite as v3; convert v2 profile documents likewise.
- **Pros**: Preserves alpha users' current layouts and saved profiles.
- **Cons**: Requires a second, lenient decode path beside the strict one (the exact dual-format shape SD-002 forbids), upgrade tests, and a converter for profiles; the preserved asset is presentation arrangement, recreatable in minutes.
- **Why rejected**: User decision — migration code for presentation state is not worth the policy exception.

### Alternative 2: Keep version 2 and add fields as optional

- **Description**: Same version, new fields tolerated as zero-values.
- **Cons**: Strict decode (`DisallowUnknownFields`) makes old daemons reject new snapshots anyway; version numbers exist precisely to name this boundary; silently mixed shapes across daemon versions.
- **Why rejected**: Violates the versioning contract already in place.

## Consequences

### Positive

- Zero migration code; strict decode stays the only decode path.
- The pre-existing brick failure mode is fixed for every future version bump.

### Negative

- Every existing workspace loses its window arrangement once (and saved v2 layout profiles until re-exported).

### Risks

- Discard masking a corrupted-but-current snapshot → discard triggers only on version mismatch or malformed decode, both logged loudly with the raw reason before deletion; workspace-ID mismatch and v3 topology validation failures hard-fail without deletion, preserving evidence. The QA scenario for layout recovery extends to assert both the discard path and the preserved-blob hard-error path.

## Implementation Notes

The discard lives in the daemon repository load path (composition root owns reconciliation, SD-008). `compozy layout apply` and profile PUT keep their strict version equality check — the error message already names the version.
