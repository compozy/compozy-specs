# ADR-010: Generated window IDs with semantic focus-first lookup (multi-instance identity)

## Status

Accepted

## Date

2026-07-30

## Context

ADR-002 (product) made every app multi-instance. Today the browser derives the durable window ID deterministically — `osWindowId(app, instanceKey)` returns `app:<app>` for every non-session app and `session:<key>` for sessions (`os-types.ts:189-191`) — and that convention is what enforces the singleton: `openOrFocus` finds the existing window by recomputing the ID, the dock skips any window with a non-null instance key (`use-desktop-dock.ts:44`), and the daemon rejects duplicate IDs on open (`reducer_window_open.go:76-78`). The daemon itself never validates `InstanceKey`. Multi-instance cannot be expressed until the ID scheme changes, and window IDs are the durable primary key inside the snapshot.

## Decision

1. **Window IDs become opaque and generated.** The web client generates a unique ID per open (`w-<random>`); CLI/agents may pass any unique ID or omit it, in which case the daemon generates one (new: `WindowSpec.ID` optional, filled server-side and returned in the `Result`). The `app:`/`session:` derivation scheme is deleted.
2. **Dedup moves from ID collision to semantic lookup.** "Focus-first" launch behavior scans live windows for `(app, instanceKey)`: sessions dedup on `instanceKey == sessionId` (opening an open session focuses it); plain app launches focus the most-recently-focused instance of that app and cycle on repeat; "open new instance" skips the lookup and always opens.
3. **Dock aggregates per app.** The instance-key skip is deleted; dock state derives from all windows of the app (lit if any exists, badge aggregation unchanged), and click focus/cycle uses the same semantic lookup.
4. **`window.open` keeps rejecting duplicate IDs** — that check is referential integrity now, not dedup policy.

## Alternatives Considered

### Alternative 1: Instance-suffixed deterministic IDs (`app:tasks:2`)

- **Description**: Keep derived IDs, append an instance ordinal.
- **Pros**: IDs stay human-readable; minimal web changes.
- **Cons**: Ordinals need coordination (two clients opening "tasks:2" concurrently collide), reordering/closing leaves gaps with false meaning, and the scheme still encodes app identity redundantly with `Window.App`.
- **Why rejected**: Coordination cost without benefit — `Window.App` + `InstanceKey` already carry the semantics; the ID should carry none.

### Alternative 2: Daemon-enforced uniqueness on `(app, instanceKey)`

- **Description**: Make the daemon dedup opens semantically.
- **Pros**: Single enforcement point.
- **Cons**: The product default (focus-first) is a launch-surface behavior, not a topology invariant — "open new instance" is legal and common; pushing policy into the reducer forces a policy flag through every command surface.
- **Why rejected**: Policy belongs to launch surfaces; topology stays mechanism.

## Consequences

### Positive

- Multi-instance becomes expressible everywhere (web, CLI, agents) with zero ID coordination.
- The daemon-side model is untouched except for optional server-side ID generation — `InstanceKey` stays a passthrough.

### Negative

- Every web derivation keyed on `osWindowId` (routing coordinator lookups, dock state, palette focus, session dedup, deep-link reconciliation) is rewritten to semantic lookups over the windows map.
- Deep links resolve to "most recently used instance showing that route's app" (PRD BR 11) — a lookup, no longer a constant-time ID hit.

### Risks

- Any missed `osWindowId` call site silently recreates singleton behavior or misses windows — mitigated by deleting the function (compile-time sweep) and covering launch surfaces in the web suites.

## Implementation Notes

`routing-coordinator.ts` keeps its cause model; only window resolution changes (`resolveAppForPath` → candidate windows → focus/open decision). The v3 reset (ADR-012) means no legacy `app:*` IDs survive in snapshots.
