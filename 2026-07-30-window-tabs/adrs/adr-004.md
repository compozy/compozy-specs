# ADR-004: Frictionless tab close with multi-level reopen

## Status

Accepted

## Date

2026-07-30

## Context

Market research ranks accidental close of live work as a top tab-UX failure (the #1 macOS tabs complaint is ⌘W ambiguity), and browsers answer it with cheap, multi-level "reopen closed tab" rather than confirmation dialogs. CompozyOS has a structural advantage: closing a tab never kills the work — agent sessions run in the daemon and remain reachable from the sessions list and dock regardless of any tab or window. A confirmation dialog would therefore protect against a loss that does not exist, while adding friction to a frequent action. The keyboard contract also shifts: ⌘W currently closes the whole window; with tabs it must close the tab (the window when it is the last tab), per reference rule D7.

## Decision

Closing a tab is **immediate and silent** — no confirmation, regardless of the hosted surface's state (running, needs-input, idle). A closed session tab never stops or pauses its session; attention signals (needs-input, running) continue on the dock and sessions surfaces. **⌘⇧T reopens closed tabs in reverse order, multiple levels deep**, restoring each tab's surface and navigation stack into its original group when it still exists (otherwise as a standalone window). ⌘W closes the active tab and closes the window when it is the last tab. Pinned tabs are the one exception: they refuse ⌘W and hover-close; closing one requires unpinning first (see ADR-006).

## Alternatives Considered

### Alternative 1: Confirm when closing live work

- **Description**: A dialog guards tabs hosting running/needs-input sessions.
- **Pros**: Perceived safety; matches document-editor conventions.
- **Cons**: Protects against nothing (the session survives); trains users to click through dialogs; punishes the most common workflow (closing done-with views) with repeated friction.
- **Why rejected**: The runtime makes close genuinely non-destructive; honesty about that (plus easy reopen) beats theatrical protection.

### Alternative 2: Soft-close (tab hides, lingers in a "recently closed" tray)

- **Description**: Closed tabs move to a visible holding area instead of disappearing.
- **Pros**: Very discoverable recovery.
- **Cons**: New chrome surface to manage; duplicates ⌘K search and the sessions list; the "unmanaged pile" pitfall relocated rather than solved.
- **Why rejected**: ⌘⇧T plus palette search achieve recovery without new persistent UI.

## Consequences

### Positive

- Closing feels safe (mitigates the hoarding "blackhole effect" — users keep strips clean when closing is reversible).
- No dialog fatigue; keyboard flow stays uninterrupted.
- Truthful UI: the interface never implies a tab close endangers a session.

### Negative

- Users must learn that sessions live beyond tabs (onboarding/docs responsibility; dock badges already teach it).

### Risks

- A needs-input session with no open tab must remain discoverable — covered by existing dock badge + sessions list, and stated as a PRD success criterion.
- Reopen history scope (per window vs per workspace, retention depth) needs definition — PRD states the behavior; exact depth is a TechSpec constant.

## Implementation Notes

Reopen must restore surface + navigation stack, not merely re-launch the app at its root.
