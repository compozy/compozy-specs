# ADR-007: Design-system amendment — route views move to the strip everywhere; the deck is a sanctioned third bar

## Status

Accepted

## Date

2026-07-30

## Context

The current OS-shell design rules forbid what the tabs reference proposes: S2 caps window chrome at "two bars maximum — 44px head + optional 38px strip", and S3 plus the pagehead migration map place route views (List | Kanban) inside the head, "never in the strip". The window-tabs reference explicitly amends both: D3 moves route views to the strip's leading slot (head stays two-element), and D4 rewrites S2 as "head + strip, plus the deck while the window holds ≥2 tabs". D3 states the route-views move "applies everywhere, single-tab included". The open question was whether to apply that amendment globally at ship time or only inside multi-tab windows.

## Decision

Apply the amendment **globally and immediately**:

1. **Route views relocate from the head to the strip's leading slot on every route with peer views**, in single-tab windows included, from the first ship. Strip order becomes: views · filters · spacer · display-mode. Only two routes use head-hosted views today, so the migration is small.
2. **The deck becomes a sanctioned third bar**: chrome is head + strip, plus the 37px deck only while a window group holds ≥2 tabs. A single-tab window renders today's chrome exactly (rule D1).
3. The canonical design-system documents (shell rules, migration map) are updated in the same program so the rules and the product never disagree.

## Alternatives Considered

### Alternative 1: Amend only inside multi-tab windows

- **Description**: Head keeps route views while a window has one tab; views drop to the strip when a second tab arrives.
- **Pros**: No visible change for current users until they use tabs.
- **Cons**: Layout jumps when the deck mounts/unmounts; two simultaneous head grammars; every route with peer views must implement both.
- **Why rejected**: Permanent inconsistency and a moving head to avoid a one-time, two-route migration.

### Alternative 2: Keep route views in the head, deck coexists

- **Description**: Ignore D3; head keeps identity + views + status/actions even under the deck.
- **Pros**: No route migration at all.
- **Cons**: Three-element heads compete with per-tab breadcrumbs at full width — the exact congestion D2/D3 exist to prevent; contradicts the chosen reference contract.
- **Why rejected**: Breaks the reference's core layout invariant (breadcrumb gets the head's whole width).

## Consequences

### Positive

- One head grammar everywhere (identity/breadcrumb + status + ≤2 actions); no mount/unmount layout jumps.
- The design system stays truthful — rules updated with the product change, not after it.

### Negative

- Two existing routes change visually for all users at ship, independent of tabs adoption.

### Risks

- Future routes may reintroduce head-hosted views by copying stale examples — mitigated by updating the canonical DS documents and migration map in the same program.

## Implementation Notes

Affected DS artifacts: shell rules (S2/S3 text), pagehead migration map row for route nav, and the OS-shell window chapter; production routes with peer views migrate in the same program.
