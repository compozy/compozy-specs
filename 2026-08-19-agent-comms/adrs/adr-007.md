# ADR-007: Subagent invocation — explicit registry name, injected roster, new `description` field, batch fan-out

## Status

Accepted

## Date

2026-08-20

## Context

CompozyOS already owns AGENT.md agent definitions with registry precedence, shadowing, and digests (`$COMPOZY_HOME/agents/<name>/`, `.compozy/agents/<name>/`). The invocation-model exploration (pi full sweep + hermes/codex verification, 2026-08-20) found the de-facto market standard: 4 of 5 harnesses converge on *named agent from a registry + one spawn verb carrying the first prompt + roster injected into the tool/param description*. Nobody ships description-based auto-routing. pi's error-driven roster (agent names only leak via error messages) costs a wasted turn per unknown name and is the anti-pattern. One gap blocks the standard shape here: agent definitions have no `description` field (`internal/api/contract/agent_observe_payloads.go:28-41`).

## Decision

Subagent invocation is **explicit by definition name from the existing registry**. The call verb's agent parameter carries an **injected roster** (name + short description per available definition, rendered shadow-aware) in its description, codex-style. AGENT.md frontmatter, the create/observe payloads, and the definition digest gain a **`description` field** — the one schema change the standard shape forces. `compozy__agent_list` and CLI/HTTP/UDS listing remain the agent-manageability surface; the model never depends on a list call to discover the roster. No auto-router exists in the runtime. Fan-out is a **batch of tasks in one call** (hermes/omp/pi shape): one concurrency budget, one consolidated return; over-cap requests are hard-rejected with a clear error, never silently truncated.

## Alternatives Considered

### Alternative 1: Inline persona per call (hermes)

- **Description**: No registry; caller describes the worker inline every time.
- **Pros**: Zero registry coupling.
- **Cons**: Discards the AGENT.md registry CompozyOS already built; zero persona reuse.
- **Why rejected**: Throws away an existing asset to gain nothing.

### Alternative 2: Description-based auto-routing

- **Description**: Runtime picks the agent by matching task descriptions.
- **Pros**: Less caller decision-making.
- **Cons**: No shipped harness does it; non-deterministic routing collides with truthful-UI/observability posture.
- **Why rejected**: Market-unvalidated magic; the model reading an injected roster achieves the same outcome deterministically.

### Alternative 3: Repeated single-task calls (codex fan-out)

- **Description**: One task per call; parallelism = model calls N times.
- **Pros**: Smaller schema.
- **Cons**: Models demonstrably under-parallelize (hermes documents the failure mode); N× tool-call token cost.
- **Why rejected**: Batch keeps one budget and one consolidated return.

## Consequences

### Positive

- Deterministic selection; roster reaches the model with zero extra turns; registry investment pays off.

### Negative

- `description` ripples through frontmatter parsing, payloads, digests, and docs.
- Roster injection must re-render when definitions change (staleness window to design in Part II).

### Risks

- Roster bloat with many definitions — bounded rendering (count/length caps) decided in Part II.

## Implementation Notes

Verb name and exact parameter shape land in `_dx.md`. Roster rendering is shadow-aware (workspace shadows global).
