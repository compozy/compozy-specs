# ADR-003: Finished children are parked and revivable, with TTL as the hard ceiling

## Status

Accepted

## Date

2026-08-20

## Context

Today a child that finishes its work stays silent (no `idle`/`done` wake reason) until the TTL reaper kills it — the parent is woken by the child's *death*, not its *result* (`internal/session/spawn_wake.go:108-119`, `internal/daemon/spawn_reaper.go`). Any follow-up question requires a re-spawn with all context lost. The market converged on the opposite: omp parks finished children and messaging is the only revival primitive; Codex evicts idle children via LRU residency and lazily reopens them from persisted rollout; Claude Code (GA) resumes a completed subagent with full history when messaged.

## Decision

A child that completes its work becomes **parked: addressable but not running**. A new call or mailbox message revives it — the runtime process may be gone, but session state is already durable in SQLite, so revival is a read-model concern, not new storage. The TTL is an **idle ceiling** (surface-grill amendment, 2026-08-20): the clock runs only while the child is parked/idle and **suspends while a call is in flight** — a working child is never reaped by wall-clock (SD-001: activity supervision, not timeouts, handles stalls). A child parked past its idle TTL is reaped, and a call targeting it returns a typed `call_target_expired` error. There is likewise **no default call deadline** — `--deadline` is per-call opt-in. Parent-terminal behavior (drain vs orphan outstanding calls) follows the #438 descendant-drain precedent and is resolved in Part II.

## Alternatives Considered

### Alternative 1: Reaped-on-TTL only (status quo)

- **Description**: Finished child lives until TTL, then dies; no revival semantics.
- **Pros**: No reaper changes; simplest memory story.
- **Cons**: Forecloses follow-up exchanges; keeps the "wake by death" anti-pattern; contradicts every shipped reference.
- **Why rejected**: The mailbox and the follow-up call are core scope; a lifecycle that destroys the addressee defeats them.

## Consequences

### Positive

- Follow-up calls preserve child context (the market-standard behavior users now expect).
- Daemon memory stays bounded: parked = no live subprocess.

### Negative

- The reaper must distinguish "runtime stopped" from "no longer addressable"; the mailbox must hold messages for parked recipients.

### Risks

- Unbounded parked-session accumulation — bounded by TTL and existing spawn caps; revival counts against liveness caps at revive time.

## Implementation Notes

Revival mechanics (who restarts the subprocess, cap accounting at revive, interaction with `AutoStopOnParent`) are Part II design. Typed error vocabulary for past-TTL calls lands in the `_dx.md` failure copy.
