# ADR-013: Result contracts are stored in a digest-keyed registry; calls pin the digest

## Status

Accepted

## Date

2026-08-20

## Context

Settle-time validation (the Issue-5 fix generalized) needs the contract at the store boundary; the UI needs a canonical schema to render; validation runs at message frequency, so recompiling schemas per validation (today's behavior) does not scale. Precedents exist: capability digests are recomputed and enforced; native-tool contracts pin schema digests at start.

## Decision

A **digest-keyed contract registry**: schemas are canonicalized, hashed, and stored once in a registry table; every call (and contracted task) pins the **digest**. Settle-time validation and UI rendering resolve the schema from the registry by digest; a per-digest **compiled-schema cache** makes repeated validation cheap. Identical contracts used by N calls dedupe to one row.

## Alternatives Considered

### Alternative 1: Inline schema on every call record

- **Description**: Each call carries its full schema.
- **Pros**: No registry table; self-contained rows.
- **Cons**: N copies of identical contracts; settle validation either recompiles per call or caches by full-body hash (a registry in disguise); no canonical source for the UI.
- **Why rejected**: The digest registry is the same storage cost with dedup, plus the cache key falls out for free.

## Consequences

### Positive

- One canonical schema per digest; validation cost amortized across the system.
- The digest doubles as the contract identity shown on call records and previews.

### Negative

- Registry rows are append-only shared state (retention policy needed — resolved in Part II).

### Risks

- Canonicalization drift (two byte-forms of one logical schema) — mitigated by normalizing before hashing, the capability-digest precedent.

## Implementation Notes

Registry and cache live in `internal/contracts` (ADR-010); the store owns persistence. Task `expect` (US-026) pins digests the same way.
