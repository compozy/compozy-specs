# ADR-001: Typed call result lives in a first-class durable call record

## Status

Accepted

## Date

2026-08-20

## Context

CompozyOS needs a typed return path for delegated work (parent session → child session, and later subagents). Today no durable slot exists for a delegation result: session lineage has no result column (`internal/store/session_lineage.go`), task results are untyped `json.RawMessage` capped at 64 KiB (`internal/task/coordinator_control.go`, `internal/task/limits.go`), and the loop `output_ref` column is an overloaded 5-way string union. The single most consequential schema decision in the exploration corpus (summary.md, Divergences) was where the typed result should live.

## Decision

Introduce a **first-class durable call record**: a new domain entity with its own lifecycle states, a pinned result schema (digest), and a content-addressed result payload. The record is inspectable independently of the participating sessions ("list my open calls"), supports N concurrent calls per session pair, and carries caller-chosen idempotency. It owns **no claim/lease machinery** — it is a delegation/conversation record, not a work queue; settlement follows the single-writer authority precedent shipped in #438 (`task.RequireLeaseSettlementActor`). When the caller is a loop node, the call references that node's existing `task_run` instead of duplicating it.

## Alternatives Considered

### Alternative 1: Typed column on `task_runs`

- **Description**: Every delegation becomes a task run; add `result_schema`/typed result columns.
- **Pros**: Reuses lease/claim/wake/budget for free; every Network wake is already a durable task run (`network_live_wakes.task_run_id UNIQUE`).
- **Cons**: Conflates work-queue semantics with conversation semantics; `task.Task` has no output schema; `MaxResultBytes` 64 KiB would reject valid results; a session→session call would fabricate an artificial run.
- **Why rejected**: The task queue is an execution primitive; a call is a communication primitive. Overloading `task_runs` repeats the `output_ref` overloading mistake at table scale.

### Alternative 2: Session-attached result

- **Description**: Result column on `sessions`/lineage.
- **Pros**: Cheapest schema change.
- **Cons**: One slot per session forecloses fan-out, concurrent calls, and follow-up calls; the Goal single-active-target model (`global_db_goal_tools.go:59-64`) already shows this ceiling.
- **Why rejected**: Kills the concurrency model the feature exists to serve.

## Consequences

### Positive

- Calls are listable/inspectable as their own read model (CLI/HTTP/UDS/web parity).
- No interference with the `task_runs` single-queue rule (L-003).
- Content-addressing + digest re-verification reuse the strongest existing primitive (`generation_output_runtime.go`).

### Negative

- New tables, new read models, new migration stream work (`eng-schema-migration`).

### Risks

- "Parallel queue" misreading — mitigated by having no claim/lease columns and by documenting settlement authority; the child's execution remains session/task-owned.

## Implementation Notes

Schema design, exact states, and the loop-node bridge land in `_spec.md` Part II. Storage decisions must state side-table-vs-JSON per field.
