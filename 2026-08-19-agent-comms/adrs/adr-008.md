# ADR-008: Recursive delegation enabled with default max depth 3; containment is budget-based

## Status

Accepted

## Date

2026-08-20

## Context

Today `DefaultSpawnMaxDepth = 1` blocks delegation trees outright (`internal/session/spawn.go:20`). The market defaults to depth 1 (Claude Code: no nested teams; Codex `max_depth` 1 in V1; hermes `MAX_DEPTH = 1` behind an orchestrator unlock), while the zero-guard end (pi: no depth check at all, child reloads the spawn extension) is the documented runaway failure mode. The operator wants recursion available by default — subagent trees are a core use case — but unbounded depth with no containment story invites infinite A→B→A loops and runaway cost.

## Decision

Recursive delegation is **enabled by default with a maximum depth of 3**, configurable by the operator. At the depth limit the call verb is **stripped from the child's toolset** (omp mechanic) **and** the child's prompt states its **literal remaining depth** (hermes mechanic) so the model cannot confabulate nesting it does not have. Depth is a wall, not the primary brake: containment remains **budget-based** — per-parent child caps, per-governed-root active-session caps, mandatory TTL, wake/turn budgets (ADR-004), and protocol loop-breakers (rate limit, dedup, unread caps) bound total work at every depth.

## Alternatives Considered

### Alternative 1: Keep default depth 1

- **Description**: Market default; trees require explicit config.
- **Pros**: Most conservative; matches every shipped reference.
- **Cons**: Forecloses the subagent-tree use case out of the box; operator explicitly rejects the wall.
- **Why rejected**: Recursion is core scope, not an advanced unlock.

### Alternative 2: Unlimited depth (budgets only)

- **Description**: No depth wall at all; containment purely by budgets.
- **Pros**: No arbitrary number.
- **Cons**: Removes a cheap emergency brake; the pi zero-guard failure mode shows what unbounded looks like in practice.
- **Why rejected**: Operator chose a finite default; 3 covers real tree shapes while keeping a wall.

## Consequences

### Positive

- Orchestrator → worker → helper trees work with zero configuration.
- The wall + strip + literal-depth trio makes depth exhaustion observable and honest.

### Negative

- Deeper trees multiply governance accounting paths (caps count by governed root across depths).

### Risks

- Cost amplification at depth 3 fan-outs — bounded by governed-root caps and wake budgets; usage stays visible through the shared accounting substrate.

## Implementation Notes

Flips `DefaultSpawnMaxDepth` 1 → 3. Config key naming and interaction with per-workspace caps land in Part II / Config Lifecycle.
