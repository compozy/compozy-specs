# ADR-012: Loop nodes do not create call records — loops adopt the contract regime only

## Status

Accepted

## Date

2026-08-20

## Context

Loop `run-agent` nodes already have a durable execution record (`task_runs` + loop generation outputs), their own settlement path (hardened by #438), and their own visualization (the Loops app DAG). ADR-001 creates the call record for session-origin delegation. Should loop-driven agent work also materialize call records so one tree shows everything?

## Decision

**No call records for loop nodes in v1.** Loops adopt the unified `internal/contracts` regime (same validation, failure vocabulary, budgets, provenance) so a node's `output_schema` and a call's `expect` behave identically — but a loop node's durable record remains its `task_run` + loop output cell. The Agents app Activity tree renders session-origin calls; the Loops app remains the owner of loop-run visualization. A loop that needs a group decision uses the Network bridge; a session (including a Loop-bound worker session) that calls an agent creates a call like any other caller.

## Alternatives Considered

### Alternative 1: Materialize a call record per run-agent node

- **Description**: Every loop delegation also writes a call referencing its task_run.
- **Pros**: One tree in the UI covers loops and calls.
- **Cons**: Two durable records for one event; settlement spans two domains (double single-writer authority); read models must dedupe; contradicts the "no parallel record" instinct that killed the task_runs option in ADR-001.
- **Why rejected**: Duplicated identity for zero behavioral gain — the unification users feel is the contract regime, not the record shape.

## Consequences

### Positive

- One settlement authority per record kind; no cross-domain settle transaction.
- Loops UI and Agents UI each render their own truth without dedup logic.

### Negative

- The Activity tree does not show loop-internal delegation (by design; the Loops DAG does).

### Risks

- Future desire for one unified tree — solvable later as a read-model union without changing storage.

## Implementation Notes

Worker sessions bound to loop nodes may themselves make calls (they are sessions); those calls appear in the Activity tree under the worker session as caller.
