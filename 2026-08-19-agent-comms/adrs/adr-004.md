# ADR-004: Hybrid cost semantics — durable delivery always; waking an idle recipient consumes a turn on the existing wake/budget substrate

## Status

Accepted

## Date

2026-08-20

## Context

A message or completed call must reach the counterpart without losing the result (the documented Claude Code stall: an idle notification that does not carry the output). But every delivery starting a billable model turn makes fan-out expensive (Claude Code charges each delivered message like a typed prompt), while "never a turn" leaves results unprocessed. CompozyOS already owns a wake/budget accounting substrate keyed by `owner_key` (Network live wakes); a second parallel activation path would make `compozy network usage` untruthful (slice 02: "one activation substrate").

## Decision

**Delivery and activation are separate facts.** Every message/result is committed durably first (commit-then-notify). Delivering to a busy recipient injects at the next turn boundary — non-interrupting, no extra turn cost. Delivering to an idle (or parked) recipient **wakes it, and that wake is a billable turn accounted through the existing wake/budget substrate** (same owner-key accounting the Network uses). Loop-breakers — per-sender rate limit, identical-repeat dedup, unread cap, depth guard — are protocol properties, not etiquette.

## Alternatives Considered

### Alternative 1: Every delivered message is a turn (Claude Code model)

- **Description**: Delivery = prompt.
- **Pros**: Simple, honest cost accounting.
- **Cons**: Fan-out multiplies token spend; forces very aggressive loop-breakers.
- **Why rejected**: Charges for deliveries that never needed a model activation (busy-recipient injection).

### Alternative 2: Messages are never turns

- **Description**: Mailbox-only; recipient reads on its next natural turn.
- **Pros**: Cheapest.
- **Cons**: A result nobody processes is the documented orchestration stall; parked children would never revive.
- **Why rejected**: Breaks the core "completion delivery carries the result and the parent acts on it" contract.

## Consequences

### Positive

- One truthful activation/usage story across Network and calls.
- Fan-out costs scale with actual activations, not with message count.

### Negative

- Wake admission logic must be shared/extended rather than duplicated — a coupling point with `internal/network`'s budget vocabulary.

### Risks

- Budget-vocabulary drift between Network wakes and call wakes — mitigated by reusing the same admission/skip-reason vocabulary and accounting keys.

## Implementation Notes

Which bounds apply to call wakes (subset of the seven Network Live bounds vs a leaner set) is a Part II decision.
