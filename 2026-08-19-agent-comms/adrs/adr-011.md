# ADR-011: Call activations are accounting-only in v1 — no Network-Live-style admission bounds

## Status

Accepted

## Date

2026-08-20

## Context

Network Live participation requires seven mandatory positive bounds before a peer may be woken; wake admission runs a budget funnel with named skip reasons. Calls also wake sessions (completion wakes, message wakes to idle/parked recipients — ADR-004). The question: do call wakes get their own defaults/limits pair and admission ceilings in v1?

## Decision

**Accounting without admission ceilings.** Call and message wakes are recorded durably with the shared owner-key vocabulary and wake-event dedup fences, so usage stays truthful on one substrate — but v1 imposes no wake-count/wall-time/token ceilings on call activations. Containment comes from the protocol brakes that already exist by design: per-sender rate limits, identical-repeat dedup, unread caps, the depth wall, per-parent and per-governed-root child caps, and idle-TTL reaping. A completion wake is never budget-denied — denying it recreates the documented result-less stall.

## Alternatives Considered

### Alternative 1: Full bounds pair (`[calls.wakes]` defaults/limits) in v1

- **Description**: Mirror Network Live's seven-bound model for calls.
- **Pros**: Maximum containment from day one.
- **Cons**: A completion wake that budget-skips reintroduces the stall; doubles the config surface; no evidence yet that message-path brakes are insufficient.
- **Why rejected**: Wrong failure mode for completions; premature config weight.

## Consequences

### Positive

- Completion delivery is unconditional (durable + activation), preserving the core contract.
- Config stays lean; admission ceilings can be added later as a pure tightening.

### Negative

- A pathological message storm is bounded by rate/dedup/caps rather than a hard wake ceiling.

### Risks

- If practice shows brake-evasion patterns, add ceilings as config evolution — the accounting substrate already records everything needed to justify them.

## Implementation Notes

Delivery records carry `owner_key` and charge markers; the usage read model exposes call activations without double-booking against Network budgets.
