# ADR-010: Two new packages — `internal/calls` (call + mailbox + delivery) and `internal/contracts` (unified result-contract regime)

## Status

Accepted

## Date

2026-08-20

## Context

The feature needs a home for the call domain and a home for the unified validation regime. The mailbox exists *because* the call/lineage edge exists (derived-availability rule), sharing addressing, delivery, and loop-breakers with calls — splitting them invites an import cycle or a third glue package. The contract regime is consumed by loops, tasks, sessions, store, and calls, so it must sit below all of them. `internal/store` currently imports `internal/loop` for ref/validation helpers (157 files at HEAD) — a layering smell this structure fixes.

## Decision

Two packages. **`internal/calls`**: call records, states, settlement, mailbox, delivery contracts, loop-breakers, park/revive orchestration — one domain, file-split decided up front (types / service / create / settle / await / cancel / mailbox / delivery / breakers). Interfaces it consumes (session spawn-or-address, boundary delivery, revival) are defined in `internal/calls` and implemented by the daemon bridge. **`internal/contracts`**: schema registry + digest pinning, the single declared-schema resolver, admission validation, compiled-schema cache, shorthand normalization, JSON candidate extraction, byte budgets + overflow, contract-preserving redaction, `x-compozy-kind` entity walk. `internal/contracts` imports no runtime packages; `internal/store`, `internal/loop`, `internal/task`, and `internal/calls` all consume it — which deletes the store→loop imports for ref/validation helpers.

## Alternatives Considered

### Alternative 1: Separate `internal/mailbox`

- **Description**: calls and mailbox as sibling domains.
- **Pros**: More explicit boundary.
- **Cons**: Shared lineage addressing, delivery seam, and loop-breakers force either a cycle or a third package.
- **Why rejected**: One domain in the product model; one package with file discipline.

### Alternative 2: Extend `internal/loop/dsl` schema types instead of a new contracts package

- **Description**: Grow the loop-owned schema code.
- **Pros**: No new package.
- **Cons**: Cements the store→loop layering smell; makes loops the dependency of sessions/tasks.
- **Why rejected**: The regime is cross-domain by definition.

## Consequences

### Positive

- Downward-only imports restored; `mage Boundaries` gains two clean nodes.
- Every consumer (including future subagent work) links one validation regime.

### Negative

- Two package bootstraps + boundary rules to write in the same change.

### Risks

- `internal/contracts` scope creep (it must stay runtime-free) — guarded by boundary rules and review.

## Implementation Notes

`internal/api/contract` (wire DTOs) is unrelated to `internal/contracts` (validation regime); the spec's glossary note disambiguates. Boundary rules land in `magefiles/boundaries.go` in the same commit.
