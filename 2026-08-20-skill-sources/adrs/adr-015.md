# ADR-015: Exposure ownership records persisted in a side table; health reconciled from the filesystem

## Status

Accepted (supersedes the "filesystem-only, deliberately stateless" implementation note in ADR-011)

## Date

2026-08-20

## Context

Peer review round 1 (B-001) proved the filesystem-only exposure model cannot deliver the accepted product behavior: once a link is deleted there is no evidence it ever existed (US-011.EC-3 requires reporting it as missing and repairing), a symlink that happens to resolve into a managed skill does not prove CompozyOS created it (the "never touch foreign links" rule needs creation proof), and cleanup after the canonical skill disappears has no target list. Disabling a target preset also removes its root from inspection sets while existing links still need to be visible and removable.

## Decision

Persist one ownership record per created link in a new `skill_exposures` side table (global SQLite stream): skill name, canonical dir (realpath at creation), target slug, link path, **link target (the literal symlink destination written at creation — the ownership proof)**, owner scope, workspace id (when workspace-owned), timestamps. The record is the **ownership authority**; link **health** is always reconciled live against the filesystem and reports the full four-state vocabulary — `healthy` (link resolves into the canonical dir), `missing` (record without a link), `broken` (`Readlink(link) == record.LinkTarget` but resolution fails — provably ours, repair allowed), `foreign_conflict` (entry at the path that is not our link — report only, never mutated). The record is never trusted as current filesystem state, and the `Readlink == LinkTarget` proof is what authorizes any removal. Schema ships per `eng-schema-migration`: declarative schema change + next gap-free Goose migration + `atlas.sum`/sqlc refresh + extended fresh/reopen/ahead/integrity/equivalence suites.

## Alternatives Considered

### Alternative 1: Filesystem-only (original ADR-011 note)

- **Pros**: Zero persistence; self-healing inspection.
- **Cons**: Cannot distinguish "never exposed" from "our link was deleted"; ownership by inference; cleanup loses its target list; disabled-target links become invisible.
- **Why rejected**: Makes accepted acceptance criteria unimplementable (B-001).

### Alternative 2: JSON metadata on the skill or config

- **Cons**: Matchable, queryable state in an opaque blob violates the side-table-vs-JSON rule (L-003 posture); per-workspace filtering would parse JSON.
- **Why rejected**: This is exactly the "matchable state" case that demands a side table.

## Consequences

### Positive

- Missing-link diagnostics, foreign-link refusal, and remove/update cleanup become provable; per-workspace ownership filters are indexed queries.

### Negative

- One migration + reconcile logic; record/filesystem divergence becomes a state to manage (mitigated: reconcile is retryable and idempotent, and divergence maps to the `missing`/`broken` statuses the product already promises).

### Risks

- Stale records after manual filesystem surgery — reconcile reports them (`missing`) and unexpose clears them; never auto-deleted silently.

## Implementation Notes

Commit order per target: record → link (a record without a link reads as `missing`, which is repairable; a link without a record would read as foreign — never create that state). Multi-target semantics per ADR-011 amendment (preflight all, rollback on partial failure).
