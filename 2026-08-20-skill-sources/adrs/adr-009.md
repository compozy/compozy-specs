# ADR-009: Native double-load is resolved by suppressing prompt injection only, driven by an internal provider→native-roots mapping

## Status

Accepted

## Date

2026-08-20

## Context

Providers load skills from their own folders natively: OpenClaw and Hermes read `.agents/skills` (workspace + home), Claude Code reads `.claude/skills` + `~/.claude/skills`. Once CompozyOS absorbs those same folders into its catalog, a session can receive the same skill twice — once via the provider's native load, once via CompozyOS's injected catalog (startup `<available-skills>` section + per-turn `<current-available-skills>` augmenter, which already double-inject today per `analysis/slash-picker-injection.md`).

ACP research (`analysis/acp-commands.md`) is conclusive: the protocol's only announcement channel (`session/update: available_commands_update`) carries `name/description/input.hint` with **no source path and no skill concept**; the Claude Code adapter announces skills by name as a session-start snapshot; OpenClaw and Hermes announce zero skills while still loading them from disk. Protocol-driven dedup is therefore impossible.

## Decision

- Each preset row carries `native_readers` — the provider IDs that read that preset's roots natively (`agents` → openclaw, hermes; `claude` → claude-code; `compozy` → none; custom roots → none).
- When assembling the **prompt-injected catalog** (startup section A and per-turn augmenter B, evaluated together), skills whose winning root belongs to a preset the session's provider reads natively are filtered out.
- Everything else stays complete: registry, HTTP/UDS list APIs, enable/disable, shadows, the session `/` picker, and the explicit `/<skill>` expansion (injection C) — an explicit user invocation always injects, because the user asked.

## Alternatives Considered

### Alternative 1: ACP name-matching against advertised commands

- **Description**: Suppress catalog entries whose names match `Info.AdvertisedCommands`.
- **Pros**: Reflects what the agent actually loaded (for Claude Code).
- **Cons**: OpenClaw/Hermes advertise no skills (mapping still required for them); Claude Code's snapshot never refreshes mid-session; plugin (`plugin:skill`) and `mcp:` name rewriting create false negatives.
- **Why rejected as primary**: Cannot cover two of three providers; retained as a possible future confidence signal (plumbing exists in `store.SessionAdvertisedCommand`).

### Alternative 2: Suppress everywhere (hide the skill from the session entirely)

- **Description**: Filter the picker and APIs too.
- **Cons**: Breaks enable/disable/shadow management, contradicts Truthful UI (the skill exists), and removes the user's explicit invocation path.
- **Why rejected**: The problem is context redundancy, not existence.

## Consequences

### Positive

- No triple-injection; context budget respected; skill remains fully manageable and invocable.
- Deterministic, testable rule (provider × preset), independent of third-party adapter behavior.

### Negative

- The mapping is an assertion about external tools' behavior that can drift with their releases — mitigated: the table is data in one Go file, and harness diagnostics/logs record every suppression decision (ADR-010).

### Risks

- A provider stops (or starts) reading a folder natively — table update, no schema change.

## Implementation Notes

Recommended insertion (Option 2 from `analysis/slash-picker-injection.md`): add `Provider` to `HarnessSessionInput`/`HarnessSessionContext`, resolve a skill-injection filter in `ResolvedHarnessPolicy`, thread into section A via the section selector and augmenter B via the composite augmenter; filter **before** B's sha256 unchanged-hash; `session_commands.go:project` stays unfiltered.

**Amendment (round 1, B-008):** `native_readers` uses the **canonical provider registry ids** — `claude`, `openclaw`, `hermes` (the values the config provider registry canonicalizes aliases to: `claude-code → claude`, `hermes-agent → hermes`). Suppression classifies through a typed native-reader resolution alongside the resolved agent/provider — never by matching command text or alias formats — and the public `native_readers` field carries the same canonical vocabulary. Verified end-to-end by UT-085 + IT-008.

**Amendment (round 2, B-003):** native-reader knowledge is **per root**, and suppression keys on the session's **resolved** native roots, not on provider identity alone. The preset table records workspace-root and global-root readers separately (workspace `.agents/skills` → openclaw+hermes; global `~/.agents/skills` → openclaw only — Hermes's global home is `~/.hermes/skills`; both claude roots → claude). At session start the daemon resolves the provider's actual native skill roots from the canonical provider id, the per-root table, and the session's effective env/home policy (`CLAUDE_CONFIG_DIR`, `HERMES_HOME`, `OPENCLAW_STATE_DIR`, `home_policy = isolated` relocate or eliminate native homes). A skill is suppressed only when its winning root realpath is in that resolved set; anything unproven fails open to inclusion. Public `sources[].roots[].native_readers` reports the same per-root granularity.
