# ADR-007: Workspace override merges by tri-state replace; precedence keeps the six existing tiers with root lists

## Status

Accepted

## Date

2026-08-20

## Context

Two composition questions: (a) how a workspace override combines with the global value, and (b) how roots from new sources slot into the existing precedence model. The repo's overlay standard is pointer-typed tri-state replace (`internal/config/merge_features.go:12-29` — absent inherits, present replaces the whole list). The skills registry has six precedence tiers (`bundled → marketplace → user → additional → workspace → agent-local`, `internal/skills/types.go:96-111`) with name-keyed last-writer-wins overlay and a shadow audit.

## Decision

- **Merge**: tri-state replace. A workspace config without `skills.sources` inherits the global list; with the key, it replaces the whole list. `sources` and `custom_sources` merge independently.
- **Precedence**: keep the six tiers unchanged; each tier owns a **list of roots** instead of one. Workspace-level preset roots map to the `workspace` tier, global-level preset roots to the `user` tier, `custom_sources` to the `additional` tier. Intra-tier order = configured list order, with `compozy` roots loaded last (they win intra-tier ties).

## Alternatives Considered

### Alternative 1: Add/remove granular merge (`sources_add` / `sources_remove`)

- **Description**: Incremental workspace adjustments without restating the list.
- **Pros**: Expressive for large lists.
- **Cons**: No overlay in the repo behaves this way; three-state per-preset UI (inherited/forced-on/forced-off) is unrepresentable in a simple toggle; more keys.
- **Why rejected**: Novel semantics for marginal benefit on lists of ≤ a handful of entries.

### Alternative 2: New precedence tiers per source (e.g. `agents`, `claude` tiers)

- **Description**: Each preset becomes its own tier with its own rank.
- **Cons**: `SkillResourceSpec.Source` is a tier string — new tiers ripple through resource records, shadow labels, API `source` fields, and the web; the tier enum becomes open-ended.
- **Why rejected**: The existing overlay + shadow machinery already resolves intra-tier collisions; tiers stay a closed set.

## Consequences

### Positive

- Zero new merge semantics to teach; the shadows UI, `skill where`, and diagnostics keep working unchanged.
- The documented five-layer precedence chain survives with one amendment ("each layer may own multiple roots").

### Negative

- A workspace that wants "global minus one preset" must restate the full desired list (accepted trade-off of replace semantics).

### Risks

- `mergeSkillPaths` assumes one dir per root order — needs a stable intra-root ordering key (flagged in `analysis/backend-runtime.md` §7c); covered by tests.

## Implementation Notes

Same-name skills across roots of the same tier: later-loaded root wins, shadow recorded — compozy-last ordering makes the canonical root win ties inside `workspace`/`user` tiers.
