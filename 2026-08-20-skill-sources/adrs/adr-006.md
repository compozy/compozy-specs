# ADR-006: Workspace-scope override ships in v1 with full CLI + API + web management

## Status

Accepted

## Date

2026-08-20

## Context

The `[skills]` settings section rejects workspace scope today (`internal/settings/section_skills_update.go:29-33`) — only global and agent scopes exist, and agent scope edits only `disabled_skills`. But skill sources are inherently workspace-flavored: one repo may standardize on `.agents/skills` while another must not absorb `.claude/skills`. The workspace resolver already reads per-workspace config (`resolved.Config.Skills` feeds per-workspace disabled lists), so a workspace-level vehicle exists.

## Decision

`skills.sources` and `skills.custom_sources` are overridable per workspace in v1. This opens the `[skills]` settings section to workspace scope for the first time — across CLI (`compozy config set --workspace`), HTTP/UDS settings routes, and the web settings page, whose scope selector gains the workspace scope for these keys. Merge semantics per ADR-007.

## Alternatives Considered

### Alternative 1: Global-only in v1

- **Description**: One discovery policy for the daemon; workspace override later if demanded.
- **Pros**: Follows the existing section contract; smaller isolation-proof surface; less UI.
- **Cons**: A single repo with conflicting conventions forces the global policy to the lowest common denominator; per-repo interop is the feature's core scenario.
- **Why rejected**: Owner explicitly chose workspace override in v1 over the recommended global-only option.

### Alternative 2: Workspace override via config file only (UI read-only)

- **Description**: Editable through workspace `config.toml` + CLI/API; web shows effective values without editing.
- **Pros**: Cuts web scope-editing work.
- **Cons**: Operator/agent parity gap; the settings API must open to workspace scope anyway, so the marginal UI cost is moderate (scope-selector pattern already exists on the page).
- **Why rejected**: Owner chose full parity in v1.

## Consequences

### Positive

- Per-repo interop policy without touching global config; operator and agent surfaces stay in parity (SD-011).

### Negative

- First workspace-scoped write path in the skills section: new merge path, scope-gated UI states, and a cross-workspace isolation proof in the impact audit.

### Risks

- Cross-workspace leakage of resolved roots or counts — mitigation: per-workspace cache keys already exist (`registry_workspace_cache.go:391-416`); tests assert that two workspaces with different overrides resolve disjoint root sets.

## Implementation Notes

Only the two source keys open to workspace scope; the rest of the `[skills]` section (enabled, marketplace, allowlists) stays global-only. The settings envelope reports scope provenance so the UI can show "inherited from global" vs "workspace override".

**Amendment (round 1, B-006):** the workspace-scope PATCH uses a dedicated presence-aware override object (`{"override": {"sources": …, "custom_sources": …}}` — absent = untouched, null = clear override/inherit, array = set) instead of the full-config payload, whose required fields cannot encode tri-state and would appear to touch forbidden global keys. Global scope keeps the full-config body. HTTP/UDS identical.

**Amendment (round 3, B-001):** presence is carried by the explicit `OptionalStringList{Present, Null, Value}` wrapper with custom JSON decoding, parsed by one shared decoder for both transports — plain pointer fields cannot distinguish an omitted field from explicit `null` and are forbidden for this request shape (`*[]string` remains valid only in the TOML overlay model).
