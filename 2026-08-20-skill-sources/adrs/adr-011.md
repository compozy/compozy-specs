# ADR-011: Skills stay canonical in Compozy homes; interop is symlink **expose** — a dedicated verb, a create option, and a web action

## Status

Accepted

## Date

2026-08-20

## Context

With multiple sources enabled, two write-path questions appear: where `compozy skill create` puts new skills, and how a Compozy-owned skill becomes visible to external tools that read their own folders (Claude Code does not read `.agents/skills`; other tools read `.agents/skills` but not `.compozy/skills`). vercel-labs/skills proves the symlink pattern at ecosystem scale: canonical dir + per-skill symlinks, with Claude Code documented to follow symlinks and load once per realpath.

## Decision

- `compozy skill create` keeps its default target: `<ws>/.compozy/skills` (workspace) — canonical home unchanged.
- **Expose** is the new interop primitive: create a per-skill symlink `<source-root>/<name>` → canonical skill dir, into any **enabled preset** the user names. Custom sources are not valid expose targets in v1 (surface grill 2026-08-20): a symlink points at a machine-local absolute path, and custom sources are typically shared/committed team directories where such a link breaks on every other machine.
- Surfaces in v1: dedicated CLI verbs (`compozy skill expose|unexpose <name> --to <sources>`), an option on `skill create`, HTTP/UDS parity, and a web action on the skill detail surface.
- Eligibility: any skill with a physical directory (user, workspace, marketplace, custom). Bundled skills are excluded — `go:embed` has no filesystem path to link; exposing one requires copying it into a real home first (existing create flow).
- Expose targets match the skill's scope: workspace-scoped skills expose into workspace-level roots, global skills into global roots.

## Alternatives Considered

### Alternative 1: Create option only

- **Description**: Choose expose targets only at creation time.
- **Cons**: Asymmetric — existing skills (including marketplace installs) need manual symlinks; no lifecycle management.
- **Why rejected**: Owner chose the full verb + create + web scope.

### Alternative 2: Copy instead of symlink

- **Description**: Duplicate the skill directory into target sources.
- **Cons**: Content drift between copies; edits in one place don't propagate; violates single-source-of-truth.
- **Why rejected**: Symlinks keep one canonical body; the ecosystem (vercel-labs, Claude Code realpath dedup) is built for them.

### Alternative 3: Change the canonical home to `.agents/skills`

- **Description**: Author new skills in the universal convention dir.
- **Cons**: Breaks existing behavior and marketplace/provenance assumptions; mixes Compozy-managed skills with third-party-managed files.
- **Why rejected**: Compozy-first with explicit interop beats convention migration.

## Consequences

### Positive

- One canonical body per skill; external tools see it via their own conventions; user opts in per skill.
- Marketplace skills become exposable to the whole toolchain — a real differentiator.

### Negative

- Symlink lifecycle to manage: `skill remove`/rename must clean or repair exposes; broken links need a diagnostic.

### Risks

- Self-shadow (Compozy scanning its own expose symlink) — prevented by realpath dedup (ADR-012).
- Marketplace update/remove swapping content under a link — update preserves the path (link stays valid); remove cleans exposes in the same operation.

## Implementation Notes

Windows fallback: if symlink creation fails, the operation errors with a deterministic message (no silent copy in v1 — copies drift).

**Amendment (round 1, B-001/B-002/B-003 — supersedes the original "no new database state" note):**
- Ownership is persisted per link in the `skill_exposures` side table (ADR-015); health is reconciled live from the filesystem against the record.
- Destination safety: `validateExposeName` (single normalized segment, skill-name grammar, traversal rejection) + `resolveExposeDest` (deepest-existing-parent containment inside the preset root) run before any write — the name comes from untrusted frontmatter.
- Multi-target semantics: preflight every target, commit per target record→link, roll back completed targets on mid-sequence failure, return structured per-target results — every expose/unexpose failure (single- or multi-target) uses the ONE `expose_failed` envelope wrapping per-target codes; reconcile on remove/update is retryable and idempotent.
