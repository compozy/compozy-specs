# ADR-012: The skill scanner follows first-level symlinks in source roots, deduplicating by realpath

## Status

Accepted

## Date

2026-08-20

## Context

The current walker resolves the root itself via `EvalSymlinks` but does not follow nested symlinks (`internal/skillscan/scan.go:44-53`). The dominant ecosystem installer (vercel-labs/skills) works by symlinking: `.claude/skills/<name>` → `.agents/skills/<name>`, canonical body in `.agents/skills`. With the current behavior, a user who installed skills that way and enables the `claude` preset would see nothing from `.claude/skills` — the most common real-world layout would be invisible. Our own expose feature (ADR-011) also plants symlinks inside scanned roots, which must not self-shadow.

## Decision

The scanner follows **first-level symlink entries** in skill source roots (a symlinked skill directory directly under the root). Resolution:

1. `EvalSymlinks` the entry; reject targets that escape allowed containment (existing hardening applies).
2. Deduplicate by realpath: if the resolved directory was already scanned (e.g. the canonical `.agents/skills/<n>` and the symlink `.claude/skills/<n>` in the same pass, or Compozy's own expose link), the skill loads **once**, attributed to the highest-precedence root that reached it.

Deeper nested symlinks remain unfollowed.

## Alternatives Considered

### Alternative 1: Keep not following symlinks

- **Description**: Preserve current behavior.
- **Pros**: Simplest; no new traversal surface.
- **Cons**: `claude` preset blind to vercel-labs-installed skills (the ecosystem's most common layout); our own exposes would be invisible to us while visible to external tools — confusing asymmetry.
- **Why rejected**: Defeats the feature's purpose for the largest real-world population.

### Alternative 2: Follow symlinks at any depth

- **Pros**: Maximum coverage.
- **Cons**: Cycle risk, unbounded traversal, larger attack surface for escape tricks.
- **Why rejected**: First-level covers every known installer layout; depth adds risk without a use case.

## Consequences

### Positive

- vercel-labs installations appear correctly under either preset; one skill body → one catalog entry regardless of how many links point at it.
- Self-shadow from expose is structurally impossible.

### Negative

- Scanner gains a realpath-seen set and containment checks per link — slight complexity and I/O cost.

### Risks

- Symlink escape attempts (`.claude/skills/x` → `/etc`) — mitigated: same `EvalSymlinks` + approved-root containment posture as the existing security invariants (`internal/CLAUDE.md` Security Invariants: symlink escape hardening); escaping links are skipped with a diagnostic, never followed.

## Implementation Notes

macOS `/private/var` canonicalization quirk applies.

**Amendment (round 2, B-008 — supersedes the original trust-union note):** containment is **per projection**, never a process-wide union. A followed link may resolve only into that projection's trusted set — the owning workspace's configured roots plus the intentionally visible global roots (Compozy homes, enabled global preset roots, global custom roots). Another workspace's roots are never in the set: a link in workspace A resolving into workspace B's configured root is rejected with an `escape` diagnostic. Canonical workspace id propagates through resolution, registry/cache keys, and diagnostics (Safety Invariant 1; UT-083 + two-workspace integration coverage in IT-002).
