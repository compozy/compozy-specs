# ADR-010: Injection suppression is automatic — no config key

## Status

Accepted

## Date

2026-08-20

## Context

Given ADR-009's suppression mechanism, the remaining question was whether it is configurable. Every config key costs: struct/defaults/merge/validation, lifecycle-matrix row, settings envelope, docs, and tests (SD-011 makes config a full-lifecycle commitment). The suppression rule is correct by construction — injecting a skill the provider already loaded is never desirable.

## Decision

Suppression is always on, with no `config.toml` key. The decision is observable: harness diagnostics and observability tags record every suppressed skill with the reason (provider reads the winning root natively), so "why isn't my skill in the prompt?" is answerable without a debugger.

## Alternatives Considered

### Alternative 1: Global kill switch (`skills.suppress_native_duplicates = true`)

- **Description**: Default-on boolean for debug escape.
- **Pros**: Off-switch for odd cases.
- **Cons**: Full config-lifecycle cost for a switch whose "off" position produces strictly worse behavior; another settings row to explain.
- **Why rejected**: Greenfield posture — add the escape hatch only if QA demonstrates the need.

### Alternative 2: Per-preset config (`suppress_injection_for_providers` per source)

- **Description**: Expose the mapping itself as configuration.
- **Cons**: Freezes an internal behavioral table into public contract; nobody asked for per-preset control.
- **Why rejected**: Maximum surface for zero demonstrated demand.

## Consequences

### Positive

- Zero new config surface; correct default behavior; simpler settings page.

### Negative

- No operator override if a provider's native loading behaves unexpectedly — mitigated by observability (the suppression is visible, and disabling the source preset re-injects globally).

### Risks

- If real-world QA finds a case needing an override, adding a key later is additive and non-breaking.

## Implementation Notes

Suppression decisions surface through `buildHarnessObservabilityTags` and harness diagnostics; the settings envelope does not model suppression (it is not configuration).
