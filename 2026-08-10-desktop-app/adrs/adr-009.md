# ADR-009: Deep links are validated product-path pass-through; `compozy app open` accepts an optional path

## Status

Accepted

## Date

2026-08-09

## Context

The PRD left two link-scope questions to the TechSpec: which product views are addressable by CompozyOS links in v1 (US-010), and whether `compozy app open` accepts a target argument (US-019.EC-1). The product UI is a routed SPA whose views are addressed by paths; a curated per-view catalog would need maintenance on every route change, while the shell's link handling must stay inside the thin-shell rule (no product knowledge in the shell) and reject hostile payloads safely (BR-15/BR-16).

## Decision

1. A CompozyOS link carries a **product path**, not a named target: the scheme URL encodes a path (plus query/fragment) relative to the product origin.
2. The shell **validates shape, never meaning**: the decoded value must be an absolute product path with no scheme, no authority/host component, and no path traversal; anything else is rejected safely and the app opens at the default view (BR-16). The shell never maintains a route catalog — an unknown-but-well-formed path renders whatever the product UI renders for it, including the product's own not-found experience (US-010.EC-1).
3. Validated links navigate the window to `<daemon-origin><path>`; cold-start links queue behind runtime readiness and survive the shell-state phase (US-010.AC-2, EC-4); with multiple links, the last one wins (EC-3).
4. `compozy app open [path]` accepts the **same optional product path with the same validation**, composing the scheme URL so CLI, second-launch forwarding, and OS link activation converge on one code path (US-019.EC-1 resolved as "supported in v1").
5. Every capability of this decision is scheme-registered per platform at install time, with a distinct dev-build scheme so development and installed builds never fight for registration.

## Alternatives Considered

### Alternative 1: Curated named-target catalog

- **Description**: Links name views (`sessions/<id>`, `settings`, …) from a fixed set the shell maps to routes.
- **Pros**: Every accepted link is known-good; stable link vocabulary.
- **Cons**: The shell learns product routes (thin-shell violation); every route addition or change requires a shell release; links to new views break until the catalog catches up.
- **Why rejected**: Permanent per-view maintenance and a coupling the thin-shell rule exists to prevent, for no additional safety — path validation already bounds what a link can do.

### Alternative 2: Open/focus only in v1

- **Description**: Links only launch or focus the app at the default view; `compozy app open` takes no target.
- **Pros**: Smallest scope.
- **Cons**: Breaks the stated promise of US-010 ("open the right view"); link arguments would still arrive via single-instance forwarding and be dropped.
- **Why rejected**: The delta between "focus" and "focus + validated navigate" is small, and the PRD names view-opening as the acceptance criterion.

## Consequences

### Positive

- Zero per-route maintenance; product routing stays the single navigation truth.
- One validation + navigation path serves OS links, second-launch forwarding, and the CLI verb.
- Hostile payloads collapse to "open at default view" — no dialog, no navigation outside the product.

### Negative

- Link "correctness" beyond shape (does the entity exist) is delegated to the product UI — links cannot be pre-validated against product state, by design.

### Risks

- Scheme hijacking on platforms with last-writer-wins registration — bounded by pinned durable identity (ADR-006) and the payload validation above (a hijacked activation can still only produce a product path navigation).

## Implementation Notes

Scheme identity derives from CompozyOS (ADR-006); the exact scheme string, its dev-build variant, per-platform registration, and the queueing state machine are TechSpec sections.
