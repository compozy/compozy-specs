# ADR-001: Ship a native desktop app as a thin shell over the existing runtime and web UI

## Status

Accepted

## Date

2026-08-09

## Context

Users report that living in browser tabs makes CompozyOS feel like "yet another tab": no native presence, no single-instance focus, no OS-level launch/update story. The product already has a complete web UI served by the daemon itself and a full daemon lifecycle (discovery record, single-instance lock, graceful stop, versioned status). A prior desktop effort in the legacy repo (`compozy-code`, branch `tauri`) rebuilt product capabilities inside the shell (~58.6K lines of Rust, ~25 plugins) and collapsed under its own scope without ever launching. The operator has decided the packaging vehicle is Tauri V2; the research corpus (`.compozy/tasks/desktop-app/analysis/`) confirms the minimal and the robust path coincide: a thin native shell that reuses the daemon-served UI, with all native affordances implemented shell-side.

## Decision

Ship a native desktop application that is strictly a **thin shell**: one native window hosting the existing web UI exactly as the daemon serves it, plus native-only affordances (single instance, deep links, window state, honest boot/error states, auto-update). Nothing that the daemon or the web UI already does is rebuilt inside the shell. The web interface requires zero changes in v1. Every capability the shell adds must also be operable through CLI/HTTP structured surfaces (project premise SD-011).

## Alternatives Considered

### Alternative 1: Status quo (browser only)

- **Description**: Keep the web UI as a browser-only surface.
- **Pros**: Zero effort.
- **Cons**: The stated user pain persists; no native identity, no update story, no single-instance behavior.
- **Why rejected**: It is the problem, not a solution.

### Alternative 2: Full native rebuild (rich shell)

- **Description**: Rebuild product surfaces natively in the shell (the legacy `compozy-code` approach).
- **Pros**: Maximum native fidelity; offline-capable UI shell.
- **Cons**: Duplicate product surface, enormous scope, proven failure mode (legacy effort died with phases unfinished and benchmarks unconfirmed).
- **Why rejected**: Direct contradiction of the "minimum possible" mandate; the legacy record is the evidence.

### Alternative 3: PWA / browser install banner

- **Description**: Ship the web UI as an installable PWA.
- **Pros**: Cheapest possible packaging.
- **Cons**: No real auto-update control, no daemon lifecycle management, weak OS integration (no deep-link scheme registration guarantees, no native update prompts), still browser-engine chrome.
- **Why rejected**: Cannot satisfy the auto-update and daemon-supervision requirements.

## Consequences

### Positive

- Smallest possible new surface; the daemon and web UI remain the single product truth.
- Browser users and desktop users share the same UI, state, and behavior.
- Shell scope is enforceable by rule (thin-shell discipline, per Open-Design's ~18-handler precedent).

### Negative

- The page inside the window gets no native in-page privileges in v1; native affordances must be shell-side (native dialogs/prompts rather than in-page UI).
- Some future product ideas (in-page native file pickers, custom title-bar UI) will require an explicit escalation decision.

### Risks

- WebView engine differences (macOS/Windows/Linux) for a streaming-heavy UI — mitigated by cross-platform validation requirements in the PRD.
- Scope creep into the shell — mitigated by the thin-shell rule and agent-manageability requirement for every shell capability.

## Implementation Notes

Packaging vehicle: Tauri V2 (operator decision, pre-PRD). Loading strategy, capability model, and process supervision details belong to the TechSpec; the research corpus documents the recommended v1 shape (window loads the daemon-served UI; no remote-IPC capability grants; Rust-side updater/dialogs).
