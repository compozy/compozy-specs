# ADR-007: Main window loads the daemon-served UI; pure-Rust shell with zero page IPC

## Status

Accepted

## Date

2026-08-09

## Context

ADR-001 fixed the thin-shell direction but left the loading strategy to the TechSpec. Three candidate strategies exist, and the research corpus shows they are not interchangeable: (a) point the window at the daemon-served URL (`http://localhost:2123`), (b) bundle the SPA into the app (`frontendDist`) and grant the page IPC, (c) put a Rust proxy in front of the daemon to create a stable origin. The runtime facts are decisive: the SPA resolves its API base from `window.location.origin` and the daemon's browser-protection middleware accepts only its own origin — bundling breaks the SPA outright today (API base + CORS + SSE ticket origin), while loading the daemon URL requires zero web or daemon changes and preserves existing browser users' `localStorage`/IndexedDB (same origin = same storage). Tauri marks remote-origin IPC (`remote.urls` capability grants) as dangerous, and the product UI needs no native calls in v1.

## Decision

1. The main window loads the URL the daemon already serves — the same URL `compozy open` computes (default origin `http://localhost:2123`; the effective port is always read from the daemon discovery record).
2. The shell is **pure Rust**: the product page receives **no Tauri IPC** — no `remote.urls` capability grant exists in the app, and the capability files grant nothing to the daemon origin. Updater UX, dialogs, single-instance focus, deep-link routing, and window-state live entirely on the Rust side using native surfaces.
3. Shell-owned states (starting, provisioning, version skew, port conflict, runtime down, update prompts) render from **bundled app pages in a dedicated `boot` window**; the `main` window is created hidden at the daemon origin and shown only after the bound identity handshake passes. *(Amended after verified research — analysis 06 §3: two windows instead of navigating one window across origins; URL-swapping splits storage buckets and lets webview history walk back into shell pages. The product UI is never mixed with shell chrome either way.)*
4. The port policy is **the daemon's fixed default (2123)** for daemons the app starts or provisions: it preserves browser-era local state by keeping the origin stable, and a busy port is an honest named error state, never a silent fallback origin.
5. In-window navigation is fenced to the daemon origin plus the bundled app pages; every other destination opens in the OS default browser (deny-by-default).

## Alternatives Considered

### Alternative 1: Bundle the SPA (`frontendDist`) with IPC

- **Description**: Ship the web bundle inside the app and let the page call native APIs.
- **Pros**: Official Tauri path; full IPC; offline shell assets.
- **Cons**: Breaks the SPA today (origin-derived API base, origin-checking middleware, SSE ticket origin); requires daemon CORS extension (`tauri://localhost` + `http://tauri.localhost`), API-base injection into `web/`, and browser→app state migration; violates the zero-web-changes constraint.
- **Why rejected**: Every cost lands in v1 for a capability (page IPC) v1 does not use. Documented as the escalation path if in-page native affordances become product requirements.

### Alternative 2: Rust stable-origin proxy

- **Description**: The shell serves a stable origin and proxies to the daemon.
- **Pros**: Stable origin decoupled from the daemon port.
- **Cons**: Re-implements the daemon's HTTP surface (SSE, WebSocket, streaming) in the shell; the reference product that chose this path accumulated a proxy failure catalogue (SSE pool starvation, gzip double-decode, retry amplification); conflicts with "daemon truth wins".
- **Why rejected**: Highest-risk option solving a problem (origin instability) the fixed-port decision removes.

### Alternative 3: Ephemeral ports for app-started daemons

- **Description**: Daemons the app starts bind port 0 to avoid conflicts.
- **Pros**: No port-conflict state.
- **Cons**: Origin changes every boot — browser-era `localStorage`/IndexedDB is lost (breaks the browser-coexistence promise), and per-boot origins make displayed URLs unstable.
- **Why rejected**: Trades a rare, honestly-reportable failure for a guaranteed state loss.

## Consequences

### Positive

- `web/` requires zero changes; API/SSE/WS remain same-origin; browser and app share one origin, one state.
- No IPC exposure to remotely-served content; the attack surface of the page is the browser-equivalent one.
- Shell states are native-owned and cannot be confused with product UI.

### Negative

- The page cannot call native APIs in v1; any future in-page native affordance requires the documented escalation decision.
- Shell states involve an origin swap (bundled page ↔ daemon origin); the transition must be flash-free by design.

### Risks

- OS webview engines under a streaming-heavy SPA (per-origin connection limits) — bounded by cross-platform validation before release (PRD constraint).
- A foreign process squatting the daemon port — bounded by the daemon-identity probe before rendering (the shell verifies the responder is a CompozyOS daemon before showing product UI).

## Implementation Notes

The shell code lives in a top-level `desktop/` directory (Rust crate + Tauri config + bundled shell pages), outside the Bun/turbo graph, with its own make targets and a desktop job in the existing release workflow. Escalation trigger recorded: if in-page native affordances become product requirements, the fallback is bundling with daemon CORS extension and injected API base — a separately-specced initiative.
