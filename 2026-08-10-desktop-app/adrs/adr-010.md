# ADR-010: Minimal `[app]` config section for the updater; shell reads `config.toml` directly; channel is build identity

## Status

Accepted

## Date

2026-08-09

## Context

Every capability's configuration lives in the product's standard configuration file with the standard lifecycle (PRD Core Feature 5; SD-011). The desktop shell introduces exactly one behavior that plausibly needs operator control in v1: the background update check (QA labs and air-gapped machines need a structured off switch; PRD privacy posture forbids surprise network traffic that cannot be disabled). Window geometry is state, not configuration; the release channel is pinned per-install identity (ADR-005) and must not be user-switchable in v1 (US-018.AC-2). The shell is a Rust process that starts before (and independently of) the daemon, so it cannot depend on a daemon API to obtain its own configuration.

## Decision

1. v1 adds a **minimal `[app]` section** to `config.toml` covering only the updater check behavior: an enable flag (default on) and a check interval (default sane, validated bounds).
2. The **shell reads `$COMPOZY_HOME/config.toml` directly** (same home-resolution rules as the CLI), applying defaults when the file or section is absent — configuration must work with no daemon running.
   - *Amended (peer review round 1, B-011):* the error policy is single-authority and matches the Go lifecycle: **absent** file or section → defaults; **present but invalid** (malformed TOML, unknown key, out-of-bounds value) → the update consumer **fails closed** (no network checks run) with a stable visible diagnostic in `app.json` and `compozy app status`. The shell never "defaults through" configuration the canonical Go loader would reject, and both sides validate against one shared fixture corpus.
3. The **daemon owns the lifecycle** of these keys exactly like any other section: struct, defaults, validation, examples, generated docs, and tests — so `compozy config` surfaces and documentation stay the single source of configuration truth.
4. **Channel is not a config key.** Channel identity (feed path, app identity) is baked into the build per ADR-005; no runtime knob can point an install at another channel's feed.
5. Anything beyond the updater keys (theme, window behavior, provisioning paths) is explicitly **not configurable in v1**.

## Alternatives Considered

### Alternative 1: Zero configuration in v1

- **Description**: Hardcode update-check behavior; add keys later on demand.
- **Pros**: Smallest surface; nothing to validate or document.
- **Cons**: No structured off switch for QA labs or air-gapped machines — disabling background network traffic would require firewall hacks; retrofitting the section later reopens the config lifecycle for a predictable need.
- **Why rejected**: The off switch has concrete consumers today (isolated QA, privacy posture); two keys are cheaper than the workaround culture their absence breeds.

### Alternative 2: Broad `[app]` section (theme, window, paths)

- **Description**: Configure shell behaviors beyond the updater.
- **Pros**: Maximum operator control.
- **Cons**: Geometry is persisted state, not intent; theme follows the product UI; every key enters validation/docs/tests forever without a named consumer.
- **Why rejected**: Design minimalism — no key without a demand.

### Alternative 3: Shell-owned config file or daemon-API-served config

- **Description**: The shell keeps its own settings file, or fetches config from the daemon.
- **Pros**: No daemon involvement (own file) / no file parsing in Rust (API).
- **Cons**: A second config surface violates the standard-lifecycle rule and hides keys from `compozy config` and docs; the API route fails exactly when the shell needs config most (daemon not running yet).
- **Why rejected**: Both break "configuration, runtime state, and documentation never disagree" (PRD BR-30 lineage) or fail the no-daemon boot path.

## Consequences

### Positive

- Agents and operators manage the desktop surface through the same config file, CLI, and docs as everything else.
- Updater behavior is testable and lab-controllable without network interception.

### Negative

- The shell carries a TOML reader and must track the config schema for its section (drift is bounded by the daemon-owned validation tests).

### Risks

- Shell and daemon disagreeing on defaults for the same keys — bounded by defining defaults once in the daemon config package and asserting the shell's parsed defaults against the daemon's generated docs/values in tests.

## Implementation Notes

Exact key names, types, bounds, and the generated-docs impact are TechSpec sections (Config Lifecycle). The shell treats an unreadable or invalid section as "defaults + visible diagnostic", never as a startup failure.
