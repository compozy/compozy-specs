# ADR-003: Update ownership split by installer

## Status

Accepted

## Date

2026-08-09

## Context

With the hybrid model (ADR-002) there are two updatable artifacts: the app and the runtime. The runtime already ships through managed channels (installer script, package managers) and its own self-update logic deliberately refuses to touch managed installs (it returns a recommendation instead). Force-updating a package-manager-owned binary desynchronizes the manager's database (checksum/receipt mismatch, silent downgrade on next manager operation), requires privilege escalation into paths the app does not own, and would require stopping daemons the app did not start — each a documented failure mode.

## Decision

Update ownership follows **who installed the artifact**:

1. The app always updates itself through its own update mechanism (background download, apply on explicit restart).
2. The app updates the runtime **only when the app provisioned that runtime** (ADR-002 path 2) — giving new users a single perceived update experience.
3. Runtimes installed through any managed channel are never modified by the app. The app surfaces "update available" with the correct channel's recommendation, mirroring the runtime's own managed-install discipline.

## Alternatives Considered

### Alternative 1: Unified force-update (app updates runtime always)

- **Description**: The app updates the runtime regardless of install channel.
- **Pros**: One update experience for everyone.
- **Cons**: Package-manager database desync and version ping-pong; privilege escalation from a GUI app; must stop processes it does not own; contradicts the runtime's own managed-install contract; breaks channel trust chains.
- **Why rejected**: Every identified failure is structural, not polish; option collapses into "adopt/hijack the install", which is ADR-002's rejected standalone model with extra steps.

### Alternative 2: App never touches the runtime

- **Description**: The app updates only itself, even for runtimes it provisioned.
- **Pros**: Simplest possible ownership rule.
- **Cons**: New users (whose runtime came from the app) are stranded on aging runtimes with no obvious update path.
- **Why rejected**: Breaks the single-update-experience promise for exactly the population the app onboards.

## Consequences

### Positive

- No fights with package managers; CLI users' mental model intact.
- New users get one coherent update experience.
- Consistent with the runtime's existing managed-install detection semantics — one policy, two enforcers.

### Negative

- Two version surfaces exist (app, runtime); skew is possible and must be a designed-for state (version handshake, ADR-002).
- Update state UI must distinguish "app update", "runtime update (applying)", and "runtime update (go use channel X)".

### Risks

- A provisioned-runtime update colliding with in-flight agent work — mitigated by explicit user-confirmed apply timing (business rule in PRD).

## Implementation Notes

The runtime's update-state surface already reports install method, managed flag, latest version, and a recommendation; the app consumes it rather than re-deriving channel logic.
