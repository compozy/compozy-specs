# ADR-008: First-run provisioning downloads the runtime to an app-owned path with a durable provenance marker

## Status

Accepted

## Date

2026-08-09

## Context

ADR-002 decided attach-first, provision-if-absent, and left the provisioning mechanism open ("install script or bundled payload is a TechSpec decision"). The PRD requires a newcomer to reach a working product from a single download without a terminal (US-001), provisioning to be resumable after failure (US-002), and update ownership to follow who installed the artifact (ADR-003) — which requires provisioning to leave a durable, inspectable ownership record. The bundled-payload route inherits two documented Tauri sharp edges (nested-binary notarization breakage, NSIS sidecar staleness) and duplicates the binary source of truth per channel; the install-script route does not exist on Windows and lands the binary in a location the app does not own.

## Decision

1. When no runtime exists for the active home, the guided first-run flow **downloads the per-platform runtime artifact from the product's release distribution at first run**, verifies its integrity, and installs it to an **app-owned location under the active `COMPOZY_HOME`**.
2. Provisioning writes a **durable provenance marker** alongside the installed binary recording that this runtime is desktop-app-provisioned (app version, runtime version, channel, timestamp). The marker is the ground truth ADR-003's ownership split reads: app-provisioned → the app owns runtime updates; anything else → recommendation only.
3. Provisioning is **stage-visible and resumable**: each stage (download, verify, install, start, ready) reports progress; a failed or interrupted run leaves no half-state that blocks retry, and retry re-runs cleanly.
4. If a runtime appears externally between failure and retry (user installed via a CLI channel), the flow **detects and attaches instead of provisioning a duplicate**.
5. The app installer itself stays runtime-free: no bundled daemon payload, no sidecar supervision of a bundled binary.

## Alternatives Considered

### Alternative 1: Bundle the runtime as a Tauri sidecar payload

- **Description**: Ship the daemon binary inside the app bundle (`externalBin` or resource payload) and install from it.
- **Pros**: Offline first-run; no download step.
- **Cons**: macOS notarization of nested binaries is a live breakage (tauri#11992 — open and untriaged for 20 months; its documentation PR was closed unmerged in Aug 2026); the installer grows by the runtime size per platform; two artifacts must stay version-locked per release; the shell's entitlements file would apply to the bundled Go binary too (Tauri signs every target with one file). *(Evidence note, post-verification: the NSIS sidecar-staleness report tauri#15134 previously cited here was found to be labeled `ai-slop` by maintainers with zero corroboration — it is withdrawn as evidence and the rejection stands on the verified grounds above.)*
- **Why rejected**: Every sharp edge is permanent pipeline complexity, bought to remove one network round-trip that only first-run newcomers ever pay — and the offline case is already an honest designed state (US-001.EC-1).

### Alternative 2: Drive the existing install channels programmatically

- **Description**: The app shells out to the hosted install script (or a package manager) to install the runtime.
- **Pros**: One installation truth with the CLI channels.
- **Cons**: No install script exists for Windows; the resulting install is channel-managed, which contradicts app ownership of updates (ADR-003) for the population the app onboarded; progress and failure states belong to a foreign script, breaking the guided-flow requirement.
- **Why rejected**: Platform-incomplete and ownership-inverted for exactly the newcomer population provisioning serves.

## Consequences

### Positive

- Small app installer; zero nested-binary signing; one canonical binary source (the release distribution) for every install path.
- Ownership is inspectable on disk — the app, the runtime's own update surface, and agents can all read the same provenance truth.
- Isolated homes get isolated provisioned runtimes, matching `COMPOZY_HOME` semantics.

### Negative

- First run requires network; offline first-run is a designed refusal with retry, not a success path.
- A second runtime binary location exists (app-owned path) distinct from operator-managed installs; status surfaces must name which binary a daemon runs from.

### Risks

- Download integrity — bounded by artifact verification before install (checksum bound to the release; exact verification chain specified in the TechSpec).
- The provenance marker diverging from reality (user manually replaces the binary) — bounded by treating an inconclusive or mismatched marker as not-app-owned (recommendation-only, per PRD BR-8).

## Implementation Notes

The runtime's managed-install detection gains a desktop-provenance branch so `GET /api/settings/update` reports the app-provisioned install method and defers its self-update to the app — one ownership policy, both enforcers (ADR-003). Exact paths, marker schema, verification chain, and the runtime-update apply flow are TechSpec sections.
