# ADR-011: App-side runtime-update apply reusing the provisioning pipeline; `desktop-app` install method

## Status

Accepted

## Date

2026-08-09

## Context

ADR-003 gives the app ownership of runtime updates for runtimes it provisioned; ADR-008 gives the app a download-verify-install pipeline for provisioning. The runtime carries its own self-update engine (`internal/update`: check, download, checksum verification, in-place apply, release tracks) with managed-install detection that refuses to touch package-manager-owned binaries. Two facts constrain the apply mechanics: the engine's direct-binary self-update is unsupported on Windows (a running exe cannot be swapped in place; the engine returns a manual-replace recommendation), and an app-provisioned update requires a stop→swap→start sequence that only an outside actor can drive end-to-end.

## Decision

*(Decisions 5–8 added by peer review round 1 incorporation — B-001, B-003, B-004, B-005.)*

1. For app-provisioned runtimes, the **app applies runtime updates itself**: with timing consent (PRD BR-9), it quiesces and stops the daemon it owns, re-runs the ADR-008 pipeline (download, verify, swap at the app-owned path), starts the daemon, verifies the new version via the status surface, and reconnects. One pipeline serves first install and every subsequent update, identically on all three platforms.
2. The runtime's install-method detection gains **`desktop-app`** as a first-class install method, derived from the ADR-008 provenance marker. It reports as **managed** (`managed: true`) with the recommendation naming the app — so the runtime's own self-update engine refuses to write, exactly as it does for package managers. One managed-install discipline, three enforcers (engine, package managers, app).
3. The app **consumes** `GET /api/settings/update` for availability/version/recommendation truth and never re-derives channel or version-comparison logic.
4. Update apply is **atomic-or-absent**: staging is verified **before** the daemon is stopped; the swap is a staged-file-then-rename commit journaled so a crash at any boundary is recoverable; a failed download or verification leaves the installed runtime untouched and running.
5. **The runtime publication is authenticated (B-001).** `runtime.json` is signed with the update-feed minisign key over canonical manifest bytes; the manifest binds version, platform, size, and archive `sha256`. The pipeline verifies the manifest signature before trusting anything in it, then the archive digest against the signed value. An unsigned or signature-invalid manifest is a hard refusal.
6. **Runtime mutation runs inside a home-scoped cross-process transaction (B-003).** A dedicated update lock under `$COMPOZY_HOME` (flock + PID + process start-time, stale-detected like `daemon.lock`) covers the full quiesce→stop→swap→start interval; after acquisition the runtime state is re-probed before acting. **Ownership is durable, not in-memory:** app-provisioned ownership is reacquired at any time from the provenance marker + executable path/hash agreement — a relaunched shell can update a surviving provisioned daemon it did not start in this process lifetime.
7. **Stop only through the daemon's quiesce contract (B-004).** The shell never infers queue safety: it drives the daemon's own drain surface (close admission, settle authoritative claims/session execution), waits for the daemon-reported safe-to-stop state, revalidates immediately before SIGTERM, and un-drains on abort or failure. The shell never reads or reasons about `task_runs` directly.
8. **Updates are migration-aware (B-005).** The signed manifest carries the runtime's schema-stream heads; the app persists an update-phase journal before stopping the old daemon. If the new daemon advances migrations and then fails, the app does **not** silently restart the old binary (its schema may now be behind); it surfaces an explicit recovery state distinguishing pre-migration rollback (safe: journal shows no boot) from post-migration roll-forward (recover with a later signed build), readable by agents.

## Alternatives Considered

### Alternative 1: Daemon-side apply on app trigger

- **Description**: The app calls the runtime's existing self-update engine (new HTTP trigger) and lets the daemon swap its own binary.
- **Pros**: Reuses the tested engine end-to-end; no download logic in Rust.
- **Cons**: The engine cannot self-swap on Windows (running-exe lock) — the platform floor forces a second, app-driven path anyway; a daemon mid-self-update still needs the app to drive restart and reconnect; and it requires the engine to special-case "managed but writable by my caller", softening the managed-refusal invariant.
- **Why rejected**: Ends as two apply paths plus a weakened invariant, versus one uniform app-driven path that the provisioning flow already requires.

### Alternative 2: Report app-provisioned installs as unmanaged

- **Description**: Let detection classify the app-owned binary as `direct-binary` so the engine's own self-update keeps working for terminal users.
- **Pros**: No detection change.
- **Cons**: Two writers (app and engine) own the same binary — the dual-updater desync the research corpus flags as the top ownership risk; the update-state recommendation would name the wrong channel.
- **Why rejected**: Recreates the exact failure ADR-003 exists to prevent.

## Consequences

### Positive

- Single apply implementation for install and update, uniform across macOS/Windows/Linux.
- The managed-install invariant stays absolute: the engine never writes anything it does not own.
- `compozy` CLI users see truthful update state for app-provisioned runtimes (method, managed flag, app-naming recommendation).

### Negative

- The Rust pipeline carries download + checksum verification (bounded scope: fetch, sha256 against the release checksums, staged rename) — a small duplicated slice of the engine's transport layer, justified by the Windows constraint.

### Risks

- Stop→start under active agent work — bounded by BR-9 timing consent and by the daemon's own graceful-stop contract (in-flight work follows the runtime's normal shutdown semantics, surfaced to the user before consent).
- Provenance marker mismatch (binary replaced manually) — detection treats mismatch as inconclusive → recommendation-only (PRD BR-8), and the app stops offering apply.

## Implementation Notes

The `InstallMethod` enum (`internal/update/types.go`) gains `desktop-app`; detection reads the ADR-008 provenance marker before the generic path heuristics. Exact marker schema, staging paths, and the consent/restart state machine are TechSpec sections.
