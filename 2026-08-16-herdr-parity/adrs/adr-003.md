# ADR-003: Command palette nested views — generic mechanism, built-in views only, Sessions view first

## Status

Accepted

## Date

2026-08-15

## Context

Herdr's navigator (`prefix+g`) is a searchable tree with agent-state filters — the fastest way to jump between many agents. Compozy's command palette (⌘K) is already ahead of Herdr as a launcher but is flat: one search surface, no way to enter a scoped, filterable view of one entity type. The user wants a quick session switcher with state filters and, beyond it, a general concept: the palette gains nested submenus — stackable views for different visualization types.

## Decision

1. The command palette gains a **generic nested view mechanism**: views push onto a navigation stack (enter a view, breadcrumb shows the path, backspace on empty query pops one level, dismiss closes the stack). Depth is unbounded by design.
2. **v1 registrations are built-in only.** Extension-contributed palette views are an explicit non-goal for v1, recorded as a future extension surface in the extensibility plan.
3. **One built-in view ships in v1: Sessions** — state-filter chips (needs-you / working / finished / idle parity with Herdr's navigator filters) and attention-first ordering; activating an entry focuses that session's window.
4. The surface keeps its shipped name, **"Command palette"** — no rename to "Command Center".

## Alternatives Considered

### Alternative 1: Hardcoded sessions mode (no mechanism)

- **Description**: Bolt a single sessions filter mode onto the palette.
- **Pros**: Smallest build.
- **Cons**: The second view (worktrees, approvals, …) forces a rewrite; contradicts the product concept the user described (nested views for different visualizations).
- **Why rejected**: User decision (grill Q11): the mechanism is the feature; Sessions is its first proof.

### Alternative 2: Extension-contributed views in v1

- **Description**: Ship the mechanism plus a manifest surface for extensions to register palette views.
- **Pros**: Immediate ecosystem leverage.
- **Cons**: Large scope jump — host surface, render sandboxing, security review — attached to a parity spec.
- **Why rejected**: Deferred deliberately; the registry design must not preclude it.

### Alternative 3: Dedicated switcher surface (Herdr navigator clone)

- **Description**: A separate overlay/window for session navigation.
- **Pros**: Closest visual parity with Herdr `prefix+g`.
- **Cons**: A parallel surface to maintain; violates the product's calm-defaults posture; the palette is precisely where Compozy already beats Herdr.
- **Why rejected**: User decision (grill Q8): extend the palette instead.

### Alternative 4: Rename to "Command Center"

- **Description**: Adopt the broader name as the surface grows multi-view.
- **Pros**: Name fits the expanded concept.
- **Cons**: Rename sweep (copy, docs, glossary, identifiers) mid-feature; "command palette" is the industry-legible term already consistent across the UI.
- **Why rejected**: User decision (grill Q10): keep "Command palette"; nested views are "palette views".

## Consequences

### Positive

- Sessions switching gets Herdr-navigator power inside the surface users already reach for.
- Future views (worktrees, approvals, tasks) become registrations, not redesigns.
- No new top-level surface to teach or maintain.

### Negative

- The palette's interaction model grows (stack, breadcrumb, per-view filters) and must stay keyboard-first and discoverable.
- The view registry is one more contract to keep consistent with the shortcut/cheatsheet registries.

### Risks

- Scope creep into "mini-apps inside the palette" → v1 constrains views to list-shaped, keyboard-navigable results.
- Backspace-pop colliding with query editing → pop only when the query is empty.

## Implementation Notes

The Sessions view defaults to the active workspace and carries the Show all option (US-031) widening it to every workspace; the bell remains the attention-first jump path. The registry design must leave room for extension registration without committing to it.
