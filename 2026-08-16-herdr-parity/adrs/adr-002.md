# ADR-002: Notification policy — focus-suppressed, coalesced completions, cross-workspace delivery, needs-you-only counters

## Status

Accepted

## Date

2026-08-15

## Context

Compozy has no user notification channel at all: no desktop/browser alerts, no sound, no title/tab signal — the in-app bell only counts permission waits in the active workspace. Market research documents two failure modes that kill this feature class: **volume fatigue** (N agents finishing → N simultaneous alerts; users disable sound entirely, losing real alerts — claude-code #45781) and **precision loss** (counters that mix "needs action" with "worth a look" until the number means nothing). Herdr suppresses notifications for the focused pane and only alerts for background panes; AgentsRoom escalates by focus (desktop only when unfocused) with a per-agent dedup window.

## Decision

1. **Triggers**: notify on every transition into a needs-you state (question, permission) and into failure — always, per-session (dedup window per session). Completion ("finished") notifications are **coalesced**: near-simultaneous completions group into one notification.
2. **Focus suppression**: never notify for the session whose window is focused while the app is visible — you are already looking at it.
3. **Delivery ladder defaults**: in-app toast **on**; **sound on** (single built-in sound, no custom sound files, no per-session mute in v1); system-level (OS) notifications **opt-in**, and when enabled they fire only while the app is unfocused/hidden (conditional escalation, never a double-fire); the browser tab / app title always carries the awaiting count (zero-permission signal).
4. **Counters**: the bell badge and the title count show **needs-you only** (`waiting-for-input` + `waiting-for-auth` + `failed`). Finished-unseen (`done`) sessions appear in the bell dropdown as their own "Finished" section and never inflate the needs-you number.
5. **Cross-workspace**: attention aggregates across all workspaces — the bell lists rows from every workspace, notifications fire for background workspaces, and activating a row/notification switches to that workspace and focuses the session window. A **per-workspace mute** silences that workspace's notifications (toast/OS/sound) without hiding its bell rows or counts.
6. **Agent-triggered notifications** ride the same channel, suppression, and rate limits.

## Alternatives Considered

### Alternative 1: Active-workspace-only notifications

- **Description**: Bell aggregates cross-workspace but toasts/sound fire only for the active workspace.
- **Pros**: Fewer interruptions.
- **Cons**: A stalled background workspace goes unnoticed until the operator happens to check the bell — the exact blindness this feature removes.
- **Why rejected**: User decision (grill Q5/Q9): attention is attention; the mute valve handles noisy workspaces.

### Alternative 2: OS notifications on by default

- **Description**: Ship system-level alerts enabled.
- **Pros**: Maximum reach without setup.
- **Cons**: Browsers require a permission prompt anyway; combined with toasts it double-fires; highest fatigue risk on day one.
- **Why rejected**: Escalation should be chosen; the title count + toast already covers the unfocused-tab case without any permission prompt.

### Alternative 3: One counter for everything (Herdr aggregate parity)

- **Description**: Needs-you and finished-unseen share the bell number.
- **Pros**: Single number; closest to Herdr's priority aggregation.
- **Cons**: "3 awaiting" may be three sessions merely awaiting reading — dilutes urgency; the documented precision failure.
- **Why rejected**: User decision (grill Q13): counter = needs-you; done sectioned apart.

### Alternative 4: Sound off by default

- **Description**: Ship the sound layer disabled.
- **Pros**: Quieter first-run.
- **Cons**: The operator working away from the screen misses the highest-value alert moment.
- **Why rejected**: User decision (grill Q4): sound on by default, simple global toggle.

## Consequences

### Positive

- Both documented fatigue causes are neutralized (coalesced completions, focus suppression) while needs-you alerts stay per-session and immediate.
- The needs-you counter stays trustworthy; finished work still has one inbox (bell "Finished" section).
- Background workspaces can no longer stall silently.

### Negative

- Cross-workspace delivery makes the attention pipeline a cross-workspace read surface — workspace data isolation analysis becomes mandatory in the design.
- More configuration surface (delivery toggles, mute) to validate, document, and test.

### Risks

- Notification storms from a misbehaving workspace → per-workspace mute plus per-session dedup window bound the blast radius.
- OS-level permission denial states must render honestly (no pretending the channel is armed).

## Implementation Notes

Stage 2 defines the transition/edge detection point (server-side — clients cannot see transitions today), exact dedup/coalescing windows, and the config lifecycle for delivery/sound/mute keys. Click-through target: focus the session window, switching workspace first when needed.

Amended by peer review round 1 (B-006): agent-facing notify outcomes are daemon-provable only — `delivered` (published to ≥1 live operator client), `no-client`, `muted-workspace`, `rate-limited`. The daemon never claims a human saw a notification; focus suppression remains client-side rendering per decision 2.
