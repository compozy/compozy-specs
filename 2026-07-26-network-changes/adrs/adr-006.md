# ADR-006: One Explicit Participation Contract — Resolved Once, Persisted as an Immutable Snapshot, Projected Everywhere

## Status

Accepted

## Date

2026-07-11

## Context

Today a single nullable channel string drives every network behavior: environment injection, peer join, prompt sections, tool projection, scheduler eligibility, coordinator bootstrap, and delivery activation all infer intent from `channel != ""` (`internal/daemon/harness_context.go:321-326,535`; `internal/session/manager_helpers.go`; `internal/coordinator/coordinator.go:100`). Multiple layers re-derive or fall back independently (store auto-derives `coord-<run>` at `internal/store/globaldb/global_db_task_aux.go:804-880`; hooks fall back at `internal/task/manager_run_hooks.go:180-187`). The PRD (ADR-001) requires explicit per-execution participation with provenance, and PRD rule 5 requires stability for the execution's lifetime.

## Decision

1. **One contract, two values.** A `NetworkParticipation` contract with modes `local` and `live` replaces every channel-string inference. `local` is the zero value and built-in default.
2. **A leaf contract package** owns the request/spec types, validation, and diagnostics, so `task`, `session`, `loop`, `automation`, and `network` all consume the same shapes without upward imports. It imports nothing from those packages.
3. **Resolve once, snapshot forever.** Each execution boundary (session create, task-run reservation, loop-run start, automation fire) resolves requested intent through one resolver — the only owner of precedence (execution request > owning definition/setting > built-in local) and of channel-strategy derivation (`named` | `run` | `loop_run`). The resolved spec (mode, channel, source, bounds) persists on the owning record before any side effect and never mutates in flight.
4. **Everything projects from the snapshot.** Environment variables, prompt sections, tool availability, conversation membership, delivery admission, and UI/CLI/API read models derive from the persisted spec. No runtime code may re-infer participation from channel presence, config, or execution shape.
5. **No silent degradation or upgrade.** Resolver failures (network unavailable, unknown channel, authority exceeded, network-using loop step while `local`) are typed diagnostics returned before the owning record is created.

## Alternatives Considered

### Alternative 1: Keep channel-string inference, fix the defaults

- **Description**: Make blank channel truly local, keep `channel != ""` as the participation switch.
- **Pros**: Smallest diff.
- **Cons**: A string stays the control plane for membership, prompts, tools, and activation; provenance and validation have no home; future code re-grows inference (the corpus documents this exact drift).
- **Why rejected**: It preserves the ambiguity this program deletes; PRD rules 6–7 are unsatisfiable without a typed contract.

### Alternative 2: Three-value contract with a dormant `mailbox` value

- **Description**: Ship the enum with `mailbox` defined but rejected, easing the future program.
- **Pros**: One less contract change later.
- **Cons**: Dead vocabulary across contract, docs, validation, and UI for a mode whose semantics the future external-interaction program will define on its own terms; violates zero-legacy posture (speculative surface).
- **Why rejected**: Adding an enum value later is additive; carrying a dead one now is not (ADR-004).

## Consequences

### Positive

- One place answers "does this execution participate and why"; every surface agrees by construction.
- Compiler-driven migration: replacing typed fields enumerates every consumer of the old string.

### Negative

- Every execution surface's contract changes in one release (co-shipped generated clients, CLI, web, docs).

### Risks

- A missed inference site survives the cut → the implementation TechSpec carries an explicit delete-target list and a repository-wide search gate for the old fields.

## Implementation Notes

Package name, exact type/field names, and persistence columns are TechSpec-owned. The resolved spec's persisted identifier (schema/version string) is brand-neutral so the product-line rename never rewrites stored snapshots.
