# ADR-010: In-Process Delivery Replaces the Embedded Broker for This Release

## Status

Accepted

## Date

2026-07-11

## Context

Today every network message — all of it loopback within one daemon — pays an embedded message-broker round trip: the transport starts a broker bound to the local host with a private token and an in-process client (`internal/network/transport.go:93-159,195`); publishes marshal and synchronously flush (`internal/network/router.go:1166-1191`); no production path supplies a second daemon with that address (audit P1-1). Two proven correctness defects live exactly on that hop: persist-before-publish can acknowledge an envelope that was never published (C-05), and the first local thread send can select zero receivers because routing runs after the sender's own persistence mutates participants (C-02).

The corpus kept the broker lazy-started and deferred the transport decision to profiling — under the assumption that remote delivery might need it. ADR-004 removed external interaction from scope entirely: after this release there is **no remote consumer, actual or planned, until the external-interaction program exists**.

## Decision

1. **Delete the embedded broker from the delivery path.** Message flow becomes: validate → durable commit (conversation + routing decision computed from the pre-message participant snapshot, in one transaction) → in-process dispatch to admitted local recipients.
2. This **structurally removes** C-05 (no publish hop to fail after persistence — the commit is the acceptance) and C-02 (the routing decision is computed against the pre-message snapshot inside the same transaction).
3. **Protocol semantics survive the transport.** Envelope shapes, message kinds, conversation surfaces, and validation rules are unchanged; only the hop between persistence and local delivery changes. The single durable work authority (C-04) is part of the same restructure.
4. **The broker returns with external interaction.** The future program that introduces recipients outside the installation owns the remote transport decision on real requirements; nothing in this release may keep broker code "just in case".

## Alternatives Considered

### Alternative 1: Keep the broker, start it lazily (corpus P0-B)

- **Description**: Same architecture, transport starts on first participation.
- **Pros**: Smaller refactor; preserves a future remote path.
- **Cons**: Keeps broker/flush/callback overhead and the persist-before-publish defect class on a path with zero remote consumers; dead infrastructure violates zero-legacy posture; the future program will re-decide transport anyway.
- **Why rejected**: With external interaction out of scope (ADR-004), the broker serves nothing; lazy-starting nothing is still nothing.

### Alternative 2: Broker plus transactional outbox (corpus P0-C design 1)

- **Description**: Keep the broker and add a durable outbox state machine to fix C-02/C-05.
- **Pros**: Correct under any transport.
- **Cons**: Builds durable-delivery machinery to protect a loopback hop that can simply be removed; largest option for the least benefit in a local-only release.
- **Why rejected**: The outbox exists to survive an unreliable hop; deleting the hop is strictly simpler and equally correct locally.

## Consequences

### Positive

- Two P0-class defects fixed structurally rather than patched; less latency and resource use per message; the "local execution indistinguishable from network-disabled" goal gets easier.
- The network package sheds its heaviest infrastructure while keeping protocol semantics intact.

### Negative

- The delivery path refactor is substantial (manager/router/delivery restructure — which the two-touch rule already demanded as a structural redesign, not a third patch).
- Re-introducing remote transport later is a real project (by design: it will be specified against real external requirements).

### Risks

- Hidden broker dependents → repository boundaries already confine the broker to the network package; the TechSpec's delete-target sweep verifies no other consumer exists.
- Wire-protocol identifiers referenced by docs/RFCs (subject names) become transport-internal history → docs updated in the same cut; the product-line merge's subject-rename item is flagged as superseded for alignment.

## Implementation Notes

The restructure lands inside the existing network package as new single-responsibility files (the current over-cap files must shrink, never grow). Delivery ordering, dedup keys, and admission integration are TechSpec-owned.
