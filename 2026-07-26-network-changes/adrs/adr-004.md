# ADR-004: One Complete Release — Local and Live Ship Together, No Public "Under Construction" Window; Mailbox Removed from Scope

## Status

Accepted (amended 2026-07-11: mailbox removed from release scope — originally "all three modes ship together")

## Date

2026-07-11

## Context

The redesign has two halves that could ship separately: (a) the decoupling — everything defaults to Local and implicit enrollment is deleted — and (b) the rebuilt opt-in — participation released behind quality gates. Shipping (a) alone creates a public window where the old implicit path is gone and the new opt-in is not yet released: the Agent Network would be temporarily un-joinable ("under construction"). This program also runs alongside the AGH→Compozy merge, whose launch narrative advertises the agent network.

The research corpus additionally proposed a third participation mode — **Mailbox**: a durable address that accumulates messages for an offline recipient without waking it. During technical grilling the operator identified the flaw in shipping it now: **within a single installation, "offline" is a fiction.** The daemon owns every agent and decides who wakes; any recipient the runtime can name, it can also run. A durable address for unreachable recipients only earns its cost when recipients exist *outside* the installation — and external interaction has no conditions to exist now. The mailbox concept also carried the heaviest engineering in the corpus: a stable-address identity layer for offline delivery (audit blocker C-07), durable-delivery guarantees, and (in its full form) cross-machine protocol machinery.

## Decision

1. **No public under-construction window, ever.** The redesign ships as one complete release: Local-by-default and the working explicit opt-in land together. At no public release point is the Agent Network un-joinable.
2. **The release ships two modes: Local and Live.** Live (message-triggered wake within bounds) is the mode the flagship coordinated-run experience uses.
3. **Mailbox is removed from this program entirely** and recorded as a PRD non-goal. It returns as its own fully separate specification together with external interaction — the moment recipients outside the installation exist is the moment a durable offline address earns its cost. Message durability inside conversations (history agents read on their own turns) remains, but it is not a participation mode.
4. Internal development may stage however engineering needs; public releases only ever move from "old model" to "new model, fully joinable".

## Alternatives Considered

### Alternative 1: Staged with a launch guard

- **Description**: Ship the decoupling early (window acceptable in alpha releases); require working opt-in before the product-line launch.
- **Pros**: Light users get the cost win earlier; smaller first release.
- **Cons**: Alpha users watch a working feature disappear and return; two migration moments.
- **Why rejected**: Operator decision — no public state with the network unavailable, even in routine releases.

### Alternative 2: All three modes in the release (original form of this ADR)

- **Description**: Local, Mailbox, and Live publicly selectable together from day one of the new model.
- **Pros**: Complete participation contract at launch.
- **Cons**: Mailbox's premise (offline recipient) does not exist in a single-installation runtime — the daemon decides who is awake; its durability/identity machinery is the heaviest in the corpus and would be built for a fiction.
- **Why rejected**: Superseded during technical grilling by the operator's analysis above. Not merely deferred — removed until external interaction exists.

### Alternative 3: Unconditional windows

- **Description**: Ship each half when ready regardless of launch timing.
- **Pros**: Fastest path per piece.
- **Cons**: Risks launching the product line while its advertised network is unavailable.
- **Why rejected**: Unacceptable narrative and adoption risk.

## Consequences

### Positive

- One migration story; the launch always demonstrates the network it advertises, complete.
- Removing mailbox deletes the release's heaviest prerequisite chain: the stable offline-address layer (C-07), offline durable-delivery gates, and every cross-machine protocol concern leave the critical path.
- The participation model collapses to a simple, teachable pair: Local (nothing) and Live (bounded wake).

### Negative

- Asynchronous agent-to-agent handoff to a *not-running* recipient has no mode until the external-interaction program lands; the workaround is conversation history read on the recipient's own next turn.
- The future mailbox program must re-open participation vocabulary (adding a mode is additive, but docs/UI/contract grow again then).

### Risks

- "Removed until external interaction" drifting into ambiguity → the PRD non-goal names the return condition explicitly (external recipients) and this ADR records that mailbox is not a staged phase of this program.
- Release size still concentrates on Live's activation-bounds gate → mitigated by ADR-008 (practical accounting floor).

## Implementation Notes

The research corpus's mailbox-specific material (stable mailbox addressing, offline delivery gates, remote-home protocol) is out of scope for the implementation TechSpec and is not a delete target — it remains research input for the future external-interaction program.
