# ADR-001: Network Participation Is Explicit, Per-Execution, and Default-Local

## Status

Accepted

## Date

2026-07-11

## Context

Today the runtime enrolls ordinary work into the Agent Network implicitly: sessions resolve an omitted channel to a configured default, every workspace task run receives an auto-derived coordination channel, loop worker/judge sessions bind generated channels unconditionally, and network tooling is advertised to every agent session whenever the subsystem is available. Light users — the majority persona once AGH ships as the Compozy product line — pay network cost (context tokens, storage, transport, potential model activations) for a capability they never requested. At the same time, the enforcement audit proved that task orchestration authority is local: the kanban, queue, leases, coordinator wake, and review verdicts do not functionally require the network.

Market research confirms the industry standard: no major agent platform ships ambient default-on agent-to-agent communication; all model multi-agent as an explicit, user-constructed topology, and the one ambient-chat design in the field is being deprecated.

## Decision

Network participation becomes an explicit, per-execution choice with **Local as the built-in default**, governed by two independent planes:

1. **Availability (installation-level):** an administrative switch answers "does this installation offer the Agent Network at all". It stays on by default and costs nothing while no execution participates. Availability never enrolls anyone.
2. **Participation (execution-level):** each session, task run, loop run, and automation run resolves its **own** participation. The scope of an opt-in is the smallest unit that asked — enabling participation on one loop affects only that loop's runs, never other loops, sessions, tasks, or the workspace.

Corollary rules:

- No implicit inheritance: children, spawned agents, reviewers, detached work, and automation targets do not inherit participation from their parent or origin; they participate only by their own explicit request within delegated authority.
- Work that references network capabilities (for example a loop step that posts to a channel) must declare participation on its owning definition; validation rejects the mismatch at authoring/start time with a clear message — the runtime never silently upgrades an execution because a network-using step appeared.
- A participation request while the network is administratively unavailable fails with a clear diagnostic; it is never silently downgraded to Local.
- Every participating execution records why it participates (which request or saved setting selected it), and that provenance is visible wherever the execution is inspected.

## Alternatives Considered

### Alternative 1: Global network ON/OFF as the only control

- **Description**: Keep one installation-wide switch; users who want network for anything turn it on for everything.
- **Pros**: Simplest mental model; smallest change.
- **Cons**: All-or-nothing cost — enabling network for one loop re-enrolls every session and run; light users regain the tax the redesign exists to remove.
- **Why rejected**: It reproduces the current problem one level up. Granularity is the product requirement, not a nicety.

### Alternative 2: Keep implicit enrollment but suppress its cost (quiet channels)

- **Description**: Continue auto-creating channels and memberships but strip prompts/tool advertisement so the visible cost drops.
- **Pros**: No behavior change for existing flows; cheap.
- **Cons**: Storage, roster, transport, and lifecycle side effects remain; future code keeps inferring participation from artifacts that exist without intent; the ambiguity that caused today's coupling survives.
- **Why rejected**: It optimizes the symptom and preserves the architectural ambiguity.

### Alternative 3: Smart defaults (auto-enable for "obviously multi-agent" work)

- **Description**: Infer participation from execution shape (e.g., multi-worker runs get channels automatically).
- **Pros**: Zero-friction for the flagship case.
- **Cons**: Reintroduces inferred participation — the exact pattern being deleted; creates unrequested spend; makes cost unpredictable as execution shape changes.
- **Why rejected**: Explicit intent is the invariant this redesign establishes; shape-based inference violates it by construction.

## Consequences

### Positive

- Light users pay zero network cost — no artifacts, no context overhead, no memberships — without touching settings.
- Cost becomes attributable to a decision: every participating execution can answer "who asked for this".
- Aligns the product with the industry-standard explicit-topology posture.

### Negative

- Users who want everything connected must express that intent (once per scope) instead of getting it for free.
- Every execution surface (sessions, tasks, loops, automations) must carry a participation control, growing those contracts.

### Risks

- Opt-in without strong discoverability starves the feature → mitigated by ADR-002 (flagship enrollment) and ADR-003 (discoverability model).
- Downstream code regressing to channel-presence inference → mitigated by making "no inference from artifacts" an explicit business rule with delete targets in the implementation phase.
