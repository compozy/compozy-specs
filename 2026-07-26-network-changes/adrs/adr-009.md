# ADR-009: Coordination Setting Home — Workspace-Scoped Record Plus Execution Profile; Configuration Never Enrolls

## Status

Accepted

## Date

2026-07-11

## Context

ADR-002 requires a persisted "coordination conversations" opt-in per workspace or per task, written by the kanban invitation and inspectable/revocable. Verification of the current tree found: task-scoped orchestration intent already has a typed home — `ExecutionProfile` (`internal/task/profile.go:53-63`, persisted in `task_execution_profiles` + selector side tables) — but **no workspace-scoped settings entity exists**: today's settings surface applies global daemon configuration sections and records applies to SQLite (`internal/settings/config_apply_service.go:37`), which cannot carry per-workspace state. The workspace entity itself is managed in the store.

Separately, today's configuration enrolls executions (default channel resolution at `internal/api/core/bundles.go:177-195`; `network.default_channel` in `internal/config/config.go`), which ADR-001 forbids.

## Decision

1. **Task scope:** the participation request lives on the task's `ExecutionProfile` as a typed block (mode + channel strategy), persisted with the profile's existing typed-column/side-table discipline. Profile precedence and replacement semantics are unchanged.
2. **Workspace scope:** a new workspace-scoped record (side table keyed by workspace id) holds the coordination-conversations toggle plus its provenance (who/when). It is readable and writable through workspace-scoped structured surfaces — which is what the kanban invitation writes.
3. **Resolution precedence** for a coordinated run: run-start request > task ExecutionProfile > workspace coordination record > built-in local. Task-level wins over workspace-level (PRD rule 3); each resolved run records which source selected it.
4. **Configuration's role shrinks to availability, defaults, and ceilings.** `network.enabled` stays the administrative switch; activation-bound defaults/ceilings live in configuration. `network.default_channel` and bundle default-channel binding are deleted — no configuration value selects participation for anything (ADR-001).

## Alternatives Considered

### Alternative 1: Global config-section settings (existing ApplySection path)

- **Description**: Put the toggle in daemon configuration via the existing settings apply surface.
- **Pros**: Reuses existing machinery.
- **Cons**: Global scope only — cannot express per-workspace opt-in; makes configuration select participation, violating ADR-001; the invitation would mutate installation-wide config from a run view.
- **Why rejected**: Wrong scope and wrong authority model.

### Alternative 2: Profile-only (no workspace scope)

- **Description**: Only task-level opt-in; operators enable per task.
- **Pros**: No new workspace record.
- **Cons**: The flagship enrollment ("turn on once for my workspace") dies; per-task ceremony is the friction ADR-002 rejected.
- **Why rejected**: Contradicts the decided enrollment model.

## Consequences

### Positive

- Both scopes have typed, inspectable, agent-writable homes; the invitation writes exactly one record.
- Provenance falls out naturally: each run's snapshot names profile/workspace-record/request as its source.

### Negative

- A new workspace-scoped storage surface (record + endpoints + CLI verb) must be built and maintained.

### Risks

- Scope confusion between workspace record and task profile → resolution precedence is a numbered safety invariant in the TechSpec with dedicated tests.

## Implementation Notes

Exact table/route/verb names are TechSpec-owned. The workspace record is workspace-isolated data; every read/write path carries the workspace id.
