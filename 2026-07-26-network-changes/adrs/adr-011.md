# ADR-011: Durable Network Wakes Ride task_runs Through ClaimNextRun

## Status

Accepted

## Date

2026-07-12

## Context

The first TechSpec draft gave the Live admission layer its own durable reservation table (`network_live_wakes` with `reserved`/terminal lifecycle) and a dispatcher that recovered accepted-but-undispatched work after restart. Peer review round 1 (B-002, reviewer gpt-5.6-sol) correctly identified that as a second durable work queue with its own claim authority — exactly what L-003 (`task_runs` is the single durable queue) and L-005 (`ClaimNextRun` is the only claim primitive) forbid, regardless of what the table is called. The same round found the pre-existing manual `task.Service.ClaimRun` path bypassing `ClaimNextRun` (B-001), reinforcing that claim-authority drift is a live failure mode in this codebase.

## Decision

1. **Every durable, recoverable model wake is a `task_runs` record** under an explicit substrate generalization (round-2 B-009): `run_kind` gains `'network_wake'`; `task_id` becomes nullable with kind-fenced CHECK constraints (`network_wake` rows have no task; every other kind still requires one); correlation columns carry wake id, owner key, and targeted session. Wake runs never touch task/kanban authority — `tasks.current_run_id`, task status reconciliation, and open-run-per-task rules remain task-anchored-kind-only. `origin_kind` remains the untouched ingress enum.
2. **Execution flows through `task.Service.ClaimNextRun`** — the wake run is claimed via run-kind + target-session criteria and executed by the daemon-owned `NetworkWakeRunner` (composition root): claim, `PromptNetwork`, token-fenced heartbeat, terminal transition, settle. Enqueue happens inside the message-acceptance transaction (round-2 B-010), so there is no crash window between acceptance and schedulable work. Restart recovery is the normal `task_runs` recovery; the network layer has no recovery machinery of its own.
3. **`network_live_wakes` is immutable accounting only**: admission/usage evidence keyed to the canonical `task_run_id`, plus the idempotency (`network_wake_sources`) and coalescing (partial unique open-wake) constraints. It owns no pending work, polling, claim, retry, or recovery authority.
4. **Budget counters (`network_participation_budgets`) mutate only inside the admission/settlement `BEGIN IMMEDIATE` transactions**, making them the serialization point that prevents concurrent overdraw.
5. The manual exact-run claim converges on the same primitive through the **existing** `ClaimCriteria.RunID` selector (already applied as `tr.id = ?` inside the authoritative selection at HEAD); `task.Service.ClaimRun` and its callers are deleted, and no second exact selector is introduced (B-001; round-2 B-008).

## Alternatives Considered

### Alternative 1: Network-owned reservation queue (first draft)

- **Description**: `network_live_wakes` holds reserved state; the dispatcher executes and recovers it.
- **Pros**: Self-contained in the network package; no task-domain coupling.
- **Cons**: A second durable queue and a peer claimer — the two most-litigated architecture violations in this repo (L-003/L-005); duplicate recovery, lease, and fencing machinery would follow.
- **Why rejected**: Peer review B-002; the repo's single-queue law exists precisely to prevent this class.

### Alternative 2: Ephemeral in-memory wakes (no durability)

- **Description**: Admit and prompt in-process; a crash drops pending wakes.
- **Pros**: No queue question at all.
- **Cons**: A crash between admission and prompt silently loses an admitted, budget-charged wake; contradicts truthful settlement and the recovery expectations in the test contract.
- **Why rejected**: Durability of admitted work is required; the only lawful home for durable work is `task_runs`.

## Consequences

### Positive

- Network wakes gain claims, leases, fencing, heartbeats, recovery, and observability for free — and manual/autonomous/network paths converge on identical primitives (L-004).
- The admission layer shrinks to: decide + enqueue + account.

### Negative

- Wake execution latency includes the claim path (acceptable: coalescing already batches bursts; the target-session criteria make claims direct).
- `task_runs` gains a new run kind and correlation columns (append-only migration; more rows under heavy Live traffic — bounded by budgets).

### Risks

- Wake runs appearing in operator-facing run lists could add noise → run list projections filter/badge `run_kind='network_wake'` truthfully (UI decision in design phase; daemon truth either way).
- Generalizing `task_runs` (nullable `task_id`) forks semantics by kind → fenced with CHECK constraints and kind-scoped projection rules; the destructive rebuild is part of the v82+ hard cut.

## Implementation Notes

The store-owned acceptance method (`AcceptNetworkMessage`) performs admission and enqueues the run, writing ledger + sources + counters atomically (round-2 B-010/B-011, round-3 B-018: owner-level open-wake unique, `task_run_id` UNIQUE, CAS settlement); `Settle` consumes the run's terminal outcome. The claim-path hard cut is contract, not implementation detail (round-3 B-017): `ClaimCriteria.TargetSessionID`, `RunKindNetworkWake`, optional `ClaimResult.Task` (nil exactly for wake runs), kind-fenced selection predicates, and task-projection-skipping lifecycle branches. The governing invariant set is: task-run wake authority and exact-claim convergence (TechSpec invariants 10–18), atomic acceptance (invariant 20), and detached deadline execution (invariant 23).
