# ADR-006: Inventory and preview as dedicated read-only verbs and routes

## Status

Accepted

## Date

2026-07-29

## Context

P1 requires operators and agents to (1) inspect what an installed extension ships vs what is currently live, and (2) preview the effect of enabling without mutating state. Today neither exists for extensions: `ExtensionStatus` is runtime-health only, `DescribeExtension` drops every resource enumeration except bundle summaries, and the only dry-run in the product is `POST /api/bundles/preview` — which dies with the product. The in-process `Extension` snapshot already holds the shipped-resource data, and owner attribution (ADR-004) makes the live set queryable.

## Decision

Two dedicated read-only surfaces (user decision, 2026-07-29):

- **Inventory** — `compozy extension inventory <name>`, `GET /api/extensions/{name}/inventory` (HTTP + UDS), native tool `compozy__extensions_inventory` (read-only). Returns the shipped set (from the loaded manifest/snapshot: agents with `has_soul`/`has_heartbeat`, skills, loops, tools, mcp_servers, hooks, automation jobs/triggers, layouts) joined with the live set (owner-queried records), per item: kind, id, name, `live` bool, and the enabled/registered gates explaining any diff.
- **Preview** — `compozy extension preview <name>`, `GET /api/extensions/{name}/preview` (HTTP + UDS), native tool `compozy__extensions_preview` (read-only). A dry-run of enable: what would publish (same item shape), agent-name conflicts against visible non-owned agents, `missing_env`/unbound keys with the suggested `secrets set` command, automation that would start (ADR-002 consent visibility), and the network-requirement digest + whether confirmation would be required (ADR-005). Never mutates: no records, no vault access beyond metadata, no subprocess start.
- `extension status` stays health-focused; `ExtensionPayload` is not widened with inventory arrays (the payloads stay in their own response types).

## Alternatives Considered

### Alternative 1: Enrich existing surfaces (`status --resources`, `enable --dry-run`)

- **Description**: Fold inventory into the status payload and preview into an enable flag.
- **Pros**: No new verbs.
- **Cons**: Status payload becomes dense mixed-concern; `enable --dry-run` has no natural HTTP route for agents (enable is POST + privileged; a dry-run should be unprivileged read); discoverability suffers.
- **Why rejected**: User decision; agents need dedicated structured routes.

### Alternative 2: Both dedicated verbs and enriched payloads

- **Description**: Ship the verbs and also mirror the data into status/describe.
- **Pros**: Convenience.
- **Cons**: Same truth in two payloads drifts; more contract surface to co-ship.
- **Why rejected**: User decision; single source per truth.

## Consequences

### Positive

- The bundle-preview capability (the one genuinely good bundle idea) survives, generalized to the whole kit.
- Enable-as-consent (ADR-002) gets its informed-consent companion.
- Agents get unprivileged, structured GET routes for both.

### Negative

- Two new routes/verbs/tools + payload types to maintain and document.

### Risks

- Preview accuracy drifting from enable behavior — mitigated by implementing both over the same desired-state computation (preview = compute, enable = compute + publish), asserted by an equivalence test in `_tests.md`.

## Implementation Notes

Preview of an already-enabled extension reports the delta (what would change on reload — e.g. after an update), reusing the same desired-vs-live diff as inventory. Both handlers are unprivileged reads; workspace binding is not involved (kit scope is global, ADR-004).

**Item identity (peer-review R1 N-002):** the shipped↔live join key is `(Kind, Name)`; the displayed ID is the live record id when live, else the content-independent source key `extension/<ext>/<kind>/<name>`. A content change keeps one row (rendered as changed in preview); only a genuine rename splits into remove+add.
