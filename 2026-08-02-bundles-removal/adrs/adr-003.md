# ADR-003: MCP-shaped extension env binding (`extension_env_bindings` + `compozy extension secrets`)

## Status

Accepted

## Date

2026-07-29

## Context

The brief (P0.5) requires a post-install secrets/env binding path "comparable in agent/operator manageability to what MCP install already provides for vault bindings". Today the *injection* half already exists for extensions — `[subprocess.secret_env]` refs are validated against the `extensions` vault namespace and resolved through `vault.Service.ResolveRef` at spawn with redaction registration (`internal/extension/manager_env_resolution.go:29-113`) — but the *binding* half does not: zero producers of `vault:extensions/...` exist in the repo, there is no ref-namer helper, no bind verb, and no per-extension binding storage. Authors hardcode `env:NAME`, which forces daemon-process env. `requires_env` warns forever while an unresolvable `secret_env` crashes the spawn.

The MCP bar (`internal/settings/mcp_secrets.go`, `mcp_catalog_install.go`): transactional multi-secret writes with reverse rollback, superseded-ref GC tagged by ownership kind, bind-to-existing-ref with a presence check, rotation without re-supplying values, presence projection without values, and secret intake via hidden TTY/stdin (never argv). The manifest is a generated build artifact (ADR-001 of ext-improvs), so operator bindings cannot live in the manifest — they must be daemon-side state.

## Decision

Mirror the MCP shape with a typed side table and dedicated verbs:

- **Storage**: new global-stream table `extension_env_bindings (extension_name, workspace_id, env_name, secret_ref, kind, created_at, updated_at, PRIMARY KEY (extension_name, workspace_id, env_name))` — **instance-keyed** (peer-review R1 B-001): `workspace_id = ''` is the global published instance; a dev-linked instance binds under its workspace, bound server-side from caller scope. Bindings are daemon-owned state, independent of the (immutable, regenerated) manifest — they survive `extension update` under the same managed identity, and are deleted by `extension remove` (global) / `dev unlink` (workspace) with owned-ref GC, so secret authority never transfers across a remove→reinstall (R1 B-003).
- **Ref namer**: `vault.ExtensionSecretOwnerPrefix(extension, workspaceID)` producing `vault:extensions/global/<ext>/...` or `vault:extensions/ws/<workspace>/<ext>/...` (the exact `vault.MCPSecretOwnerPrefix` dual convention, `internal/vault/mcp_refs.go`), with the same unsafe-segment hex encoding.
- **Verbs**: `compozy extension secrets set <ext> --env NAME` (value via hidden TTY prompt or `--value-stdin`; writes the vault secret at the conventional ref + upserts the binding, transactionally with reverse rollback and superseded-ref GC scoped to ownership kind `extension_env`), `secrets bind <ext> --env NAME --vault-ref <ref>` (bind to an existing ref; namespace + `metadata.Present` check — a dangling ref is a validation error), `secrets list <ext>` (bound keys + declared `requires_env`, values never shown), `secrets unset <ext> --env NAME`.
- **Transports**: `GET/PUT /api/extensions/{name}/secrets` + `DELETE /api/extensions/{name}/secrets/{env_name}` on HTTP (privileged) and UDS; requests are write-only (values never echo); `ExtensionPayload` gains `bound_env_keys` presence projection.
- **Input shape**: each env name carries exactly one of value/ref (overlap → 400); mutation order is sorted normalized env names, rollback reverse (R1 N-006).
- **Spawn resolution order**: safe allowlist → manifest `env` → manifest `secret_env` → the launching instance's own `(name, workspace_id)` bindings — no cross-scope fallback; injection intersects bindings with the **current** normalized `requires_env`, so a binding whose declaration was dropped by an update is stale: listed by `secrets list`, never injected, removed only by explicit `unset` (R1 B-003). Operator intent overrides author defaults for the same NAME. Binding resolution failure aborts launch naming key + ref (existing behavior).
- **Reporting**: `missing_env` becomes "declared `requires_env` minus (process env ∪ bound keys)"; enable stays non-blocking but its output and the doctor probe suggest the exact `compozy extension secrets set` command.
- Binding an env name not declared in `requires_env` is rejected with a deterministic error listing the declared names (mirrors MCP's undeclared-input rejection).

## Alternatives Considered

### Alternative 1: Convention-only vault refs (no table)

- **Description**: `secrets set` writes `vault:extensions/global/<ext>/env/<NAME>`; spawn auto-resolves the conventional ref for any unmet `requires_env` name.
- **Pros**: No schema change; vault is the only store.
- **Cons**: No bind-to-existing-ref (MCP-bar feature); presence projection requires vault metadata scans; unbinding vs deleting the secret conflate; no ownership tagging for GC.
- **Why rejected**: Below the "comparable to MCP install" bar; user selected the MCP shape.

### Alternative 2: Config-set + generic vault put (sandbox-shaped)

- **Description**: Document `compozy vault put` plus a per-extension `secret_env` overlay in `config.toml` (like `SandboxProfile.SecretEnv`).
- **Pros**: Cheapest; zero new verbs.
- **Cons**: Not transactional, no rollback, no presence projection, no preservation semantics, couples operator state to config files, and adds a config-lifecycle surface for something that is runtime state.
- **Why rejected**: Fails the brief's explicit bar; user rejected.

## Consequences

### Positive

- Extensions reach MCP-grade secret manageability; the dead `extensions` vault namespace gains its producer.
- Bindings survive `update` under the same managed identity without re-supplying values (rotation = `secrets set` again); remove→reinstall deliberately starts clean — no implicit secret transfer across package identity.
- The `requires_env`-warns vs `secret_env`-crashes inconsistency becomes a coherent story: declare → report → bind → inject.

### Negative

- One new table and five new transport surfaces to maintain.
- Two sources of env truth at spawn (manifest + bindings) — resolved by the documented, tested precedence order.

### Risks

- Secret leakage through new surfaces — mitigated by write-only request shapes, presence-only projections, redaction registration before injection, and leak assertions in `_tests.md`.

## Implementation Notes

No native tool for secret writes (parity with MCP, which exposes read-only status tools only); agents use CLI/UDS. Bridge `secret_slots` remain a separate subsystem (`bridge_secret_bindings`, namespace `bridges`) — extension enable never binds bridge console secrets. Do not name this mechanism "env profile" (term reserved by spawn-narrowing vocabulary in the glossary).
