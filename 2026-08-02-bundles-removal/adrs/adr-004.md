# ADR-004: Extension-owned resource records; kit scope is global-only

## Status

Accepted

## Date

2026-07-29

## Context

Extension-published static resources today carry no owner: records are written with `MutationActor.Source = {daemon, "<syncer>"}` and attribution survives only inside `sourceKey` strings (`extension/<name>/<kind>/<id>`) plus soft per-kind fields (`skill.InstalledFromExtension`, `HookDecl.Metadata["extension"]`). Bundle *activations*, by contrast, own their records via `ResourceOwner{Kind:"bundle.activation", ID:<activationID>}`, and that owner drives three behaviors the kit switch needs: soul/heartbeat sidecar↔agent matching (`internal/daemon/agent_skill_catalog.go:205-283`), `PackageOwned` semantics (heartbeat policy honored, authored-context read-only), and owned-set sweeps.

Bundle activation was also the only workspace-scoped packaging mechanism; extension enable is global-only (`internal/extension/registry_lifecycle.go:12-42`). The brief lists workspace-scoped enable as a non-goal.

## Decision

- Every record published from an extension package (agents, souls, heartbeats, skills, loops, tools, mcp_servers, hook bindings, automation jobs/triggers, window layouts) carries `ResourceOwner{Kind: "extension", ID: <extension_name>}` alongside the existing source attribution.
- `PackageOwned` is redefined as `Owner.Kind == "extension"` after the cut (the `bundle.activation` comparison in `agent_skill_catalog.go:171` is replaced, not extended). Heartbeat policy resolution and authored-context read-only rules key off it unchanged.
- Sidecar↔agent matching keeps requiring `AgentResourceID` + same `Scope` + same `Owner` — extension-published sidecars match because agent and sidecars now share the extension owner.
- The extension resource inventory (ADR-006) queries live state by owner; the declarative sync's delete-stale semantics operate on the owned/sourced set, so disable/remove removes exactly the extension's records.
- **Kit scope is global-only** in this program: all package resources publish at `ResourceScopeKindGlobal` (already true for every static kind). Workspace-scoped packaged resources — the one capability bundle activation scoping provided — are dropped without replacement.

## Alternatives Considered

### Alternative 1: Parse `sourceKey` strings for attribution

- **Description**: Derive ownership by parsing the `extension/<name>/...` source-key convention at query time.
- **Pros**: No write-path change.
- **Cons**: String-format coupling as an API; no index; sidecar matching (which compares `Owner` structs) still fails; `PackageOwned` cannot be derived.
- **Why rejected**: Fragile and insufficient for the sidecar and read-only semantics.

### Alternative 2: Workspace-parameterized enable

- **Description**: Make `extension enable` accept a workspace scope so packaged resources can be workspace-scoped like activations were.
- **Pros**: Preserves the dropped capability.
- **Cons**: Explicit brief non-goal; doubles the enable/disable matrix, the inventory model, and the conflict rules for a capability with zero first-party users.
- **Why rejected**: Brief non-goal ("Do not require workspace-scoped enable").

## Consequences

### Positive

- Owner-indexed queries make inventory, sweeps, and read-only guards uniform across every kit kind.
- Static extension agents finally get working SOUL/HEARTBEAT semantics (matching + policy) with no bundle in the path.
- One scoping rule ("package resources are global") replaces the dual global/workspace activation matrix.

### Negative

- Workspace-scoped packaged resources are lost (accepted; a future workspace-enable program can add scope without changing the owner model).
- A data-shape change to every extension-published record (owner added) — converged automatically by the declarative sync on first reload; no migration needed for these records.

### Risks

- Owner semantics drifting between kinds — mitigated by a single publisher-side helper constructing the owner/actor pair and a cross-kind ownership test in `_tests.md`.

## Implementation Notes

`resource_records` already indexes `(owner_kind, owner_id, kind)` (`34_resources.sql:32`) — owner queries are free. Agent-name conflict validation (bundle's `validateActivationAgentBindings` semantics) moves to the extension register/publish phase: a shipped agent name colliding with a visible non-owned agent fails enable deterministically and is surfaced by preview first (ADR-006).

**Executable convergence (peer-review R1 B-004):** ownership is carried through the substrate, not asserted — `resources.Draft` gains an explicit optional `Owner *ResourceOwner` (kernel persists it when set; actor-derived ownership remains the fallback), every extension publisher sets it via one shared constructor, and managed-record equality (`sameManagedRawRecord` + per-kind peers) compares normalized owner + source in addition to scope + spec. A pre-existing daemon-owned row with an unchanged spec is therefore rewritten with the extension owner on the first reconcile after upgrade; a seeded pre-cut-record integration test per kind (IT-017) proves the rewrite, sidecar matching, inventory visibility, and disable cleanup.
