# ADR-005: In-memory manifest synthesis — plugin.json stays the single source of truth

## Status

Accepted

## Date

2026-08-15

## Context

An ingested package needs a Compozy extension manifest for everything downstream (registry row, resource loading, kit publication). Two ways to produce it: materialize a synthesized `extension.toml` into the installed directory at install time, or synthesize the manifest in memory every time the extension loads. Materialization would keep every load path untouched, but it plants a second manifest inside our own install tree (the exact dual-manifest situation whose precedence we had to legislate), forces inventing a `min_compozy_version` value the portable format cannot express, and makes the installed directory diverge from upstream bytes — weakening the checksum story and the "pristine package" property both reference implementations preserve.

## Decision

Synthesis is **in-memory at load**. The installed directory holds exactly the upstream package; `plugin.json` is the only manifest. Manifest loading gains a detection branch: no native manifest + conformant `plugin.json` → run the standard reader and convert its output to the extension manifest shape (explicit per-skill paths honoring non-recursive discovery; MCP entries mapped to the canonical server shape with placeholders expanded to absolute paths). The registry row records `manifest_path` pointing at `plugin.json` and persists `format` plus the recorded ingest diagnostics. The `min_compozy_version` daemon-compatibility gate is waived for adapted manifests — the portable format has no equivalent declaration, so there is nothing truthful to enforce.

## Alternatives Considered

### Alternative 1: Materialize `extension.toml` at install

- **Description**: Install writes the synthesized manifest next to `plugin.json`.
- **Pros**: Zero changes to manifest-loading paths; synthesis runs once.
- **Cons**: Dual manifest inside our own tree; invented `min_compozy_version`; installed bytes diverge from upstream; update must re-materialize and re-diff; the "native wins" precedence rule now fires on our own artifact.
- **Why rejected**: Trades one small load-path branch for a permanent provenance lie.

### Alternative 2: Synthesize once into the registry (persist the converted manifest as data)

- **Description**: Store the converted manifest JSON in the registry row; load reads the stored copy.
- **Pros**: No re-parse at boot.
- **Cons**: A second durable representation that can drift from the directory the checksum covers; contradicts the manifest-on-disk model every other extension follows.
- **Why rejected**: Same drift problem as materialization, hidden in the database.

## Consequences

### Positive

- Installed content is byte-identical to upstream; the content checksum covers exactly what the author shipped.
- Conformance re-validates on every load for free — a corrupted directory surfaces immediately instead of loading a stale synthesized manifest.
- Dev links work naturally: reload re-runs the reader against the edited directory.

### Negative

- Every manifest-load call path must handle the detection branch (one function, several callers).
- Synthesis must be deterministic: same directory bytes → same manifest, or checksum-based update detection would misfire.

### Risks

- Boot-time cost of re-reading packages — bounded: reading a manifest plus frontmatter for tens of skills is microseconds-to-milliseconds against directories already walked today.
