# ADR-006: Fixed MCP headers land on the canonical server config, consumed daemon-side

## Status

Accepted

## Date

2026-08-15

## Context

The standard's `streamable-http` servers may declare fixed HTTP `headers` (tenant routing, API keys). Compozy's canonical session `MCPServer` has no headers field, and the `mcp.json` sidecar parser hard-rejects unknown fields — a headers-bearing package fails to parse today. The user asked whether MCP v2 semantics make a headers field sensible. Research (2026-08-15) established: (a) the MCP spec itself defines no client-supplied custom headers — they are a host concern; (b) the TS SDK v2 keeps `requestInit.headers` as the first-class static-header carrier (a static map is v2-idiomatic); (c) v2 TS semantics are not binding anyway — the daemon is the actual MCP client via the official Go SDK v1.7.0, where headers inject through the `*http.Client` seam Compozy already owns (`authorizationRoundTripper`); (d) remote servers never serialize to ACP providers — `toSDKMCPServers` forwards stdio only, and agents reach remote servers through the daemon's hosted proxy.

## Decision

Add `Headers map[string]string` and `SecretHeaders map[string]string` to the canonical `MCPServer`, mirroring the existing `Env`/`SecretEnv` split, valid only for non-stdio transports. Both fields are **declarative**: `Headers` carries package-declared plain values; `SecretHeaders` carries header name → secret **reference** (vault ref / binding identity) — resolved values never enter either field or any serializable type. The daemon's MCP executor resolves references immediately before request construction into a non-serializable request header. Operator bindings created with `secrets bind --remote-header <server>:<header>` project as references into `SecretHeaders`.

Header policy is **source-aware**, owned by one leaf (`internal/mcppolicy`) shared by sidecar validation, ingestion, and the executor, with one deterministic outcome per violation: `content-type` and the `mcp-*` family are rejected for every source; the sensitive set (`authorization`, `proxy-authorization`, `cookie`, `set-cookie`) declared in **package bytes** rejects that server entry with a stable scoped code (never stripped, never silently dropped); `authorization` via **operator binding** is allowed only when the server has no OAuth auth configured (the broker owns it otherwise); duplicate detection is case-insensitive across the union of both maps. Headers are consumed exclusively by the daemon's MCP executor client; they never serialize toward ACP providers.

## Alternatives Considered

### Alternative 1: Reject headers-bearing remote entries in Phase 1

- **Description**: Skip such servers with a diagnostic; minimum conformance still passes via stdio.
- **Pros**: No schema change.
- **Cons**: Breaks the common tenant-header case (the standard's own example uses one); leaves the approved `--remote-header` surface without a mechanism.
- **Why rejected**: Cuts a mainstream case to avoid a two-field change on an existing seam.

### Alternative 2: Auth-provider indirection only (static-bearer mode on `MCPAuthConfig`)

- **Description**: Model credentials as a bearer-token auth mode; no header map.
- **Pros**: Matches the v2 `AuthProvider` shape for pure API keys.
- **Cons**: Cannot express non-auth headers (`X-Tenant`, region routing) packages actually ship.
- **Why rejected**: Solves half the problem; the header map subsumes it. A static-bearer auth mode remains open as a later refinement, not a Phase 1 need.

### Alternative 3: Middleware/fetch-style dynamic header surface

- **Description**: Expose a configurable request-middleware surface like the TS SDK's `fetch` option.
- **Pros**: Maximal flexibility.
- **Cons**: The Go analogue is the `RoundTripper` the daemon already owns internally; exposing middleware config for static values is speculative infrastructure with no consumer.
- **Why rejected**: Playbook forbids infrastructure without a shipped consumer.

## Consequences

### Positive

- Headers-bearing packages ingest instead of hard-failing; the `--remote-header` binding gets its mechanism.
- Secrets stay daemon-side by construction — the provider process never sees remote-server credentials, because the provider never sees remote servers.
- Reuses the existing secret resolution and redaction machinery; no second secret mechanism.

### Negative

- The canonical server config widens by two fields — scoped as **internal wire fields** in this spec (produced by plugin synthesis and binding projection, consumed by the executor, redacted everywhere): the workspace `mcp.json` sidecar format, `compozy config` MCP verbs, and the web MCP editor deliberately do not expose them; that generalization is a future spec with its own frozen surface.

### Risks

- Header-name policy drift between ingestion validation and executor enforcement — mitigated by one shared validation function used by both.
