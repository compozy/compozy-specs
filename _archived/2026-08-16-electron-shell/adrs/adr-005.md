# ADR-005: One update command — `compozy update` covers runtime and app; `compozy app update` is deleted

## Status

Accepted

## Date

2026-08-15

## Context

After ADR-004 unified the runtime self-update mechanism, two CLI entry points would have remained: `compozy update` (runtime/CLI binary) and `compozy app update --check|--apply app|runtime` (a proxy over the app control channel driving the shell's two update tracks). Two verbs for one concept — "update CompozyOS on this host" — duplicate the decision surface, and the `--apply app|runtime` target selection exposes internal track structure the operator should not need to know. During the surface grill (2026-08-15) the user chose a single command over preserving verb parity.

## Decision

`compozy update` is the only update command. Default invocation updates everything applicable on the host: the runtime always; the desktop app when installed (applied immediately when the app is running, staged for the next launch when it is closed). `--check` stays read-only. The structured record becomes multi-target (`runtime` object always, `app` object present only when the app is installed) with an aggregate `status` (precedence: `failed` > `blocked` > `staged` > `updated` > `available` > `up-to-date`). `compozy app update` is deleted — command, docs page, and tests are delete targets. This is a deliberate, user-decided exception to the strict-parity contract; the remaining `compozy app` verbs (`status`, `open`, `retry`, `diagnose`) stay byte-compatible.

## Alternatives Considered

### Alternative 1: Keep both verbs (full parity)

- **Description**: Preserve `compozy app update` as a byte-compatible proxy alongside the unified `compozy update`.
- **Pros**: Zero breaking change for scripts; honors the original parity bar.
- **Cons**: Two commands answering "how do I update?"; the app-verb's `--apply app|runtime` leaks track internals; both must be documented, tested, and kept convergent forever.
- **Why rejected**: User decision (surface grill S3): one command, delete the other. Alpha base makes the break free.

### Alternative 2: Runtime-only `compozy update`

- **Description**: The CLI updates only the runtime; app updates remain exclusive to the app's own surfaces.
- **Pros**: Smaller command.
- **Cons**: Headless hosts cannot keep the app current; contradicts the agent-first manageability outcome.
- **Why rejected**: Breaks US-018's promise and splits "update CompozyOS" back into two mental models.

## Consequences

### Positive

- One documented, one tested, one remembered way to update a host; agents get per-target structured results from one invocation.
- Staged-on-next-launch semantics make the closed-app case deterministic instead of impossible.

### Negative

- Any existing script calling `compozy app update` breaks (accepted: alpha, announced in the cutover notes).
- The multi-target record is a new shape for `compozy update` consumers (old flat fields live under `runtime`).

### Risks

- Aggregate-status ambiguity — mitigated by the documented precedence order and per-target objects carrying full detail.

## Implementation Notes

Delete targets: `compozy app update` command wiring and tests, `packages/site/content/docs/cli/app/update.mdx`, the app-update rows in `cli/app/meta.json` and `cli/compozy.mdx`. `compozy app status` keeps reporting both tracks' states unchanged.
