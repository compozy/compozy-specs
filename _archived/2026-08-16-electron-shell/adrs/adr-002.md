# ADR-002: Relocate runtime management out of the shell before the swap (thin-shell sequencing)

## Status

Accepted

## Date

2026-08-15

## Context

The current shell is not thin: beyond windowing, it owns runtime supervision (attach → start installed → provision app-owned), the runtime update track (staged download, integrity verification, rollback journal, quiesce, recovery), and the CLI control server (`~/.compozy/app.sock`, consumed by `compozy app ...`). Reference research across three Electron products (`analysis/electron-reference-blueprint.md`) shows none of them solves these subsystems in the shell — they are CompozyOS-specific and would be a from-scratch rewrite in the new shell's language. The runtime update track is the subsystem that must not regress (a broken updater cannot be fixed by an update). The team's strength and the daemon already live on the runtime side.

## Decision

The migration program includes relocating runtime supervision, runtime self-update, and as much of the control surface as the design allows from the shell into the runtime side. The shell — old or new — shrinks to windowing, app-track updates, deep links, single instance, and thin orchestration calls. The shell swap happens against the thin shell.

## Alternatives Considered

### Alternative 1: Wholesale port (shell swap only)

- **Description**: Reimplement all ~12.3k lines of shell logic (supervision, runtime updater, control server) in the new shell.
- **Pros**: One program, one cut; no runtime-side changes.
- **Cons**: Rewrites the most critical, hardest-to-test subsystem (staged update + rollback) in a new language under parity pressure; the rewrite has no reference implementation; the shell stays a second brain that duplicates runtime concerns.
- **Why rejected**: Highest-regression-risk path concentrated exactly where regression is unacceptable.

### Alternative 2: Relocate later (swap first, thin second)

- **Description**: Port wholesale now, move logic to the runtime side in a follow-up program.
- **Pros**: Faster first visible result.
- **Cons**: Pays the full rewrite cost anyway, then pays the relocation on top; the throwaway port must still hit the no-regression bar.
- **Why rejected**: Strictly more work than thin-first with no risk reduction.

## Consequences

### Positive

- The updater logic is written once, on the side that owns `~/.compozy` and already ships migrations/integrity machinery.
- Unlocks ADR-004 (single runtime self-update consumed by app and CLI) and headless runtime updates.
- The new shell becomes commodity work with direct reference implementations for every remaining subsystem.

### Negative

- The program is larger and lands in phases (relocation, then swap).
- The runtime side takes on update/supervision responsibilities it did not have.

### Risks

- Phase-1 relocation could destabilize the current Tauri app before the swap — mitigated by keeping the shell↔runtime contract (`app.sock` methods, `app.json` schema) stable during relocation and gating each phase on the affected `APP-*` scenarios.

## Implementation Notes

Part II owns the exact split (which responsibilities land where, what remains shell-side). The `desktop/schema/app-state.schema.json` contract and `compozy app` verb surface are frozen product behavior (strict parity per the spec's scope decisions).

_Note (2026-08-15, post peer-review round 2, B-010): the first-run gap is closed by **bundling the lockstep runtime binary inside the app package**. The shell executes the bundled `compozy` bootstrap entry point from t=0 — resolution (attach → start → provision), self-install into the home, readiness, retry policy, and typed progress are Go-owned even on an empty home; the shell only launches it and renders. First-run provision becomes an offline install-from-bundle, not a network download._
