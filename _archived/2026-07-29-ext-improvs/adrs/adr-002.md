# ADR-002: First-class dev lane — `compozy extension dev` with link semantics and single-extension reload

## Status

Accepted

## Date

2026-07-28

## Context

Installing your own local extension takes 5 commands + a prompt + a global policy flip, because a local path is evaluated by *marketplace* trust policy (`internal/daemon/extensions.go:49` → `ValidateUnverifiedSideLoad`, policy checked before consent at `internal/extension/marketplace_trust.go:152-173`). Reinstalling over the same name returns `409` (`WithInstallReplaceExisting` exists at `registry_types.go:56` but no CLI path passes it). There is no reload, watch, or logs verb; iteration is rebuild → remove → install → re-consent. Every mature reference system has a two-tier install: a throwaway/dev lane and a published lane (Zed `InstallDevExtension`/`RebuildDevExtension`; Claude Code `--plugin-dir` + `/reload-plugins`; OpenClaw `plugins install -l`; pi auto-discovered dirs + `/reload`). The install/trust path has already absorbed multiple patches — the two-touch rule requires structural redesign, not a third patch.

## Decision

Split installs into two lanes:

- **Dev lane** — `compozy extension dev <path>`: builds (ADR-001) into an **immutable generation directory**, then records a **workspace-scoped dev link** (no copy) in the `extension_dev_links` side table (`workspace_id`, `origin_path`, `bundle generation`). The published `extensions` row — when one exists — is never touched or displaced: the runtime resolver simply prefers an active dev link over the published row for that workspace, so "override" is a resolution rule, not a row mutation, and unlink is a side-table delete that trivially restores the published copy. No marketplace trust, no consent ceremony — the directory is author-owned, exactly like running your own code. `compozy extension reload <name>` rebuilds into a fresh generation and atomically swaps the link's generation pointer; `compozy extension dev <path> --watch` runs a CLI-side poll loop (filesnap pattern) that rebuilds and calls reload on change. Dev-linked state is labeled `dev (overrides published)` in `list`/`status`; re-linking the same name replaces the link in place (no 409). Agent-facing dev/reload/logs bind the workspace from trusted session scope — a session can only link, reload, or read logs for its own workspace.
- **Published lane** — `install` from curated/GitHub/git/archive sources keeps digest verification and trust tiers. Unverified side-load collapses to **policy + one consent**: the `--allow-unverified` flag *is* the consent; the config policy remains only as the operator-level opt-out (default flips to allow with per-install consent — see Config Lifecycle in the TechSpec).

## Alternatives Considered

### Alternative 1: Trust-on-first-use per directory (pi model)

- **Description**: One install path; first install from any local path prompts "trust this directory?" and persists the grant.
- **Pros**: One lane; minimal new verbs.
- **Cons**: No link semantics (still copy + reinstall per iteration), no reload story, conflates author iteration with third-party side-load distribution.
- **Why rejected**: Solves consent fatigue but not the inner loop — the audit's create-flow score (1/5) stays.

### Alternative 2: Reorder gates only

- **Description**: Keep one install path; check consent before policy, pass replace-existing, drop `--yes` coupling.
- **Pros**: Smallest diff.
- **Cons**: Still copies on every iteration; still no reload/watch; still marketplace vocabulary on the author's own code.
- **Why rejected**: A third patch on a twice-patched path; two-touch rule demands the structural cut.

## Consequences

### Positive

- Author loop becomes edit → `reload` (or watch) → observe; first contact is one command with zero trust ceremony.
- Trust affordances collapse from four to two; the dev lane never weakens published-lane integrity (invariant: `install` can never create a dev link — dev is a lifecycle overlay, not an install source).
- Override/restore is durable by construction: the published row survives untouched in `extensions`, the overlay lives in `extension_dev_links`, and generation directories are immutable — no backup blobs, no invented persistence.

### Negative

- Daemon must supervise a subprocess whose binary lives outside `$COMPOZY_HOME` (dev only); path-security containment checks apply to the linked root.
- One more *effective-source label* (`dev (overrides published)`) across list/status/web projections — a resolution-time overlay, never an `InstallSourceKind` value (ADR-005).

### Risks

- Stale dev links (deleted source dir) → `status` reports `missing_origin`; daemon refuses to start the subprocess and marks the extension errored, never crashes boot.
- Watch loop churn → debounce + serialized reloads per extension.

## Implementation Notes

New `extension_dev_links` side table (Goose migration; typed columns `extension_name`, `workspace_id`, `origin_path`, `bundle_generation`, `linked_at`) with `Registry.LinkDev`/`UnlinkDev` operating on it; the `extensions` table is not reshaped by the dev lane. `Manager.ReloadExtension(ctx, key, generationHash)` — instance-keyed by `(extension name, workspace)`; today only whole-registry `Reload` exists — runs inside a per-instance operation coordinator that serializes build/stage/swap/reload/watch; a failed activation restarts the last-good generation. Runtime dev state (subprocess, coordinator, last-good generation, log ring, status, events) is keyed by that instance, with the global published installation as the `(name, "")` instance. Dev paths are canonicalized (`EvalSymlinks` + containment) under the bound workspace root before any registration, and generation identity crosses transports only as a content-hash handle — the daemon reconstructs `dist/gen-<hash>` under the canonicalized origin and re-validates manifest + digest before activation; no caller-supplied generation path exists. New routes `POST /api/extensions/dev`, `POST /api/extensions/{name}/reload` with UDS parity and native tools. CLI-side watch uses the `internal/filesnap` poll pattern (no fsnotify dependency exists in the repo).
