# ADR-006: Closed-surface positioning — bridges become a declared follow-up program; four surfaces filed as Future ideas

## Status

Accepted

## Date

2026-07-28

## Context

Five extension-shaped surfaces are closed to third parties today: external bridge authoring (`internal/bridges/ADDING_A_BRIDGE.md:9-11` — "Compozy does not yet publish a complete external bridge SDK, grant surface, or conformance harness"), ACP agent providers (hardcoded `builtinProviders` map, operator `config.toml` as the only escape), notification channels/presets (`BuiltInPresets` hardcoded), CLI verb contribution, and web UI contribution. The brief (R11) requires an explicit recorded position — supported path or non-goal — for each. The user decision (2026-07-28): bridges get the strong position; the rest are good ideas without proven demand.

## Decision

- **Third-party bridges = declared supported-path follow-up program.** Public positioning changes from "not supported" to "planned": the docs' bridge-wall paragraphs are rewritten to state the direction. The program itself (public bridge SDK surface, grant model, importable conformance harness) is **not implemented in this TechSpec**; this program lands its groundwork (generated contracts incl. bridge service methods, public test-harness pattern, permissions model). A follow-up TechSpec owns it.
- **Consequence for this program's public claims (peer-review B-008):** `bridge.adapter` is **excluded from the public completeness surface** until the bridge TechSpec lands. The generated contract layer still emits its method names (internal groundwork consumed in-tree), but the public SDK templates, the public conformance-harness matrix, the docs' supported-provides list, and the closed-set accepted for *installed* third-party manifests cover **four** provide capabilities (`tool.provider`, `memory.backend`, `model.source`, `loop.watch_source`). An installed extension manifest declaring `bridge.adapter` is rejected with a deterministic "external bridge authoring is a planned follow-up" error; in-tree bridge packages are unaffected (they are not installed extensions). No compatibility placeholder ships.
- **ACP providers via extension, notification channels via extension, web UI contribution = Future** (explicitly *not* non-goals). **Superseded in part (2026-07-28): ADR-008 pulls CLI verb contribution into this program's MVP scope — only that item is superseded.** The remaining three surfaces stay tracked as Linear **AGH-105** (team AGH, status Ideas — already rewritten to hold only these three, with a note that CLI contribution moved into ADR-008), with per-surface context and the dependency note: they build on this program's surfaces registry + generated contracts + permissions model. Revisit after third-party authorship is real.

## Alternatives Considered

### Alternative 1: Declare all five as non-goals

- **Description**: Record "not planned" for everything closed.
- **Pros**: Zero ambiguity; no roadmap debt.
- **Cons**: Bridges are where traction lives (Jira/Notion/Zendesk/Intercom-class integrations); a non-goal on bridges contradicts the product premise and the traction goal driving this program.
- **Why rejected**: User decision; bridges are the highest-leverage open surface.

### Alternative 2: Implement the bridge SDK in this program

- **Description**: Fold external bridge authoring into this TechSpec.
- **Pros**: One program.
- **Cons**: Bridge contracts (delivery broker, checkpoints, conformance) are a program-sized surface on their own; folding it in doubles scope and risks both.
- **Why rejected**: Groundwork-first sequencing; the follow-up spec starts from generated contracts instead of hand-built ones.

## Consequences

### Positive

- Honest public roadmap: the docs stop advertising a dead end; ideas are preserved with context instead of dying as non-goals.

### Negative

- "Planned" language creates an expectation the follow-up program must meet.

### Risks

- AGH-105 rotting unvisited → the bridge follow-up TechSpec references it; the surfaces registry keeps the extension points enumerable.

## Implementation Notes

Docs edits in this program: `packages/site/content/runtime/core/extensions/develop.mdx` bridge-wall paragraphs and `internal/bridges/ADDING_A_BRIDGE.md` preamble adopt the "planned follow-up" position. No runtime code for the three remaining Future surfaces (ACP providers, notification channels, web UI contribution); the CLI-contribution runtime — commands read model, `GET /api/extensions/commands` + UDS, `extension commands`/`extension exec` — ships in this program under ADR-008, which supersedes that item.
