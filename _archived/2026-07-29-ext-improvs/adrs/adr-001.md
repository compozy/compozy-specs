# ADR-001: Code-first authoring — the manifest is a build artifact, not a source

## Status

Accepted

## Date

2026-07-28

## Context

Extension authors declare the same facts twice: tools/schemas/capabilities live in `extension.toml`/`extension.json` **and** in SDK code (`ExtensionDefinition` + `tool()` registrations). The daemon reconciles the two by byte-equality on canonical SHA-256 schema digests (`internal/extension/tool_reconciliation.go:19`), and any drift silently flips the tool to `unavailable` with undocumented reason codes (`runtime_descriptor_mismatch`, `extension_runtime_mismatch`). The DX audit measured 45 concepts to first success (71% ceremony) and the dual declaration is the single largest cluster. Reference systems avoid the problem structurally: eve generates the manifest from `defineExtension` at build time; pi and opencode have no manifest at all; Zed requires a manifest but no code.

## Decision

The SDK definition is the single source of truth. A new `compozy extension build` verb produces the canonical bundle:

1. Runs the author's toolchain (`package.json` build script for TS, `go build` for Go, `--cmd` override).
2. Executes the built artifact in **describe mode** (`__describe` argv, handled by both SDKs): the process prints a `DescribePayload` JSON (definition, tool descriptors with digests, hook events, watch kinds, SDK compat floor) and exits.
3. Emits a deterministic, sorted `dist/extension.toml` + digests, stamping `min_compozy_version` from the SDK's compat constant — never hand-authored.
4. Validates closed sets (`capabilities.provides`, `permissions.requires`) before writing.

The daemon keeps consuming manifests exactly as today; install-time reconciliation remains as a defense-in-depth assert, but drift is impossible by construction because both sides derive from one definition. Resource-only extensions (no process) keep a minimal handwritten manifest; `compozy extension build` only validates it.

## Alternatives Considered

### Alternative 1: Manifest-first + generated bindings

- **Description**: Manifest stays the source; codegen emits typed stubs the code must implement (missing registration = compile error).
- **Pros**: Manifest remains human-readable input; no describe-mode execution during build.
- **Cons**: Adds a codegen step inside the author's inner loop; keeps manifest authoring (TOML schema knowledge) as an up-front concept; two artifacts still exist in the repo (source manifest + generated bindings).
- **Why rejected**: Optimizes the wrong direction — authors think in code; the manifest is packaging metadata the machine can derive.

### Alternative 2: Keep dual declaration with loud validation

- **Description**: Both sides stay authored; `build`/`validate`/install fail hard on any digest drift.
- **Pros**: Smallest change; no build verb required.
- **Cons**: Concept bill unchanged (45); boilerplate unchanged; drift becomes a frequent hard error instead of a silent one — better, still hostile.
- **Why rejected**: Fixes the symptom (silence) and keeps the disease (duplication).

## Consequences

### Positive

- Kills the digest-drift failure class; deletes `security.capabilities`/`actions.requires` hand-authoring (with ADR-004); scaffold shrinks to code + package file.
- `min_compozy_version` cannot go stale (the 0.5.0-vs-0.3.0 incident class is structurally gone).
- Any language that can print a `DescribePayload` can author extensions — the contract is JSON, not an SDK binary dependency.

### Negative

- Subprocess extensions require a build step before install/dev (mitigated: `compozy extension dev` runs it automatically).
- Describe mode executes author code at build time (local, author-owned — same trust as running their own build).

### Risks

- Non-deterministic manifest output would break digest stability → invariant: sorted keys, stable ordering, covered by a determinism test.
- Describe mode hanging → bounded timeout in `BuildBundle`.

## Implementation Notes

`DescribePayload` lives in `internal/extension/contract` — the codegen source both SDK generators already read (imported by `internal/codegen/sdkts/generate.go:12` under the `extensioncontract` alias); it composes runtime protocol types from `internal/extensionprotocol`. `BuildBundle` lives in `internal/extension/build.go`; the CLI verb wraps it daemon-free. Reconciliation (`ReconcileManifestToolRuntime`) is retained as an install/activate assert.
