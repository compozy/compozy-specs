# ADR-008: Extension-contributed commands — a presentation facade over the existing tool runtime (`compozy extension exec`)

## Status

Accepted

## Date

2026-07-28

## Context

CLI-verb contribution was filed as a Future surface (ADR-006 / Linear AGH-105), but a concrete first-party use case already exists: legacy `compozy archive` (branch `legacy/v0.2`, `internal/cli/commands_simple.go:101-128`) moves fully completed workflows from `.compozy/tasks` into `.compozy/tasks/_archived/<timestamp>-<id>-<slug>` with eligibility computed from global.db task/review state. It was deliberately not migrated to v0.3 because the `.compozy/tasks` workflow convention is a dev-cycle concern, not agent-OS core — exactly the coupling an extension should absorb. Meanwhile the invocation stack extensions need already exists end to end: extension tools register as `ext__<name>__<tool>` with descriptors/schemas/risk/availability, `POST /api/tools/:id/invoke` runs them through daemon policy with the approvals machinery (`compozy tool invoke|approve|approvals`), and `tools/call` carries `trusted_workspace`. The *surface* gap is presentation: an operator-facing verb with real flags, help, and formatted output (SD-009: data exists, consumer missing — build the consumer; L-031: primitive reuse is a gate). The archive use case itself is **not** purely presentation — peer-review round 2 (B-007) verified that legacy archive wrote durable state (`MarkWorkflowArchived`, `legacy/v0.2:internal/core/archive.go:537`) and that the head task domain has no closure primitive an extension could call. Archive is therefore deferred to its own program (`.compozy/tasks/cmd-archive/_brief.md`, which owns the task-domain primitive and the dev-cycle command); this ADR ships the command surface only, with **no product command in this program**.

## Decision

A command is **presentation metadata on an extension tool**, not a new runtime surface:

- **Authoring (code-first, ADR-001)**: the SDK `tool()` registration accepts an optional `command` block — verb, summary, example, and a `flags` map of CLI flag name → top-level input-schema field. It flows through `DescribePayload` into the generated manifest (`resources.tools.<name>.command`). Build/validate enforce: reserved host flag names rejected (`cmd`, `input`, `output`, `o`, `json`, `help`), flags must reference existing schema fields, verb paths unique per extension.
- **Nesting**: a verb is a path whose segments are joined by `/` (`review/fetch`) — the same hierarchy idiom the Host API already uses for method paths (`sessions/list`). **Every leaf is exactly one tool** (one handler, one input schema, one flag map, one risk class); a group is a presentation node only. Rules: maximum depth 2 (`group/leaf`, rejected at build beyond that); groups are **not executable** (`--cmd review` errors and lists its leaves); **no group-level persistent flags** — each leaf declares its complete flag set, so no leaf inherits state and every invocation stays exactly one tool call; groups may be declared for help text (`ext.commandGroup("review", "Manage review rounds")`) or left implicit (the help tree still groups by prefix, without a description); uniqueness is by full path. Declared groups are first-class generated contract data: they flow `DescribePayload.command_groups` → manifest `[[resources.command_groups]]` → the daemon read model, in both SDKs (generated `ExtensionCommandGroupSpec`). Build and manifest load both reject: a group path equal to a leaf verb, group/leaf collisions, empty segments, leading/trailing slashes, duplicate group declarations, group paths deeper than one segment, and a declared group with no leaf under its prefix. The command path is decoupled from the tool ID — `review/fetch` may back `ext__dev_cycle__review_fetch`, so the presentation tree can be reorganized without breaking the IDs agents call.
- **Canonical invocation**: `compozy extension exec <ext> --cmd <verb-path> [flags] | --input '<json>'`. The CLI fetches the command descriptor from the daemon, dynamically registers the descriptor's flags, converts argv to a typed input document (per-flag conversion errors name the flag and the field; repeated flags for arrays; nested objects require `--input`; `--input` and projected flags are mutually exclusive), then executes **exactly** `POST /api/tools/ext__<ext>__<tool>/invoke` — same policy, approvals, risk gates, and `trusted_workspace` as any tool invocation. The result renders through the standard output bundle (`human|json|jsonl|toon`).
- **Flag projection (closed subset)**: a projected flag must reference a top-level input-schema field whose schema, after canonical `$ref` resolution, is in the closed MVP subset — scalar `string | boolean | integer | number` (optionally with `enum`, `default`, and numeric bounds), a nullable scalar (`[T, "null"]`, treated as the optional scalar; explicit null requires `--input`), or an `array` whose `items` is exactly one supported scalar (repeated flag appends). Everything else — `object`, nested arrays, tuples/`prefixItems`, `oneOf|anyOf|allOf|not`, multi-type unions beyond nullable, unresolvable `$ref` — is rejected **at build and at manifest load** with an error naming the field and the `--input` remediation. Conversion semantics are fixed: booleans are presence-true with explicit `--flag=false`; an absent optional flag omits the field (never null — schema defaults render in help but are applied by the tool's own validation, never injected by the CLI); required fields become required flags checked client-side before invoke; enum choices and numeric bounds render in help, while value-level validation stays in the daemon's schema validation on invoke with errors mapped back to the flag name.
- **Discovery**: `compozy extension commands [<ext>]` lists installed commands from `GET /api/extensions/commands` (UDS parity), rendering the group/leaf tree in human mode and a flat path-keyed array in structured modes. CLI + HTTP + UDS discovery is the **complete** MVP surface — a read-only web command list is deliberately not promised in this program (it would be a partial surface with no product command shipped; it can ride the `cmd-archive` program or a later web pass).
- **Agents**: no new tool — agents already invoke the underlying `ext__*` tools natively; `exec` is the human-ergonomics skin.
- **Reference proof**: the surface is proven by in-repo E2E fixture extensions (nested + flat command declarations exercised by the runtime-lane journey); **no product command ships in this program**. The first product command — the dev-cycle `archive` port — belongs to the follow-up `cmd-archive` program (`.compozy/tasks/cmd-archive/_brief.md`), which owns the task-domain closure primitive that command requires (peer-review B-007).

Deferred by decision, all additive on top of this facade (no hard cut when adopted): executable group nodes, group-level persistent flags, depth beyond 2, and top-level fallback dispatch (`compozy archive` resolving unknown verbs git/kubectl/cargo/gh-style, core-wins — which would map depth-1 leaves only, a question worth answering when the fallback itself is designed).

## Alternatives Considered

### Alternative 1: New `command.provider` capability + `commands/execute` protocol

- **Description**: A dedicated provide surface with its own protocol method, registration, and dispatch.
- **Pros**: Room for command-specific semantics later (streaming TTY, interactivity).
- **Cons**: Duplicates the tool runtime's registration, policy, approvals, risk, availability, and workspace plumbing — a parallel model for the same act (L-031 violation); doubles the audit surface for agent-manageability.
- **Why rejected**: Everything a command needs at MVP is what a tool invocation already is.

### Alternative 2: Dynamic top-level cobra verbs

- **Description**: CLI queries the daemon at startup and mounts `compozy archive` directly.
- **Pros**: Best typing ergonomics.
- **Cons**: Cold-start cost or index cache on every invocation, daemon-down ambiguity, verb-collision policy against future core verbs, help-tree pollution.
- **Why rejected for MVP**: The user chose the explicit canonical form; fallback sugar can layer later (see Decision).

### Alternative 3: Raw argv passthrough / `--param k=v`

- **Description**: Deliver unparsed argv (after `--`) or repeated `k=v` pairs to the extension.
- **Pros**: Trivial host implementation.
- **Cons**: Passthrough pushes parsing/validation/help onto every author (N authors × one parser each); `--param` is verbose and alien next to native verbs.
- **Why rejected**: Descriptor-projected flags give legacy-identical UX with schema-derived types and uniform errors.

### Alternative 4 (nesting): flat compound verbs, or `:` as the path separator

- **Description**: Either keep verbs flat with kebab compounds (`review-fetch`) and defer hierarchy, or use `review:fetch`.
- **Pros**: Flat is the smallest surface today and stays additive; `:` reads as a script namespace and never autocompletes as a filesystem path.
- **Cons**: Flat degrades into an unreadable list once an extension ships 8–10 verbs, with a prefix convention emerging informally that the help cannot reflect; `:` collides with the source-scheme meaning this program just assigned it (`github:owner/repo`, `git:https://…`) — one symbol, two grammars in one CLI.
- **Why rejected**: `/` already means hierarchy in this runtime, so it costs no new vocabulary.

### Alternative 5 (nesting): positional path after the extension name

- **Description**: `compozy extension exec dev-cycle review fetch --round 2`.
- **Pros**: Reads like native subcommands.
- **Cons**: Displaces the chosen `--cmd` form (or duplicates it), and the two-phase parse becomes ambiguous — the host must decide where a variadic path ends and flags begin *before* it knows the descriptor.
- **Why rejected**: Incompatible with the canonical invocation form.

## Consequences

### Positive

- The closed-CLI wall falls with **zero new authority**: policy/approvals/workspace isolation hold by construction; the archive use case gets its delivery vehicle without core coupling (the command itself ships with `cmd-archive`).
- Command metadata is validated at build (code-first), so a broken flag map is an author-time error, not a runtime surprise.

### Negative

- Two round trips per exec (descriptor fetch + invoke) — acceptable for operator verbs; both hit the local daemon.
- Nested/complex input *documents* fall back to `--input` JSON (documented limitation, orthogonal to nested command *paths*).
- Command paths are a second naming space beside tool IDs; the mapping is explicit in the descriptor, and the help/discovery surfaces show both.

### Risks

- Flag-name collisions with future host flags → the reserved set is a closed contract list, versioned with the spec; build re-validation on daemon upgrade surfaces new conflicts as diagnostics.
- Confusing `extension exec` (commands) with `tool invoke` (raw tools) → docs present `exec` as the operator path and `tool invoke` as the low-level path; both hit the same runtime.
- `/` mistaken for a filesystem path, or typed as a space (`--cmd review fetch`) → unknown-path errors print the group's leaves and a did-you-mean suggestion computed from the installed command index.

## Implementation Notes

`ExtensionCommandSpec` and `ExtensionCommandGroupSpec` live in `internal/extension/contract` (the codegen source; generated into both SDKs like the describe schema — ADR-003). Manifest: `command` block on `ToolConfig` plus `[[resources.command_groups]]`. Daemon: aggregated read model for `GET /api/extensions/commands` derived from active tool descriptors and manifest groups (no new storage — projection only); descriptor `Flags` serialize in canonical lexicographic order by flag name, and the descriptor's `ApprovalRequired` field is static approval metadata mirrored from the tool descriptor — invoke-time policy remains authoritative. CLI: `extension exec` + `extension commands` in `internal/cli`, two-phase flag parse (host flags → descriptor flags), output via the existing bundle renderer.
