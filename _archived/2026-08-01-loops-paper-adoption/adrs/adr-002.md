# ADR-002: Gate-rejection re-attempt semantics (livelock and DoD `next_generation` fix)

## Status

Accepted

## Date

2026-08-01

## Context

Two confirmed defects in the succeeded-generation rejection paths (validated 2026-08-01 against
current code):

1. **In-body gate reject livelock.** On `RouteRevise`/`RouteNextGeneration` the gate node itself is
   marked failed (`control_gate.go:182-184`), so the default `failed_only` re-attempt re-queues the
   gate + its dependents (`coordinator_generation_reattempt.go:131-141`) while upstream producers
   are carried forward succeeded with byte-identical `OutputRef`s. The gate re-evaluates unchanged
   inputs → same verdict, generation after generation, while `Revision: max(0, generation-1)`
   (`control_gate.go:134`) climbs to `max_revisions` → `exhausted`. A livelock that burns
   generations and budget.
2. **DoD `next_generation` terminates the run.** All-succeeded → `definitionOfDoneTerminal` →
   `terminalFromDefinitionOfDoneVerdict` maps `RouteNextGeneration` to
   `Terminal{Status: failed, Cause: contract}` (`control_contract_gate.go:127-133`); the plan
   carries no `NextCoordinator` and `StatusFailed` is terminal (`service_types.go:58-59`,
   `coordinator.go:160-170`). The route literally named `next_generation` ends the run — a contract
   violation of the route vocabulary.

The only succeeded→fresh-generation path today is contract `stop_when`
(`coordinator_generation.go:246-268`), which wipes all outputs.

## Decision

1. **`revise` rerun-roots are the producers of ALL route-causing gates.** When gates route
   `revise`, the re-attempt rerun set becomes the deterministic UNION of transitive ancestor nodes
   across every route-causing gate (persisted as `route_cause_rank`, peer-review B-003) plus those
   gates and their dependents — producers re-run with `previous.*` repair context (ADR-001)
   instead of being carried forward byte-identical. For metric gates, carry-forward seeding
   follows ADR-003 (seed from best when a baseline exists).
2. **`RouteNextGeneration` starts a generation on BOTH surfaces (peer-review B-002).** In-body
   gate `next_generation` and DoD `next_generation` each build a fresh full-body generation plan
   (same builder as `stop_when`) carrying the verdicts into `previous.verdicts.*`/
   `previous.route_causes` — origin `gate_next_generation` (in-body) or `dod_retry` (contract
   gate). The in-body action is deliberately full-body (fresh pass) while `revise` stays
   producer-scoped — two distinct verbs, two distinct semantics, neither livelocks. The
   `Terminal{failed, contract}` mapping is deleted. `iteration_cap`, budgets, stall detection, and
   `max_revisions` continue to bound the run; when the cap is already reached the existing
   `iterationCapTerminal` fires (`exhausted`), never a silent loop. Tests assert exact terminal
   outcomes per scenario — never `done|exhausted` alternatives.
3. **Delete targets** (greenfield, no compat): the `RouteNextGeneration → Terminal` branch in
   `control_contract_gate.go:127-133`; the blank-output revise seeding behavior in
   `coordinator_generation_reattempt.go:240-245` (superseded by repair-context seeding).

## Alternatives Considered

### Alternative 1: Keep terminal behavior, rename the route

- **Description**: Rename DoD `next_generation` to `fail` so the vocabulary stops lying.
- **Pros**: Trivial; honest naming.
- **Cons**: Removes the only DoD-driven iteration affordance; contradicts the Loop contract
  (goal → act → verify → **iterate when verification says not done**); leaves the livelock.
- **Why rejected**: The route's intent is correct — the implementation is missing. The Loop domain
  glossary defines iteration as what happens when verification says "not done".

### Alternative 2: Re-run the full body on any gate rejection (`full_body` semantics)

- **Description**: Treat rejection as generation failure and re-run everything.
- **Pros**: Simple rule; no producer-set computation.
- **Cons**: Throws away expensive succeeded work unrelated to the rejecting gate (parallel branches
  that passed); ignores the existing `failed_only`/`full_body` strategy distinction.
- **Why rejected**: Producer-scoped rerun preserves unrelated succeeded outputs and matches the
  paper's targeted-repair shape; `full_body` remains available as an explicit strategy.

## Consequences

### Positive

- `revise` becomes a real repair loop (changed inputs each revision) instead of a livelock.
- DoD gates gain the iterate-on-reject behavior their route vocabulary promises; run outcomes stop
  misreporting `failed/contract` for "not done yet".

### Negative

- Rejection re-runs cost real work (producers re-execute) — bounded by `max_revisions`,
  `iteration_cap`, and budgets, and now that work is non-wasted by construction.
- Behavior change for any existing definition that (accidentally) relied on DoD rejection
  terminating the run — acceptable in greenfield alpha; `halt` remains the explicit stop route.

### Risks

- Producer-set computation on dense graphs re-runs most of the body — documented; authors can
  restructure gates closer to producers or use `full_body` deliberately.
- Interaction with `ReattemptFailedOnly` child-run preservation (`ChildLoopRunID` carry rules) —
  covered by dedicated re-attempt tests in `_tests.md`.
