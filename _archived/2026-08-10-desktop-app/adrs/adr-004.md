# ADR-004: Three-platform launch reusing organization signing credentials; own-domain hot update path

## Status

Accepted

## Date

2026-08-09

## Context

The initial platform plan considered staging (macOS+Linux first) to dodge Windows code-signing lead time. A credentials inventory (read-only audit via the GitHub CLI against the `compozy` org and the legacy `compozy/compozy-code` repo) found the premise false: the org already holds a complete, working Windows signing setup (Azure Trusted Signing service principal — tenant/client/secret, account `compozy-signing`, profile `CompozyCodeSigning`) with exactly the variable names the legacy signer script consumes, plus the macOS Developer ID certificate and notarization credentials (under legacy variable names). What does **not** exist anywhere: an update-feed signing keypair (the legacy desktop pipeline never ran), and visibility of these org secrets to the `compozy/compozy` repo (they are scoped to the legacy repo only). Object-storage credentials for the `releases.compozy.com` distribution domain also exist at org level.

## Decision

1. **v1 launches on all three platforms simultaneously**: macOS (arm64 + x64, signed and notarized), Windows x64 (signed), Linux x64.
2. **Reuse the organization's existing signing material**: Windows signing as-is; macOS credentials via variable-name remapping (legacy-era names → the names the new bundler reads). An org admin grants the new repo visibility to these secrets (or copies them) — an administrative prerequisite, not a procurement one.
3. **Generate a brand-new update-feed signing keypair** with documented custody (backup + rotation procedure written before first public release). Nothing legacy to inherit; clean chain of trust from day one.
4. **The hot update path (feed + payloads) is served from the organization's own storage/domain** (`releases.compozy.com`), keeping a single origin of availability and trust for the entire update flow, with stable URLs independent of code-hosting choices. The code-hosting release page remains the canonical archive of versions, out of the updater's hot path. Fine-grained artifact placement is a TechSpec decision.

## Alternatives Considered

### Alternative 1: Staged launch (macOS+Linux first, Windows later)

- **Description**: Ship Windows only after acquiring signing credentials.
- **Pros**: Decouples launch from a procurement dependency.
- **Cons**: The dependency turned out not to exist — credentials are already provisioned and battle-named.
- **Why rejected**: Premise invalidated by the credentials audit; staging would delay a platform for free.

### Alternative 2: Host the update feed with the code-hosting releases

- **Description**: Serve the update manifest and payloads from the release page infrastructure.
- **Pros**: Zero additional infrastructure; feed generated by release tooling.
- **Cons**: Update availability coupled to repo visibility and a second provider; egress pricing and URL stability outside our control; split origins if payloads move later.
- **Why rejected**: Own-domain single-origin path is equally serverless (static objects), uses credentials we already hold, and keeps the in-app endpoint stable forever.

## Consequences

### Positive

- No platform staggering; Windows users are first-class at launch.
- Signing/notarization path is inherited, not invented; the only new cryptographic artifact is the update keypair (which must be new anyway).
- Update endpoint stability decoupled from code-hosting decisions.

### Negative

- Two administrative gates enter the critical path: org-secret visibility grant, and update-keypair generation + custody documentation.
- Own-domain distribution adds one upload/verification step to the release pipeline.

### Risks

- Lost update-signing private key = installed base can never update again → mitigated by mandated custody/backup/rotation documentation as a launch gate.
- Notarizing an app that carries nested executables has a known sharp edge → TechSpec must own the signing order.

## Implementation Notes

Windows arm64 stays out (the runtime build matrix excludes it). Variable remapping (three macOS names) can happen in workflow env-mapping without touching org secret values. The legacy repo's never-executed desktop release workflow and its Windows signer script are reference material for the new pipeline.
