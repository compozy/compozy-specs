# ADR-002: Hybrid attach-first runtime relationship with guided provisioning

## Status

Accepted

## Date

2026-08-09

## Context

The desktop app needs a running CompozyOS runtime. Two user populations exist: CLI users who already run the daemon (possibly with active agent sessions and a single-writer local store under one `COMPOZY_HOME`), and new users whose first contact is the desktop download. The runtime is a shared user resource — two daemons contending for one home is a data-integrity problem. Industry precedent for local-runtime apps (Ollama, Docker Desktop) converges on attach-first with explicit version handshakes and the rule "never kill a daemon you did not start".

## Decision

The app resolves its runtime **attach-first, provision-if-absent**:

1. If a healthy runtime for the active home exists, attach to it. The app never stops, restarts, or replaces a runtime it did not start.
2. If none exists, the app provisions one through a guided first-run flow (using the product's existing install channels/mechanisms) and starts it.
3. Version compatibility is checked before rendering; incompatible skew is a first-class UI state with a recommended action.

## Alternatives Considered

### Alternative 1: Companion-only (require pre-installed CLI)

- **Description**: The app refuses to run without an operator-installed runtime.
- **Pros**: Smallest engineering scope; zero provisioning surface.
- **Cons**: "Downloaded the app and it demands another install" is a hard wall for new users; the desktop app cannot serve as a first-contact channel.
- **Why rejected**: Kills the new-user story the desktop app exists to improve.

### Alternative 2: Standalone bundle (app embeds and owns the runtime)

- **Description**: The app ships its own runtime copy and always manages it.
- **Pros**: Best possible first-run ("it just works"); single artifact.
- **Cons**: Two runtime owners on machines that also use the CLI; version skew between embedded and CLI-installed runtimes over one home; update-ownership collisions; heaviest bundle.
- **Why rejected**: The conflict cases identified in research (shared home, single-writer store, live agent sessions) are data-integrity risks, not just UX ones.

## Consequences

### Positive

- Both personas served without runtime ownership conflicts.
- Existing CLI workflows unaffected; the app is a good citizen on machines it does not own.
- Provisioning reuses the already-shipped install channels — one installation truth.

### Negative

- First-run for new users includes a visible provisioning step (guided, but not invisible).
- The app must implement discovery, health, and version-handshake states rather than assuming a bundled runtime.

### Risks

- Provisioning flow failure modes (offline, permissions) need honest error states — covered as PRD business rules.
- Home isolation (`COMPOZY_HOME`) must be respected in discovery, or the app misbehaves for operators running isolated homes.

## Implementation Notes

The daemon already exposes the attach protocol pieces: discovery record, PID/start-time liveness, single-instance lock, versioned status. Whether provisioning drives the existing install script or a bundled payload is a TechSpec decision.
