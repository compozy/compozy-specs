# ADR-001: Attention state model — two distinct needs-you states plus server-derived done/seen

## Status

Accepted

## Date

2026-08-15

## Context

A session that stops to ask the operator a question is indistinguishable today from a session doing work: pending clarifications never feed the canonical badge, so the session shows `running`. Herdr (the parity target) collapses "needs permission" and "asked a question" into a single `blocked` state because its screen-parsing detection cannot tell them apart, and derives a `done` state ("finished while you were not looking") exclusively server-side from an AgentState + `seen` bit. Market evidence (Cursor unclearable badges, Codex desktop badge with no in-app dismiss) shows every client-owned read-state implementation breaks and destroys trust in the signal.

## Decision

1. The attention vocabulary distinguishes **`waiting-for-input`** (session asked a question) from **`waiting-for-auth`** (session requested permission). Both belong to one visual "needs you" class but remain separate states, because the required response action differs (type an answer vs approve/deny) and Compozy has first-class knowledge Herdr lacks.
2. **`done`** means "finished while unseen" and is **derived only by the daemon** — never reportable or writable by agents or clients. Focusing the session's window in the web UI marks the session seen (auto-clear, no manual dismiss). Passive reads — CLI status/list, agent read tools — never mark seen (Herdr's "CLI reads don't mark seen" rule), so orchestrators cannot steal the human's unread marker.
3. `done` **satisfies `idle`** in orchestration wait predicates: attention is a presentation-layer concept and never leaks into orchestration semantics (Herdr parity).
4. The "needs you" class is `waiting-for-input | waiting-for-auth | failed`. `done` is a separate "finished, unseen" class and never inflates needs-you counters.

## Alternatives Considered

### Alternative 1: Single collapsed `needs-input` state (Herdr's `blocked`)

- **Description**: Merge permission and question into one token.
- **Pros**: Smaller vocabulary; exact Herdr parity.
- **Cons**: Throws away signal the runtime already has; human and orchestrator cannot tell "one-click approve" from "compose an answer" without opening the session.
- **Why rejected**: Herdr collapses out of detection weakness, not product preference. Compozy knows the difference natively.

### Alternative 2: Client-side read tracking (web owns seen state)

- **Description**: The web client records which sessions were viewed and derives `done` locally.
- **Pros**: No daemon/storage change.
- **Cons**: Breaks across clients and restarts; the documented market failure mode (badges that never clear).
- **Why rejected**: Every shipped client-side implementation is broken in the field; multi-client and CLI/agent surfaces need one authority.

### Alternative 3: `done` as a distinct waitable orchestration state

- **Description**: Wait predicates treat `done` and `idle` separately.
- **Pros**: Orchestrators could wait specifically for "finished and unseen".
- **Cons**: Couples a UI attention concept to orchestration semantics; whether a human glanced at a window changes agent control flow.
- **Why rejected**: Attention must stay presentation-layer; Herdr enforces the same split deliberately.

## Consequences

### Positive

- Honest dots: asking, blocked-on-permission, failed, finished-unseen, working, and idle are all distinguishable at a glance and over structured surfaces.
- One authority for seen-state eliminates the desync class of bugs; auto-clear on focus needs no dismiss UX.
- Orchestration predicates stay stable regardless of human viewing behavior.

### Negative

- Vocabulary grows (one new state plus a derived class); every surface that renders or filters states must be updated in the same change (greenfield hard cut, no aliases).
- Seen-state requires durable per-session storage and a schema change.

### Risks

- Precedence ambiguity when a session simultaneously has a pending question and a pending permission → the spec must define a total precedence order.
- Multi-client seen semantics (two browsers open) → first focus wins for all clients; must be explicit in the design.

## Implementation Notes

Stage 2 defines the badge derivation precedence, the durable seen/read markers, and the restart-durability of pending question/permission state. Greenfield rule applies: no aliases or dual fields for renamed/extended vocabulary.
