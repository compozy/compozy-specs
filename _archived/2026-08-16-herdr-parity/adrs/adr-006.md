# ADR-006: Shortcut chord defaults move to the daemon

## Status

Accepted

## Date

2026-08-15

## Context

Default chords live only in the web registry (`window-manager-command-registry.ts`); the daemon stores and validates overrides alone (`internal/windowmanager/shortcuts.go`). Consequences today: the daemon cannot detect override-vs-default (shadowed) conflicts — only override-vs-override; `compozy config get` cannot show the effective keymap, so agents have no discovery path (SD-011 violation); the cheatsheet's truth depends on the web bundle; and a preset preview cannot be validated server-side against the real defaults. Shortcuts v2 (arrays, ranges, preset, new actions, migrated shell chords) multiplies every one of these gaps.

## Decision

Chord defaults become daemon-owned: the `internal/windowmanager` package declares the default keymap (action → default binding, including range families), validation diagnoses conflicts across the full effective map (defaults + overrides, arrays and range expansions included), and `GET /api/settings/window-manager` serves the effective keymap (default, override, effective per action). The web registry keeps only UI metadata (labels, grouping, `needsFocusedWindow`) and consumes daemon truth for chords; CLI `compozy config get` exposes the same effective view.

## Alternatives Considered

### Alternative 1: Status quo — defaults only in TypeScript

- **Description**: Keep defaults web-side; Go validates overrides blindly.
- **Pros**: No refactor.
- **Cons**: Shadowed conflicts stay undetectable server-side; agents cannot discover the keymap; preset validation is client-trust; two sources of truth as the map grows past 50 actions.
- **Why rejected**: User decision (grill T7); SD-011 requires agent-discoverable state.

### Alternative 2: Generated shared artifact (defaults JSON consumed by both sides)

- **Description**: One generated file both runtimes embed.
- **Pros**: Single authored source without moving ownership.
- **Cons**: Adds a codegen artifact and drift gate for data the daemon must interpret at validation time anyway; the daemon still ends up owning it operationally.
- **Why rejected**: Moving ownership outright is the same work with one fewer artifact.

## Consequences

### Positive

- Complete conflict diagnosis (blocked and shadowed) in one validator, arrays/ranges included; config writes fail with full truth.
- Effective-keymap discovery through settings API and CLI — agents and the cheatsheet read the same truth.
- The preset preview diffs against daemon-known defaults.

### Negative

- One-time migration of ~40 default chords into Go and a settings payload extension; the web registry type narrows (chords removed) — a hard cut, no dual ownership period.

### Risks

- Web/daemon default drift during the cut → the settings payload becomes the only chord source for the web in the same change; a parity test asserts the TS registry carries no chord literals afterward.

## Implementation Notes

The Go allowlist grows to the full v2 action set in the same change (it is a hard wall — unknown ids reject config writes). Range families get explicit prefix rules (`desktop.switch.1..9` separate from the `window.tab.jump.1..8` bound).
