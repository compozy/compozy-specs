# ADR-006: Lifecycle Safety — Bootstrap Contract, Two-Step Removal, Branch Preservation, Reconcile-Never-Cascade

## Status

Accepted

## Date

2026-08-11

## Context

Destructive lifecycle is the market's most-burned surface: a desktop "Archive" that force-removed dirty worktrees drew a public data-loss report; Conductor rewrote archiving to snapshot everything first; Superset markets "never deletes worktrees behind your back" as a feature (analysis `05_analysis_market-worktree-ux.md`). The local references supply the safety patterns: herdr's two-step dirty escalation with a machine-readable refusal code and its never-delete-the-branch rule; synara's ownership markers gating every automated deletion and its namespaced temporary branches with compare-and-delete reclamation; t3code's client-side `force: true` one-shot removal as the negative example; paperclip's assess → list blockers → explicit override cleanup shape.

A second failure class is "born broken": a fresh worktree has no environment files, no dependencies, no build cache, and colliding ports — practitioners measure minutes of manual setup per worktree, which cancels the parallelism the feature promises. The near-universal market answer is a declarative copy list for ignored files plus a post-create hook.

Compozy-specific hazard: the workspace registry currently *unregisters* any workspace whose root disappeared, cascading deletion of its runtime records — so an out-of-band `git worktree remove` would today destroy history if worktrees reused that path (analysis `04_analysis_compozy-workspace-baseline.md`).

## Decision

**Bootstrap (creation side).**

- Every created worktree runs the **bootstrap contract**: a declarative copy list carries designated ignored files (environment files, local configs) into the new tree, and a **post-create hook event** fires so extensions, hooks, and a configurable setup command can provision it (install dependencies, allocate ports). Adopted external worktrees do **not** re-run bootstrap by default. *Scope clarified 2026-08-12 (peer-review B-012, operator decision):* the recorded-and-visible setup outcome (`setup_state`/`setup_error`) covers exactly the config-owned copy list + setup command; extensions and hooks reacting to the creation event are fail-open observers whose outcomes live in their own logs/records and never gate or mark the worktree's setup state. A first-class extension-provisioner surface is a post-v1 additive increment.
- A worktree renders as **pending until materialization succeeds** — never as ready before the checkout exists (truthful UI); creation failures roll back cleanly and report what happened.

**Removal (destruction side).**

- Removal is **two-step**: a clean worktree removes directly (with confirmation naming the target); a dirty worktree — or one with unpushed unique commits — refuses with a deterministic, machine-readable reason, and only an explicit second confirmation that names what will be lost proceeds.
- **Branches are never deleted by worktree removal.** Only Compozy-namespaced, automatically created branches (from per-run isolation) are ever eligible for automatic reclamation, and only when verifiably unchanged since creation.
- Sessions bound to a worktree **stop before** its removal; their history remains in the parent workspace, and the record of the removed worktree's past work stays inspectable.
- Merged-branch detection (ADR-004) **suggests** cleanup; nothing is ever removed automatically.
- No archive/restore in v1: removal is removal, stated plainly.

**Reconciliation (out-of-band changes).**

- A worktree removed or pruned outside Compozy becomes **missing/stale** — reported truthfully, its runtime records preserved. Reconciliation never cascades deletion of sessions, tasks, or history. The user resolves missing worktrees explicitly (dismiss the record or recreate the checkout).

## Alternatives Considered

### Alternative 1: Archive-preserves-everything (Conductor model)

- **Description**: "Remove" becomes archive: committed + uncommitted + untracked state snapshots to a ref; unarchive recreates and restores.
- **Pros**: Maximum safety and reversibility; the strongest market precedent.
- **Cons**: A full snapshot/restore machine (ref management, restore adaptation when branches moved, setup re-run) lands in v1.
- **Why rejected for v1**: Deferred, not refused — the two-step refusal already prevents silent loss; archive can arrive later without changing the removal contract.

### Alternative 2: One-shot force removal (t3code model)

- **Description**: A single confirm, then `--force`.
- **Pros**: Simplest flow.
- **Cons**: Proven data-loss shape; uncommitted work gone after one click; the exact behavior that drew the public bug report elsewhere.
- **Why rejected**: Violates the safety posture outright.

### Alternative 3: Retention-based auto-sweep (synara model)

- **Description**: The daemon keeps N recent worktrees and reclaims the rest automatically.
- **Pros**: Zero-maintenance disk hygiene.
- **Cons**: Defensible only for invisible per-chat scratch trees; hostile for named, navigable, user-owned worktrees.
- **Why rejected**: Compozy worktrees are first-class user objects (ADR-001); automatic destruction of user-visible objects is out.

## Consequences

### Positive

- No silent data loss path exists: every destructive transition is explicit, named, and refusable.
- The bootstrap contract removes the "born broken" tax and gives extensions a first-class provisioning hook — the capability stays extensible instead of hardcoding provisioning.
- Out-of-band git usage stays safe: Compozy observes and reports; it never punishes.

### Negative

- Stale/missing worktree records require a resolution surface (dismiss/recreate) instead of self-cleaning.
- Two-step refusal adds friction to bulk cleanup of genuinely dirty worktrees — accepted deliberately.

### Risks

- Per-run automatic worktrees (ADR-003) accumulate if runs end without cleanup; merged-detection suggestions and the namespaced-branch reclamation eligibility are the containment, and the worktree list must keep footprint visible (ADR-005).
- Hook-based provisioning is fallible user code: bootstrap failures must be first-class, observable outcomes — a worktree whose setup failed is usable-but-flagged, never silently "ready".
