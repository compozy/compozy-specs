# ADR-007: Worktree Storage — Global `worktrees` Table Plus Nullable Binding Columns

## Status

Accepted

## Date

2026-08-11

## Context

ADR-001 fixed the product model: a worktree is a nested sub-context of exactly one workspace, never a workspace row and never a session attribute. The TechSpec must now fix where that entity lives physically. The binding facts, verified at HEAD `7fc534a0`:

- Every runtime FK (sessions, tasks, task_runs, bridges, automation) points at the **registry** workspace id in the global `compozy.db` (`internal/store/globaldb/schema/definitions/20_sessions.sql:104`, `72_task_runs.sql:77`).
- `Resolver.List` destructively prunes any `workspaces` row whose root vanished, cascading session/task deletion (`internal/workspace/resolver_reconcile.go:9-49`) — an out-of-band `git worktree remove` would destroy runtime history if worktrees were workspace rows.
- The per-workspace database `<root>/.compozy/compozy.db` exists but is empty scaffolding (`internal/store/workspacedb/schema/schema.sql`), and it cannot be an FK target for `sessions`/`task_runs`, which live in the global store.
- The durable workspace identity file is a working-tree file; every checkout of the repo carries the parent's (`internal/workspace/identity.go:106-108`) — worktree identity can never come from the checked-out tree (ADR-001).
- Competitor evidence: path-as-identity forces fragile normalization everywhere (synara/t3code, analyses 01/02); t3code's thread-attribute model makes "which threads use worktree X" unanswerable server-side (`.resources/t3code/apps/server/src/persistence/Migrations/005_Projections.ts:27` plus the client-side orphan heuristic it forces).

## Decision

1. **New `worktrees` table in the global store** (`internal/store/globaldb`), declarative fragment + appended Goose migration (next in sequence). One row per Compozy-created or adopted worktree. Discovered-but-not-adopted worktrees get **no row** — they are derived live from git and merged into read payloads.
2. **Identity**: `wt_<16-hex>` minted by the runtime (`generateID("wt")` pattern from `internal/workspace/registration_id.go`). The filesystem path is mutable metadata. No identity file is ever written into or read from the worktree's tree.
3. **Binding columns, not side tables**: `sessions.worktree_id TEXT NULL REFERENCES worktrees(id)` and `task_runs.worktree_id TEXT NULL REFERENCES worktrees(id)`, each with a lookup index. A binding is a single scalar per row — a side table would model a many-to-many that does not exist, and JSON metadata is forbidden for matchable state (L-003).
4. **Lifecycle states are rows that persist**: `pending → ready → (missing | removed) → dismissed`, plus `failed` for creation that could not materialize after a daemon restart. `removed`/`missing`/`dismissed` rows are tombstones: history stays readable and named (US-026 AC-3, US-028), and nothing ever dangles. Deleting the parent workspace cascades its worktree rows (`ON DELETE CASCADE`), matching US-028 EC-3.
5. **Reconcile-never-cascade quarantine**: the workspace prune-on-list path is never extended to worktrees. Worktree reconciliation runs against `git worktree list` + disk and only ever flips `state` to `missing`; it deletes no rows and no dependent records (ADR-006).
6. **Git-derived status lives in a `worktree_status` side row** (last-known snapshot + `refreshed_at` + explicit read-error), and forge-derived state in `worktree_forge_status` — separated from the identity row because they update on a different cadence, may be entirely unknown (NULL = unknown, never zero), and are workspace-scoped read models rather than lifecycle authority.

## Alternatives Considered

### Alternative 1: `workspaces` row with a `kind`/`parent_id` discriminator

- **Description**: Reuse the existing table; worktrees become self-referencing workspace rows.
- **Pros**: Session FKs, scope object, and CRUD plumbing work unchanged; herdr proves the UX shape.
- **Cons**: Inherits the prune-on-list cascade (data loss on out-of-band removal); collides with cross-workspace exact-match policy; inherits UNIQUE(name) globally; every workspace consumer must now filter kinds; ADR-001 already rejected the product model.
- **Why rejected**: The two hazards (prune cascade, policy denial between parent and child) attack the feature's core safety and inheritance promises.

### Alternative 2: Rows in the per-workspace database (`workspacedb`)

- **Description**: Worktree rows live in `<root>/.compozy/compozy.db`, workspace-local.
- **Pros**: Physically workspace-scoped; the empty DB finally earns its keep.
- **Cons**: `sessions.worktree_id`/`task_runs.worktree_id` cannot FK across database files; nested navigation needs all workspaces' worktrees in one query; the DB lives inside the working tree and is destroyed with the checkout.
- **Why rejected**: The FK sources live in the global store; splitting authority across files buys nothing and breaks referential integrity.

### Alternative 3: Path-as-identity (no id, no table; sessions carry a path)

- **Description**: The synara/t3code model — a nullable path column on sessions/runs.
- **Pros**: Smallest possible schema change.
- **Cons**: No selectable identity (ADR-001 rejection reason); canonicalization bugs on macOS `/private/var`; renames/moves orphan every reference; "which sessions run in worktree X" becomes a string scan.
- **Why rejected**: Contradicts ADR-001 and reproduces the exact fragility both TS competitors pay for.

## Consequences

### Positive

- Out-of-band git operations can never destroy runtime history: the worst case is a `missing` tombstone.
- Every surface (nav, CLI, tools, coordinator awareness) answers "which worktree, which sessions, which runs" with indexed SQL.
- Workspace-scoping is structural: every read path joins through `workspace_id`, so cross-workspace leakage is a query bug, not a modeling gap.

### Negative

- Two new columns on hot tables (`sessions`, `task_runs`) plus three new tables ride one migration; sqlc/codegen surface grows accordingly.
- Tombstone rows accumulate until dismissed; list queries must filter states deliberately.

### Risks

- A worktree row whose path is re-created by an unrelated repo must not silently return to `ready` — restore requires identity re-validation (same common dir), mirroring adoption validation (US-028 EC-2).
- Boot recovery must resolve stale `pending` rows (materialized → `ready`; otherwise rollback artifacts and mark `failed`) so no permanent pending exists (US-001 EC-4).

## Implementation Notes

Schema details, column-by-column rationale, and the exact migration are in `_techspec.md` (Data Models). The prune quarantine lands as a guard in the worktree reconciler, not as a change to `resolver_reconcile.go` semantics for workspaces.
