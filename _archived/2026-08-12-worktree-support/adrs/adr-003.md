# ADR-003: Creation Surfaces — Session, Tasks (Including Per-Run Automation), and Loops; Automation Jobs Deferred

## Status

Accepted

## Date

2026-08-11

## Context

The operator decided v1 includes both manual worktree creation and automatic worktree-per-task, and asked for an explicit mapping of every surface where "run this in a worktree" should be offered (task creation/definition, loop nodes, the session prompt box, "almost every ADE has this").

Analysis `06_analysis_worktree-entry-points.md` mapped Compozy's existing three-tier execution-context grammar: per-session options at create time, a per-task execution setup (whose sandbox policy — inherit/none/ref — is a complete 11-layer precedent across domain, storage, API, CLI, agent tools, configuration defaults, and web form), and per-loop-node options (the run-agent node already exposes a working-directory field). It also established: the task creation modal deliberately carries zero execution options (contract vs execution separation); execution setup is locked while a run is active; a live session cannot change its directory without an explicit fork/restart; the coordinator is intentionally never pinned to a subdirectory; and automation jobs/triggers currently carry no execution-environment field at all.

ADE precedent for the prompt box: t3code's three-item environment selector in the composer, synara's environment menu and `/fork [local|worktree]`, Cursor's `/worktree`, Claude Code's `--worktree` flag and mid-session worktree tool.

## Decision

v1 offers the worktree choice on three surface groups; the fourth is an explicit non-goal.

1. **Session surfaces.**
   - Session creation offers a worktree selector (default: workspace root) alongside the existing workspace choice — including "create a new worktree" inline.
   - The prompt box of a *new/draft* session offers an environment control (workspace root / existing worktree / new worktree), sibling to the existing per-prompt runtime control.
   - A *live* session never changes directory in place: the affordance is an explicit **fork into a worktree** (slash-command and menu action), with a confirmation naming what happens.
   - The headless/CLI session-start path and the agent-facing session-creation tool accept the same worktree choice.
2. **Task surfaces.**
   - The task execution setup gains a **worktree policy** with modes `inherit | none | ref | per_run`, mirroring the sandbox policy's shape and management surfaces (API, CLI, agent tool, configuration default, web form). `per_run` is the automatic worktree-per-task mode: each run gets a fresh worktree.
   - Fan-out (N parallel runs from one task) offers per-run isolation directly — the highest-value parallel case.
   - The task *creation* form stays execution-free (existing contract/execution separation stands); the setup surface owns the policy, and the policy is decided before a run is enqueued (setup stays locked during active runs).
3. **Loop surfaces.**
   - Loops carry a loop-level worktree default (configure dialog + per-run override), following the existing runtime-defaults layering.
   - Agent-executing nodes (`run-agent`, `goal`) get a single **Environment** control that absorbs the existing raw working-directory field — one control, no competing directory fields. Fan-out-scoped worktrees (per parallel branch) are a later increment.
4. **Automation jobs/triggers: explicit v1 non-goal.** Scheduled/triggered runs keep executing at the workspace root. The Synara-style `auto|local|worktree` automation mode is deferred until an orphan-cleanup story for unattended per-fire worktrees exists.
5. **Coordinator: never pinned.** The coordinator always operates at the workspace root and gains worktree *awareness* only (it can see and name active worktrees; it is never confined to one).

## Alternatives Considered

### Alternative 1: Manual creation only

- **Description**: Users create worktrees explicitly; tasks and loops always run at the workspace root.
- **Pros**: Smallest scope; no per-run lifecycle policy needed.
- **Cons**: Agents cannot parallelize their own work; the market's headline use case (worktree-per-task for parallel agents) is absent; contradicts the agent-first premise.
- **Why rejected**: The operator explicitly chose automatic worktree-per-task for v1.

### Alternative 2: Include automation jobs/triggers in v1

- **Description**: Jobs/triggers gain a worktree mode now.
- **Pros**: Unattended runs are precisely where "don't touch my working tree at 3 a.m." matters.
- **Cons**: Unattended per-fire worktrees accumulate with nobody watching; Synara needed a dedicated unattached-worktree cleanup sweep; disk growth is silent.
- **Why rejected**: Deferred until the cleanup story exists; deliberate non-goal, not an oversight.

### Alternative 3: Worktree option on the task creation form

- **Description**: Choose the worktree policy while creating the task.
- **Pros**: One less step.
- **Cons**: Breaks the existing contract-vs-execution separation; execution setup already owns environment policy and is the surface agents manage.
- **Why rejected**: Consistency of the setup surface wins; creation can deep-link to setup.

## Consequences

### Positive

- Every place work starts offers the same mental model: workspace root by default, worktree by choice, per-run isolation where parallelism lives.
- The sandbox-policy precedent gives the task path a complete, already-understood management pattern across UI, API, CLI, agent tools, and configuration.
- The fork-not-mutate rule for live sessions keeps transcripts truthful (file references never silently change meaning).

### Negative

- Three surface groups must ship coherently in one release; a partial subset would present inconsistent mental models.
- `per_run` introduces run-scoped worktree lifecycle (naming, ownership, cleanup eligibility) that manual worktrees don't need.

### Risks

- Session reuse across task runs must distinguish worktree bindings, or a pooled session could execute in the wrong directory — flagged as a correctness risk in the entry-points analysis; the TechSpec must carry it as an invariant.
- Two directory controls on loop nodes (legacy working-dir + worktree) would be a truthful-UI failure; the single Environment control is a hard requirement, not a styling choice.

## Implementation Notes

Surface inventory, owning files, and constraint list live in `analysis/06_analysis_worktree-entry-points.md`. The worktree policy's `per_run` mode has no sandbox-precedent equivalent; where per-run branch naming and cleanup ownership live is TechSpec scope.
