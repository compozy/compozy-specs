# ADR-004: Assisted Exit With an Extensible Forge Layer (Core Git-Local + Bundled GitHub Extension)

## Status

Accepted

## Date

2026-08-11

## Context

Worktrees exist so work can leave them. The market treats merge-back affordances as part of the feature (Crystal's rebase/squash buttons, Conductor's one-click PR, vibe-kanban's merge-to-done), while herdr deliberately cedes the whole area. The operator chose an **assisted exit** for v1 — status plus light finish actions, no in-product diff-review tool — and pointed at the previous Compozy codebase as the primary reference, which analysis `07_analysis_assisted-exit-ui.md` recovered in full: a single self-advancing split button (Commit → Push → Open PR → View PR) with machine-computed disabled reasons, a lean commit sheet, and guarded destructive actions.

On forge integration the operator set an architectural direction: if the capability is tiered, the model must be extensible — the general part lives in core, forge specifics ship as extensions (bundled or not), following the existing pattern where the connectivity core is generic and the specific provider ships as a built-in extension.

## Decision

v1 ships an assisted exit composed of:

1. **Status strip (five fields, truthful):** branch (copyable), dirty state with insertion/deletion counts, ahead/behind (both directions), pull-request state when known (`open | closed | merged`), and an explicit read-failure state. Unknown values render as unknown — never as zero; local status renders immediately, forge status arrives when it arrives.
2. **One computed primary action + a menu:** the primary is always the single next useful step derived from status (Commit → Commit & push → Push → Open PR / View PR), auto-advancing as state changes; the menu lists every action with its own disabled flag and reason; blocked states name their cause. Actions pause, with a stated reason, while the worktree's agent session is executing. Behind/diverged branches block rather than auto-resolve — the product never attempts a rebase or merge on the user's behalf in v1.
3. **Commit sheet:** what will be committed (file count + insertions/deletions — no diff viewer), a message box whose placeholder is honest about generation, and a `Commit` / `Commit & push` split submit.
4. **PR sheet:** header stating `branch → base` with a real base-resolution chain; title/description left blank are generated and staged for review; draft as a peer action; "Open in browser" always present as the zero-credential path; creation is idempotent (an existing open PR is surfaced, not duplicated).
5. **Progress and results:** one updating toast per action with the phase list announced up front, per-step structured outcomes including skip reasons, and exactly one next-step call-to-action on success.
6. **Merged-branch detection suggesting cleanup, two-tier:** forge state (`merged`) when available; local git evidence (branch holds no unique commits / exists on a remote) always. Cleanup is suggested, never auto-run.
7. **Agent participation stages, never fires:** agent-executed actions (write the commit message, open the PR, resolve conflicts) draft a reviewable prompt into the composer; the user sends it.

**Architecture expectation (extensibility):** the runtime core owns everything answerable from local git plus the zero-credential fallbacks (browser compare page, local merged evidence) and defines a **forge provider extension surface**; forge specifics — pull-request state, idempotent PR creation, merged detection via the forge — ship as **extensions**, with GitHub as the first, bundled one. A workspace whose remote has no forge extension shows no PR affordances at all (truthful UI), while every git-local capability keeps working.

## Alternatives Considered

### Alternative 1: Zero-credential only

- **Description**: v1 ships only the browser compare-page path and local merged evidence; no PR state anywhere.
- **Pros**: Fastest to ship; no credential handling.
- **Cons**: No "Merged" signal, no PR state in the strip, no idempotent creation — half the assisted exit disappears; the differentiating loop (agent finishes → PR → merged → cleanup) breaks.
- **Why rejected**: Keeps too little of the value; the extension model makes the forge tier affordable.

### Alternative 2: Multi-forge abstraction in core

- **Description**: Core implements GitHub, GitLab, Gitea behind one provider layer from day one.
- **Pros**: Broadest reach.
- **Cons**: An entire integration layer lands in core for providers nobody asked for yet; t3code's provider-terminology plumbing shows the carrying cost; contradicts the "specifics live in extensions" direction.
- **Why rejected**: The extension surface delivers the same future without the core burden.

### Alternative 3: Full merge-back suite

- **Description**: In-product diff review, rebase-from-base, squash-and-merge buttons (Crystal model).
- **Pros**: Closes the entire loop in-product.
- **Cons**: Adds a code-review tool to v1; auto-resolving divergence from a one-click affordance mutates checkouts in ways users must then debug.
- **Why rejected**: Operator decision; assisted exit covers the essential path.

### Alternative 4: No exit affordances (herdr model)

- **Description**: Create/select/remove only; commit/push/PR stay in the terminal or with the agent, unassisted.
- **Pros**: Minimal scope.
- **Cons**: Ships a one-way door; both research tracks flag the missing return path as the market's read of an incomplete feature.
- **Why rejected**: The exit is the point.

## Consequences

### Positive

- The forge extension surface turns "add GitLab support" into an extension, not a core change — and third parties can do it.
- Every element of the exit surface has a working precedent (old Compozy UI, synara, t3code, paperclip), lowering design risk.
- Truthful degradation is structural: no credential → compare page + local evidence; no forge extension → no PR affordances rendered.

### Negative

- Two-tier behavior means the exit surface must be designed for both states from day one (including copy for "why is there no PR button here").
- A bundled extension carries the extension-lifecycle obligations (manifest, permissions, enable/disable semantics) for a core-feeling capability.

### Risks

- Agent-generated text (commit message, PR body) is async and fallible; the sheets need pending/cancel states, and a hung generation must never hold a git operation open. Carried to the TechSpec.
- Forge state is a network dependency: stale PR state must be marked stale, and per-workspace scoping of cached forge data must be proven leak-free.

## Implementation Notes

The element-by-element reference map (component paths, copy inventory, state machine, safety gates) is `analysis/07_analysis_assisted-exit-ui.md`. The two anti-patterns explicitly not carried over: the previous UI's untruthful "autogenerate" placeholder backed by a constant, and its blanket stage-everything commit. *Clarified 2026-08-12 (peer-review B-011, operator decision):* the rejected anti-pattern is **silent, unlisted** staging — the v1 commit deliberately includes all changes with the scope shown before confirmation, listing untracked additions by name; gitignored files are never staged.
