# ADR-001: Remote access ships as first-party managed connectivity without Compozy-hosted infrastructure

## Status

Accepted

## Date

2026-08-06

## Context

Compozy is locked to the machine it runs on. The daemon has no authentication surface, a non-loopback bind disables the entire API instead of exposing it, the CLI only reaches the local daemon, and the web client is origin-locked. External services (e.g., GitHub webhook deliveries) cannot reach a locally running daemon, and every bridge already forces the operator to build and maintain their own reverse proxy or tunnel with a manually managed public address.

Reference research (Hermes, t3code, OpenClaw, goclaw, opencode, plus market analysis) shows:

- The OpenClaw exposure incident (~40k internet-exposed instances) was caused by the safe remote path being harder than the unsafe one, not by a bad default. If Compozy only documents "bring your own tunnel", users will build footguns.
- Hermes ships remote connection modes but leaves connectivity (tunnels/overlay) entirely to the user; an open feature request shows users want the runtime to own it.
- t3code ships managed connectivity end to end and it is the product's core value for multi-device access.
- n8n built and then discontinued its own hosted tunnel service, pointing users to third-party tunnels instead — a direct precedent against operating relay infrastructure.

## Decision

The MVP delivers both:

1. **Authenticated remote access** to the daemon with named exposure modes and mandatory authentication for any non-loopback reachability.
2. **First-party managed connectivity**: Compozy itself establishes and supervises the private overlay path (operator device access) and the stable public ingress address (webhook delivery), using accounts the operator holds with third-party network providers.

Compozy operates **no hosted infrastructure**: no relay service, no cloud-hosted daemons, no traffic passing through Compozy-operated servers.

## Alternatives Considered

### Alternative 1: Direct remote access only (documentation-only connectivity)

- **Description**: Ship auth + secure bind; document how to set up tunnels manually.
- **Pros**: Smallest scope; no third-party integration surface.
- **Cons**: Webhook ingress remains unsolved in practice; repeats the OpenClaw pattern where users improvise unsafe exposure; bridge pain remains.
- **Why rejected**: The two motivating scenarios (access from anywhere, webhook → Loop) only work out of the box if Compozy owns the connectivity path.

### Alternative 2: Compozy-hosted relay (outbound-only)

- **Description**: Operate a Compozy cloud relay; the daemon dials out, clients and webhooks reach the relay.
- **Pros**: Best possible zero-config UX; no ports, no third-party accounts.
- **Cons**: Requires building, operating, and paying for cloud infrastructure with accounts, availability, and abuse handling; effectively a second product; market precedent against it (n8n discontinued theirs).
- **Why rejected**: Out of proportion for the current product stage. The provider seam (ADR-003) keeps the door open for a relay provider later without rework.

## Consequences

### Positive

- The tweet scenario (full access to the agent fleet from any device) and GitHub-webhook-to-Loop both work without the operator building network infrastructure.
- All traffic flows over infrastructure the operator controls (their machine, their provider accounts).
- Bridges gain a first-party answer to their public-address requirement.

### Negative

- Compozy takes on integration surface with third-party network providers (account linking, lifecycle supervision, failure surfacing).
- Webhook delivery reliability is bounded by the daemon machine's uptime (no store-and-forward; see PRD non-goals).

### Risks

- Provider outages or policy changes affect Compozy users; mitigated by the provider extension seam (ADR-003) that allows alternative providers.
- Managed exposure increases the blast radius of a daemon compromise; mitigated by fail-closed posture and self-audit (ADR-006).

## Implementation Notes

Provider integration mechanics, transport, and endpoint validation belong to the TechSpec. This ADR fixes only the product boundary: managed connectivity in, hosted infrastructure out.
