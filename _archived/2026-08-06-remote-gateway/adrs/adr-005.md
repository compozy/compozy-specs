# ADR-005: Remote client methods and the bounded remote operation matrix

## Status

Accepted (amended after peer-review round 1, blocker B-010)

## Date

2026-08-06

## Context

With the daemon reachable remotely, the product must define which client paths are supported. Compozy's clients are the daemon-served web UI and the CLI (today local-only). References ship: browser access (all), remote CLI/API targets (t3code bearer targets), and an SSH connection method that launches/reuses the backend on a remote machine over SSH and tunnels it locally with zero network exposure (Hermes desktop, t3code desktop).

The user's framing for this feature is explicitly "use the harness from outside in different ways". Compozy's agent-manageability posture (SD-011) additionally requires structured, non-UI paths for operating any capability.

## Decision

Three remote client methods are in scope:

1. **Browser**: the daemon-served web UI reached over the private overlay (always) or the public address (when the UI surface is opted in, per ADR-004), gated by device pairing.
2. **Remote CLI**: the CLI gains named **connection profiles**. A profile is created through the same pairing model (ADR-002) and operates a remote daemon with the same commands, structured output, and streaming as local use — **bounded by a published remote operation matrix**.

   **The matrix is the contract** (added after peer-review blocker B-010, which found "every verb works remotely" irreconcilable with the UDS-only boundary):

   - **Remote-capable**: the operator/management surface the HTTP transport already serves — sessions, tasks (read), loops, memory, settings, bridges, extensions, and gateway management.
   - **Local-only, UDS exclusively**: the agent kernel (`/api/agent/*` — spawn, claim-next, heartbeat, complete, fail, release), hosted MCP and the MCP Host API (`/api/internal/*`), and resource mutation (`/api/resources/*`). These are never mounted on a tier listener.
   - A verb bound to a local-only operation fails against a remote profile with the deterministic `gateway_local_only_operation` error rather than silently acting on the wrong machine.
   - **The gateway owns no queue, scheduler, or claim primitive.** `task.Service.ClaimNextRun` remains the sole claim authority and claim-token fencing is untouched; no remote path may claim, heartbeat, or complete a run.
3. **SSH connection method**: from the CLI, the operator connects to a machine they can already reach over SSH; Compozy launches or reuses the daemon there and makes it available locally for the duration of the connection. Nothing is exposed beyond the local machines on either end. The remote machine must already have Compozy installed; the method uses the operator's existing SSH credentials and configuration.

## Alternatives Considered

### Alternative 1: Browser only

- **Description**: Remote access is exclusively the web UI.
- **Pros**: Smallest scope.
- **Cons**: No terminal workflow for remote daemons; violates agent-manageability (agents would need the UI); leaves the SSH-reachable-server scenario unsolved.
- **Why rejected**: Contradicts SD-011 and the user's stated intent.

### Alternative 2: Defer the SSH method to a later phase

- **Description**: Ship browser + remote CLI; add SSH later on the same profile foundation.
- **Pros**: Leaner first delivery.
- **Cons**: None structural — it is a scoping choice.
- **Why rejected**: User decision — the PRD captures full scope; sequencing belongs to the TechSpec/tasks decomposition, and manual tunneling in the meantime is not the product experience being specified.

## Consequences

### Positive

- Every operator workflow (browser, terminal, automation/agents) works against a remote daemon within a published, enforced boundary.
- The SSH method covers the "server I can SSH into" case with zero exposure and no provider account at all — and it is the supported path for the local-only operations, since it makes the operator effectively local.
- One pairing/auth model backs all client methods — no per-method credential systems.

### Negative

- The CLI grows a connection-target dimension (profile selection, local vs remote indication) that every command surface must respect.
- Remote parity is bounded rather than total: agent-kernel work requires local or SSH access. This is stated up front instead of discovered at runtime.
- The SSH method inherits SSH's environment variability (key agents, host configs, platform differences) as a support surface.

### Risks

- Divergence between local and remote CLI behavior; mitigated by the published matrix, the deterministic `gateway_local_only_operation` error, and parity suites over the remote-capable set.
- Pressure to "just add" a remote task path later; mitigated by the explicit invariant that the gateway owns no queue/scheduler/claimer, tested at the boundary.
- SSH-launched daemons left running unintentionally; mitigated by explicit lifecycle rules (reuse detection, stop-only-what-we-started teardown) in the PRD stories.

## Implementation Notes

Profile storage, credential handling, SSH mechanics (launch, readiness, reuse, teardown), and command-parity enforcement belong to the TechSpec. Reference implementations to study are cited in the PRD references.
