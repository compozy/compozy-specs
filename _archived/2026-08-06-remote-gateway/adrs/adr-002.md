# ADR-002: Single-operator identity with per-device pairing and revocable device sessions

## Status

Accepted

## Date

2026-08-06

## Context

Compozy's trust boundary today is the operating-system account running the daemon (`SECURITY.md`). Remote access introduces callers that are not on the machine, so the product needs an identity model. The candidate models observed in references:

- **Password/basic credentials** (Hermes trusted-LAN mode): familiar, but a shared memorized secret — brute-forceable on an exposed endpoint, revocation means rotating everywhere, and Hermes's own docs restrict it to trusted networks. Hermes also carries a known footgun where sessions silently reset on restart when a signing secret is absent.
- **Static shared token** (opencode): simple, but one credential shared across devices; all-or-nothing revocation.
- **Device pairing with per-device sessions** (Codex Remote, Paseo, t3code): a trusted surface mints a one-time, short-lived pairing artifact; each device becomes an individually named, revocable session. The 2026 market direction, and pairing artifacts are treated as password-equivalent.
- **Multi-user accounts with roles**: a different product (teams), requiring a full permission model Compozy does not have.

## Decision

Remote access authenticates **one operator identity across many devices**:

- A new device joins only through a **one-time, short-lived pairing artifact** (link/QR/code) minted from an already-trusted surface (the daemon machine's local UI or CLI).
- Each paired device becomes a **named, individually revocable device session** visible in a device list with origin and last-activity information.
- Revocation takes effect immediately, including for live connections.
- The daemon machine itself is the **root of trust**: losing all paired devices is recovered by re-pairing from local access on the machine. No password fallback exists.
- No multi-user accounts, roles, or guest access in this feature.

## Alternatives Considered

### Alternative 1: Operator password

- **Description**: One password set by the operator; any device logs in with it.
- **Pros**: Familiar; allows first login from a brand-new device with nothing pre-provisioned.
- **Cons**: Shared secret; brute-force target on public endpoints; revocation is global rotation; restart/session footguns observed in Hermes.
- **Why rejected**: Weakest link for an agent daemon holding keys and shell access; contradicts per-device revocation.

### Alternative 2: Pairing + emergency password fallback

- **Description**: Pairing as primary; optional disabled-by-default password for "no paired device available".
- **Pros**: Emergency escape hatch.
- **Cons**: Reintroduces a guessable credential on the exposed surface; the emergency is already covered by local re-pairing on the root-of-trust machine (or SSH access to it).
- **Why rejected**: The fallback erases the main security benefit of pairing.

### Alternative 3: Multi-user accounts with roles

- **Description**: Full login system with per-user permissions.
- **Pros**: Enables teams.
- **Cons**: New permission model across the entire product; unneeded for the motivating scenarios.
- **Why rejected**: Compozy is single-operator by design today; teams are a separate future initiative (recorded as a PRD non-goal).

## Consequences

### Positive

- No memorized secret exists to phish, leak, or brute-force.
- Compromise containment is per device; the device list gives the operator an auditable inventory.
- Matches the persona decision: one operator, many devices.

### Negative

- A brand-new device cannot join without reaching an already-trusted surface (deliberate trade-off).
- Pairing UX must be excellent (mint, expiry, re-mint) or users will keep long-lived artifacts around.

### Risks

- Pairing artifact interception; mitigated by single-use + short expiry + the new device appearing immediately in the device list with revocation.
- Operator loses the daemon machine itself; out of scope for this feature (machine access recovery is an OS concern).

## Implementation Notes

Credential format, session storage, transport binding, and artifact lifetimes' enforcement mechanics belong to the TechSpec. Product-level defaults (single-use, expiry within minutes) are stated in the PRD business rules.
