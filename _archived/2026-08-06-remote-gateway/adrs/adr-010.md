# ADR-010: Gateway state ownership — Global DB schema, secret ownership, client-local CLI credentials

## Status

Accepted (amended after peer-review round 1, blockers B-004, B-006, B-009, nit N-002)

## Date

2026-08-06

## Context

The feature introduces persistent state: device sessions, provider enrollment/state, pairing artifacts (transient), webhook-reachability bindings, and CLI connection profiles. Exploration established where daemon-global state lives and how secrets are stored.

Findings:

- Three physical SQLite DBs exist: Global (`compozy.db`, `internal/store/globaldb`), Session (`events.db`), Workspace (`.compozy/compozy.db`). The Global DB is the daemon's single operator-global index, opened once at boot; it already holds operator-global tables without `workspace_id` (`app_metadata`, `vault_secrets`, `mcp_auth_tokens`, `model_catalog`, `notifications`).
- The declarative schema for Global uses numbered domain fragments under `globaldb/schema/definitions/`; migrations are append-only Goose files with `atlas.sum` integrity; repositories embed `*repoBase` and are wired in `initializeRepositories`.
- Vault (`internal/vault`) stores encrypted secrets by ref under a closed namespace set (`providers, bridges, automation, mcp, hooks, extensions, sandbox, sessions`); `mcp_auth_tokens` is the precedent for "row holds metadata + a `*_ref` column; the secret material lives in vault".
- There is no separate CLI config file; CLI and daemon share `config.toml`, which supports array-tables written via `OverlayEditor.UpsertArrayTableItem` at global or workspace scope.
- Device sessions are established before any workspace is chosen and operate across all workspaces on a daemon — operator-global, not workspace-scoped.

## Decision

- **Device sessions, provider identity/activation, surface exposure, and ingress bindings persist in the Global DB** via a new schema fragment (`globaldb/schema/definitions/NN_gateway.sql`), an append-only Goose migration, `queries/gateway.sql`, generated sqlc output, and a `GatewayRepo{*repoBase}` in `initializeRepositories`.

- **Schema keys model the tier topology (B-004).** Peer review found the original single-column keys could not represent the MVP state they claimed to own:
  - **provider identity is split from per-tier activation**: `gateway_providers` (one row per installed provider) plus `gateway_provider_activations` keyed `(provider_name, tier)`, so one bundled provider can serve both the private and public tiers. A partial unique index on `tier WHERE desired_state='enabled'` enforces one active provider per tier.
  - **surface exposure is keyed `(surface, tier)`**, because the operator UI is always available privately and may simultaneously be enabled publicly.
  - both state tables carry `desired_state`, `observed_state`, and `generation` for the reconciler (ADR-007).

- **Scope (B-006).** Device sessions, provider identity/activation, and surface exposure are **operator-global with no `workspace_id`** and stay out of the workspace-access policy. **`gateway_ingress_bindings` is the deliberate exception**: webhook triggers and bridge instances are workspace-owned, so the binding stores the subject's resolved `scope_kind`/`workspace_id`, the owner is resolved **server-side** (client-supplied scope is never trusted), agent callers are authorized through the canonical workspace boundary, and cross-workspace bind/unbind is denied. Bindings also carry an `endpoint_generation` so a public-address change invalidates confirmations instead of silently redirecting a sender, and they are removed transactionally when their subject is deleted.

- **Secret ownership (N-002): no new vault namespace.** The daemon's only gateway secret material is the in-table device credential hash. **Provider credentials reuse the existing extension secret-binding contract** — the connectivity extension declares its env keys and the operator binds them like any extension secret — so the feature creates no second secret owner. The previously proposed `gateway` vault namespace is dropped as unused.

- **CLI connection profiles split by sensitivity (B-009)**: non-secret metadata (name, scheme, host, port, default workspace) lives in `config.toml` under a `[[gateway.connections]]` array-table at global scope, written through `OverlayEditor`. The credential itself lives in a **client-local** encrypted file under that machine's `$COMPOZY_HOME/gateway/credentials/<profile>.cred` (mode `0600`) — a remote CLI machine cannot reach the daemon's vault, so a vault ref would be unresolvable there. Removing a profile deletes both. Moving the identity to another client requires the passphrase-protected `connect export|import` bundle; copying `config.toml` alone is intentionally insufficient.

- **Pairing artifacts and stream tickets are transient and in-memory**: single-use, bounded, TTL-expired, and deliberately not durable — a spent or expired artifact is terminal (ADR-002 lifecycle), and persisting them would create rows requiring a sweeper.

## Alternatives Considered

### Alternative 1: A dedicated `gateway.db` physical database

- **Description**: Give the gateway its own SQLite file and migration stream.
- **Pros**: Isolation of gateway state.
- **Cons**: A new migration stream, `atlas.sum`, bootstrap, and integrity suite for a handful of operator-global tables that belong with the daemon's other operator-global state; more surface, no isolation benefit (the daemon opens it anyway).
- **Why rejected**: The Global DB is exactly the operator-global index these tables belong to; precedent (`mcp_auth_tokens`, `vault_secrets`) is direct.

### Alternative 2: Store profile tokens in `config.toml` alongside metadata

- **Description**: Keep the whole profile, token included, in the config file.
- **Pros**: One place; simplest read path.
- **Cons**: A bearer token in a plaintext config file is a secret in the wrong place; violates the redaction invariant (ADR-006) and the vault-by-reference precedent.
- **Why rejected**: Secrets go in vault; the config file holds only non-secret metadata and a ref.

## Consequences

### Positive

- Gateway state sits with the daemon's other operator-global state, reusing the schema/migration/repository machinery unchanged.
- The corrected keys can actually represent one provider serving both tiers and an operator UI that is private and public at once — the durable model restores the state it owns.
- Reusing the extension secret-binding contract avoids a second secret owner for provider credentials.
- Client-local CLI credentials are honest about where a remote client can reach.

### Negative

- A Global DB fragment plus an appended migration and generated sqlc output to author and cover with the fresh/reopen/ahead/integrity/equivalence suites.
- Ingress bindings introduce a workspace-scoped table into an otherwise global feature, so their read/authorize paths need their own coverage.

### Risks

- Operator-global tables leaking across workspaces; mitigated structurally by omitting `workspace_id` on those tables and keeping them out of workspace-scoped read paths.
- Ingress bindings authorizing the wrong workspace; mitigated by server-side owner resolution, rejection of client-supplied scope, canonical workspace-boundary authorization, and explicit cross-workspace denial coverage.
- Orphaned bindings after subject deletion; mitigated by transactional cleanup plus reconcile-time sweeping.
- Migration authored incorrectly breaks boot; mitigated by `eng-schema-migration` discipline, `make codegen-check`, and the existing integrity suites.

## Implementation Notes

Table definitions with per-column rationale, the credential file format, and the array-table schema are specified in the TechSpec data-model section. Migration authoring activates `eng-schema-migration`; the appended migration, declarative fragment, `queries/gateway.sql`, generated sqlc artifacts, and the canonical fresh/reopen/ahead/integrity/equivalence suites move together (nit N-005).
