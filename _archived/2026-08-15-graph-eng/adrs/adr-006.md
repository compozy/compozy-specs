# ADR-006: Bell integration rides the herdr-parity attention pipeline — composed counts, no second spine

## Status

Accepted

## Date

2026-08-16

## Context

The herdr-parity program (in execution at `_worktrees/herdr-parity/.compozy/tasks/herdr-parity/`) is rebuilding the attention system: durable pending-interaction records, badge-derived classes (`needs-you | finished | none`), a `session_attention_changed` event on the catalog stream, presence-lease seen semantics, a redesigned bell with **Needs you / Finished** sections, and a daemon-computed cross-workspace summary (`GET /api/sessions/attention-summary`) that the bell badge and title consume. Its Non-Goals explicitly exclude task/loop attention semantics (herdr `_spec.md:183`) — task approval rows keep their current place as bell rows. graph-eng's S9/S14 decision (loop requests in the bell) must join that architecture, not fork it.

## Decision

1. **One attention spine.** Loop requests do not create a second attention pipeline. They surface in the bell as rows in the **Needs you** section, following the task-approval-row pattern (workspace-labeled, jump = land on the run page's request), composed into the herdr bell's row model.
2. **Counts stay domain-owned and daemon-computed.** The loop-requests inventory response carries `aggregates: { pending }` (the existing loops list-response aggregates pattern). The bell badge/title adds this loop-owned projection to herdr's session `needs_you` count — client-side composition of two daemon-owned counts, never counting from row pages, per-workspace error isolation preserved. herdr's `attention-summary` contract is not modified.
3. **Storage stays domain-owned.** Loop requests persist in the loops stream (they are run/node/item-scoped); `session_pending_interactions` remains session-scoped. The two meet only at the bell/notification layer.
4. **Ephemeral delivery defers to the herdr notifier's pattern.** OS toasts/sound/system escalation for loop requests are out of this spec's scope; the notify path for loop requests in this spec is bridge notification + deep link (ADR-001) plus bell rows. A follow-up may emit loop-request attention transitions through the same client-side notifier once both programs are merged.
5. **Sequencing and the concrete seam.** The graph-eng bell/badge phase depends on herdr-parity's attention core and bell redesign landing on main. Post-merge, graph-eng edits only the `web/src/systems/os` **composition seam** — `use-os-attention.ts` (adds the loops request source) and the bell row model — and never the session-attention **contracts** (the `attention-summary` endpoint and its consumption, session badge derivation, `session_attention_changed` handling, the notifier). "herdr-owned" binds contracts, not file paths, once the program merges. Every other graph-eng phase is independent of herdr-parity.

## Alternatives Considered

### Alternative 1: Extend herdr's `attention-summary` with a loop-requests count

- **Description**: add `loop_requests` to the sessions summary endpoint.
- **Pros**: one endpoint feeds the badge.
- **Cons**: mutates a mid-flight program's frozen contract; puts a loops projection inside a sessions route; couples merge order both ways.
- **Why rejected**: composition of two domain-owned projections is honest, uncoupled, and keeps each contract owned by its program.

### Alternative 2: Reuse `session_pending_interactions` for loop requests

- **Description**: write loop requests into herdr's pending-interaction table.
- **Pros**: single table for "needs a person".
- **Cons**: wrong scope (run/node/item vs session), wrong store stream, wrong lifecycle owner; loop requests already have durable parking in the loops domain.
- **Why rejected**: workspace-data-isolation and stream ownership rules; the loops domain owns its requests.

### Alternative 3: Defer bell integration entirely

- **Description**: run-page only in this spec.
- **Pros**: zero cross-program coordination.
- **Cons**: pending requests invisible outside the run page; the external deep-link becomes the only discovery, which fails the "needs you" product goal (US-007).
- **Why rejected**: user kept bell integration in scope (surface grill S14) with sequencing as the mitigation.

## Consequences

### Positive

- No duplicate attention machinery; the operator has one "needs you" place; both programs merge cleanly in either development order (graph-eng's bell phase simply waits).

### Negative

- The graph-eng bell phase carries a cross-program dependency and lands last.

### Risks

- herdr bell row model changes after this spec freezes → the graph-eng bell phase adapts at integration time; the row contract (workspace label + jump + kind) is stable across both designs.

## Implementation Notes

`_uiux.md` S9 and `_dx.md` (requests `aggregates`) carry the surface half. Sequencing resolution (technical grill, 2026-08-16): **the entire graph-eng spec executes only after herdr-parity merges to main** (user directive), so the bell phase needs no special gate — it integrates directly with the merged, redesigned bell.
