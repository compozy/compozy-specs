# ADR-002: Operator time travel — read-only diff, in-run rerun, cross-run fork

## Status

Accepted

## Date

2026-08-16

## Context

Loop history is fully readable (generations, outputs, verdicts, attempt ledger, replayable event log) but there is no operator verb to compare, re-execute, or branch from it. The engine already performs one backward jump on its own (`ratchet_restore` seeds a new generation from the best one). The lineage model is append-only and forward-only (`parent_generation < generation` CHECK). The frameworks report established that the state of the art is **also append-only** — a LangGraph fork "does not roll back; it creates a new checkpoint that branches from the specified point; the original history remains intact" — so operator time travel does not require breaking the lineage model (`analysis/02_analysis_graph-frameworks.md` §1.1.13). Loop-ideas ideas 18 (re-run from a node) and 19 (rewind) were verified OPEN with the read substrate ready.

## Decision

1. **Three jobs ship**:
   - **Diff (read-only)** — compare two generations of one run, and compare two runs (e.g., a fork against its origin).
   - **Rerun from a node** — re-execute from an operator-chosen healthy node: same run, new generation whose parent is the current one, with a dedicated operator origin. Generalizes the shipped requeue path beyond quarantined nodes.
   - **Fork from a checkpoint** — start a **new linked run** seeded from a chosen historical generation's outputs; declared inputs may be overridden at fork time.
2. **Shape**: rerun stays inside the run; fork always creates a new run with cross-run lineage visible in both directions. Runs remain immutable: no path mutates or deletes an existing generation, and a fork never touches its source run.
3. **Fork surface**: inputs are overridable; node outputs are not individually editable at fork time (point corrections on a live run are ADR-001's amend verb).
3b. **Fork execution semantics (peer-review rounds 1–3, B-001/B-101/B-201)**: the source generation's outputs are written as the child run's **pre-settled seed generation 1** (`origin fork_seed`; no seed cell executes), and **generation 2** is the first executing generation (`origin initial`, parent 1), hydrating `previous.*`/`best.*` from the seed via the unmodified same-run history reader. The canonical start transaction inserts the child at `generation = 1`, reserves the generation-2 coordinator, and applies concurrency policy exactly like a fresh start. Overridden inputs can never coexist with stale derived outputs, and a no-override fork is a well-defined fresh attempt from the same baseline. Selective carry-forward at fork time is explicitly deferred until the execution-identity feature exists.
4. **Invokers**: operators and agents (capability-gated). An agent cannot rerun or fork a run that it started while that run is still executing.

## Alternatives Considered

### Alternative 1: In-run fork with modified inputs

- **Description**: forks become new generations of the same run, including input overrides.
- **Pros**: single-run history.
- **Cons**: breaks run-input immutability; conflates experiment lineage with execution lineage; history of one run becomes a tree of divergent inputs.
- **Why rejected**: "runs are immutable" is the simpler product story and matches the append-only substrate.

### Alternative 2: Mutable rewind (reset the run pointer to generation N)

- **Description**: rewind deletes/deactivates later generations.
- **Pros**: matches naive user intuition of "undo".
- **Cons**: destroys the audit ledger; violates the append-only + CAS design; state of the art does not do this either.
- **Why rejected**: forward-only branching delivers the same outcome with intact history.

### Alternative 3: Operator-only access

- **Description**: keep agents away from time travel.
- **Pros**: smaller risk surface.
- **Cons**: violates SD-011 (agent-manageable by default); agents repairing their own pipelines is a core premise.
- **Why rejected**: capability gating + the self-rerun restriction contain the risk.

## Consequences

### Positive

- The append-only ledger finally pays off: inspection, recovery, and experimentation without any mutation semantics.
- `ratchet_restore` generalizes rather than being duplicated.

### Negative

- The generation origin vocabulary grows by two values (`operator_rerun`, `fork_seed`), each landing in its owning phase's append-only migration (P7 and P8 respectively — never a shared or conditionally-reused rebuild). The briefing's open decision #1 ("batch all origins in one migration") is superseded: its other candidates died by decision, and phase-owned identity beats batching.

### Risks

- Fork sprawl (many abandoned forks) — mitigated by first-class lineage visibility; retention policy stays with the long-run economics spec (Non-Goal here).

## Implementation Notes

Stage 2 decides verb names, route shapes, diff output format, and which origins land in the single enum migration. Diff and rerun are the cheap phase (read substrate + requeue machinery exist); fork is the larger piece.
