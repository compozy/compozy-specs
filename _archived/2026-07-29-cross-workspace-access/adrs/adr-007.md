# ADR-007: Cross-workspace access is anchored on the session PermissionMode — no toggle, no grants

## Status

Accepted (supersedes ADR-002 and ADR-003; amends ADR-001 and ADR-006)

## Date

2026-07-28

## Context

The post-ADR-006 spec was still a parallel consent product: a new `[workspace_access]` config section, a `workspace_access_grants` table cloned from tool-approval grants, four HTTP/UDS routes, four CLI verbs, a four-tool native toolset, a web Settings section, a grant transition-event service, and a dedicated standing system-prompt rule. Pedro's review (2026-07-28, exported Cursor conversation): "ficou complexa demais... não seria melhor ancorar o acesso cross workspace nas permissões default que já temos: approve-all libera tudo, deny-all deny em tudo e a permissão do meio faz o agente perguntar".

The runtime already carries exactly the three-mode model the proposal needs:

- `internal/config` defines `PermissionMode` (`deny-all` | `approve-reads` | `approve-all`); the effective default is `approve-reads` (`internal/session/manager_helpers.go` `startPermissions`; dream sessions are pinned `approve-all`).
- Every session persists its resolved mode in `SessionMeta.EffectivePermissions` and carries it in memory (`internal/session/manager_start.go`), so any seam holding a validated `SessionID` can resolve the actor's mode.
- `permissions.*` is a config trust root: `ClassifyToolConfigPath` returns `ConfigPathTrustForbidden`, so `compozy__config_set` cannot raise a mode (`internal/config/tool_surface.go`, `tool_surface_security.go`).
- The ACP approval bridge (`internal/daemon/tool_approval_bridge.go`) already implements the timeout-bounded `session/request_permission` round-trip with a daemon-computed option set.

## Decision

The source of the cross-workspace decision is the **effective `PermissionMode` of the actor's session**. The central policy (ADR-001) stays; its inputs change:

| Session mode | Cross-workspace outcome |
| --- | --- |
| `approve-all` | allow |
| `deny-all` | hard deny — no prompt |
| `approve-reads` | ask: ACP prompt at the native-tool seam; deny + hint at every other seam |

1. **No new state or surfaces.** The `[workspace_access]` config section, the `workspace_access_grants` table, the workspace-access HTTP/UDS routes, CLI verbs, native toolset, Settings section, grant events, and the dedicated system-prompt rule are all removed from the design (none was implemented). The only persisted input is `EffectivePermissions`, which already exists and is already operator-managed.
2. **Prompt consent is session-scoped and in-memory.** In `approve-reads`, a native-tool denial with a live session triggers the existing approval-bridge prompt with a daemon-computed option set: `allow_once | allow_session | reject_once | reject_session` (ACP kinds `AllowOnce`/`AllowAlways`/`RejectOnce`/`RejectAlways`; "always" is presented and scoped as *for this session*). `*_session` answers land in a daemon-owned in-memory consent cache keyed by session ID, consulted by the policy for **all** seams, and dying with the session. Nothing is written to disk; there is no list/revoke surface — restart or stop clears consent, and the audit trail records every decision.
3. **`deny-all` is a hard deny on this axis.** In tool-approval semantics `deny-all` means "ask for everything"; on the workspace axis it means "never cross". This asymmetry is deliberate: the workspace boundary needs a lockdown setting, and `deny-all` is the only candidate. Documented here and in user-facing docs.
4. **Coupling tool permissiveness with the workspace boundary is the accepted product trade-off.** An `approve-all` session can now cross workspaces without further consent — the "tools open but workspace still isolated" configuration no longer exists. Accepted for the single-operator beta; if evidence demands the orthogonal axis back, that is a new TechSpec.

## Alternatives Considered

### Alternative 1: Keep the ADR-002/003 toggle + grants design

- **Pros**: Orthogonal axes (tool risk vs workspace boundary); durable per-agent consent; three review rounds already hardened it.
- **Cons**: A parallel consent product (table + routes + verbs + tools + Settings + events + rule) for a beta feature; a second permission vocabulary for operators to learn; ~half the implementation program exists only to manage grant lifecycle.
- **Why rejected**: Cost/benefit indefensible against a model the operator already understands; Pedro's explicit call.

### Alternative 2: Anchor on the mode but persist `*_always` consent in `tool_approval_grants` or a new table

- **Pros**: Consent survives restarts.
- **Cons**: Reintroduces the grant lifecycle (list/revoke surfaces, events, Settings) that is the bulk of the cut, or overloads a table whose key encodes tool semantics (rejected already in ADR-003).
- **Why rejected**: Durable consent is what made the previous design heavy; session-scoped consent covers the real case (an agent repeatedly crossing during one task) with zero new surfaces.

### Alternative 3: Once-only prompt (no session consent)

- **Pros**: Absolute minimum state.
- **Cons**: An agent fanning out N cross-workspace calls in one task re-prompts N times; prompt fatigue trains reflexive approval, which is worse for security than a session-lifetime answer.
- **Why rejected**: The in-memory cache is ~a map guarded by the session lifecycle; the fatigue cost is real, the state cost is negligible.

## Consequences

### Positive

- One permission model across tool risk and workspace boundary; operators configure nothing new.
- The implementation program shrinks to: policy core + seam wiring + one bridge extension + one in-memory cache + audit + the phase-0 web deep-link work.
- No schema change, no config change, no OpenAPI/TS surface beyond the phase-0 owner projection, no new CLI/native tools, no Settings work.
- Agent manageability needs no new surfaces: the mode is already agent-visible/operator-managed, and denials remain deterministic (`ReasonWorkspaceAccessDenied` + hint naming `permissions.mode`).

### Negative

- Loses the "permissive tools, isolated workspace" configuration (named trade-off, accepted).
- Session-scoped consent does not survive restarts and has no management UI — by design.
- `deny-all` semantics differ per axis (ask-everything for tools, never-cross for workspaces) — a documentation burden.

### Risks

- **Mode escalation via spawn**: an `approve-reads` parent could spawn a child whose agent definition carries `approve-all` (same-workspace spawn consults no policy) and the child crosses on its own authority. This is exact parity with the existing tool-risk axis (such a child can already run unprompted `bash`); agent definitions are operator-authored and `permissions.*` is trust-root-protected. Accepted; the spawn seam still validates the *crossing* actor's own mode whenever a spawn itself crosses workspaces.
- **Prompt-fatigued approve-reads operators granting session consent broadly**: bounded by session lifetime and audit visibility.
- **Direct config-file edits raising a mode**: pre-existing product gap for all of `permissions.*` (ADR-006 beta posture) — not new to this feature; covered by audit + docs, hard fix remains the future containment ADR.

## Implementation Notes

`internal/workspaceaccess` keeps the ADR-001 shape (typed `Request`, step-zero validation, actor-kind gate, fail-closed) but its dependencies become `ModeSource` (daemon-implemented session-mode lookup; lookup error or unknown session denies) and `SessionConsentCache` (daemon-owned, in-memory), plus the unchanged best-effort `AuditEmitter`. `Decision` gains `PromptEligible` (true only for `approve-reads` misses at any seam; only the native-tool seam acts on it). The TechSpec's decision chain and invariants are the single normative statement.
