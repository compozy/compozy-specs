# ADR-003: Workspace-access grants clone the tool-approval-grant template, fail closed, and prompt only at the native-tool seam

## Status

Superseded by ADR-007 (2026-07-28 — durable grants and the cloned store/CLI/native-tool/Settings surfaces were removed, never implemented. Two decisions survive in the re-anchored design: fail-closed policy errors, and the ACP prompt firing only at the native-tool dispatch seam on the existing approval-bridge layer — now with session-scoped in-memory consent instead of persisted grants)

## Date

2026-07-28

## Context

The repo already ships a complete durable-consent stack for tool approvals: globaldb table + sqlc queries (`internal/store/globaldb/schema/definitions/42_tool_approval_grants.sql`), a domain file (`internal/tools/approval_grants.go`), a daemon decorator service emitting transition events (`internal/daemon/tool_approval_grant_service.go`), core handlers + HTTP/UDS routes, CLI verbs (`compozy tool approvals`), native tools, a web Settings section, and an ACP `session/request_permission` prompt bridge with `allow_once | allow_always | reject_once | reject_always` (`internal/daemon/tool_approval_bridge.go`). Workspace-access grants (ADR-002) need the same lifecycle. Two properties of the template do NOT transfer safely: tool-approval lookups fail open (store error → fall through to prompting the human), and the prompt can fire from any tool call because the bridge lives in the dispatch path.

## Decision

Clone the template across all surfaces with three deliberate deviations:

1. **Fail closed.** A grant-store or config read error inside `Policy.Authorize` denies and emits an error-outcome audit event. Tool approvals may fail open because their fallback is a human prompt; a silent cross-workspace allow has no such backstop.
2. **Prompt only at the native-tool dispatch seam.** The ACP prompt (via a new `workspace_access_bridge` mirroring the approval bridge) fires when a native tool call is denied by policy and the calling session is live. All other seams (agent identity on HTTP/UDS, task authorizers, claim hooks, spawn, coordination) consult toggle + persisted grants only and deny with a hint pointing at `compozy workspace access`. Prompting from arbitrary domain services would require threading a session bridge into packages that have no session concept.
3. **Simpler key.** `UNIQUE(workspace_id, agent_name)` with `agent_name` required — no input digests, no wildcard sentinels, no TTL, no target column (ADR-002: a grant covers all targets).

## Alternatives Considered

### Alternative 1: Reuse the `tool_approval_grants` table with a reserved pseudo-tool id

- **Description**: Store workspace-access consent as rows with `tool_id = "compozy__workspace_access"`.
- **Pros**: Zero schema work.
- **Cons**: Overloads a table whose unique key and lookup ranking encode tool semantics; listing/revoking mixes two products; the fail-open lookup path would govern a security decision.
- **Why rejected**: Storage is cheap; semantic overloading is not. Separate table keeps the fail-closed path auditable.

### Alternative 2: Prompt at every seam

- **Description**: Fire the ACP prompt from identity, task, spawn, and coordination denials too.
- **Pros**: Uniform UX.
- **Cons**: Those packages have no session-bridge dependency today (adding one violates the downward import graph); HTTP identity denials often belong to CLI calls where a blocking 120s prompt is wrong; prompt storms multiply.
- **Why rejected**: The tool seam is where agents actually hit the boundary in practice, and the deny-copy hint covers the rest.

### Alternative 3: TTL/expiry column on grants

- **Description**: `expires_at` for time-bounded consent.
- **Pros**: Auto-expiring exposure.
- **Cons**: Tool approvals shipped without TTL and the model held; all-or-nothing semantics make "revoke" the natural lifecycle verb; TTL adds sweep machinery.
- **Why rejected**: Parity and simplicity; revisit only with evidence.

## Consequences

### Positive

- Operators manage both grant kinds with the same verbs, events, and Settings patterns.
- `allow_once` handles the one-off case with zero persisted state.
- Every persisted transition emits `workspace.access_grant_put/revoked` events like the approval-grant precedent.

### Negative

- Full six-surface budget (store → domain → service → handlers → HTTP/UDS → CLI → native tools → web) per the "No partial-surface completions" rule.
- Non-tool seams have a deny-then-configure UX rather than an inline prompt. Accepted; the hint names the exact command.

### Risks

- Prompt storm when an agent fans out many cross-workspace calls before answering: same-key concurrency is absorbed by the single-flight below; distinct calls after an `allow_always`/`reject_always` answer stop prompting.
- Concurrent or racing consent decisions: **tool-approval parity, accepted (ADR-006).** Rounds 1–2 designed CAS'd revisions, per-target flights, leader/follower settlement, and dispatch-id-bound permits; round 3 found even that incomplete, and the beta-posture decision removed the machinery. The shipped contract mirrors `tool_approval_grants` exactly: plain upsert on the unique key, last-write-wins on `decision`, prompting wired at the same dispatch layer the tool-approval bridge already uses (per-call semantics inherited wholesale, including its `allow_once` scope and re-prompt behavior). Known accepted quirks: a stale prompt answer can overwrite a newer manual mutation, and concurrent same-subject prompts are not coalesced — both visible in the audit trail and revocable. The prompt still carries a daemon-computed option set (workspace-less sessions: once-only) and out-of-set answers deny.

## Implementation Notes

New reason code `ReasonWorkspaceAccessDenied` distinguishes policy denials from identity-spoofing `ReasonScopeMismatch` (which stays for session/agent field mismatches). Grant lookups touch `last_used_at` in the same statement, mirroring `LookupApprovalGrant`.
