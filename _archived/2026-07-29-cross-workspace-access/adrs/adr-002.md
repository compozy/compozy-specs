# ADR-002: All-or-nothing access model — global toggle plus per-agent grants, no pair or capability granularity

## Status

Superseded by ADR-007 (2026-07-28 — cross-workspace access is anchored on the existing session `PermissionMode`; the `[workspace_access]` toggle and per-agent grants were never implemented. The all-or-nothing granularity decision itself survives: still no pair lists, no capability levels)

## Date

2026-07-28

## Context

With a central policy in place (ADR-001), the opt-in sources needed a granularity decision. The design space ranged from per-workspace-pair trust declarations (target workspace lists `allow_from` in its own `.compozy/config.toml`) with `read | full` capability levels, up to a single global switch. Pedro rejected pair/level granularity explicitly: "não precisa desse nível de complexidade, o toggle é 'ou tem acesso a todos' ou não tem", and selected the toggle-plus-prompt runtime model.

## Decision

Cross-workspace access for agent actors is **all-or-nothing** along two axes:

1. **Global toggle** — default off. When on, every agent actor may access every workspace with the same rights it has in its own workspace; when off, isolation is the default. *Storage history: round 2 (ADR-005) moved the toggle to daemon DB state for security; ADR-006 restored the original, simpler `config.toml` key (`[workspace_access] cross_workspace = false`, global-scope-only, not agent-mutable via `compozy__config_set`) after the beta-posture decision — agent reachability of the file is an accepted, documented gap enforced instructionally.*
2. **Per-agent grants** — with the toggle off, a persisted grant keyed `(workspace_id, agent_name)` (the agent's home workspace) with `decision ∈ {allow, reject}` gives or denies that agent access to **all** workspaces. Grants are created from the runtime approval prompt (allow/reject "always") or by the operator via CLI/HTTP/UDS/Settings; they carry no target list, no capability level, and no TTL.

A persisted `reject` grant wins over the global toggle (specific beats general), so one misbehaving agent can be banned while the toggle stays on. There is no `read` vs `full` split: an allowed actor gets full same-as-home rights in the target workspace.

## Alternatives Considered

### Alternative 1: Target-side `allow_from` trust lists (original recommendation)

- **Description**: The accessed workspace's `.compozy/config.toml` declares which workspaces may reach in, optionally with `read | full` level.
- **Pros**: Best blast-radius story (compromised agent in A cannot open B without write access to B's config); trust versioned with the project it protects.
- **Cons**: Per-pair mental model and config babysitting; N×N declarations for the actual use case (one operator's own machine, workspaces that are all theirs); level enforcement forces a capability taxonomy across ~10 seams.
- **Why rejected**: Pedro judged the complexity unjustified for a single-operator local daemon — the threat model is agent misbehavior, not mutually distrusting tenants, and the ban hammer (reject grant) covers the misbehaving-agent case.

### Alternative 2: Toggle only, no runtime grants

- **Description**: One boolean; off = hard deny, on = open.
- **Pros**: Minimal surface.
- **Cons**: Forces the operator to open the whole machine to satisfy one agent's one-off need; no audit trail of who was allowed; no per-agent ban.
- **Why rejected**: Loses the approval-prompt UX Pedro selected, which handles the common "just this once / just this agent" case without flipping the global switch.

### Alternative 3: Per-session CLI override

- **Description**: No prompt; `compozy session new --cross-workspace` marks a session as unrestricted.
- **Pros**: Explicit at spawn time.
- **Cons**: Requires predicting the need before the session starts; no in-flight consent; session flags proliferate.
- **Why rejected**: The prompt model covers the same need reactively and reuses proven approval machinery.

## Consequences

### Positive

- The config surface is one boolean; the grant surface is one `(workspace, agent, decision)` row — both trivially explainable.
- Grant semantics mirror tool approval grants (same wildcard-free subject, same allow/reject vocabulary), so operators learn one model.
- The policy decision chain stays four steps and cheap.

### Negative

- No way to expose only part of a workspace or read-only access; an allow is a full allow. Accepted deliberately.
- A future granularity need (pairs, capabilities) is a new TechSpec, not an extension of this one.

### Risks

- Toggle on + prompt-fatigued operator = broad exposure of every workspace to every agent. Mitigated by: default off, `reject` grants beating the toggle, audit events on every cross-workspace allow, and the deny-copy hint teaching the narrower per-agent grant first.

## Implementation Notes

*Re-simplified by ADR-006:* the toggle is the `workspace_access.cross_workspace` config key; `workspace_access.*` is excluded from `agentMutableConfigKinds` (fail-closed for `compozy__config_set`) and rejected in workspace overlays (global-scope-only). Grant mutation surfaces use the existing guards (loopback HTTP guard, UDS peer-cred, `scope.Operator` on native tools); the standing system-prompt rule instructs agents never to flip the toggle or self-grant, and audit events make violations visible. Remaining reachability is the documented beta gap.
