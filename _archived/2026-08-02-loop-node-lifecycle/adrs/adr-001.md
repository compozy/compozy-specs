# ADR-001: Spec 1 scope — the node lifecycle & failure contract slate

## Status

Accepted

## Date

2026-08-01

## Context

The loop-ideas corpus (`.compozy/tasks/loop-ideas/_briefing.md`) consolidates 37 deduplicated hardening ideas for the loop engine from three competitor analyses (Sim, Temporal, previous-generation Compozy), later extended with a fourth (Mastra) and a defaults deep-dive. The briefing proposes a three-spec train; Spec 1 owns one coherent domain: how a node classifies failure, reacts, retries, times out, stays alive, pauses, cancels, and waits durably. Everything lands after the loops-paper-adoption techspec, whose safety invariants (immutable generations, single coordination authority, repair paths never bypass bounds) bind every decision here.

## Decision

Spec 1 covers nineteen ideas: the briefing's proposed eighteen — commit-gated effect dispatch (3), authorable reactions (1), error routing (2), payload-level failure detection (5), remediation hints (9), author-vs-runtime error distinction (10), predicate failure policy (37), per-node retry (4), opt-in dual timeouts (6), bounded predicate evaluation (36), stale-future-work invalidation (27), per-target breaker (7), quarantine (8), heartbeat with progress checkpoints (13), control signals on the liveness channel (14), cancel ≠ kill with parent-close policy (15), node pause with rule-driven auto-pause (16), durable wait (17) — plus idea 24 (duplicate-suppression claim on watch-event admission), pulled forward from Spec 3 because watch-event redelivery is a today-problem and the idea is small.

Idea 11 (structured-output re-ask) is cut: the generation-level repair cycle and the goal node already own that feedback loop; a third loop would have unpredictable interactions. Idea 12 (graduated stall recovery) is held: it ships only if post-repair-context evidence shows generations repeating identically even with repair context present.

## Alternatives Considered

### Alternative 1: Briefing slate exactly (18 ideas, 24 stays in Spec 3)

- **Description**: Keep admission dedupe with the rest of the ingress domain.
- **Pros**: Purest domain cohesion; Spec 3 keeps all ingress concerns together.
- **Cons**: Watch-event redelivery already happens today (durable-history replay after restart); waiting two specs for a small fix leaves a known correctness hole open.
- **Why rejected**: User pulled idea 24 forward; the briefing itself flags it as small enough to advance.

### Alternative 2: Trimmed slate (defer quarantine, pause, durable wait)

- **Description**: A smaller first delivery covering only classification, routing, reactions, and retry.
- **Pros**: Faster to ship; fewer new states.
- **Cons**: Splits one contract across two specs; operators would get failure handling without any live-repair verbs, and the pause/wait/quarantine interactions with succession would be retrofitted.
- **Why rejected**: The domain is one contract; task decomposition happens later at `cy-create-tasks` granularity, so spec size is not a constraint.

## Consequences

### Positive

- One spec owns the entire "what happens when a node fails, stalls, waits, or dies" story; no cross-spec seams inside the failure contract.
- The dedupe fix closes a live correctness hole without waiting for Spec 3.

### Negative

- Spec 1 is large; the tasks phase must decompose carefully (the briefing already sketches an internal build order).

### Risks

- Scope gravity: fan-out strategies, rollover, inbox, and time-travel verbs are adjacent and tempting — they stay in Specs 2/3 (recorded as non-goals in the PRD).
