# ADR-011: Node-lifecycle persistence — controls row per node, attempt ledger per execution, wait rows per pause point

## Status

Accepted

## Date

2026-08-01

## Context

There is no per-node durable lifecycle row today. `loop_generation_outputs` (PK
`(loop_run_id, generation, node_id, item_index)`) is the only per-node table; its `status` has no
SQL CHECK and it is mutated by two independent writers (`WriteGenerationSnapshot` in
`internal/loop/generation_snapshot.go:57` and `updateLoopNodeOutputStatusWithExecutor` in
`internal/store/globaldb/global_db_task_claim_complete.go:349`). The Goal subsystem already chose a
two-table shape: `loop_goal_checkpoints` (current state) + `loop_goal_turns` (append-only per-turn
ledger). The contract needs three distinct state scopes:

- **Per execution** (one `(generation, node_id, item_index)` cell): attempt counter,
  `next_attempt_at`, first-schedule anchor, authored-deadline anchor, epoch.
- **Per author-node, spanning generations**: pause (US-019), quarantine (US-024), attention flag
  (US-017) — succession must respect them across generation boundaries.
- **Per pause point** (node + branch + iteration): durable waits with single-claim resume
  (US-021).

Workspace-wide inventories (waiting / quarantined / attention, US-022/024/026) must be listable
with pagination and stable ordering — matchable state, which the playbook forbids burying in JSON.

## Decision

1. **`loop_node_controls`** — one row per `(loop_run_id, node_id)`, created lazily on first
   control event. Carries pause state + provenance (actor kind/id, reason, rule id, requested
   at), the durable cancellation state machine (`cancel_state '' → requested → delivering →
   draining → canceled` + actor/reason/requested-at), quarantine state + entry payload
   reference, attention flag + reason + last-evidence timestamp, death-resume streak, and the
   verb-CAS `revision`. Spans generations; the coordinator consults it when planning.
2. **`loop_node_attempts`** — append-only ledger, PK
   `(loop_run_id, generation, node_id, item_index, attempt)`. One row per attempt: failure class,
   sanitized cause + remediation hint refs, started/ended timestamps, disposition
   (`succeeded | retried | routed | absorbed | escalated | quarantined | canceled | resumed`), and
   `next_attempt_at` when a retry was scheduled. This is the quarantine entry's evidence and the
   attempt-visibility source (US-008 AC-3).
3. **Retry scheduling state lives on `loop_generation_outputs`** — four new columns:
   `attempt INTEGER NOT NULL DEFAULT 1`, `next_attempt_at TIMESTAMP`, `first_scheduled_at
   TIMESTAMP`, `epoch INTEGER NOT NULL DEFAULT 0`. `epoch` is the single authoritative
   stale-work fence (ADR-012; round-2 B-005 aligned): schedules persist the epoch they were
   issued under, superseding mutations bump affected cells in-transaction, and
   `loop_node_controls.revision` fences verb CAS only. Same grain, read by the same coordinator
   refresh; a sibling current-state table would duplicate the PK and force a second join on the
   hottest read. The `status` column gains a SQL CHECK with the extended vocabulary (adds
   `retrying`, `waiting`, `paused`, `quarantined`, `canceled`) — a table rebuild, legal
   greenfield.
4. **`loop_node_waits`** — one row per pause point, PK
   `(loop_run_id, generation, node_id, item_index)`. Carries wait kind (`timer | event |
   approval_escalation`), `resume_at` (timers), expected-payload schema ref, claim state
   (`waiting | claimed | resumed | intervention_required`) with claimant provenance (no token —
   claims are row CAS, nothing credential-shaped is stored), `issued_epoch`, admission failure
   count, escalation cursor + next escalation at, created/age. Indexed on `(claim_state)`,
   `(resume_at)`, and `(next_escalation_at)` for the due-scan. Resume is one atomic transaction
   (`ResumeWait`) that also reserves the coordinator task run.
5. **`loop_admission_claims`** — watch-event dedupe tombstones, PK
   `(workspace_id, loop_name, source_key, event_key)` + `loop_run_id`, `claimed_at`,
   `suppressed_count`, `last_suppressed_at`. Inserted `INSERT OR IGNORE` in the same transaction as
   the loop-run start; conflict = duplicate → suppression answer. Swept past the configured
   horizon.
6. **`loop_effect_outbox`** — authored effect deliveries, PK `(loop_run_id, delivery_id)`;
   rows written in the same transaction as the trigger's state change; drained post-commit by
   the idempotent relay (ADR-015).
7. **Target-breaker state is NOT a new loop table** — it reuses `internal/deadentity`; the same
   migration rebuilds `dead_entities` so the kind CHECK accepts `loop_target` (ADR-014).
8. **Migration scope (one Goose file):** five CREATEs (controls, attempts, waits, admission
   claims, effect outbox); three row-preserving rebuilds (`loop_generation_outputs`,
   `loop_generations` origin CHECK, `dead_entities` kind CHECK); and two column additions —
   `loop_run_events.delivery_key` (+ partial UNIQUE index) and `loop_runs.cancel_requested` +
   `cancel_kind` for the run-level cancel authority (round-3 B-001).

Side-table-vs-JSON: pause/quarantine/attention/wait/claims state is **matchable** (inventories
filter and sort on it) → typed columns. The quarantine entry's failure chain and the wait's
expected-payload schema are **opaque, read-whole** → sanitized JSON columns on their owning rows.

## Alternatives Considered

### Alternative 1: One wide `loop_node_lifecycle` table for everything

- **Description**: Single table keyed `(loop_run_id, node_id, item_index)` holding retry, pause,
  quarantine, wait, and flags.
- **Pros**: One table to join.
- **Cons**: Mixes three lifetimes (per-execution, per-node, per-pause-point) in one grain —
  generation-scoped fields would need nulling/resetting on every succession; wait rows and control
  rows have different cardinality and retention.
- **Why rejected**: The Goal precedent (checkpoints + turns) proves the split shape; mixed grains
  are how JSON bags happen.

### Alternative 2: All new state in new tables, `loop_generation_outputs` untouched

- **Description**: Retry scheduling in a sibling current-state table with the same PK.
- **Pros**: Zero churn on the existing hot table.
- **Cons**: Every coordinator refresh joins two tables at the same grain; the two-writer problem
  (already flagged as ADR-guarded at `global_db_task_claim_complete.go:350`) doubles.
- **Why rejected**: Same grain = same row; four columns on the existing PK is strictly simpler.

### Alternative 3: Attempt state inside `task_runs`

- **Description**: Reuse `task_runs.attempt` and add `next_attempt_at` to the task queue.
- **Pros**: The queue already has attempt/lease/heartbeat columns.
- **Cons**: A loop node retry is loop-domain policy, not queue policy; task-run attempts count
  claims of one enqueued run, not node executions across scheduled retries; L-003 allows columns
  on `task_runs` but the loop coordinator would then own scheduling state in a foreign domain.
- **Why rejected**: Node retries are planned by the loop coordinator; each scheduled attempt is a
  fresh deterministic task-run id (attempt-suffixed), keeping `task_runs` single-purpose.

## Consequences

### Positive

- Every inventory (waiting/quarantine/attention) is one indexed query; quarantine entries are
  diagnosable from rows alone (Temporal DLQ anti-lesson closed).
- Recovery stays "re-derive from durable rows": attempt state survives restarts by construction.

### Negative

- One migration touching nine tables (five new + three rebuilds + column additions on
  `loop_run_events` and `loop_runs`) plus sqlc/Atlas regeneration; both output writers and the
  Goal sqlc queries must learn the new columns.

### Risks

- The two-writer seam on `loop_generation_outputs` now carries scheduling state — the epoch
  column (ADR-012) is what keeps a stale writer from resurrecting a superseded schedule; the
  finalizer suite must induce write races.
