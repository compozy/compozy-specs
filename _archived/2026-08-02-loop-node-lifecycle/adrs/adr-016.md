# ADR-016: Liveness by evidence — session-activity probes, death-resume as continuation, silence flags, cancel/kill delivery, parent-close policy

## Status

Accepted

## Date

2026-08-01

## Context

The session layer already models everything the contract needs: `SessionActivityMeta` with
`LastActivityAt`/`CurrentTool`/`ToolCallID` (real activity via `touchWithTool`) versus
liveness-only waiting heartbeats (`recordWaitingHeartbeat` deliberately does **not** advance
`LastActivityAt`) — the exact heartbeat-vs-progress split ADR-004 requires. The loop plane already
polls it: `internal/daemon/loop_action_liveness.go:186-212` reads `Status()` and treats an
in-flight tool as progress-suppressing. But the same file enforces
`loopActionNoProgressTimeout = 7m30s` with reasons `node_timeout`/`no_progress` — a hidden
duration kill that contradicts the PRD's core premise (days-long goal nodes) and the user's
explicit direction. Session supervision defaults (`inactivity_warning_after = 15m`,
`inactivity_timeout = 30m`) would likewise cancel long-quiet-but-alive loop sessions. Cancellation
today: non-goal run-agent nodes have **no** operator cancel at all (only the timeout-armed
`CancelActionSession`); goal nodes have durable prompt-lease revocation; run-level `stop` hard-
fails the run. Temporal supplies the reference verbs (cancel/terminate, parent-close policy,
heartbeat-ack control delivery); Mastra supplies the anti-lesson (bidirectional unconditional
propagation).

## Decision

1. **Delete the hidden clocks.** The 7m30s no-progress kill and its `node_timeout`/`no_progress`
   failure reasons in `loop_action_liveness.go` are removed. Loop-bound action sessions launch
   with session-supervision `inactivity_warning_after = 0` and `inactivity_timeout = 0`
   (supervision heartbeats and metadata persistence stay — they are the evidence stream).
   Authored `timeout:`/`deadline:` remain the only duration bounds.
2. **Liveness is evidence, evaluated by the existing poll.** Evidence of life = fresh
   `LastActivityAt`, an in-flight tool execution (`CurrentTool`/`ToolCallID`), or transport
   presence (the ACP subprocess is alive). The liveness poller updates the node's
   last-evidence timestamp; it never fails anything.
3. **Confirmed death → bounded continuation through ONE atomic authority.** Death is
   deterministic only: the session process exited / the manager reports terminal stop — never a
   silence heuristic (ambiguity resolves to the silence path). The liveness prober is
   evidence-only; it hands confirmed death to `ResumeDeadNode`, a single `BEGIN IMMEDIATE` transaction that
   validates the expected live cell status and that no run- or node-scope cancellation is
   pending (a raced cancel wins with a deterministic no-op), transitions the outputs cell to
   its continuation state under a bumped epoch, appends the `resumed` attempt-ledger
   disposition, increments the streak with provenance, rotates the managed binding
   (`AdvanceActionSessionRetry` precedent), appends the lifecycle event, and reserves exactly
   one deterministic continuation task run — losers leave both the cell and the ledger
   unchanged (round-2 B-007; round-3 B-006). The
   prompt carries the progress checkpoint (last event-seq window and harvested partials; goal
   nodes resume from their durable checkpoint as today). Provenance records `resume` distinct
   from `retry`. Streak: 3 consecutive resumes with no post-resume activity evidence →
   needs-attention; any evidence resets it — daemon restarts over a week-long run never exhaust
   it.
4. **Silence flags, nothing else.** No evidence of life across the configured window (default
   30m; 0 disables) with no confirmed death → attention flag on the control row + event; any
   evidence self-clears it. Flags aggregate per run and workspace (US-017 EC-4).
5. **Cancel ≠ kill, delivered where liveness flows, with a durable state machine.** `cancel`
   (run- and node-level) is cooperative and idempotent, owned by `loop_node_controls.cancel_state`
   (`"" → requested → delivering → draining → canceled`; round-1 review B-005): the verb writes
   `requested` + provenance and bumps every affected cell epoch (pending retries/timers die);
   delivery rides the existing prompt-cancel path (`CancelPrompt` → ACP `session/cancel` →
   scoped tool interrupt) and marks `delivering`; the attempt drains (`draining` — grace overrun
   stays visible here, nothing silent); close runs `on_cancel` effects and lands `canceled`.
   Every transition is idempotent; repeat verbs answer with current state. `kill` bypasses the
   machine: session stop-with-cause + tool-registry interrupt (SIGTERM→grace→SIGKILL ladder),
   **no node-trigger effects; contract terminal effects still ride the resulting terminal truth**
   (round-1 review B-006; US-013 AC-3). No silent cancel→kill escalation — kill is always an
   explicit call or an authored grace bound. The verbs replace `stop` everywhere (grill
   decision, hard cut). **Run scope (round-2 B-001):** `canceled` becomes the seventh terminal
   outcome across the domain (DSL terminal states, runtime status, contract enum, transition
   causes `operator_cancel`/`operator_kill`, `contract.on_canceled` trigger); run-level requests
   live on `loop_runs.cancel_requested`/`cancel_kind` (the `pause_requested` pattern); the
   request transaction also projects `requested` onto every live node's control row with epoch
   bumps (delivery and death-resume read one truth), and both verbs carry the existing Goal
   stop cleanup (prompt-lease revocation, binding close) before terminalizing; kill
   terminalizes in the service transaction, cancel drains via the coordinator, and runs with no
   active node terminalize directly — one authority per scope (round-3 B-001).
6. **Parent-close policy on spawned work.** `run-loop` (and future spawning nodes) declare
   `on_parent_close: terminate | cancel | abandon` (default `terminate`); propagation is strictly
   parent → child; child failures cross the boundary as a classified failure
   (class + child-run reference, fail-closed redaction) so `on_error.route` works on composite
   nodes.

## Alternatives Considered

### Alternative 1: New heartbeat transport from executors to the loop plane

- **Description**: Executors push periodic heartbeats to a loop-owned channel/table.
- **Pros**: Loop-owned signal, no session coupling.
- **Cons**: SD-001 forbids heartbeats through event channels; the signal already exists in session
  metadata; a second liveness plane invites divergence.
- **Why rejected**: The transport work is already done — derive, don't duplicate.

### Alternative 2: Keep a (longer) default no-progress kill

- **Description**: Raise 7m30s to hours instead of deleting.
- **Pros**: Wedged sessions eventually die unattended.
- **Cons**: Any default duration kill eventually murders a legitimate long node; ADR-004 and the
  user's grill direction are explicit.
- **Why rejected**: Flag-and-decide replaces kill-by-clock; stopping wedged-but-alive work is an
  operator/agent verb.

### Alternative 3: Cumulative death-resume cap

- **Description**: Cap total resumes over the node's lifetime.
- **Pros**: Simplest counter.
- **Cons**: A week-long node consumes one resume per daemon restart and eventually parks despite
  being healthy — punishes longevity, not crash-loops.
- **Why rejected**: Grill correction — streak with progress-reset targets the actual failure
  mode.

## Consequences

### Positive

- Days-long nodes never fight a hidden clock; a 3 a.m. crash costs one continuation; every
  control verb reaches live work through machinery that already exists (prompt cancel, tool
  interrupts, stop-with-cause).

### Negative

- Truly wedged-but-alive sessions are only flagged — stopping them is a deliberate verb (accepted
  by design, PRD ADR-004).

### Risks

- Evidence quality decides everything: if in-flight tool executions were ever invisible, quiet
  gates would flag falsely — the conformance tests pin "in-flight tool = life" against the
  `refreshActionProgress` seam.
