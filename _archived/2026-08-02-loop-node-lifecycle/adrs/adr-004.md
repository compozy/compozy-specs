# ADR-004: Long-running-first supervision — no default time limits, liveness-based health, death-triggered resume

## Status

Accepted

## Date

2026-08-01

## Context

The central premise of the loop engine is agents that run for hours or days — a single goal-carrying node can legitimately consume days. Default duration limits would kill exactly the workload the product exists for. At the same time, the market's wedged-node story is grim: Mastra has no per-step timeout and no wedged-step detection (cancel cannot even break a hung step); Sim detects wedged runs with a ~95-minute external sweep; re-running a long agent from zero after a crash is the most expensive failure in the system. SD-001 already settles the philosophy at the session layer: supervise activity, never wall-clock.

A user-supplied caution binds this decision: long quiet tool executions are normal (a full verification gate can run many minutes producing no output). Liveness must never mistake "quietly working" for "dead".

## Decision

1. **No default duration limits on any node.** Time limits (per-attempt and total) exist only as author opt-in, for authors who know their nodes are short. Long-running work is a first-class citizen, not an exception.
2. **Health is liveness, not elapsed time.** A node is healthy while its session shows any sign of life — streamed activity, an in-flight tool execution, transport-level presence. Duration alone never triggers anything.
3. **Confirmed session death → automatic resume from the last progress checkpoint.** Death is a deterministic event (process/transport gone), never a heuristic. Resume is continuation — the node picks up from its recorded progress, not from zero — and is bounded by a small resume-attempt cap; exhaustion surfaces the node as needing attention.
4. **Prolonged true silence → needs-attention flag only.** When there is no evidence of life and no confirmed death, the engine flags the node for operator/agent attention. It never auto-kills and never auto-pauses on silence. The silence window is generous, configurable, and only starts when no in-flight work is evidenced — a running tool execution is activity by definition (false-positive protection is a hard requirement).
5. **Progress checkpoints ride the existing agent activity stream.** Long nodes report progress as a side effect of working; the latest checkpoint is visible to operators and is what resume continues from; on terminal failure it attaches to the failure record.

## Alternatives Considered

### Alternative 1: Default per-family timeouts (v0 posture: 5-minute default on everything)

- **Description**: Every node born with attempt + total time limits.
- **Pros**: No wedged node ever lives past the default; matches small-task engines.
- **Cons**: Kills days-long goal nodes — the product's core use case; forces every long-work author to discover and disable a hidden default.
- **Why rejected**: User decision — limits are for small-task situations, not the engine's primary workload.

### Alternative 2: Mandatory explicit timeouts (Temporal posture)

- **Description**: Validation requires every fallible node to declare a time limit.
- **Pros**: No silent defaults; failure bounded by construction.
- **Cons**: Verbose authoring; breaks existing definitions; still wrong for "this may take as long as it takes" work.
- **Why rejected**: Same conflict with the long-running premise, plus authoring burden.

### Alternative 3: Signal-only anomaly handling (no auto-resume)

- **Description**: Death and silence both merely flag; humans decide everything.
- **Pros**: Maximum predictability.
- **Cons**: A 3 a.m. crash stops a days-long loop until someone wakes up, even though resume-from-checkpoint is safe and cheap.
- **Why rejected**: Death is deterministic; auto-resume on death is the safe automation that makes long loops actually survivable.

## Consequences

### Positive

- Days-long nodes run without fighting the platform; crash recovery is continuation, not re-execution.
- Wedged-vs-working is decided by evidence of life, never by a clock — no false kills of slow work.

### Negative

- A truly wedged-but-alive session (looping internally, never progressing) is only flagged, not stopped — by design; stopping it is an operator/agent decision via cancel.

### Risks

- Liveness signal quality decides everything: if in-flight tool executions are not visible as activity, quiet gates become false positives. The techspec must enumerate what counts as evidence of life before choosing any window value.
