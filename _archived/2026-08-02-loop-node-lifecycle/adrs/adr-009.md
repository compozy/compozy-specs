# ADR-009: Watch-event admission — duplicate suppression that is loud, durable, and validated at authoring time

## Status

Accepted

## Date

2026-08-01

## Context

Watch-driven loops start runs from delivered events, and event redelivery is not hypothetical — durable-history replay after a restart re-delivers, and external sources re-send. Without admission dedupe, one real-world event becomes N runs. The references agree on the mechanism and disagree on the failure modes: Sim claims run identity durably (permanent tombstones, explicit conflict answer to the caller) but falls back to a random key with only a warning when no delivery id exists; previous-generation Compozy answers duplicates loudly (conflict + log + metric) but silently proceeds **undeduplicated** when no key can be derived — a hole its own docs never admitted; Mastra has no admission dedupe at all, and a second start on the same run id silently overwrites the first.

## Decision

1. **Every watch-triggered admission derives a stable suppression key** from the event's source, the event's identity, and the target loop. Admission claims the key durably in the same act that records the run start — a duplicate can never win the race.
2. **Duplicates are suppressed loudly.** A suppressed duplicate is a recorded diagnostic (visible in run/loop inspection and the event stream) and a structured answer to whoever delivered it — never a silent no-op, never a second run.
3. **Suppression records persist as tombstones** so that redelivery after restart, however late, stays suppressed within the source's redelivery horizon.
4. **A watch source that cannot yield a stable event identity is an authoring error at validation time.** The definition fails validation with a diagnostic naming what is missing — the run never starts undeduplicated and never falls back to a random key. This closes both reference failure modes (v0's silent pass-through, Sim's random fallback).

## Alternatives Considered

### Alternative 1: Keep dedupe in Spec 3 with the rest of ingress

- **Description**: Ship Spec 1 without admission dedupe.
- **Pros**: Purer domain boundary.
- **Cons**: Redelivery is a today-problem; every watch loop built before Spec 3 double-fires on restart.
- **Why rejected**: User pulled it forward (ADR-001); it is small and self-contained.

### Alternative 2: Best-effort dedupe (random-key or skip when underivable)

- **Description**: Dedupe when possible, warn otherwise.
- **Pros**: Nothing fails validation.
- **Cons**: Reproduces the v0 hole and the Sim fallback: the loops most exposed to duplicates are exactly the ones that silently lose protection.
- **Why rejected**: An unenforced guarantee is worse than none (anti-lesson: unenforced knob = failed compile).

### Alternative 3: Time-boxed suppression only (short expiring window)

- **Description**: Suppress duplicates for a fixed short window, then forget.
- **Pros**: Small storage.
- **Cons**: Restart-replay horizons exceed short windows; late redelivery double-fires.
- **Why rejected**: Tombstone durability must match the redelivery horizon, not a convenience window (retention calibration belongs to the techspec).

## Consequences

### Positive

- One event, one run — guaranteed at admission, observable when it triggers.
- Authors learn at validation time, not in production, that their source lacks a stable identity.

### Negative

- Watch sources must expose stable event identity to be usable — a real (and intended) constraint on source authors, including extension-provided sources.

### Risks

- Overlap policy (what happens when a *distinct* event fires while a run is live) remains Spec 3 scope; this ADR covers identity duplicates only. The PRD records that boundary to prevent scope confusion.
