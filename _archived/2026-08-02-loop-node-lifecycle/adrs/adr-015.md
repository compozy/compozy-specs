# ADR-015: Effect dispatch — same-transaction effect outbox + idempotent pending-row relay; tool effects run daemon-side in the run's workspace scope

## Status

Accepted

## Date

2026-08-01

## Context

PRD ADR-006 fixes the contract: effects are fail-open, observe-only, isolated per entry, and
dispatched only after the state they announce is durably recorded, at-least-once with stable
identity. The runtime already has every ingredient: lifecycle events append inside the coordinator
transaction (`loop_run_events` via `GenerationLifecycleEventIntent`), the bridge plane's
`TerminalTaskNotifier` (`internal/bridges/task_notifier.go:62`) demonstrates the durable-event +
cursor-sweep delivery pattern (`notifications.CursorStore`, replay-safe, suppression-aware), and
the gate `extension` criterion already invokes tools daemon-side without a session
(`gate/evaluator_extension.go:14-70` builds `tools.CallRequest` with workspace scope). Hooks are
deny-only pre-commit for control and observe-only post-commit — they are the wrong vehicle for
authored side effects. Grill decision (2026-08-01): tool effects execute daemon-side in the loop
run's workspace tool scope; approval-requiring tools fail the effect deterministically.

## Decision

1. **Every trigger firing is first a durable lifecycle event, and its deliveries are rows in the
   same transaction.** New event kinds append in the transaction that commits the state change
   (`node_retry_scheduled`, `node_paused`, `node_resumed`, `node_canceled`, `node_quarantined`,
   `node_wait_started`, `node_wait_resumed`, `node_attention_flagged`,
   `node_attention_cleared`, plus the existing `node_failed`/`status_changed` family). The same
   transaction expands the definition's declared effects for the trigger into
   `loop_effect_outbox` rows — one per entry — each with a deterministic
   `delivery_id = sha256(loop_run_id, source_event_id, trigger, entry_index)`. The delivery id,
   not the run-local event seq, is the stable at-least-once identity (round-1 review B-002).
2. **A pending-outbox relay drains deliveries post-commit.** Outbox rows persist the FULLY
   rendered, sanitized execution payload (rendering happens once, inside the committing
   transaction; the relay executes immutable bytes — round-2 N-001). A render/resolution
   failure inside the owning transaction persists an error-as-data row instead — same
   deterministic delivery_id, `{render_error, sanitized diagnostic}` payload — which the relay
   acks as `failed` without tool execution; the trigger's state transition always commits and
   sibling entries still deliver (round-3 B-004, fail-open preserved). The relay is boot-started
   and cycle-driven: it pages ALL pending rows (workspace-safe join through `loop_runs`) as a
   daemon-singleton sequential drain, executes entries in isolation, and acks each in one
   transaction — result events append idempotently via `loop_run_events.delivery_key =
   "<delivery_id>:<kind>"` (nullable column + partial UNIQUE index) and the row flips
   `delivered`/`failed` with `attempts++` (round-2 B-004). The post-commit observer nudge is a
   latency hint only; stranded rows are always rediscovered at boot or on the next cycle. Tool
   execution is at-least-once by contract — `delivery_id` rides the tool correlation so
   consumers dedupe. Crash between commit and drain, lost nudge, crash after tool success
   before ack, and duplicate drains all converge on the same identity (US-011 EC-3, US-014).
   **The relay never fires hooks and never derives work from `loop_run_events`** — hooks keep
   dispatching at the call sites that own each transition (round-1 B-001; `internal/CLAUDE.md`
   "never tail event tables").
3. **Pre-bound context before input resolution:** node identity (loop, run, generation, node,
   item), classified failure (class, sanitized cause, hint), attempt info, and ready-to-use
   resume/approval links (deep link to the pause point), available to effect templates as an
   `effect.*` namespace root — Sim's pre-binding rule, adopted.
4. **`emit` effects** append a `custom_event` loop-run event (authored kind, bounded payload,
   idempotent on the delivery id) feeding SSE and the watch-events mapping — they do NOT enter
   the closed hook taxonomy and fire no hooks. **`tool` effects** call `tools.Call` daemon-side
   with the run's workspace scope, actor `daemon:loop-effect`, correlation ids of the
   run/node/delivery, and the effect's rendered `with` input. A tool whose policy would require
   interactive approval fails the effect with a deterministic `effect_tool_approval_required`
   result — recorded, never blocking (observe-only cannot wait).
5. **Results are recorded, never load-bearing.** Each entry's outcome
   (`ok | failed | approval_required | tool_missing`, duration, sanitized error) appends to an
   `effect_results` event on the run; node/run outcomes never read them. Kill dispatches no
   node-trigger effects; the contract terminal effect for the resulting outcome still fires
   (PRD Rule 20 as refined by round-1 B-006); the kill event itself remains observable.

## Alternatives Considered

### Alternative 1: Dispatch effects inline from the coordinator after commit

- **Description**: `CompleteCoordinatorAndEnqueueNext` returns, then the same goroutine runs
  effects.
- **Pros**: No outbox paging machinery; lowest latency.
- **Cons**: Crash between commit and dispatch silently drops effects (violates at-least-once);
  effect execution time rides the coordinator hot path; replay after restart has no pending-row
  record to resume from.
- **Why rejected**: The delivery guarantee is the contract; the notifier pattern already paid for
  it.

### Alternative 2: Route effects through the hooks plane

- **Description**: Model authored effects as auto-registered hooks.
- **Pros**: One dispatch system.
- **Cons**: Hooks are operator/extension-owned configuration, deny-only pre-commit or observe-only
  post-commit; authored per-node effects are definition-owned data with rendering and pre-bound
  context — different lifecycle, different matcher model; entangling them couples definition
  publishing to hook registration.
- **Why rejected**: Hooks observe the same transitions the outbox records — they compose
  without merging.

### Alternative 3: Effect tools run under a dedicated restricted identity with an allowlist

- **Description**: New `loop-effect` scope with a configurable effect-safe tool allowlist.
- **Pros**: Tighter blast radius.
- **Cons**: A new permission surface to author, validate, document, and keep in sync; the
  workspace tool policy already bounds what the loop could do via a toolcall node — effects never
  widen it.
- **Why rejected**: Grill decision — reuse the extension-criterion path; no new permission
  surface.

## Consequences

### Positive

- Truthful ordering by construction (durable-append-then-dispatch generalizes loops-paper-adoption
  Invariant 14 to effects); replayed history equals live emissions; a dead webhook costs a
  recorded failure, nothing else; the hook boundary stays intact.

### Negative

- At-least-once means consumers must dedupe on the delivery identity (documented; the identity
  is the deterministic `delivery_id`, reproduced across crash/replay).

### Risks

- Effect storms on retry-heavy runs — bounded by per-entry isolation, the existing 16 KiB event
  payload cap, and per-sweep page limits; `on_retry` volume is the authored author's choice.
