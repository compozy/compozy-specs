# ADR-002: Coordinated Task Runs Are the Flagship Network Use Case, Enrolled by Persisted Opt-In Plus Contextual Invitation

## Status

Accepted

## Date

2026-07-11

## Context

With participation explicit and default-Local (ADR-001), the Agent Network needs a product anchor — one "aha moment" that shows a light user why turning it on is worth it — or it decays into an unused advanced feature. Candidate anchors considered: coordinated task runs on the kanban, in-session second opinions between agents, a durable agent inbox, and cross-workspace fleet operation.

Coordinated task runs are adjacent to value users already touch daily (the kanban and the autonomy loop), produce a natural behavior-triggered moment (a run with a coordinator and multiple workers is visibly multi-agent), and match the pattern the market evidence validates: additional agents contributing intelligence and coordination around single-threaded ownership, not ambient chat.

## Decision

1. **The flagship Agent Network experience is the coordinated task run**: a coordinator and its workers exchanging messages in a conversation attached to the run, observable from the run's detail view. Task state remains authoritative; the conversation is collaboration evidence, never an ownership or status channel.
2. **Enrollment is a persisted, scoped opt-in**: the operator turns on "coordination conversations" once for a workspace or for a specific task, and subsequent coordinated runs in that scope participate. The setting is inspectable, revocable, and carried as the provenance of each run's participation.
3. **The kanban invites at the right moment**: when a run is active with a coordinator/multiple workers and its scope has coordination off, the run detail presents a contextual invitation that explains the value and offers one clear action (enable for this workspace or task). The invitation is dismissible and never blocks or nags.
4. **Orchestration never degrades without it**: the kanban, coordinator, scheduler, and reviews work fully with coordination off. The conversation is an additive layer.

## Alternatives Considered

### Alternative 1: Per-run opt-in every time

- **Description**: No persisted setting; each run start carries its own explicit participation choice.
- **Pros**: Maximum explicitness; zero standing state.
- **Cons**: Repeated friction for the core loop; the realistic outcome is that nobody enables it and the feature dies — the exact failure this PRD exists to prevent.
- **Why rejected**: Friction placed on the flagship moment kills the flagship.

### Alternative 2: Auto-enable for multi-worker runs

- **Description**: Runs with a coordinator and two or more workers get a conversation automatically.
- **Pros**: Zero friction; showcases the feature by default.
- **Cons**: Reintroduces shape-inferred participation (violates ADR-001); creates unrequested model-activation spend precisely on the heaviest runs.
- **Why rejected**: Conflicts with the explicit-intent invariant and with cost predictability.

### Alternative 3: Anchor the network on a different aha moment (second opinion / inbox / fleet)

- **Description**: Make in-session agent consultation, the durable inbox, or fleet operation the flagship.
- **Pros**: Each is a real use case with an audience.
- **Cons**: None is adjacent to the daily kanban loop; second-opinion nudges inside sessions were explicitly excluded from on-ramps; inbox and fleet are power-user postures, not a light user's first touch.
- **Why rejected**: The flagship must sit where the majority persona already is. The other use cases remain supported, just not the anchor.

## Consequences

### Positive

- Network discoverability gets a concrete, high-value home instead of an abstract settings toggle.
- One persisted decision covers the whole scope — no per-run ceremony after enrollment.
- Cost stays predictable: participation follows a visible saved setting, not run shape.

### Negative

- A scoped persisted setting is broader than a single execution: operators must understand that enabling for a workspace covers future coordinated runs in it.
- Invitation quality becomes load-bearing product surface — bad copy or timing will read as an upsell banner.

### Risks

- Invitation fatigue → dismissal is persisted per scope; the invitation reappears only on explicit reset.
- Conversation misread as task authority → business rule: task state is authoritative; the conversation is evidence (already the documented posture of the runtime).

## Implementation Notes

Deferred to the TechSpec. The persisted setting must live on surfaces the runtime already treats as saved orchestration intent, and each run's resolved participation must record this setting as its source.
