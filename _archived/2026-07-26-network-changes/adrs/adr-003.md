# ADR-003: Discoverability Model — Disclosed, Not Hidden

## Status

Accepted

## Date

2026-07-11

## Context

The explicit risk of making the Agent Network opt-in (ADR-001) is that it becomes invisible and unused. Product research on progressive disclosure in developer tools converges on: advanced features should be *disclosed, not hidden* — reachable surfaces with oriented empty states and behavior-triggered reveals, at most two disclosure levels, anchored to one aha moment — while settings-only discoverability reliably starves a feature.

The operator also decided a boundary: agent sessions themselves must stay clean — no network suggestions injected into the session experience.

## Decision

The Agent Network is permanently visible and self-explanatory, with exactly three on-ramps:

1. **Always-visible network area with oriented empty states.** The network section of the product remains in the navigation even when nothing participates. Every zero-data view answers: where am I, why is this empty, what does it look like when full, and what is the one action that starts (for a light user: enable coordination conversations for a workspace).
2. **The kanban contextual invitation** on active coordinated runs (ADR-002) — the single behavior-triggered reveal.
3. **A light onboarding mention**: a getting-started item that introduces the Agent Network and points to its area. It enables nothing by itself.

Explicitly excluded: in-session nudges or suggestions (e.g., prompting the user to network when they spawn a second agent), timed popups, and any on-ramp that enrolls an execution as a side effect of being viewed.

## Alternatives Considered

### Alternative 1: Settings-only discoverability

- **Description**: Network exists behind configuration; no navigation presence until enabled, no invitations.
- **Pros**: Maximum minimalism; zero product surface for non-users.
- **Cons**: Research and precedent show buried advanced features die; contradicts the operator's core requirement that the feature stay alive.
- **Why rejected**: It optimizes for silence at the cost of the feature's existence.

### Alternative 2: In-session behavioral nudges included

- **Description**: Add a third reveal — when a user spawns a child agent or runs multiple agents, the session suggests network collaboration.
- **Pros**: Catches the second-opinion use case at its natural moment.
- **Cons**: Pollutes the session surface — the one place the light user lives — with feature marketing; the operator explicitly rejected it.
- **Why rejected**: Operator decision; sessions stay clean.

### Alternative 3: Hide the network area until first participation

- **Description**: Navigation shows the network section only after something participates.
- **Pros**: Cleaner navigation for pure-local users.
- **Cons**: Creates a chicken-and-egg: the place that explains the value is invisible until the value is already adopted; violates "disclosed, not hidden".
- **Why rejected**: Empty-but-oriented beats invisible.

## Consequences

### Positive

- The feature has a permanent front door plus one high-signal contextual moment — enough presence to stay alive without ambient noise.
- Empty states become the product's own explanation of the network, reducing docs dependence for first contact.

### Negative

- Pure-local users permanently see one navigation entry they may never use.
- Empty-state and invitation copy become maintained product surfaces with quality requirements.

### Risks

- The single invitation is the only behavior-triggered reveal; if its trigger conditions are too narrow, discovery leans entirely on the navigation area → mitigate by treating the invitation's trigger and dismissal rules as explicit business rules, reviewed with usage evidence after release.

## Implementation Notes

Empty-state composition and invitation placement follow the design system's empty-state guidance; final copy passes through the product-language spec before ship.
