# ADR-007: Live-Only Identity — Session-Scoped Durable Relations, No Offline Address Layer

## Status

Accepted

## Date

2026-07-11

## Context

The audit's C-07 finding: durable conversation relations (thread participants, subscriptions, direct-room identity, work ownership) are keyed by the **process peer id**, which rotates on restart — and directed sends require live presence (`internal/network/router.go:354-379`). The corpus solved this with a new stable "mailbox id" identity layer supporting offline delivery. ADR-004 removed mailbox mode: every participant in this release is **Live** — attached to a running execution — so the identity problem shrinks to: relations must survive a *restart of the same execution*, not the absence of one.

The runtime already has a stable identity that satisfies exactly that: the **session id** (stable across process restarts of the same session; every participating execution owns or binds sessions).

## Decision

1. **Durable conversation relations key on session identity** (workspace + channel + session id), not process peer id: thread participants, subscription preferences, direct-room pair identity, and network work ownership. Peer id remains ephemeral presence/transport metadata only.
2. **Directed sends require a live, participating target.** Sending to an execution that is not participating (or whose session no longer exists) fails with a typed diagnostic — there is no offline queue-for-later address. Messages posted to threads/channels persist as durable conversation history that any later participant reads on its own turns.
3. **No stable-address layer ships.** Mailbox ids, offline ingress, delivery cursors for absent recipients, and every remote-home concern stay out; they belong to the future external-interaction program (ADR-004).
4. **Restart continuity invariant:** a session restart preserves its direct rooms, subscriptions, thread membership, and usage attribution because all are session-keyed; only presence/lease state resets.

## Alternatives Considered

### Alternative 1: Full stable mailbox-address layer (corpus C-07 hard cut)

- **Description**: New mailbox identity for every durable relation + fenced mailbox-to-lease resolution + offline directed delivery.
- **Pros**: Complete durability; ready for external recipients.
- **Cons**: The heaviest engineering in the corpus, justified by offline recipients — which cannot exist in a single-installation Live-only release.
- **Why rejected**: Builds identity for a fiction (ADR-004 rationale); the external-interaction program will design it against real requirements.

### Alternative 2: Keep peer-id keys, patch presence checks

- **Description**: Leave relations peer-keyed; tolerate restart forks.
- **Cons**: A restarted worker mid-run loses its direct rooms/subscriptions and forks conversation identity — breaks the flagship experience (coordinated runs restart sessions routinely).
- **Why rejected**: Restart continuity is required by the flagship; session-keying costs little and fixes it structurally.

## Consequences

### Positive

- C-07's blocker load leaves the release; the remaining identity work is a key swap on existing relations.
- Restart-safe conversations for coordinated runs with no new identity concepts.

### Negative

- Direct rooms/subscriptions die with their session (explicit session deletion) — acceptable for Live semantics, documented.

### Risks

- Future mailbox program needs a different key → session-keyed rows are workspace-scoped and enumerable; that program owns its own migration when real requirements exist.

## Implementation Notes

The alpha migration destructively rebuilds peer-keyed relation tables around session keys (no compatibility read, per zero-legacy). Exact table/column names are TechSpec-owned.
