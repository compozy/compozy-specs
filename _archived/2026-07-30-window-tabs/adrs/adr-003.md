# ADR-003: Tab persistence split — durable membership, per-client active tab

## Status

Accepted

## Date

2026-07-30

## Context

Window-manager topology is daemon-durable per workspace (all connected clients see the same windows; state survives restart), while focus, active desktop, and z-order are per-client presentation. Tabs introduce new state: group membership, tab order, each tab's navigation stack, and which tab is active in each group. Reference rule D8 says tab set, order, active index, and per-tab navigation stacks persist with desktop state. Market research is unambiguous that losing tab state on restart destroys user trust in tabs; it also shows two clients fighting over one shared "active tab" is a real failure mode for multi-screen workflows.

## Decision

Split tab state along the existing durability boundary:

- **Durable per workspace**: group membership, tab order, pinned flags, and each tab's navigation stack. Every client sees the same groups; a restart restores them exactly.
- **Per-client**: which tab is active in each group — like focus and active desktop today. Two browsers on the same workspace switch tabs independently.
- **Restore**: each group durably records its last-active tab so a fresh client (or restart) opens groups on the tab the user last used, then diverges per client.

## Alternatives Considered

### Alternative 1: Fully durable active tab (mirrored everywhere)

- **Description**: Active tab is shared workspace state; all clients follow every switch live.
- **Pros**: Perfect mirroring across screens; matches a literal reading of reference rule D8.
- **Cons**: Two clients cannot look at different tabs of the same group — each switch yanks the other client; contradicts the established per-client treatment of focus.
- **Why rejected**: The user chose per-client; mirroring breaks the two-monitor/two-browser workflow that per-client focus already protects.

### Alternative 2: Everything client-local (browser storage)

- **Description**: Tabs are a per-client presentation overlay; the daemon stays unaware.
- **Pros**: No daemon/topology changes.
- **Cons**: Tabs differ per browser, vanish with browser storage, are invisible to agents and management surfaces, and cannot round-trip through layout export/profiles.
- **Why rejected**: Violates the daemon-authoritative window-manager premise and the repo rule that features must be agent-manageable; state loss on client reset is the exact trust-killer market research warns about.

## Consequences

### Positive

- Restart-proof tabs (the market table-stake), consistent across clients, visible to agents and management surfaces.
- Multi-screen users keep independent reading positions in the same group.

### Negative

- "Active tab" means "active on this screen" — documentation and any activity indicators must be precise about this.
- Last-active recording adds a small write path on tab switches.

### Risks

- Per-client active state must degrade gracefully for brand-new clients (fall back to the group's last-active record) — stated as expected behavior in the PRD.

## Implementation Notes

Where last-active is recorded and how per-client active state rides the existing client-view mechanism are TechSpec decisions.
