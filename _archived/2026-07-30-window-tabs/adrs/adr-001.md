# ADR-001: Window tabs are grouped windows (unified tab model)

## Status

Accepted

## Date

2026-07-30

## Context

The window-tabs reference contract (`docs/design/opendesign/design-system/window-tabs-variations.html`, rules D1–D8) specifies a thin deck above the window head that multiplexes surfaces — app routes, drilled-in states, and live session documents — with the 44px head belonging entirely to the active tab.

Codebase research surfaced a load-bearing fact: the durable window-manager topology already models a tabbed stack of windows (`NodeKindStack` — an ordered list of window IDs plus an active ID), creatable via `layout.arrange --arrangement stack`, but with **no live UI**: inactive stack members are hidden and unreachable by pointer. Market research (i3/sway, VS Code editor groups, macOS window tabs) converges on "tabs are a layout mode of a container whose members are full windows", and flags "two similar-but-different tab concepts coexisting" as a classic confusion pitfall.

Two candidate models existed: (A) a tab is a full OS window grouped into a frame — the deck is the switching UI for any window group, tiled or floating; (B) a tab is an internal surface list inside a single window, invisible to the rest of the OS, with tiled stacks remaining a separate, still-UI-less feature.

## Decision

A window tab **is a full OS window grouped into a shared frame**. One product concept — the window group — covers both containers: a tiled pane holding multiple windows and a floating frame holding multiple windows. The deck is the switching UI of a window group wherever it appears. Each tab therefore carries its own identity, route, head (root / breadcrumb / document), and navigation state, satisfying the reference rule "the head belongs to the active tab" by construction. Dragging a tab out dissolves it back into a standalone window; dragging a window onto a deck groups it. The existing tiled stack becomes this same feature and gains the deck as its missing UI.

## Alternatives Considered

### Alternative 1: Internal tab list per window

- **Description**: A window owns an ordered list of internal surfaces; the OS sees only the parent window.
- **Pros**: No change to window identity rules; dock and window lists untouched.
- **Cons**: Duplicates the existing stack concept (two overlapping "tabbed" features, one still without UI); every per-tab behavior (head, navigation, status) must be re-modeled inside the window; tabs invisible to OS-level surfaces (window lists, agent commands) without extra work.
- **Why rejected**: Creates permanent product ambiguity between "stacked windows" and "window tabs" — the exact pitfall market research documents — and leaves the live unreachable-stacked-window bug unfixed.

### Alternative 2: Hybrid (deck for floating; stacks stay separate)

- **Description**: New internal tabs for floating windows only; tiled stacks remain as-is.
- **Pros**: Smaller initial surface.
- **Cons**: Same duplication as Alternative 1 plus an inconsistent story across tiled and floating contexts, contradicting reference rule D6 ("in splits, each pane carries its own deck").
- **Why rejected**: Worst of both — two concepts and an asymmetric UX.

## Consequences

### Positive

- One concept to learn, document, and manage; identical behavior in tiled panes and floating frames.
- The unreachable-stacked-window defect is fixed by the same feature that ships tabs.
- Every tab is a real window, so OS-level surfaces (dock, window lists, agent-facing commands, palette) see tabs with no parallel bookkeeping.
- Drag-out/drag-in reduce to ungroup/group of windows — no state conversion between "tab" and "window".

### Negative

- Grouping semantics (which window is active, group ordering) become durable topology state that all clients and management surfaces must understand.
- Window identity rules must be renegotiated (see ADR-002), since grouping many windows of the same app becomes expressible.

### Risks

- Group chrome (deck) must appear only when a group holds ≥2 members, or single windows regress visually — mitigated by reference rule D1 (deck mounts at the second tab, unmounts at one).
- Existing layout export/apply flows must round-trip groups faithfully or tab state silently vanishes — captured as a PRD success criterion.

## Implementation Notes

The existing durable stack node is the natural substrate for tiled groups; floating frames need an equivalent grouping. Which internal representation carries this is a TechSpec decision — the product commitment is solely "tab = grouped window, one concept everywhere".
