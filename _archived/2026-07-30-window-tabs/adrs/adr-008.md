# ADR-008: Tab groups ride the existing stack node; floating frames become first-class floating stacks

## Status

Accepted

## Date

2026-07-30

## Context

ADR-001 fixed the product model: a tab is a full window grouped into a frame, one concept for tiled and floating containers. The durable topology already has half of this: `NodeKindStack` (`internal/windowmanager/types.go:97-106`) holds `WindowIDs []WindowID` + `ActiveID *WindowID` inside tiled layout groups, validated by `topology.stack_size` (≥2 members) and `topology.stack_active`, with `NormalizeSnapshot` collapsing a 1-member stack to a leaf (`normalize.go:98-104`) — which is exactly the product's deck-unmounts-at-one-tab rule (D1). Floating windows, however, are a flat `Desktop.Floating []WindowID` list with per-window `FloatingRect`; no grouping exists there.

## Decision

Keep `NodeKindStack` as the tab-group representation inside tiled groups, unchanged in shape. Add a sibling representation for floating frames:

```go
type FloatingStack struct {
    ID        NodeID         `json:"id"`
    WindowIDs []WindowID     `json:"window_ids"` // ordered; pinned members first
    ActiveID  *WindowID      `json:"active_id"`  // durable last-active (restore seed)
    Rect      NormalizedRect `json:"rect"`       // frame rect; members' FloatingRect is ignored while grouped
    Minimized bool           `json:"minimized"`  // the frame minimizes as a unit
}
// Desktop gains: FloatingStacks []FloatingStack `json:"floating_stacks"`
```

Membership rules are uniform: a window referenced by any stack (node or floating) carries `Placement == WindowPlacementStacked`; validation extends `topology.stack_size` / `topology.stack_active` / membership-exactly-once to floating stacks; normalize dissolves a 1-member floating stack into a plain floating window at the frame's rect. The deck is the single UI for both containers.

## Alternatives Considered

### Alternative 1: Generalize `LayoutGroup` with a floating placement

- **Description**: Allow `LayoutGroup{Frame, Root}` entries whose frame is a free-floating rect and whose root is a stack.
- **Pros**: One container list; projection already consumes groups.
- **Cons**: Tiled group frames are derived from arrangement and participate in gap/seam math; floating frames are free rects in z-order. Overloading one type forks every group consumer (`layout-projection`, arrange/resize/balance reducers, seam logic) on a placement flag.
- **Why rejected**: The two containers share almost no behavior beyond "holds a stack"; a dedicated small struct is cheaper than a polymorphic group.

### Alternative 2: New unified `TabGroup` entity replacing stack nodes

- **Description**: Introduce one `TabGroup` referenced from both tiled leaves and a floating list; retire `NodeKindStack`.
- **Pros**: Single grouping entity.
- **Cons**: Rewrites the entire tiled tree grammar, every reducer touching nodes, `ReturnAnchor.SourceGroup` byte-compare restore, and the canonical topology/lifecycle/layout test suites — for zero user-visible gain over reusing the proven node.
- **Why rejected**: Maximum churn, no behavioral difference.

## Consequences

### Positive

- Tiled tab groups are already implemented, validated, arrangeable (`layout.arrange --arrangement stack`, `DropCenter` merges), and covered by canonical suites; only floating grouping and the deck UI are net-new.
- D1 (deck threshold) is enforced by existing normalize/validate invariants rather than UI convention.

### Negative

- Two container shapes (node vs `FloatingStack`) must stay behaviorally aligned; shared helpers (member add/remove/activate/pin-order) must be written once and used by both.

### Risks

- `ReturnAnchor.SourceGroup` embeds full group clones and byte-compares on restore (`return_anchor.go:131-165`); adding stack fields or reordering members invalidates stored anchors → acceptable: anchors degrade to the documented fallback path, and the v3 hard cut (ADR-012) resets snapshots anyway.

## Implementation Notes

`window.move` with `DropPlacement="center"` already creates/extends tiled stacks; it is extended to floating targets (dropping a window onto a floating window or frame forms/extends a `FloatingStack`). Bulk grouping gets a dedicated command (see TechSpec §Command Surface) so merge-all is one revision change.
