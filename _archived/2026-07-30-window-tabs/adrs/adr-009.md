# ADR-009: Active tab = focus-driven per-client presentation; durable last-active written coalesced; History leaves the wire snapshot

## Status

Accepted

## Date

2026-07-30

## Context

ADR-003 (product) split tab state: membership/order/pins/nav durable, active tab per-client, durable last-active as restore seed. The codebase constrains the design three ways: (1) there is no command that changes a stack's `ActiveID` today — the web derives display-active by letting `focusedWindowId` override `activeId` (`layout-projection.ts:167-172`); (2) `ClientView` is in-memory per client and never persisted — the right home for per-client active state; (3) every durable command bumps the workspace revision, and web clients react to each event frame by refetching the entire snapshot, which currently embeds `History` — up to 50 entries each deep-cloning all desktops+windows. A durable command per ⌃Tab press would broadcast heavyweight refetches to every client on every switch.

## Decision

1. **Activation is focus.** Focusing a window that belongs to a stack activates it in that stack for the focusing client. `ClientView` gains `StackActive map[NodeID]WindowID` (in-memory, per client, projected on the client frame). No new presentation command: `window.focus` already exists, requires a ClientID, and bumps only that client's `PresentationRevision`. Display-active resolution becomes `ClientView.StackActive[stack] ?? stack.ActiveID`; the focus-override hack in `preferredActiveWindow` is deleted.
2. **Durable last-active is written coalesced.** The manager records pending last-active updates per `(workspace, stack)` on focus and flushes them as one internal durable commit — history-exempt, emitting the typed `window_manager.stack.activated` hook (the durable write is the observable activation record) — after a short quiet period (2s), and immediately on client unregister, workspace shutdown, and synchronously before any other durable command for that workspace. A failed pre-durable flush fails that durable command; timer-path failures retain pending values for retry. The coalescer binds to the per-workspace lock with an explicit lifecycle (timer handles, detached context, cancel+flush+join on Close) — see TechSpec Core Interfaces.
3. **Agent path.** A new durable command `window.stack.set_active {window_id}` sets `ActiveID` directly (history-exempt; emits `stack.activated`) for agents operating without a client; with a `client_id` it also updates that client's `StackActive`. The public noun everywhere is **activate**; `set_active` is the internal command ID.
4. **History leaves the wire.** `WindowManagerSnapshot` (contract) drops the `history` field; `History` stays domain-internal for undo/redo. Snapshot refetches become cheap enough for event-driven refresh to stay the sync model.

## Alternatives Considered

### Alternative 1: Durable `window.stack.activate` on every switch

- **Description**: Each tab switch is a normal durable command updating `ActiveID`.
- **Pros**: One code path; last-active always exact.
- **Cons**: Every ⌃Tab press bumps the workspace revision and triggers a full-snapshot refetch on every connected client; violates the product rule that active tab is per-client (two browsers would fight); history/hook exemptions still needed.
- **Why rejected**: Wrong semantics (shared active) and pathological chattiness.

### Alternative 2: Fully client-local active tab (no durable seed)

- **Description**: Active tab lives only in browser state.
- **Pros**: Zero daemon changes.
- **Cons**: Restores land on `windowIDs[0]` instead of the last-used tab (violates PRD US-022 AC-2); agents cannot read or set active state; two clients cannot even seed from each other.
- **Why rejected**: Breaks the accepted product contract (ADR-003).

## Consequences

### Positive

- Tab switching costs one client frame to one client — no workspace-wide traffic, no history growth.
- Restart/fresh-client restore lands on the recorded last-active per group.
- The focus↔active disagreement in today's projection is resolved by construction.

### Negative

- A coalescing buffer with flush triggers is new manager machinery (timer + flush hooks) that must be correct under shutdown and concurrent structural commands.
- Last-active may lag live focus by up to the quiet period on other clients — irrelevant to them (their active is per-client) and bounded for restores.

### Risks

- Flush racing a structural command → mitigated by flushing pending last-active synchronously before applying any durable command for the workspace (single manager mutex already serializes Execute).

## Implementation Notes

The internal flush commit reuses the normal commit path (revision bump, event frame, clientstate CAS), is excluded from `recordCommandHistory`, and dispatches `window_manager.stack.activated` (raw per-client focus flips dispatch nothing). `restoreStatePreservingRoutes` keeps preserving live routes on undo/redo; `ActiveID` participates in history states as plain data.
