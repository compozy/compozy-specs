# ADR-005: Windows by default; opening in a tab is an explicit, context-menu-first action

## Status

Accepted

## Date

2026-07-30

## Context

With tabs available, every launch surface (dock, command palette, sessions list, in-app links) faces the question "window or tab?". macOS answers with a global three-state preference — and market research shows that preference is a documented source of unpredictability complaints ("the same gesture does different things on different machines"). The user directed that the default stay as today (open a window) and that the right-click context menu become the explicit chooser, leveraging the design system's existing context-menu primitive.

## Decision

**Default unchanged: launch surfaces open (or focus) a window.** Opening into a tab is always an explicit, predictable gesture:

1. **Context menu (primary path)**: right-clicking an openable item (dock app, palette/list entries, session rows) offers destination choices — e.g., "Open in new window", "Open as tab in focused window", and, per ADR-002, "Open new instance".
2. **⌘T inside a window**: creates a new tab in that window's group, opening the destination picker (palette) scoped to "what can this tab become".
3. **Drag**: dragging a window onto another window's deck groups it (with a clear, cancelable drop affordance); dragging a tab off the deck ungroups it.
4. **Tab context menu**: close, close others, close to the right, pin/unpin, move to new window, merge windows (per ADR-006).

No global "prefer tabs" preference ships in v1.

## Alternatives Considered

### Alternative 1: Default to tab-in-focused-window

- **Description**: Everything opens as a tab in the focused group; windows become the explicit gesture.
- **Pros**: Fewer scattered windows.
- **Cons**: Breaks every current habit; silently mixes unrelated apps into whatever group happens to be focused; makes the focused window a moving target for launches.
- **Why rejected**: Unpredictable composition of groups the user never asked for.

### Alternative 2: Global user preference (macOS-style)

- **Description**: A setting chooses window vs tab per launch.
- **Pros**: Flexibility.
- **Cons**: The same gesture yields different outcomes across machines/configs — the documented macOS complaint; support and QA surface doubles.
- **Why rejected**: Predictability of a single default plus explicit gestures beats configurable ambiguity; revisitable post-v1 if demand appears.

## Consequences

### Positive

- Zero behavior change for users who ignore tabs (reference rule D1: tabs cost nothing until the second one).
- Every group is intentional — assembled by explicit gesture only.
- The context menu becomes a consistent, discoverable "power path" across launch surfaces.

### Negative

- Right-click affordances must be added uniformly across launch surfaces, or the chooser feels inconsistently available.

### Risks

- Drag-grouping without a clear drop target recreates the macOS accidental-merge complaint — the PRD requires a visible, cancelable drop affordance and an undo path (⌘⇧T-equivalent for grouping: drag back out).

## Implementation Notes

The design system already ships a context-menu primitive; launch-surface integration points are enumerated in the TechSpec.
