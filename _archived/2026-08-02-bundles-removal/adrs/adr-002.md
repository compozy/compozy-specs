# ADR-002: Package automation with enable-as-consent

## Status

Accepted

## Date

2026-07-29

## Context

Bundles are the only way an extension package ships automation today: `BundleJob`/`BundleTrigger` materialize as `automation.job`/`automation.trigger` records with `Source: package` at activation, default `enabled = true`, and register with the scheduler immediately (`internal/bundles/service_materialize_automation.go`, `internal/automation/manager_runtime_apply.go:13-32`). The brief requires extensions to declare jobs/triggers as package resources, with the constraint: "Recurring work must not auto-start merely because the package was installed; enable (or an explicit consent step after enable) is the gate."

The automation domain already has the pieces: `Source` taxonomy (`config|package|dynamic`), read-only definitions for non-dynamic sources, and operator `enabled_override` overlay rows for managed sources (`internal/automation/manager_definition_sync.go:300-325`).

## Decision

- Extensions declare automation statically: `resources.automation = ["automation/"]` — dirs/files of TOML declaring `[[jobs]]` and `[[triggers]]` (schema mirrors `BundleJob`/`BundleTrigger` minus profile nesting; webhook-event triggers stay rejected).
- **Enable is the consent act.** `compozy extension enable` (an explicit operator/agent action) materializes the declared jobs/triggers with their authored `enabled` state (default `true`) and the scheduler starts enabled ones. Install alone materializes nothing — static resources only publish for enabled extensions, which already holds for every kind.
- The enable success output (CLI human + JSON, HTTP payload, native tool result) enumerates the automation that started, so consent is informed.
- Per-item toggling after enable uses the existing overlay mechanism (`compozy automation job/trigger enable|disable` → `enabled_override` rows); package definitions remain read-only through the normal automation API.
- Disable/remove deletes the package-owned records via the declarative sync, and garbage-collects the matching overlay rows (fixing the orphan-overlay gap the bundle path has today).

## Alternatives Considered

### Alternative 1: Consent flag on enable (`--accept-automation`)

- **Description**: Enable fails with a deterministic 409 listing the jobs/triggers that would start; repeating with `--accept-automation` proceeds.
- **Pros**: Explicit per-kit automation consent, mirrors `--confirm-network-requirement`.
- **Cons**: Second ceremony inside the single verb; every enable of an automation-bearing kit needs the flag; agents and web must thread one more confirm field for a gate the operator already crossed by running enable.
- **Why rejected**: User decision (2026-07-29): enable itself is the explicit consent; the flag adds friction without adding information the enable output doesn't already give.

### Alternative 2: Always materialize disabled

- **Description**: Package automation always lands `enabled = false`; the operator turns each job/trigger on via overlay.
- **Pros**: Maximum safety; nothing recurs without a per-item act.
- **Cons**: Reintroduces the second ceremony bundles were deleted for; "enable is the kit switch" (P0.4) becomes false for automation; authors cannot ship a working recurring kit.
- **Why rejected**: User decision; contradicts the single-switch product goal.

## Consequences

### Positive

- One-step kit activation; the author's declared shape is what runs.
- Reuses `Source: package` and the overlay mechanism unchanged — no new automation authority.
- Install stays inert (brief constraint satisfied).

### Negative

- An operator enabling a kit for its skills also starts its declared automation; mitigation is the mandatory enumerated enable output plus `compozy extension preview` (ADR-006) showing `automation_starting` before the act.

### Risks

- Surprise recurring work if enable output is ignored — mitigated by preview, by the enumerated output being part of the contract (tested), and by overlay toggles being one command.

## Implementation Notes

Job/trigger names are namespaced `<extension>/<name>` (bundle used `<ext>/<bundle>/<profile>/<name>`). Records carry `Owner{Kind:"extension", ID:<name>}` (ADR-004) and `Source: package`. `JobSourcePackage`/`BridgeInstanceSourcePackage` doc comments update from "bundle" to "extension package" wording.

**Target restriction (peer-review R1 N-003):** package jobs/triggers may target only agents shipped by the same extension — a kit is self-contained. Targeting an external visible agent would create a dependency that can disappear independently of the owning extension; operator-authored dynamic jobs already cover cross-agent automation. Violations fail at load/validate with the shipped agent set named.

**Enable result contract (peer-review R1 B-005):** the started-automation enumeration is the dedicated action result `ExtensionEnableResult.AutomationStarted` (namespaced, name-sorted, exactly the definitions made runnable by the committed operation), identical across CLI/HTTP/UDS/native output and equal to the `extension.enabled` event count — never mirrored into status/list payloads.
