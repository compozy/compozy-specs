# ADR-001: Hard-delete the public Bundle product; Extension is the single kit unit

## Status

Accepted

## Date

2026-07-29

## Context

Compozy ships two user-facing concepts for add-ons: **Extension** (install/enable) and **Bundle** (catalog/activate/deactivate). The bundle implementation is a narrow activation projector owned by one already-installed extension: it materializes desired-state records (agents + soul/heartbeat sidecars, automation jobs/triggers, window layouts, disabled bridge presets, declared channels) but does not install dependencies, bind secrets, health-check, or enable bridge delivery. No first-party extension ships a bundle profile (`docs/ecosystem/bundle-opportunities.md:9`); every bundle TOML in the repo is a test fixture. Meanwhile the dual concept costs: `internal/bundles/**` (33 files, ~8.6k lines), 13 `bundle*.go` files in `internal/extension`, 8 HTTP/UDS routes, 8 OpenAPI operations, 6 CLI files, 5 native tools + 1 toolset, a marketplace kind, 11 dedicated web files + ~40 shared strips, 11 site doc files, 10 QA scenarios, and a permanent line in every extensibility checklist.

The `ext-improvs` program (baseline for this spec) made Extension authoring/distribution mature (code-first build, dev lane, source-union distribution, contributed commands) and left bundles untouched — deepening the asymmetry.

## Decision

Delete the public Bundle product completely and make Extension the single kit unit:

- Delete `internal/bundles/**`, the bundle schema/loaders in `internal/extension`, all `/api/bundles/*` routes (HTTP + UDS + OpenAPI), `compozy bundle *` CLI, `compozy__bundles_*` native tools and the `compozy__bundles` toolset, marketplace kind `bundle`, resource kinds `bundle` and `bundle.activation`, surface families `bundles`/`bundle_activations`, `ErrExtensionHasActiveBundles`, and all web/site/skill/QA teaching of Bundle as a product unit.
- Absorb the bundle-only capabilities into plain extension enable (P0/P1 of the brief): agent sidecar packaging, package automation, package layouts, enable preview, resource inventory, network-participation confirm on the extension lifecycle, post-install secrets binding (ADR-002..008).
- Homonyms survive untouched: support diagnostics bundles, skill `SourceBundled`/`--source bundled`, task ContextBundle, `crash_bundle_path`, CLI `outputBundle` helpers, sigstore/JS bundling, and the extension dev-lane "bundle generation" (`dist/gen-<hash>`) vocabulary.

## Alternatives Considered

### Alternative 1: Keep bundles and ship first-party profiles

- **Description**: Invest in bundle content (dev-cycle profile, bridge kits) instead of deleting the surface.
- **Pros**: No removal work; the "outcome preset" vision stays alive.
- **Cons**: The implemented projector cannot deliver the outcome promise (no dependency install, no secret binding, no bridge enablement — `docs/ecosystem/bundle-opportunities.md:30`); every fit-labeled flagship blueprint is "Platform evolution"; the dual mental model and surface tax remain; first-party content would legitimize a second ceremony we would then have to keep forever.
- **Why rejected**: Product decision recorded in the brief; the projector is a second ceremony without a second capability.

### Alternative 2: Merge bundles into extensions as "profiles" under the extension detail

- **Description**: Keep multi-profile activate/deactivate but present it as part of the extension surface.
- **Pros**: Preserves profile selection and workspace-scoped activation.
- **Cons**: Renaming does not remove the second lifecycle (activate/deactivate beside enable/disable); explicitly listed as a non-goal ("do not reintroduce multi-profile activate/deactivate as a second public concept, even under a new name").
- **Why rejected**: Violates the brief's non-goal; keeps all the ceremony cost.

### Alternative 3: Delete the public surface but keep `internal/bundles` as a dormant projector

- **Description**: Remove routes/CLI/tools but leave the runtime package "for later".
- **Pros**: Cheaper now; a future pack/compose product could reuse it.
- **Cons**: Zombie API with no consumer; violates greenfield zero-legacy (SD-002, L-006) and the brief's explicit constraint ("no zombie API — delete or fully rehome").
- **Why rejected**: Explicitly forbidden by the brief.

## Consequences

### Positive

- One concept for operators and agents: `extension install → (bind secrets if needed) → enable → kit live; disable → kit off`.
- ~15k lines of production+test code, 8 routes, 5 tools, 1 marketplace kind, and a docs/QA surface removed.
- Extensibility checklists (CLAUDE.md, SD-011, spec playbook) shrink by one permanent surface.
- The `internal/resources` mixed-kind projector escape hatch (`BundleActivationProjector`) loses its only consumer and is deleted too.

### Negative

- Capabilities that existed only via bundles must be rebuilt extension-side (ADR-002/004/005/007) before the cut is complete.
- Profile selection (one catalog entry, several activatable shapes) and workspace-scoped packaged resources are lost with no replacement (accepted: brief non-goals).
- Bundle bridge presets (disabled instances + secret-slot metadata) die without replacement; bridge instances remain a separate operator step (`compozy bridge setup`).

### Risks

- Missed living references after the cut — mitigated by the verified removal inventory (exploration report with file:line evidence) and grep/contract verification gates in the techspec.
- Homonym collateral damage — mitigated by the explicit keep-list and homonym smoke tests (`_tests.md`).

## Implementation Notes

Replacement capabilities land before the cut (techspec phases A–C before D) so `dev-cycle` and fixtures always have a working kit path. Orphaned `resource_records` rows (`kind IN ('bundle','bundle.activation')` and rows with `owner_kind = 'bundle.activation'`) are removed by a one-shot Goose cleanup migration in the removal phase — no boot repair.
