# ADR-005: Network-participation confirm moves to the extension lifecycle; update refuses before apply

## Status

Accepted

## Date

2026-07-29

## Context

Extension manifests already declare `network_participation` (`required`, `mode: live`, `channel_scopes`) with a canonical SHA-256 digest (`internal/extension/manifest_network_participation.go:66-88`) — but the confirm machinery is keyed entirely to bundle activation rows: activate refuses without `confirm_network_requirement`, the digest is stored on the activation, a digest change invalidates prior confirmation, and reconcile re-gates (`internal/bundles/network_requirement*.go`). With activations deleted, the manifest declaration would become inert: `extension install/enable/update` have no confirm gate today.

The confirmation is a consent record (digest + actor + timestamp), deliberately decoupled from runtime enforcement — participation modes are resolved elsewhere (`internal/network/participation`).

## Decision

Move the confirm state machine onto the extension lifecycle:

- **Storage is instance-scoped** (peer-review R1 B-001): three columns on `extensions` for the published instance — `network_requirement_digest TEXT NOT NULL DEFAULT ''`, `network_confirmed_by TEXT`, `network_confirmed_at TEXT` — and the same three on `extension_dev_links` for dev instances (a dev-only extension has no `extensions` row and still persists consent). Digest recomputed from the loaded manifest; confirmation is valid only while the stored digest equals the manifest digest.
- **Confirmation is digest-exact and actor-true** (peer-review R1 B-006): the request carries `confirm_network_digest` — the exact digest the caller saw (from preview or the 409) — never a bare boolean; the lifecycle coordinator re-reads the candidate manifest under its lock and rejects a mismatch with the current digest, so a stale digest is never ratified. The recorded actor is the real caller identity: `operator` on operator transports, `agent:<session-scoped id>` via the native tool's canonical dispatcher.
- **Enable gate**: when the manifest digest is non-empty and unconfirmed, `extension enable` fails with a deterministic 409-class error carrying the current digest; a matching `confirm_network_digest` records `{digest, actor, now}` atomically with the enable commit. Confirmation persists across disable/enable cycles; only a digest change invalidates it.
- **Update refuses before apply** (user decision, 2026-07-29): `extension update` resolves the staged new manifest, computes its digest, and — if it differs from the confirmed digest and the request carries no matching `confirm_network_digest` — refuses with the deterministic error **before any swap**. The running kit stays on the old version with its old, still-valid consent. `update --all` never blanket-confirms: digest-changing items are refused per-item with their digests in the batch partial progress; confirmation happens per extension via a single update call.
- **Serialization** (peer-review R1 B-002): both gates run inside the daemon's per-extension lifecycle mutation coordinator — preflight fence, staged mutation, confirmation write, reload, reconcile, and response form one operation with reverse rollback (a failed update restores the prior confirmation tuple).
- Dev-lane reloads follow the same gate against the dev link's confirmation state (a dev generation whose manifest declares a changed requirement needs re-confirm on reload).

## Alternatives Considered

### Alternative 1: Apply the update, then block the reload

- **Description**: Swap files, then fail activation with `errored (network_confirmation_required)` until confirmed.
- **Pros**: Update verb never blocks; consent still gates the run.
- **Cons**: Takes a working kit down until an operator acts; leaves the install in a half-state (new files, refusing to run) that agents must diagnose.
- **Why rejected**: User decision; downtime is a worse failure mode than a refused update with a precise remediation.

### Alternative 2: Apply and keep running with a pending flag

- **Description**: Update applies, extension keeps running, status/doctor show `network_confirmation_pending`, next enable re-gates.
- **Pros**: Softest UX.
- **Cons**: The kit runs under a requirement the operator never consented to — the consent record becomes theater.
- **Why rejected**: User decision; violates consent-first semantics.

## Consequences

### Positive

- Zero downtime and zero consent gap: nothing runs under an unconfirmed requirement, and nothing already-consented breaks.
- The manifest declaration regains meaning without any bundle object.
- Deterministic, remediable errors for agents (`error carries digest; retry with --confirm-network-requirement`).

### Negative

- `update` gains a refusal path callers must handle (surfaced in batch progress and web update affordances).
- Three new columns on `extensions` (Goose migration; alpha hard cut acceptable).

### Risks

- Staged-manifest availability differences across sources — the update pipeline already stages and parses the new manifest before swap (`internal/extension/marketplace_update_*.go`, `managed_change.go`); the digest compare hooks into that point. Covered by per-source integration tests.

## Implementation Notes

`GET /api/bundles/network/settings` (declared-channels read model) is deleted with the product; the network observability merge in `internal/api/core/handlers_observability.go:144-151` drops the bundle branch. Extensions do not project declared channels in this program — the manifest requirement + consent record is the whole surface (channels were bundle-profile data, which no longer exists).
