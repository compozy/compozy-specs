# ADR-008: Code-first static resource declaration (SDK → describe → generated manifest)

## Status

Accepted

## Date

2026-07-29

## Context

Since ext-improvs, subprocess-extension manifests are build artifacts: `compozy extension build` runs the SDK in describe mode and generates `extension.toml` exclusively from `DescribePayload` (`internal/extension/build_describe.go:37-81`). The payload carries tools/hooks/command groups but **no static resource dirs**, and the TOML encoder emits only `tools`, `hooks`, `command_groups` (`manifest_encode.go:64-95`). Loose files copied into `dist/` are carried into the generation but never declared — so a code-first extension cannot ship skills, loops, agents, automation, or layouts today. With bundles deleted and the kit story moving entirely to static resources (ADR-002/007), code-first authors need a first-class way to declare them; resource-only extensions keep handwritten manifests.

## Decision

- The SDK definition (Go and TypeScript) gains a `resources` declaration listing static resource dirs relative to the package root: `skills`, `loops`, `agents`, `automation`, `layouts` (string lists, same semantics as the manifest fields).
- `DescribePayload` gains a `resources` block (generated contract type in `internal/extension/contract`, emitted into both SDKs like the command specs).
- `compozy extension build` copies each declared dir into the immutable generation and emits the corresponding `[resources]` entries in the generated `extension.toml`; validation of the declared content (agent dirs, automation TOML, layout JSON) runs at build/validate time with TOML/JSON positions, so a malformed kit fails the build, never the runtime.
- Handwritten manifests (resource-only extensions) declare the same fields directly — one schema, two authoring modes, unchanged from the ext-improvs split.
- `resources.bundles` is deleted from the manifest schema in the same change (ADR-001).

## Alternatives Considered

### Alternative 1: Hybrid authoring (authored `extension.toml` merged with generated)

- **Description**: Let subprocess authors keep a handwritten manifest fragment for resources that build merges with the describe-derived manifest.
- **Pros**: No SDK/describe change.
- **Cons**: Reintroduces the dual-declaration/drift class ADR-001 (ext-improvs) was created to kill; two files must agree; deterministic-manifest invariant gets a second input.
- **Why rejected**: Directly contradicts the accepted code-first architecture.

### Alternative 2: Convention over declaration (build auto-detects `skills/`, `agents/`, …)

- **Description**: Build scans the package for well-known dir names and declares whatever exists.
- **Pros**: Zero authoring.
- **Cons**: Implicit shipping (a stray `agents/` dir becomes product surface); no way to exclude or rename; violates the explicit-consent posture of the kit switch.
- **Why rejected**: Implicit product surface is the wrong default for anything enable will activate.

## Consequences

### Positive

- Code-first parity: one SDK definition describes the entire kit (tools + hooks + commands + static resources); the manifest remains a pure build artifact.
- Build-time validation gives authors kit errors with file positions before anything is installed.

### Negative

- Describe contract, generated SDK contracts, and build/validate all change together (codegen co-ship, byte-checked).

### Risks

- Generation-size growth from copied resource dirs — bounded by existing archive limits; build reports per-dir sizes in verbose output.

## Implementation Notes

`copyLooseBuildArtifacts` behavior (copying whatever sits in `dist/`) is unchanged but no longer the only path — declared dirs are copied from the source tree into the generation explicitly, with the existing canonical-overlap and containment guards. `min_compozy_version` stamping and manifest determinism (sorted keys) apply to the new fields.
