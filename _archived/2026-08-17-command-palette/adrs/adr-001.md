# ADR-001: One unified command registry with full OS coverage

## Status

Accepted

## Date

2026-08-17

## Context

The web palette and the daemon shortcut system evolved as two disjoint catalogs. Of the ~60 window-manager action ids registered in `internal/windowmanager/shortcuts.go`, ~46 are keyboard-only and unreachable from the palette; conversely, palette rows (Toggle sessions, Appearance, workspace switching, worktree scoping) have no action id and can never be key-bound. Commands are hand-written JSX literals across four components with no id, category, keywords, or predicate — nothing can be enumerated, ranked, tested, or contributed. Entity search covers only sessions, open tabs, and ready worktrees; agents, tasks, loops, jobs, triggers, bridges, knowledge, vault, network, marketplace, and ~25 settings pages are invisible. CompozyOS positions the palette as an OS-grade surface (Raycast-class), and the repo premise requires every capability to be enumerable and manageable.

## Decision

Build one unified command registry as the single source of truth for every palette-invokable capability:

- Every window-manager action id becomes a palette command; every palette command gets a stable, bindable id. The "two catalogs, one wall" split is eliminated.
- The root catalog covers the full OS surface: all shell/window/tiling/desktop/workspace actions, all apps, entity search across every daemon domain (sessions, agents, tasks, loops, jobs, triggers, bridges, knowledge, vault, network, marketplace), and settings pages/keys.
- Commands are data descriptors (serializable), not JSX — render sites consume the registry.

## Alternatives Considered

### Alternative 1: Keep two catalogs, patch the palette

- **Description**: Add missing rows to the palette by hand; leave keyboard actions and palette rows as separate systems.
- **Pros**: No architectural work; incremental.
- **Cons**: The wall persists — every new action must be added in two places; extensions and agents still have nothing to enumerate; drift continues.
- **Why rejected**: The gap is structural, not a backlog of missing rows.

### Alternative 2: Unify actions only, defer entity/settings search

- **Description**: Merge the action catalogs but keep entity search at today's three domains.
- **Pros**: Smaller spec; less API surface.
- **Cons**: "Complete palette" was the explicit product goal; per-domain follow-up specs would re-litigate the same provider design N times.
- **Why rejected**: User decision 2026-08-17 (grill round 1): full OS coverage in this spec.

## Consequences

### Positive

- One enumerable catalog serves palette, keyboard, cheatsheet, menubar, agents, and extensions.
- Every command becomes bindable, rankable, testable, and addressable by id.
- Entity and settings search make the palette the primary navigation surface of the OS.

### Negative

- Registry becomes a load-bearing contract shared across web, daemon, CLI, and extensions — schema changes ripple.
- Initial migration touches every hardcoded palette row and the closed action-id enums (Go + TS).

### Risks

- Catalog scale (hundreds of rows + entity results) demands ranking and sectioning discipline — mitigated by ADR-003 ranking and section assembly.
- Registry/cheatsheet/shortcut-table consistency is one more contract to keep in sync — mitigated by deriving all three from the same source.

## Implementation Notes

Greenfield alpha: hard cut, no aliases or dual fields. The old hand-written JSX groups and the closed TS/Go action enums are delete targets, replaced by registry-driven rendering (details in Part II of the spec).
