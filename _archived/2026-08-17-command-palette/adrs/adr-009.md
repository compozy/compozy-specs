# ADR-009: Two composable view tiers; the programmable tier is TypeScript-only this cycle

## Status

Accepted

## Date

2026-08-17

## Context

With programmable views decided (ADR-008), two authoring questions remained. (1) Does the declarative tier (manifest + `source: tool` returning a payload) survive alongside programs? Research (analysis/09 F13): VS Code, Slack, and Raycast all run declarative + programmable tiers without regret; the one documented regret (VS Code) is tiers that cannot compose. (2) What does each language's author write? The "React in Go" question was researched to ground truth (analysis/09): classic SSR emits HTML (wrong artifact); RSC/Flight has no stable non-DOM contract (unbundled build pulled from npm, live RCE class) and does nothing for Go; embedded JS engines either break npm built-ins (pure-Go QuickJS) or break distribution (v8go); WASM components are not ready for either language (Zed still ships no UI extensions); and **no react-reconciler analog exists in Go** — a Go MVU library emitting a retained diffable tree is net-new work (Bubble Tea proves the DX model, not the machinery).

## Decision

1. **The frame/patch vocabulary is THE contract** — language-neutral, defined by Go types (ADR-007), produced by either tier.
2. **Two composable tiers**:
   - **Tier 1 — declarative** (`source: {tool}`): the view is a projection of a tool's payload into the frame vocabulary. Available to **both** TypeScript and Go extensions. Zero view code; interactivity limited to declared chips/actions resolved by the host or routed as tool invocations.
   - **Tier 2 — programmable** (`program: true`): a live view program over `view.provider` (ADR-008).
   - **Composability rule** (the VS Code lesson): both tiers emit the same vocabulary, so a declarative view can appear inside a programmable flow (e.g. pushed as a frame) and programmable views render with the identical host components. No parallel rendering systems.
3. **The programmable tier ships TypeScript-only this cycle**: the **`@compozy/extension-react` package** (separate workspace package at `sdk/react/` — user decision; the monorepo versions everything together and `codegen-check` + the Bun typecheck lane gate typing drift) — real React via `react-reconciler` in persistent mode (Fabric pattern), diffed to patches in the extension, npm ecosystem intact. **The Go MVU library is explicitly deferred** (user decision: building a Go retained-tree/MVU DSL is not worth it now). Go extensions contribute palette commands, default shortcuts, and Tier-1 views this cycle; the wire contract's language neutrality keeps the door open for a Go program tier later without redesign.

## Alternatives Considered

### Alternative 1: Ship the Go MVU library now (full language parity)

- **Pros**: Both languages get programmable views; matches the both-languages examples requirement symmetrically.
- **Cons**: Net-new framework work (retained tree + diff + Elm runtime) with no existing Go analog; delays the whole cycle for the minority authoring path.
- **Why rejected**: User decision 2026-08-17 — "criar todo um DSL em Go para isso é um trabalho que não vale a pena agora."

### Alternative 2: Embedded pure-Go QuickJS in the daemon (one runtime for TS)

- **Pros**: Single static binary runs TS extensions; hard per-extension limits.
- **Cons**: Loses Node built-ins (SDK clients importing `node:http`/`fs`/`crypto` fail to load); runaway extension shares the daemon's process fate — the exact trade Raycast declined; doesn't help Go anyway.
- **Why rejected**: npm-ecosystem loss is disqualifying for v1; recorded as the researched fallback.

### Alternative 3: Programmable-only (drop the declarative tier)

- **Why rejected**: Would leave Go extensions with zero view capability this cycle and forces ceremony on the trivial case; two tiers is the industry norm (analysis/09 F13).

### Alternative 4: RSC/Flight as the TS serialization

- **Why rejected**: No stable non-DOM public API; Dec-2025 RCE class in Flight deserialization; tracks React internals; nothing for Go.

## Consequences

### Positive

- TS authors get literal Raycast DX (JSX, hooks, npm); Go authors keep a real (if bounded) view story via Tier 1; one renderer, one vocabulary, tiers compose.
- Honest scope: no half-built Go DSL shipped for symmetry's sake.

### Negative

- Language asymmetry this cycle — must be documented loudly in `_dx.md` and the site docs (Go: commands + shortcuts + declarative views; programs: TS).
- The TS reconciler layer becomes load-bearing SDK surface (its own tests/stories/versioning).

### Risks

- Pressure to "just embed an engine" later — the analysis/09 table records why each shortcut fails, so the decision doesn't get re-litigated blind.
- Tier-1 expressiveness creep (declarative views growing pseudo-programmability) — mitigated: interactivity beyond declared chips/actions requires Tier 2.

## Implementation Notes

`_dx.md` carries: Tier-1 examples in BOTH languages (tool implementations returning view payloads — Go and TS), the complete Tier-2 React example (TS), and the explicit Go limitation note. DescribePayload/manifest: `views[].program: true` requires the extension to implement `view.provider` (validate-time check); Go extensions declaring `program: true` fail validate with an actionable message this cycle.
