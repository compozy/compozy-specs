# ADR-004: View vocabulary is the full Raycast kit — List, Detail, Form, Grid

## Status

Accepted

## Date

2026-08-17

## Context

The herdr-parity program constrained palette views to "list-shaped, keyboard-navigable results" and recorded "mini-apps inside the palette" as its scope-creep risk (archived herdr ADR-003). That constraint fit a single built-in Sessions view. This spec opens views to extensions (ADR-002) and targets Raycast-class functionality; Raycast's proven extension UX rests on a small fixed component vocabulary — List (sections, detail accessory, dropdown), Detail (+metadata), Form (drafts), Grid — which is precisely why third-party extensions feel native there: expressive enough for real workflows, closed enough to stay keyboard-first and design-consistent. A list-only vocabulary would cap extension UX at fire-and-close commands plus flat result lists (no entity preview, no structured input, no media browsing).

## Decision

The palette view vocabulary for this cycle — built-in and extension-contributed alike — is the full four-kind kit:

- **List** — rows, sections, chips/filters, optional detail accessory split.
- **Detail** — read-only content pane with a metadata sidebar.
- **Form** — typed input fields for structured command input (beyond inline arguments).
- **Grid** — icon/media-oriented results.

All four remain keyboard-navigable, serializable data (no extension code in the renderer, per ADR-002), and rendered exclusively by host-owned components on `@compozy/ui` primitives. This supersedes the list-only constraint of herdr ADR-003; the "no mini-apps" intent survives as a rule — views compose only this fixed vocabulary, arbitrary layout/embedded UI stays impossible by construction.

## Alternatives Considered

### Alternative 1: List-only plus inline arguments (the recommended conservative option)

- **Description**: Keep herdr's list-only rule; typed arguments render inline in the input; no detail/form/grid.
- **Pros**: Smallest serialization contract; zero risk of palette-as-app-platform; honors the prior guard-rail as written.
- **Cons**: Extension UX ceiling is low (no preview, no structured forms, no media); would force a second vocabulary expansion spec almost immediately.
- **Why rejected**: User decision 2026-08-17 (grill round 2): full kit — the Raycast bar was the explicit product target.

### Alternative 2: List + read-only Detail accessory only

- **Description**: Add entity preview but no standalone Detail/Form/Grid.
- **Pros**: Covers the highest-value addition (preview) with one extra format.
- **Cons**: Structured input still homeless (forms), media browsing impossible; an in-between contract that satisfies neither constraint nor ambition.
- **Why rejected**: Same user decision; the marginal spec cost of Form/Grid over Detail is bounded once the serializable-vocabulary machinery exists.

## Consequences

### Positive

- Extensions can ship real workflows (browse → preview → structured input → execute) without renderer code.
- One vocabulary serves built-ins too — Sessions gains a Detail accessory path; marketplace/media surfaces gain Grid.
- The fixed-kit approach preserves native feel and design-token fidelity (host renders everything).

### Negative

- Four serialization contracts to design, validate, version, and test instead of one.
- Keyboard-navigation contracts must be specified per kind (focus order in forms, grid arrow semantics).
- Larger security/validation surface for extension-supplied content (markdown in Detail, field constraints in Form).

### Risks

- Vocabulary creep beyond the four kinds ("just one more component") — mitigated: adding a view kind requires a new ADR.
- Form views drifting into general app UI — mitigated: forms exist to collect command input and submit to a command action; no free-form navigation between forms.

## Implementation Notes

The serialization/rendering technology is settled by ADR-007 (Go-owned typed vocabulary + JSON Patch, covering all four kinds) and extended by ADR-008/009 (programmable tier). Keyboard contracts per kind land in `_uiux.md`.
