# ADR-006: The command registry is daemon-canonical with a web projection

## Status

Accepted

## Date

2026-08-17

## Context

Command authority is split today: the daemon registers ~60 window-manager action ids (bindable, agent-invisible), while the web hardcodes palette rows as JSX (searchable, unbindable, agent-invisible). The frozen surface requires agents to enumerate and invoke every command (core + extension) via CLI/HTTP/UDS with availability reasons and bindings, the menubar/cheatsheet/settings to render the same truth, extensions to contribute at runtime, and personalization to be workspace-scoped daemon state (ADR-003). A client-owned registry cannot satisfy any of that; a fully daemon-evaluated registry would add a round-trip to every keystroke-latency context change.

## Decision

The Go daemon owns the canonical command registry:

- **Daemon side**: the full catalog (core commands, extension contributions, entity/settings providers' command metadata), descriptor validation, id namespacing, availability policy, binding/alias state, personalization **signals and versioned weights** (scoring executes in the single client-side scorer — ADR-003 as amended), and the `/api/cmd-palette/*` + SSE (`cmd_palette.catalog.changed`) surfaces. Core commands are declared in Go — the daemon never needs the web to know what exists.
- **Web side**: a hydrated projection (stale-while-revalidate, revision-keyed) that renders all surfaces from one client registry object and evaluates only **volatile local context** (focused window, presentation state, destination intent) against daemon-declared predicates — so keystroke-level availability never round-trips.
- **Execution**: one dispatch seam — UI-effecting actions run in the attached client; runtime-effecting actions run in the daemon; both report through the same result contract regardless of entry surface (palette, chord, menubar, agent).

## Alternatives Considered

### Alternative 1: Split authority (web owns core UI commands, daemon owns extension commands)

- **Description**: Evolve the status quo — register web commands in TS, merge extension commands from the API.
- **Pros**: Least Go work; no core-command migration.
- **Cons**: Agents cannot enumerate/invoke core commands; menubar/cheatsheet keep a second source; bindings for web-only commands stay impossible (the exact wall ADR-001 removes); two registries to keep consistent forever.
- **Why rejected**: Structurally incompatible with the frozen `_dx.md` surface; user confirmed daemon-canonical (internals grill, 2026-08-17).

### Alternative 2: Fully daemon-evaluated (no client context evaluation)

- **Description**: Every availability change round-trips to the daemon.
- **Pros**: Single evaluation site.
- **Cons**: Focus/window context changes are keystroke-frequency; latency and reconnect degradation would make availability flicker or lag.
- **Why rejected**: Violates the "opens instantly, never blocks on daemon" constraint.

## Consequences

### Positive

- One catalog serves palette, keyboard, cheatsheet, menubar, settings, CLI/HTTP/UDS, and native tools — drift is structural, not procedural, impossible.
- Extension contributions and core commands are the same kind of thing, enabling uniform policy, search, and binding.

### Negative

- Core command declarations move to Go (large one-time migration of the hardcoded groups); web keeps thin client-effect handlers keyed by command id.
- A context-predicate contract (daemon-declared, client-evaluated) must be specified precisely.

### Risks

- Client/daemon catalog skew — mitigated by `catalog_revision` + SSE invalidation + stale-while-revalidate hydration.
- Predicate vocabulary creep — mitigated by a closed, versioned context-key set (Part II).

## Implementation Notes

Delete targets and the migration inventory (hardcoded palette groups, TS action-registry mirror, closed Go action enums growing a registry API) are specified in `_spec.md` Part II Impact Analysis.
