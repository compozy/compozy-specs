# ADR-004: Desktop state persists daemon-side in a bbolt-backed client-state KV with WebSocket sync

## Status

Accepted

## Date

2026-07-19

## Context

The desktop layout (open windows, rects, z, minimized, focus, wallpaper, rail state — per workspace) must survive reloads and stay consistent across clients in real time. Pedro decided persistence is daemon-side from v1, explicitly NOT in SQLite: layout is high-churn, schemaless presentation state that would drag Goose/Atlas migration ceremony (L-008) for every shape tweak, and the SSE→invalidate→refetch pattern is a poor fit for layout sync. He asked for a key-value substrate with real-time over WebSockets. Verified in-repo: `gorilla/websocket` is already a Go dependency (Daytona sidecar); there is no NATS, no embedded KV, and the web app has no WebSocket usage today (SSE everywhere). The spec-authoring playbook refuses "generic event bus / remote-carrier infrastructure without a shipped consumer".

## Decision

Add a small, generic **client-state service** to the daemon:

- **Storage: bbolt** (etcd's embedded B+tree KV; pure Go, ACID, single file) at `$AGH_HOME/state/clientstate.db`, bucketed `ws:<workspace_id>` → `<domain>` → key, value = envelope (monotonic rev, updatedAt, opaque JSON payload).
- **Transport: one WebSocket endpoint** per workspace (`gorilla/websocket`, already in the tree) carrying subscribe/snapshot/put/delete/event/ack/error frames — clients write and watch over the same socket. HTTP + UDS CRUD endpoints and `agh client-state` CLI verbs provide agent-manageable parity (SD-011).
- **Concurrency model**: last-writer-wins per key with monotonic revision; optional `if_rev` compare-and-swap; echo suppression by origin connection id; slow consumers are disconnected, never block writers.
- The service is domain-namespaced and payload-opaque: the OS shell uses domain `os_shell`; other domains are reserved for future consumers (no extension API in v1).

## Alternatives Considered

### Alternative 1: SQLite table in the existing workspace stream

- **Pros**: No new storage engine; existing store discipline.
- **Cons**: Migration ceremony for presentation state; refetch-style sync; explicitly vetoed by Pedro on churn/perf posture.
- **Why rejected**: Wrong lifecycle fit for schemaless high-churn UI state; owner decision.

### Alternative 2: Embedded NATS server + JetStream KV + nats.ws

- **Pros**: KV with native watch; browser WebSocket transport; future pub/sub substrate.
- **Cons**: A full messaging runtime inside the daemon (goroutines, storage dir, auth surface, config) to persist window rects; playbook-refused "generic infrastructure without a shipped consumer".
- **Why rejected**: Disproportionate for v1; belongs to its own future TechSpec if a real pub/sub consumer materializes.

### Alternative 3: Debounced HTTP PUT + existing SSE invalidation

- **Pros**: Maximum consistency with current web data patterns.
- **Cons**: No bidirectional channel; PUT spam during gestures; refetch instead of patch.
- **Why rejected**: Pedro asked for WS; layout sync wants ordered per-key patches.

### Alternative 4: localStorage only

- **Why rejected**: Owner decision — daemon-side from v1 (cross-device, agent-inspectable).

## Consequences

### Positive

- No schema migrations for layout shape changes; the JSON payload is versioned client-side.
- A reusable, agent-manageable KV+watch primitive with a shipped consumer (the OS shell) from day one.
- Multi-tab/multi-device desktops converge in real time.

### Negative

- New storage engine (bbolt) and first browser-facing WebSocket in the product — new operational surface (connection lifecycle, reconnect, backpressure).
- Two persistence technologies in the daemon (SQLite for relational/matchable state, bbolt for opaque client state) — boundary must stay crisp: anything the daemon must match, filter, join, or transact relationally stays in SQLite; the KV's typed envelope is its public contract (ADR-008).

### Risks

- Unbounded writes from a buggy client → per-entry size cap and per-workspace retained-key quota (including tombstones) in config, deterministic errors.
- WS lifetime vs write atomicity → writes apply under detached context (L-001); socket teardown never aborts a committing tx.

## Implementation Notes

Package `internal/clientstate` (service, bbolt store, hub); wiring in `internal/daemon` only (SD-008). Web client: `OsStateClient` in `systems/os` — connect, subscribe `os_shell`, snapshot-hydrate, debounced rect writes (250ms trailing + gesture-end flush), reconnect with backoff; if WS is unavailable the shell runs with in-memory state (`degraded` hydration) rather than blocking.

## Amendment (2026-07-19, peer-review round 1 — B-002/B-003/B-004/B-005/B-008, ADR-008)

Round 1 hardened this decision without changing the engine:

- **Ordering:** per-key `Rev` alone cannot fence snapshots. Each workspace gains a transactionally-stored monotonic **commit sequence (`seq`)**; a per-workspace sequencer serializes commit→publish so events reach the hub in commit order; deletes write **tombstones** preserving rev continuity across recreate; subscribe is linearized (register → snapshot at `as_of_seq` → only events with `seq >` fence).
- **Atomicity:** a transactional **`Apply` batch** (multiple put/delete in one tx, consecutive seqs, one ack) carries invariant-spanning window actions (focus/close/z). WS frames gain client request ids (`req`) echoed on ack/error.
- **Socket lifecycle:** one reader pump + one single-writer pump per connection, bounded outbound queue, write/ping deadlines; mutations run under a **daemon-owned lifecycle context with a per-op deadline** (not raw `WithoutCancel`); shutdown joins pumps before the store closes.
- **Workspace integrity:** the service takes a generation-fenced `WorkspaceResolver`; unknown/deleting workspaces fail `workspace_not_found`; workspace deletion runs a serialized gate (mark-deleting → reject normal ops → generation-matched purge) and queued operations revalidate their generation so state cannot resurrect after same-id recreation.
- **Surface narrowing:** the public wire drops the domain axis and ships as `desktop-state` (ADR-008); UDS serves the same upgrade endpoint so `watch` parity holds across transports.
