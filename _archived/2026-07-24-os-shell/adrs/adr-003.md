# ADR-003: Window-manager state in Zustand; react-rnd (controlled) for drag/resize; motion for animation

## Status

Accepted

## Date

2026-07-19

## Context

The desktop needs windows with fully custom chrome (traffic lights, breadcrumb head reusing the Topbar anatomy), drag by head, resize on edges/corners, z-order/focus, minimize/zoom — styled entirely by our token system. The repo already ships `zustand@5`, `motion@12`, and `cmdk` (via `@agh/ui`); React 19 removed `findDOMNode`, which broke older drag libraries. Research (2026-07) verified: react-rnd 10.5.3 works on React 19 in production (daedalOS runs react-rnd + motion on React 19.2); docking managers (dockview, FlexLayout, golden-layout, react-mosaic) impose IDE-style tabbed chrome and the wrong metaphor.

## Decision

- **Window-manager state is an app-owned Zustand store** (`web/src/systems/os`): windows, rects, z-order, focus, minimized/maximized, per-window location, presentation mode. The store is the single authority for window arrangement; drag/resize libraries are mechanisms under it.
- **react-rnd in controlled mode** provides drag + resize in floating presentation: `position`/`size` fed from the store, commits on `onDragStop`/`onResizeStop` (rect updates during gestures stay local/transient; the store commit happens at gesture end, persistence debounced per ADR-004).
- **motion** (already a dependency) animates open/close/minimize (genie-to-dock), focus transitions, and dock magnification, honoring `prefers-reduced-motion` and the appearance toggle.
- **cmdk** (already via `@agh/ui` `Command`) powers the global palette.
- New dependency added to `web/` only: `react-rnd`. `@dnd-kit` is NOT added in v1 (no dock reordering in scope).

## Alternatives Considered

### Alternative 1: Custom pointer-event geometry (zero new deps)

- **Description**: Pointer-capture drag (prototype pattern) + hand-written 8-handle resize math.
- **Pros**: No dependency, total ownership, no wrapper DOM.
- **Cons**: ~200 lines of geometry edge cases (touch, bounds, min/max clamping, cursor states) to write and maintain and test.
- **Why rejected**: react-rnd buys proven edge-case handling for one small, replaceable dep; the store-owned state keeps lock-in near zero (swapping the mechanism later touches one component).

### Alternative 2: @use-gesture/react + motion geometry

- **Pros**: Healthy pmndrs maintenance, inertia/pinch, lower lock-in than react-rnd.
- **Cons**: Still hand-written resize math; adds a dep AND custom code.
- **Why rejected**: Worst of both options for v1; remains the named hedge if react-rnd stalls.

### Alternative 3: Docking layout manager (dockview / FlexLayout)

- **Pros**: Mature persistence/popouts.
- **Cons**: Tabbed-docking metaphor, imposed DOM/chrome/theme fighting the macOS-style design; overkill.
- **Why rejected**: Wrong metaphor for free-floating windows; dockview stays bookmarked only for future popout-to-native-window work.

## Consequences

### Positive

- WM logic is testable pure TS (store actions + invariants) independent of the drag mechanism.
- daedalOS precedent de-risks React 19 + StrictMode behavior.

### Negative

- react-rnd is effectively single-maintainer with loose peers — accepted risk, isolated behind one component.

### Risks

- StrictMode double-invoke quirks → covered by an explicit spike assertion in the first shell task; fallback path (Alternative 1/2) documented here.

## Implementation Notes

react-rnd is used ONLY in floating presentation; compact presentation renders windows without rnd wrappers. Bounds clamp against the desktop layer with dock/menubar gutters; windows re-clamp on viewport resize (fixes a prototype gap).
