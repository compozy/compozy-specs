# ADR-004: Fan-out v2 — completion strategies, first-class partial, progress conditions, naming, and windowed width

## Status

Accepted

## Date

2026-08-16

## Context

`collect` is a strict all-success barrier: one failed branch blocks the join and sends the generation down the failure path; there is no early-exit, no quorum, no first-wins, and partial results have no representation (`analysis/03_analysis_loop-core.md` §3). Branch count is hard-capped at 64 (items are not — batching chunks items into branches). The literature's barrier contract (C6) demands explicit join semantics with a legitimacy rule for quorum and an explicit partial state; v0's anti-lesson 9 records that early-exit strategies that don't actually cancel outstanding work are decorative (`_briefing.md` ideas 20/21/22/23/31).

## Decision

1. **Completion strategies** on fan-out joins: `wait_all` (default, unchanged), `fail_fast` (first failure cancels remaining branches and takes the failure path immediately), `best_effort` (proceed at an author-declared quorum/percentage), `race` (first successful branch wins; the rest are canceled).
2. **Quorum legitimacy**: `best_effort` requires the author to declare that missing branches do not constitute mandatory coverage; the declaration is part of the grammar, not a comment.
3. **Partial is first-class**: a `best_effort` join that proceeds with failures completes in an explicit partial state, visible to downstream conditions and to operators. Partial never presents as complete.
4. **Cancellation first**: per-branch cancellation addressing (node + item) is a prerequisite delivered before the strategies, so `fail_fast`/`race` genuinely cancel outstanding work (anti-lesson 9).
5. **Progress conditions**: a progress namespace (totals, success/failure counts, rates) becomes available to author conditions (gates, stop conditions, strategy thresholds) — "proceed at 80%" is expressible directly.
6. **Iteration ergonomics**: authors can name the iteration variable and index per fan-out, un-shadowing nested fan-outs.
7. **Windowed width**: total branch count becomes unbounded; only a concurrency window of branches materializes at a time. The 64 hard cap on logical width is removed.
8. **Prune/skip observability**: skipped and pruned branches are recorded with their deciding cause in run history (loop-ideas idea 31 delta).

## Alternatives Considered

### Alternative 1: GraphFlow-style activation groups

- **Description**: per-target edge groups with all/any semantics.
- **Pros**: expressive for multi-path cycles.
- **Cons**: novel grammar with under-specified semantics even in its source framework; Compozy cycles live in generations, not edges, so the problem it solves barely exists here.
- **Why rejected**: strategies + progress conditions express the needed outcomes inside the existing fan-out/collect model.

### Alternative 2: Keep the 64-branch cap (defer windowed materialization)

- **Description**: ship strategies only; large collections keep using batching.
- **Pros**: cheapest path; the briefing itself lowered the urgency.
- **Cons**: the cap remains an arbitrary product cliff for legitimate wide workloads.
- **Why rejected**: the user explicitly kept unbounded width in scope (grill Q11), acknowledging it as the most expensive piece.

### Alternative 3: Partial as metadata on a succeeded join

- **Description**: join succeeds; partiality is a metadata flag.
- **Pros**: no new state.
- **Cons**: downstream cannot distinguish partial from complete without convention; violates the literature's "never present partial as complete".
- **Why rejected**: user chose first-class partial (grill Q10).

## Consequences

### Positive

- The join model reaches the full literature contract (strict / quorum / race / early-exit + explicit partial).
- Wide workloads stop hitting an arbitrary width cliff; progress becomes a first-class author signal.

### Negative

- Windowed materialization is the largest engine change in this spec (materialization, throttling, and join arithmetic all become window-aware).

### Risks

- Strategy interactions with retries/quarantine need explicit rules (e.g., does `fail_fast` fire on a retryable failure or on exhaustion?) — resolved in Part II as numbered invariants.

## Implementation Notes

Build order per the briefing: per-branch cancellation addressing → strategies → progress namespace → naming ergonomics → windowed materialization → prune observability.
