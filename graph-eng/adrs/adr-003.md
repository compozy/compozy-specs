# ADR-003: Router node and gate-verdict routing, with a mandatory default route

## Status

Accepted

## Date

2026-08-16

## Context

Loop edges carry no conditions; the `branch` node can only skip a dominated subgraph, which cannot express "continue down exactly one of {A, B, C}". The gate route action `branch` is defined and legality-checked but is a silent no-op at the coordinator (bug B-4). The literature's consensus capability C4 (conditional routing) is what enables model tiering and selective verification — routing high-risk work to expensive review and routine work to cheap validation (`analysis/01_analysis_graph-eng-concepts.md` C4; `analysis/03_analysis_loop-core.md` §7.1–7.2). Nothing in the loop-ideas backlog covered this gap.

## Decision

1. A new **router** control node: the author declares a set of named routes (each a forward destination in the graph) and a deterministic condition that selects exactly one.
2. **Mandatory default route**: a router without a default is a compile-time (lint) error. No-match at runtime is therefore impossible by construction.
3. **Gate-verdict routing**: gates gain the real semantics of their `branch` route action — a verdict (including agent-judge and human outcomes) may select one pre-declared route. This closes bug B-4 with behavior instead of deletion.
4. Non-selected routes skip their dominated subgraphs, reusing the shipped skip machinery; run history records which route was taken and why (route cause).
5. Topology stays deterministic and static: routing selects among pre-declared destinations; no runtime graph mutation, and nothing a model emits can add or rewire routes.

## Alternatives Considered

### Alternative 1: Conditional edges on the Edge grammar

- **Description**: attach conditions/labels to `Edge{From,To}` itself.
- **Pros**: closest to other frameworks' mental model.
- **Cons**: explodes the edge grammar; conditions scattered across edges are harder to lint as an exhaustive set; the node form keeps the whole decision in one lintable place.
- **Why rejected**: a router node preserves the "closed control-node enum + whole-document lint" architecture.

### Alternative 2: Delete the gate `branch` route action (zero-legacy)

- **Description**: remove the no-op action instead of implementing it.
- **Pros**: smallest change; honest grammar.
- **Cons**: loses verdict-driven routing entirely, which is half the product value (quality outcomes choosing paths).
- **Why rejected**: the user chose deciding routes by condition **and** by verdict.

### Alternative 3: Model-decided dynamic goto (Command/Send equivalents)

- **Description**: let agent output name the next node.
- **Pros**: maximum flexibility.
- **Cons**: breaks the core invariant that topology is deterministic and lint-provable; the corpus's own governance rule says the model may propose, only a trusted runtime validates and executes.
- **Why rejected**: out of scope by design; the agent-drivable DAG remains a future RFC (loop-ideas idea 35, Non-Goal).

## Consequences

### Positive

- Exclusive multi-way routing becomes expressible; model tiering and selective verification become authorable.
- B-4 is closed with semantics, not deletion; route causes make the decision auditable.

### Negative

- The linter grows a new exhaustiveness surface (routes must be forward, unique, and dominated subgraphs well-formed).

### Risks

- Authors conflating `branch` (skip) with `route` (exclusive selection) — mitigated at Stage 2 with naming/docs and lint messages that point to the right node for the intent.

## Implementation Notes

Surface resolution (Stage 2 grill, 2026-08-16): node kind is `route` with `routes: [{when, to}]` + mandatory `default:`; gate routing uses the `on_result` object form `{ route: <node_id> }`, and the legacy `branch` route action string is **deleted** (lint `route_action_removed` points at the new form) — zero-legacy, no alias.
