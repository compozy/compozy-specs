# ADR-005: Bug absorption — hash_fields deletion, predicate failure defaults, gate revision semantics

## Status

Accepted

## Date

2026-08-16

## Context

The loop-ideas verification recorded three shipped-code defects (B-1 `no_progress.hash_fields` authorable-and-dead; B-2 `ApplyPredicateFailurePolicy` complete dead code; B-3 predicate cost measured and discarded), and the graph-eng exploration found two more (B-4 gate route `branch` silent no-op; B-5 gate `max_revisions` counts generations, not gate visits). The briefing recommended fixing B-1..B-3 as bugs outside any spec; the user decided all five land inside this spec (grill Q13). The briefing's open decision #7 asked whether a failing predicate should be a routable failure and whether a broken `stop_when` should exit rather than block succession.

## Decision

1. **B-1 — delete `hash_fields`** (zero-legacy) rather than wire it: the field leaves the grammar, the public API contract, and every fixture/test. Stall detection remains the blocking-issue signature. Idea 12's restart semantics stay out entirely.
2. **B-2/B-3 — wire the predicate failure policy with the briefing defaults**: continuation predicates fail **open** (a broken `stop_when` exits the loop instead of blocking succession); routing predicates fail **closed** (a broken routing condition becomes a routable authoring failure). Per-node override exists. Predicate cost observability is wired: the measured cost and the 80% warning surface instead of being discarded.
3. **B-4 — resolved by ADR-003**: a gate verdict selects a pre-declared route.
4. **B-5 — `max_revisions` counts per-gate revise visits**, not generations. Two gates in one graph stop sharing a counter.

## Alternatives Considered

### Alternative 1: Wire `hash_fields` as a real progress fingerprint

- **Description**: the briefing's "cheap half of idea 12" — compute a generation fingerprint from the named fields for stall diagnostics.
- **Pros**: honors the field's apparent meaning; diagnostic value.
- **Cons**: keeps a knob whose only consumer would be a diagnostic; restart semantics (the real payoff) remain out, so the field's promise stays half-true.
- **Why rejected**: user chose deletion (grill R2-2) — a knob that does not change behavior is the exact anti-lesson-1/2 failure mode; delete now, redesign holistically if idea 12 ever lands.

### Alternative 2: Fix B-1..B-3 in a separate bug batch (briefing recommendation)

- **Description**: "fix as bugs, not as specs".
- **Pros**: smaller spec; bugs ship faster.
- **Cons**: B-2/B-3's behavioral decision (#7) deserves spec-grade treatment; splitting creates two delivery trains over the same files this spec touches.
- **Why rejected**: user chose all-in (grill Q13).

### Alternative 3: Always fail-closed predicates

- **Description**: any broken predicate fails the node/run.
- **Pros**: uniform rule.
- **Cons**: a broken `stop_when` would hang or kill an otherwise-healthy run — the exact behavior users cannot repair mid-flight.
- **Why rejected**: continuation and routing predicates have opposite blast radii; the split default is the safe pair.

## Consequences

### Positive

- Zero dead knobs remain in the loop grammar; predicate failures become explainable, routable behavior; gate revision budgets act per gate as authors expect.

### Negative

- Deleting `hash_fields` is a breaking grammar change for any definition using it (alpha: acceptable; lint reports unknown parameter).

### Risks

- Silent behavior change for runs relying on "broken stop_when blocks succession" (unlikely to be intentional anywhere) — release notes call it out.

## Implementation Notes

**Delete targets (B-1)**: the `no_progress.hash_fields` grammar field, its public API contract field, and every fixture/test referencing it — same change, no fallback, no compat shim.
