# ADR-007: Per-Loop Input Defaults in Configuration (`[loops.inputs.<name>]`)

## Status

Accepted

## Date

2026-07-11

## Context

`review-and-fix` declares operational inputs — at this ADR's date `pr`,
`auto_push`, `include_nitpicks`, `poll_interval`, and `quiet_period`; after
ADR-008 the declared set is `task_name`, `reviewer`, `fixer`, and
`auto_commit`. Legacy configuration persisted equivalent values, but AGH has
no configuration layer for values in a loop author's input namespace. Putting them in engine configuration would make
the engine know loop-specific knobs; requiring `--input` for every run loses
the legacy "set once" behavior.

## Decision

1. **A declarative file surface exists at global and workspace scope.**
   `[loops.inputs.<loop-name>]` supplies defaults only for inputs declared by
   that loop. The per-key resolution order at submission is explicit run value
   > workspace value > global value > definition default. A required input may
   be satisfied by any configuration layer.
2. **Presence, not truthiness, controls merge and provenance.** `false`, `0`,
   an empty-but-valid string, and any other explicit zero value remain present
   values and preserve their source. Effective-input output returns both value
   and origin (`run`, `workspace`, `global`, or `definition`) per key.
3. **Validation occurs at the truthful resolution phase.** Dynamic extension
   and user-authored loops mean config loading cannot know every input schema.
   Static `loop validate` checks only definition-contained defaults supplied in
   its definition request. Stored global/workspace values are checked by the
   shared effective dry-run/submission resolver. Both use declared-input type
   validation and typed `input_default { loop, key, reason }` errors for unknown
   keys and type mismatches. Configured and explicit per-run unknown keys both
   fail; nothing is silently dropped.
4. **Dynamic management is cross-surface, not CLI-only.** The loop
   configuration resource exposes input-default inspect, get, set/replace, and
   unset/delete operations through CLI, HTTP, UDS, and the corresponding native
   loop/config tools with the same structured shape and error contract. These
   operations select global or explicit workspace scope; they preserve
   presence/origin semantics and cannot use a browser-only or CLI-only state
   path.
5. **Runtime remains outside inputs.** `runtime_defaults` and `runtime_rules`
   remain engine configuration under ADR-001/002. They work for any loop with
   `run-agent` nodes, have their own per-item precedence and validation, and
   must not be smuggled through the author input namespace.
6. **One resolver owns every execution origin.** Dry-run and every persisted
   start invoke the same input-resolution primitive at the loop-service
   boundary. Start-binding adapters own only allowlist/mapping before
   delegation. No start kind gets a private precedence, type-check, or
   unknown-key policy.

## Alternatives Considered

### Add review knobs to `LoopConfig`

That makes the engine own every present and future author input. It violates
the namespace boundary.

### Reserved input keys

Intercepting reserved keys repeats the collision and bimodal-validation problem
rejected by ADR-002.

### Stored configuration only

A daemon-only stored value is not the inspectable, committable configuration
needed by the migration. It can complement the same managed resource surface,
but cannot replace file-backed global/workspace defaults.

### Emit invocation snippets instead of configuration

That loses persistence and regresses the legacy behavior.

## Consequences

- Every first-party and user-authored loop gains workspace defaults without
  changing its YAML contract.
- The migrator has a value-for-value target for the legacy review keys with
  real equivalents **[amended by ADR-008: only `defaults.auto_commit` retains
  one — the other review keys drop with the external-review surface]**. The
  legacy schema has no persisted default PR, and after ADR-008 no `pr` input
  exists to author; no PR value is ever fabricated.
- Dry-run, HTTP, UDS, and native tools can explain the same effective inputs
  without falsely treating `false` or zero as absent.

## Implementation Notes

`internal/config` retains raw presence-aware loop/key values; a dedicated
`internal/loop` resolver handles dry-run and every persisted start against
the loaded loop contract without growing `config.go`; start-binding code
remains an allowlist/mapping adapter. Co-ship CLI/HTTP/UDS/native
management contracts, dry-run origin output, validation tests, and migration
fixtures. The renamed loop path is `extensions/dev-cycle/loops/review-and-fix`.
