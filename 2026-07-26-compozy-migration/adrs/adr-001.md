# ADR-001: Per-Task Runtime Selection — Field-Merged `runtime`, Engine-Resolved, Binder-Applied

## Status

Accepted

## Date

2026-07-11

## Context

AGH loops can currently select only a node-level `model`. Provider and reasoning
effort are absent from loop authoring, `ActionSessionBindRequest`, and the
daemon binder. As a result, an incompatible provider/model pair fails when an
ACP session starts rather than during preflight.

The legacy Compozy surface supplied repeatable task-runtime rules. AGH-80
requires provider, model, and reasoning selection per task without moving
provider authentication, home, environment, or command policy out of the
daemon.

## Decision

1. **One shape.** `RuntimeSpec { provider, model, reasoning }` is the sole
   runtime shape in task frontmatter, runtime rules, node `params.runtime`,
   and worker/judge runtime defaults. A layer merges it field by field.
2. **Rules match by `id`, `type`, or `complexity`.** A task can expose all
   three frontmatter fields. The winning rule specificity is
   `id > type > complexity`; within the same specificity, the later rule wins.
   A rule must contain exactly one non-empty match selector and a non-empty
   runtime field. This preserves the legacy `id > type` rule while adding the
   documented task complexity discriminator without ambiguous compound rules.
3. **Resolution belongs to the loop engine.** For each worker item, the
   field-level precedence is: per-run rules > item frontmatter `runtime` >
   merged configuration rules > rendered node `params.runtime` > effective
   `runtime_defaults.worker` > agent definition. `EffectiveConfig` retains
   per-run rules separately from other rules so frontmatter remains between
   them. Judges use `runtime_defaults.judge` and criterion `runtime`, but
   never task rules. Sub-loops resolve their own layers; parent rules do not
   propagate.
4. **`params.model` is deleted and rejected.** `RunAgentParams.Model`,
   `ActionSessionBindRequest.Model`, criterion `Model`, gate
   `EvaluateInput.JudgeModel`/`JudgeRequest.Model`, `model_defaults`, and their DTO/config counterparts are hard delete
   targets. Strict DSL decoding rejects `params.model` with a migration-guided
   error; it is not sugar or an alias for `params.runtime.model`.
5. **Application belongs to the daemon binder/policy gate.** The engine sends
   the resolved triple in `ActionSessionBindRequest.Runtime`. The daemon calls
   `ResolveSessionAgentWithRuntime` with provider, model, and reasoning
   overrides, then derives command, auth, home, and environment policy. An
   override of provider is therefore a full daemon-side runtime re-derivation.
6. **Validation has two explicit timings.** `loop validate` validates only the
   definition-contained static shape supplied by its existing request. Stored
   global/workspace config and per-run overrides are resolved and validated by
   the shared dry-run/submission path; once an item is rendered, the engine
   validates its effective triple again immediately before bind. Effective
   validation is authoritative for frontmatter, templated node values, and
   rule selection. Provider identity always validates. Model membership
   validates only for providers whose model catalog is authoritative (currently
   Cursor); other provider model strings are not falsely rejected. Invalid
   authoritative values fail deterministically before any ACP process starts;
   configuration loading only performs structural decoding.
7. **Applied runtime is a durable public run contract.** The binder copies the
   final `CreateOpts` triple into `ActionSessionBinding.AppliedRuntime`.
   `resolved_runtime` and per-field provenance in durable run-status records,
   status reads, and SSE events are written from that binding result, never
   inferred from engine inputs. Fields completed by the agent definition report
   `source=agent`; canonical provider IDs and the model ID actually applied are
   retained for completed as well as active runs.
8. **Runtime configuration spans the existing four loop-config layers.**
   `runtime_defaults` and `runtime_rules` merge through definition contract,
   `[loops.defaults.delivery|watch]`, stored loop configuration, and per-run
   overrides. Runtime rules select runtime only; the `implementer` input still
   selects an agent. Cost-aware budgets and agent-per-task rules remain out of
   scope.

## Alternatives Considered

### Atomic object replacement

Replacing a whole runtime object would be simpler, but it forces authors to
repeat provider and reasoning just to change a model and diverges from the
legacy rule mental model. Field merging is safe because the final triple is
validated.

### Three independent templated fields

Separate `provider`, `model`, and `reasoning_effort` node parameters would
scatter validation and make incompatible triples easy to compose accidentally.
They also provide no coherent status contract.

### Binder-only resolution

Sending raw loop layers to the daemon would teach the binder loop concepts and
violate the dependency boundary. Resolving provider policy in the engine would
violate the opposite boundary. The split above preserves both authorities.

## Consequences

- A single mechanism supports authored intent, workspace defaults, and
  invocation-time overrides while preserving per-field provenance.
- The binder API changes in one hard cut, and all callers, contracts, OpenAPI,
  generated types, status projections, and event matchers change together.
- Runtime variance requires the isolated/ephemeral bind path. A continuous or
  run-owned binding whose creation profile differs rejects with
  `bindingMismatch`; it is never silently re-resolved.

## Implementation Notes

The affected seams are `internal/loop/dsl`, `internal/loop/config.go`,
`runtime_resolve.go`, action/binding types, gate evaluators,
`internal/daemon/loop_action_policy.go`,
`internal/config/provider_resolve.go`, `internal/modelcatalog`,
`extensions/dev-cycle/import_tasks_parser.go`, contract DTOs, and generated
OpenAPI/TypeScript. The catalog interface is defined by `internal/loop` and
implemented by the catalog service. `CanonicalProviderName` is the existing
provider alias helper. There is no general provider-model canonicalization
helper or authoritative model list for every provider; validation must respect
`HasAuthoritativeProviderCatalog` and reuse offline-safe preflight semantics.

Durability extends the existing `internal/store/globaldb`
`loop_generation_outputs` row with nullable runtime/provenance columns through
the next append-only Goose migration, declarative schema, Atlas checksum, and
sqlc regeneration. The existing output primary key remains the item identity;
no parallel run-status table or JSON fallback is introduced.
