# ADR-011: Package layout — `internal/gateway` domain package, interfaces in `internal/api/core`, handlers in existing shells

## Status

Accepted

## Date

2026-08-06

## Context

The feature adds a substantial subsystem: exposure policy, device sessions and pairing, provider supervision and endpoint verification, gateway-port lifecycle, the security self-audit, and status projection. Compozy's architecture (SD-008, `internal/CLAUDE.md`) mandates flat `internal/` domain packages composed only by `internal/daemon`, with consumer-defined interfaces, and CI-enforced import boundaries (`magefiles/boundaries.go`). The 500-line one-responsibility-per-file cap applies.

Precedent: full domains like `internal/marketplace` and `internal/modelcatalog` are domain packages wired into the daemon, with their service interfaces defined in `internal/api/core` and their handlers implemented as shared `BaseHandlers` methods registered by both `httpapi` and `udsapi`.

## Decision

- **A new domain package `internal/gateway`** owns exposure policy, device-session and pairing logic, provider supervision + endpoint verification, gateway-port lifecycle, and audit computation. It is composed only by `internal/daemon`.
- **Service interfaces the transports depend on are defined in `internal/api/core`** (e.g. a `GatewayService` the handlers call), following the `NetworkService` / marketplace precedent. `internal/gateway` does not import the API shells, `internal/daemon`, or `internal/cli`.
- **Handlers are shared `BaseHandlers` methods** in `internal/api/core`, registered by both `httpapi` (device-auth-gated gateway routes + status extension) and `udsapi` (local operator/agent management), preserving transport parity. The UDS superset is never proxied remotely (ADR-007).
- **The connectivity provider consumer lives with the extension system** (`internal/extension`, mirroring `watch_source.go`), exposing a resolved connectivity source to `internal/gateway` through an interface — gateway depends on the capability, not on `internal/extension` internals.
- **The bundled provider is a repo-root `extensions/connectivity/tailscale/` package** (like `extensions/dev-cycle/`), not under `internal/`.
- **File split is decided up front** to respect the cap: contract/types, policy, device-session store access, pairing, provider supervision, endpoint verification, port lifecycle, audit, and status projection each in their own file(s); no god file.
- **`magefiles/boundaries.go` gains the `internal/gateway` forbidden-import rules** (mirroring the `internal/marketplace` block) in the same change, and `magefile_test.go` is updated alongside.

## Alternatives Considered

### Alternative 1: Put gateway logic in `internal/api/httpapi`

- **Description**: Implement policy/auth/providers inside the HTTP shell where the middleware lives.
- **Pros**: Fewer packages; auth is near the routes.
- **Cons**: Bloats the transport shell with domain logic; makes the logic unavailable to UDS/CLI parity; violates "interfaces defined where consumed" and the shell's role.
- **Why rejected**: Domain logic belongs in a domain package; the shells only choose registration and middleware.

### Alternative 2: Split into several small packages (e.g. `internal/gatewayauth`, `internal/gatewayprovider`) from the start

- **Description**: Pre-partition the subsystem into multiple packages.
- **Pros**: Smaller units.
- **Cons**: Premature package proliferation against the "add a file before a package" guidance; the pieces share types and lifecycle and cohere as one domain.
- **Why rejected**: One cohesive domain package with disciplined file splits fits the architecture; extract a sub-package only if complexity later demands it.

## Consequences

### Positive

- Matches the established domain-package pattern; boundaries are CI-enforceable.
- Transport parity and the UDS boundary are preserved by construction.
- The provider consumer couples to a capability interface, not extension internals.

### Negative

- Interface duplication points (core interface + gateway implementation) to keep in sync, as with every existing domain.
- Several new files (by design, to honor the cap).

### Risks

- Import-cycle mistakes; caught by `mage Boundaries` in the same change.
- Gateway needing something only `internal/daemon` wires; resolved via constructor injection / functional options, never a back-pointer (SD-008).

## Implementation Notes

The concrete file list, the `core.GatewayService` interface, and the daemon boot/shutdown wiring (a `bootGateway` step before `bootServers`; teardown in the server-and-hooks phase) belong to the TechSpec Architectural Boundaries and Core Interfaces sections.
