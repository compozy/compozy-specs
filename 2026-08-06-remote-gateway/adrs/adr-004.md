# ADR-004: Public tier surface set — ingress by default, consented operator UI, never pairing

## Status

Accepted (amended after peer-review round 1, blocker B-001)

## Date

2026-08-06

## Context

Managed connectivity produces two distinct reachability tiers: a **private overlay** (only the operator's enrolled devices can reach the daemon) and a **public address** (anyone on the internet can reach it — required for webhook senders like GitHub). The question: when the public address is active, which daemon surfaces does it serve?

Evidence:

- The OpenClaw incident's blast radius came from full-gateway public exposure; their own security audit escalates risk when public exposure is on.
- Webhook ingress endpoints are safe-by-construction for public reach: each delivery is verified by per-endpoint signature, freshness, and replay checks before anything executes.
- t3code exposes the full backend through its tunnel — acceptable there because layered, key-bound auth guards every call; it demonstrates the opt-in-full model is viable behind strong auth.
- The operator sometimes needs the full UI from a device that cannot join the overlay (e.g., a restricted work machine).

## Decision

Public exposure is decided **per surface**, with a conservative default:

- **Default**: the public tier serves **only webhook ingress** (automation webhook endpoints and bridge inbound callbacks) plus the endpoint-verification challenge path. The operator UI/API is not reachable publicly.
- **Opt-in**: the operator may explicitly enable the operator UI/API on the public tier. Enabling requires an explicit consent step that states what becomes publicly reachable; access still requires a paired device session.
- **Pairing never exists publicly.** Neither the pairing **mint** route nor the pairing **redeem** route is registered on the public tier under any configuration. A new device is admitted only through the private tier or local access. This closes blocker B-001 from peer-review round 1, where the invariant list and the API contract disagreed about which tier serves redemption.
- The **private tier always carries the full surface** (UI, API, streams) for paired devices, and is the only tier with a pre-auth redeem route.
- Disabling a public surface takes effect immediately.
- The surface set is enforced **structurally**: each tier listener is constructed with its own route matrix (ADR-007), so a route absent from a tier physically does not exist there rather than being rejected at request time.

## Alternatives Considered

### Alternative 1: Public address serves webhooks only, always

- **Description**: Never allow UI/API on the public address.
- **Pros**: Smallest public attack surface.
- **Cons**: Blocks the legitimate "device without overlay" scenario; users would work around it with their own unsupervised exposure — the OpenClaw lesson.
- **Why rejected**: The safe path must cover the real need or users route around it.

### Alternative 2: Public address serves the full daemon, always

- **Description**: t3code-style: everything public behind auth.
- **Pros**: Maximum convenience; one URL for everything.
- **Cons**: Maximum standing attack surface (login door, probing, vulnerability exposure) even for operators who only wanted webhooks.
- **Why rejected**: Most operators enabling the public address only need webhook delivery; they should not inherit a public login door for it.

## Consequences

### Positive

- GitHub-webhook-to-Loop works with zero public exposure of operator surfaces.
- The full-UI-from-anywhere scenario exists for those who consciously choose it.
- Risk posture is legible: audit can state exactly which surfaces are public.

### Negative

- Two reachability descriptions per daemon (private full, public partial) that status/docs must communicate clearly.

### Risks

- Operators enable public UI casually; mitigated by explicit consent, default-off, audit findings, and pairing-gated access (no guessable credential exists per ADR-002).
- Public webhook endpoints get probed/flooded; mitigated by signature rejection without side effects and rate limiting (PRD business rules).
- An operator locked out with no paired device assumes a public bootstrap exists; mitigated by documenting that recovery is local access on the daemon machine (or SSH to it), which is the deliberate consequence of never exposing pairing publicly.

## Implementation Notes

Surface routing, request classification, and consent persistence are TechSpec concerns. The public/private surface split must be enforced at the daemon boundary, not by provider configuration alone.
