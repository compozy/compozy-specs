# ADR-008: Opaque revocable credentials, stream tickets, and connection-registry revocation

## Status

Accepted (amended after peer-review round 1, blockers B-007 and B-009, nit N-001)

## Date

2026-08-06

## Context

The gateway needs a server-side authentication mechanism where none exists. ADR-002 fixed the product model (one operator, many paired devices, per-device revocation, no passwords). This ADR fixes the credential mechanics.

Constraints from exploration:

- The repo already has an opaque-bearer precedent (`internal/mcp/serve_http.go` constant-time bearer) and an HMAC-secret precedent (webhook signing), both loopback-scoped.
- Browsers cannot set an `Authorization` header on SSE (`EventSource`) or WebSocket upgrades, and the daemon serves many SSE endpoints (`internal/api/core/sse.go`, ~10 stream routes). A stream credential distinct from the request credential is therefore required regardless of the primary scheme — every reference (Hermes, t3code) uses short-lived single-use stream tickets for exactly this reason.
- Reference credential models range from opaque bearer (OpenClaw `token` mode, Hermes trusted path) to proof-of-possession (t3code DPoP, Paseo device keypairs). t3code carries DPoP because its product crosses a public relay by design; Compozy's public default is webhook-only, and device sessions cross the public tunnel only when the operator opts the UI in.

## Decision

- **Each paired device holds an opaque credential.** The daemon stores only `sha256(credential)`; verification is constant-time; the session row is **retained with `revoked_at` set** (terminal state) so audit history survives revocation — it is not deleted.
- **Credential format (N-001):** 256 bits from `crypto/rand`, prefixed `cpz_gwd_` for device credentials and `cpz_gwp_` for pairing artifacts so redaction and misuse diagnostics can distinguish them. Stored as SHA-256 hex under a `UNIQUE` index; verification looks up by hash then runs `subtle.ConstantTimeCompare`. Rotation issues a new credential and revokes the prior session row.
- **Transport shape (B-009):** the CLI presents the credential in the `Authorization` header; the **browser never handles a raw credential** — redeeming a pairing on the private tier sets an httpOnly, Secure, SameSite cookie scoped to the gateway origin, and the middleware accepts either form. Credential-bearing responses set `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- **Credential storage ownership (B-009):** the daemon stores hashes only. A remote CLI machine stores its credential in a **client-local** encrypted file under that machine's `$COMPOZY_HOME/gateway/credentials/<profile>.cred` (mode `0600`) — the daemon's vault is on the daemon machine and is unreachable from a remote client. The connection profile holds only non-secret metadata plus that file reference. Portable transfer is explicit: `connect export` produces a passphrase-protected scrypt + AES-GCM bundle, and `connect import` recreates the same device identity on another client. Metadata by itself is not a credential.
- **Streams use a separate single-use, short-TTL ticket.** A device exchanges its credential at an authenticated endpoint for a ticket, then opens the SSE/WebSocket with the ticket as a query parameter; the ticket is consumed on connect and never reused, and **every reconnect acquires a fresh ticket**. Credentials never appear in stream URLs.
- **Revocation reaches live connections (B-007).** Peer review found that deleting or flagging a row cannot invalidate an already-established stream. Therefore:
  - a **device-keyed `ConnectionRegistry`** holds a cancel handle for every authenticated stream; streams register on connect and deregister on close;
  - `RevokeDevice` bumps a durable `revoke_epoch`, then cancels every registered handle for that device, and only then returns — so "revocation terminates active streams" is mechanically true;
  - **in-flight mutations revalidate before commit** by comparing the caller's epoch inside the mutation transaction, so a call in progress fails rather than committing a partial write.
- **Pairing artifacts are distinct from session tokens**: a pairing artifact is single-use, expires within minutes (default 5), and is exchanged once for a device session; it is minted only from a trusted surface (local UI/CLI) and never from the public gate (PRD business rules).
- **Proof-of-possession is deferred, not designed-in speculatively.** The session model is a plain credential store; adding request signing later is additive and does not require a schema placeholder now. The deferral is recorded as a known risk, not a hidden assumption.
- **Failed authentication is rate-limited per source**, with local access exempt.

## Alternatives Considered

### Alternative 1: Proof-of-possession (DPoP-style) in the MVP

- **Description**: Each device holds a keypair and signs every request; the daemon verifies the signature and binds the token to the key.
- **Pros**: A leaked or logged token is useless without the private key; strongest against token theft.
- **Cons**: Per-request crypto on both ends; key storage on every client (browser via WebCrypto non-extractable keys, CLI via a key file); materially larger surface and slower first delivery.
- **Why rejected**: The threat it neutralizes (token replay from an exfiltrated store) is bounded here by immediate revocation, at-rest hashing, and TLS in the tunnel; the public default exposes only webhooks. The cost is not justified for the alpha; the door stays open (see Deferral).

### Alternative 2: OAuth/OIDC for the public surface

- **Description**: Opaque tokens privately; require an identity provider when the public UI is enabled (Hermes public model).
- **Pros**: Strongest for open-internet exposure.
- **Cons**: Brings a full OAuth/login subsystem into scope now; heavier than the single-operator model needs.
- **Why rejected**: Over-scoped for one operator; pairing already gives per-device revocable identity. Recorded as a natural evolution for a future multi-user or hardened-public initiative.

## Consequences

### Positive

- Small, well-understood mechanism with direct prior art in the repo.
- Immediate revocation and at-rest hashing bound the damage of a leaked token; the stream-ticket split keeps long-lived secrets out of URLs, logs, and browser history.
- No client-side key management; the browser and CLI paths stay simple.

### Negative

- A credential exfiltrated in its validity window is usable until revoked (the property PoP would remove).
- Three credential shapes (bearer, cookie, stream ticket) to implement and keep consistent.
- The connection registry adds lifecycle bookkeeping to every stream handler.

### Risks

- Stream tickets leaking via proxy logs/history; mitigated by single-use + short TTL + redaction (ADR-006), matching the reference designs.
- Operators enabling the public UI widen where credentials travel; mitigated by the opt-in consent step (ADR-004) and immediate revocation.
- A stream that fails to deregister leaks a registry entry; mitigated by deferred deregistration on every exit path and by cancellation being idempotent.

## Implementation Notes

Ticket store, TTLs, rate-limit parameters, the registry's concurrency shape, and the exact revoke/commit ordering are specified in the TechSpec. **No vault namespace is introduced**: the daemon's only gateway secret material is the in-table credential hash, and provider credentials reuse the existing extension secret-binding contract (ADR-010, nit N-002). The middleware wiring is the `WithDeviceAuth` seam from ADR-007.
