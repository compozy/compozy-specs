# ADR-007: Daemon-owned tier listeners with a durable desired/observed state machine

## Status

Accepted (amended after peer-review round 1, blockers B-002 and B-005)

## Date

2026-08-06

## Context

The daemon today binds one HTTP listener (default `localhost:2123`) and one UDS socket. A non-loopback bind wraps the entire `/api` group in `loopbackAPIGuard` and 403s everything except the pre-guard webhook and MCP-OAuth routes (`internal/api/httpapi/routes.go:16`, `middleware.go:336`). There is no server-side authentication. The PRD requires remote reachability in tiers (private overlay = full surface; public = webhook ingress by default, operator UI opt-in) with fail-closed exposure.

ADR-003 fixed connectivity mechanisms as provider extensions (subprocesses). The remaining question is the network topology: does the daemon itself bind the reachable address (Hermes model — bind address is the auth switch), or does the provider terminate transport and forward to the daemon over loopback (cloudflared / `tailscale serve` model)?

A hazard shapes the answer: if any forwarded traffic arrives on the existing loopback listener, the daemon cannot distinguish "operator on the machine" from "the public internet via a tunnel", and the current loopback-trust would hand full access to forwarded traffic — the OpenClaw failure mode.

## Decision

- **The daemon never binds a non-loopback address.** Providers terminate transport (TLS included) and forward to daemon-owned loopback ports.
- **The daemon exposes dedicated gateway ports, separate from the existing web/UDS listeners**, one per reachability tier:
  - a **private-tier gateway port** carrying the full operator surface, gated by device-session authentication;
  - a **public-tier gateway port** carrying webhook/bridge ingress always, and the operator UI only when explicitly opted in.
- **Gateway ports never grant loopback trust.** Every request on a gateway port passes device-session auth (operator surfaces) or the request's own verification (webhook HMAC). The tier is a property of the port the provider forwards to, not a header the daemon must trust.
- **The existing `localhost:2123` web listener and the UDS socket are unchanged**: local operator, same-origin SPA, and local CLI keep working exactly as today.
- A provider advertises which tier(s) it establishes; the daemon binds the corresponding gateway port(s) and hands the provider the loopback target to forward to.

### Listener ownership (added for B-002)

Peer review found the original text assigned listener binding to `internal/gateway`, which cannot construct an `httpapi.Server` without violating its own import ban, and left engine construction, route matrices, SPA behavior, port publication, and shutdown undefined.

- **`internal/gateway` owns policy only.** It computes an **exposure plan** — which tiers must be up and which surface set each carries — and never touches a socket.
- **`internal/daemon` owns the listeners**, through a `gatewayServerFactory` mirroring the existing `httpFactory`/`udsFactory`. Each tier is an `httpapi.Server` constructed with a tier-specific option set (`httpapi.WithSurfaceSet(tier)`, `httpapi.WithDeviceAuth(...)`) that selects that tier's **route matrix**. A route absent from a tier's matrix physically does not exist on that listener.
- **Resolved ports are returned by the daemon-owned bind effect** and recorded synchronously by the reconciler before provider establishment or advertisement, so status reports real bound addresses rather than intent.
- **Boot order**: `bootGateway` (policy + device store + reconcile) → `bootServers` (local listener + tier listeners) → advertisement. Reconciliation completes before any tier listener serves external traffic.
- **Shutdown order**: tier listeners tear down in the existing server-and-hooks phase, before persistent resources close.
- The SPA is served on a tier listener only when that tier's `operator_ui` surface is enabled; otherwise the SPA fallback is disabled there.

### Durable desired/observed state machine (added for B-005)

Peer review found that "a failed transition leaves the prior state intact" was unimplementable across separate database, listener, provider, and advertisement effects guarded only by an in-memory lock — and that config and database both claimed authority over the public UI.

- **The database is the single authority for exposure intent.** Configuration contributes only static tunables and an immutable ceiling (`gateway.enabled`); the `gateway.public_ui.enabled` key is **deleted**.
- Every exposure row carries `desired_state`, `observed_state`, and `generation`. A transition writes desired state and bumps `generation` in one SQLite transaction; the reconciler then drives observed toward desired.
- **Generation fencing**: an effect completing against a stale generation is discarded, never applied — this is what makes concurrent transitions and crash recovery decidable.
- **Fixed effect order with compensation**: persist desired → bind listener → establish provider → verify endpoint → advertise; failure unwinds in reverse so no intermediate state is externally reachable.
- **Boot reconciles before advertising**, so a crash restores the operator's last desired state and never re-exposes a disabled surface.

## Alternatives Considered

### Alternative 1: Daemon binds the managed address directly (Hermes model)

- **Description**: The daemon binds the tailnet IP; a non-loopback bind engages auth. The provider only ensures the machine is on the network.
- **Pros**: One fewer process hop; conceptually simple ("bind is the switch").
- **Cons**: The daemon must terminate TLS itself for a public address; bind semantics change; loopback-trust becomes a special case to reason about; couples the daemon to each provider's addressing. Contradicts ADR-003's "mechanism is the extension's job".
- **Why rejected**: Pushes transport termination into the core the provider seam exists to keep out, and makes fail-closed a runtime computation rather than a structural property.

### Alternative 2: Single gateway port, tier carried in a signed header

- **Description**: One authenticated gateway port; the provider injects a signed "reachability tier" header the daemon trusts.
- **Pros**: One port to manage.
- **Cons**: Public-vs-private now depends on trusting a header from a subprocess; a spoofed or mishandled header downgrades a public request into full-surface access. More trust in the provider than the model wants.
- **Why rejected**: Tier-by-port is fail-closed by construction — the public port physically cannot route operator surfaces — whereas tier-by-header is one validation bug away from the incident class.

## Consequences

### Positive

- Fail-closed is structural: the public port cannot reach operator surfaces, and gateway ports never trust loopback, so no forwarded traffic inherits local trust.
- The local operator path is untouched; zero regression risk to same-origin web and local CLI.
- TLS and transport stay entirely in the provider, matching how `tailscale serve` / cloudflared already work.

### Negative

- The daemon manages additional internal listeners and their lifecycle alongside exposure state.
- A process hop (provider → loopback) sits in the data path; negligible against internet latency and identical to existing tunnel clients.
- A desired/observed reconciler with compensation is materially more code than a boolean toggle.

### Risks

- A provider forwarding a public reachability into the private-tier port would over-expose; mitigated because the daemon — not the provider — owns the tier→port binding, hands the provider only the target for the tier it advertised and the operator consented to, and verifies via a tier-scoped challenge (ADR-009) that the advertised endpoint actually reaches that listener.
- Port exhaustion / conflicts on constrained hosts; mitigated by OS-assigned ports (`:0`) resolved back from the listener, as the existing server already supports.
- Reconciler bugs leaving observed and desired permanently divergent; mitigated by generation fencing, boot reconciliation, fault-injection tests at every effect boundary, and the self-audit surfacing divergence as a finding.

## Implementation Notes

Tier listeners bind on loopback via the existing `listenConfig.Listen` path (`internal/api/httpapi/server_start.go`). The device-auth middleware is wired through a `WithDeviceAuth` option mirroring `WithResourceOperatorAuth` (`internal/api/httpapi/server.go:299`), and the route matrix through `WithSurfaceSet`. Webhook routes stay registered ahead of the device-auth gate, preserving their independent verification (see ADR-008). Exact route inventories per tier, the reconciler's effect/compensation table, and the provider forward-target handshake are specified in the TechSpec.
