# ADR-009: `connectivity.provider` surface, challenge-based verification, registry-derived trust

## Status

Accepted (amended after peer-review round 1, blocker B-008)

## Date

2026-08-06

## Context

ADR-003 fixed policy-in-core / mechanism-as-extension and a bundled first-party provider. This ADR fixes the extension-system mechanics: the provide surface, its service methods, the trust model for third-party providers, and how the bundled provider is packaged.

Exploration findings:

- Adding a provide surface is a one-file change in `internal/extensionprotocol/capabilities.go` (a `Capability*` const + its `capabilityServiceMethods` entry) that auto-propagates to manifest validation and public/private contract derivation. New surfaces are public by default; `bridge.adapter` is the sole bundled-only surface, gated in `registry_install.go:validateInstallConfig`.
- The daemon-side consumer pattern is established by `loop.watch_source` / `model.source` (`internal/extension/watch_source.go`, `model_source.go`): resolve the provider by capability, then `process.Call` over the JSON-RPC stdio transport.
- Trust machinery already exists: install-source tiers (`SourceBundled|User|Workspace|Marketplace`), per-source ceilings (`sourcePolicy`), consent-area derivation (`DeriveConsentAreas`), and digest confirmation (the "Network Requirement Confirmation" pattern — explicit consent to an exact normalized digest).
- The bundled `dev-cycle` extension packages via `//go:embed` + a re-exec (`{{compozy_executable}} __internal extension-provider dev-cycle`) and enrolls on fresh home through `EnsureManagedInstall` in `bootExtensions`.
- Market: embedding Tailscale via `tsnet` in-process (no separate client install, userspace stack, `ListenFunnel` for a public listener + TLS) is a differentiator no reference ships; every reference runs Tailscale as an operator-installed sidecar.

The reference sweep showed no competitor exposes connectivity as a real extension — all are core or closed seams. Restricting Compozy to bundled-only would forfeit exactly the differentiator the seam creates.

## Decision

- **Add a public provide surface `connectivity.provider`** in `internal/extensionprotocol/capabilities.go`, with service methods for the daemon→provider calls: establish reachability, report endpoints, report health, and tear down. The surface is public (third parties may implement it), not bundled-only like `bridge.adapter`.
- **Third-party connectivity providers are allowed in the MVP under the existing trust tiers**, with one addition: because a connectivity provider governs how the daemon is reached, enabling one requires **digest confirmation** — explicit operator consent to the exact normalized digest describing the reachability control it takes (reusing the Network Requirement Confirmation mechanism). Marketplace providers remain limited to verified sources; operator-owned local/dev/user/workspace sources may provide, always behind the reinforced confirmation.
- **A dedicated consent area names the connectivity control** ("this extension controls how your daemon is reached") so the operator approval summary is explicit.
- **Endpoint verification stays core-side and applies identically to every provider** (bundled or third-party): a reported endpoint is advertised only after the daemon verifies it; a provider failure degrades the affected reachability to a safe state (never half-exposed) with supervised restart. This is the primary defense against a malicious provider, and it does not depend on the provider's origin.

### Verification is a tier-scoped challenge, not a probe (added for B-008)

Peer review found that "verify by probing" proves nothing about *which* listener an endpoint reaches. Verification therefore:

1. plants a per-attempt nonce served **only** on the assigned tier listener (never on the local listener, never on the other tier);
2. fetches `<endpoint>/<challenge-path>` and requires the exact nonce — this is what proves the endpoint reaches *this* daemon's *assigned tier*;
3. enforces a **scheme allowlist** (public-tier endpoints must be `https`);
4. performs **mandatory TLS validation** — `InsecureSkipVerify` is forbidden;
5. **does not follow redirects** (a redirect fails verification);
6. **bounds the response body** (64 KiB) and applies an explicit deadline on a dedicated client with a timeout — `http.DefaultClient` is forbidden, per the external-call timeout invariant;
7. applies an **SSRF guard**: a public-tier endpoint resolving to a loopback/link-local/private/CGNAT address fails.

Failure yields `ErrEndpointUnverified`; nothing is advertised and the provider is marked degraded with a redacted reason.

### Provider trust is re-derived, never trusted from storage (added for B-008)

A persisted `install_source`/`digest_confirmed` can outlive an extension update, uninstall, or reinstall — a stale row must not authorize changed code. Therefore install source and the control digest are **re-derived from the live extension registry on every enable and every boot**; a mismatch against the operator-confirmed digest fails closed with `ErrProviderTrustStale` and requires re-consent. **Workspace-scoped extension sources are rejected for this surface**: connectivity is an operator-global capability, and a workspace-scoped source has no owner rule that could authorize it.
- **The bundled provider embeds Tailscale via `tsnet`** (in-process, no separate client install), exposing the private overlay and the public ingress (Funnel). It ships as a bundled extension packaged like `dev-cycle` (`//go:embed` manifest + re-exec `__internal extension-provider tailscale`), enrolled in `bootExtensions`.

## Alternatives Considered

### Alternative 1: Bundled-only connectivity surface (mirror `bridge.adapter`)

- **Description**: Define the surface but gate it to bundled first-party providers; open to third parties in a later phase.
- **Pros**: Smallest trust surface now; exact precedent exists.
- **Cons**: Forfeits the differentiator (the reference sweep shows core/closed seams everywhere; bundled-only makes Compozy the same); the main malicious-provider defense (core-side verification) is identical for bundled and third-party, so bundled-only buys less safety than it appears; contradicts the "extensible or it is incomplete" premise.
- **Why rejected**: The real lock is install-time digest consent, not provider origin; the machinery to gate third parties already exists.

### Alternative 2: Sidecar Tailscale (operator installs the client)

- **Description**: The bundled provider shells out to an operator-installed `tailscale` CLI (`tailscale serve`), like every reference.
- **Pros**: Smaller binary; no embedded network stack.
- **Cons**: Breaks the zero-install experience ADR-001/003 committed to; adds an external dependency and its failure modes.
- **Why rejected**: Zero-install is the point; `tsnet` embedding is the differentiator and keeps the operator from managing a second daemon.

## Consequences

### Positive

- Third parties can ship connectivity providers (other overlays, custom-domain tunnels) without runtime changes — the differentiator materializes.
- The bundled provider works with nothing to install; the operator authorizes their own Tailscale account.
- One verification/supervision path covers all providers regardless of trust tier.

### Negative

- Embedding `tsnet` adds dependency weight to the binary (the provider re-execs the main binary, so the network stack links into it).
- A public provide surface plus digest consent is more design than a bundled-only gate.

### Risks

- A malicious third-party provider attempts to misdirect exposure; mitigated by the tier-scoped challenge (which a wrong-tier or foreign endpoint cannot pass), supervised fail-safe degradation, the dedicated consent area, and registry-derived digest confirmation before any provider code influences reachability (manifests validate before execution).
- A provider that passes verification once then changes behavior; mitigated by re-verification and trust re-derivation on every enable and boot, plus supervised health with degradation.
- `tsnet` version/security maintenance burden; mitigated by pinning and by the seam itself (a sidecar or alternative provider can ship without core changes if needed).

## Implementation Notes

Service-method names, the endpoint descriptor, the challenge protocol parameters, the digest-consent payload, and the bundled provider's `tsnet` wiring are specified in the TechSpec. **No extension→daemon Host API method is added** — providers report through the daemon-initiated `connectivity/status` call — so the closed Host API method set is unchanged. That set is **95 methods**; the glossary's "87" is stale and is corrected in the same change.
