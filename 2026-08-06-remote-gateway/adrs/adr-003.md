# ADR-003: Exposure policy lives in core; connectivity mechanisms ship as provider extensions

## Status

Accepted

## Date

2026-08-06

## Context

The feature needs both a security policy layer (who may reach what, under which mode, with which auth) and connectivity mechanisms (join a personal overlay network, establish a public ingress address). The question was whether connectivity vendors get embedded in the runtime or arrive through Compozy's extension system.

A dedicated sweep of five reference repos found that **no reference ships tunnels/connectivity as a true plugin**: OpenClaw and goclaw embed the mechanism in core, t3code uses a closed in-repo seam, Hermes and opencode ship nothing. Two lessons stood out:

1. **What every reference keeps in core is policy** — anything that changes what the daemon's listener is reachable on: exposure mode, auth coupling (OpenClaw requires a credential for public exposure), risk audit, and teardown on shutdown.
2. **Not having a provider seam causes forks**: OpenClaw's `voice-call` extension needed ingress, core offered no contract, so the extension re-implemented its own tunnel stack with its own config keys — the exact duplication an extension seam prevents.

Compozy's product premise (every capability extensible by the runtime and manageable by agents; SD-011) and its existing provider seams (memory backends, sandbox providers, model sources) favor a provider contract.

## Decision

- **Core owns exposure policy**: named exposure modes, authentication and pairing, fail-closed enforcement, per-surface exposure decisions, endpoint registry/status, risk audit, and teardown. None of this is delegated to extensions.
- **Connectivity mechanisms are provider extensions**: a provider's job is to produce reachability — join a network and report endpoints, or establish a public ingress address — plus health/status. Core validates and supervises providers and treats reported endpoints as hints to verify, not truth.
- **The first provider ships bundled and first-party**: a personal-overlay provider (Tailscale integration) is included with Compozy and works out of the box, preserving the zero-install experience.
- **Connectivity providers are trust-gated**: because a connectivity provider influences how the daemon is reached, installing one from a third-party source requires explicit operator consent and is restricted to trusted install sources by default. Provider manifests are validated before any provider code runs.

## Alternatives Considered

### Alternative 1: Everything in core (what all references do)

- **Description**: Integrate the overlay/tunnel vendor directly into the runtime.
- **Pros**: Simplest; matches every reference; fewer moving parts.
- **Cons**: Vendor SDK weight in the single binary; every new provider requires runtime changes; contradicts the product premise; repeats the conditions that caused OpenClaw's voice-call fork.
- **Why rejected**: Compozy's differentiation is being extensible-by-design; the reference sweep shows core-only leads to plugin-side duplication when demand appears.

### Alternative 2: Core now, extract a seam later

- **Description**: Embed the first vendor in core for speed; refactor to a provider contract in a later phase.
- **Pros**: Faster first delivery.
- **Cons**: Creates a known migration on day one, against the greenfield hard-cut posture (SD-002); public config/docs would churn.
- **Why rejected**: Building toward a planned rework violates the project's zero-legacy discipline.

### Alternative 3: Contract only, no bundled provider

- **Description**: Ship the seam; operators install a provider themselves.
- **Pros**: Leanest core.
- **Cons**: Kills the zero-config outcome that motivated managed connectivity (ADR-001).
- **Why rejected**: Out-of-box experience is the point.

## Consequences

### Positive

- Core stays lean; vendor SDKs live outside the runtime.
- Third parties can add providers (other tunnel vendors, self-hosted overlays) without touching core.
- The provider contract forces a clean policy/mechanism boundary aligned with how references converged (policy in core).

### Negative

- More upfront design: the provider contract becomes public API surface with compatibility obligations.
- A subprocess hop sits in the data path (negligible against internet latency; identical to how tunnel clients already work).

### Risks

- A malicious or buggy provider misdirects exposure; mitigated by trust gating, manifest validation before code execution, core-side endpoint verification, and fail-safe degradation when a provider crashes (never leaving a surface half-exposed).
- Bundled-provider vendor dependency; mitigated by the seam itself (alternatives can ship without runtime changes).

## Implementation Notes

The provider contract shape (provide surface name, lifecycle methods, endpoint descriptor, health reporting), supervision strategy, and the bundled provider's packaging follow in the TechSpec. The extension system's existing manifest validation, install-source tiers, and operator-consent flows are the enforcement rails.
