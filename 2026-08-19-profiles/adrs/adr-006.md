# ADR-006: Resources compose through four additive layers bound by profile name

## Status

Accepted

## Date

2026-08-20 (decided in grill-me after three rejected shapes)

## Context

Each profile needs its own resources (agents, skills, loops, hooks) without losing machine-wide tools, per-project tools, or the ability to share a division of contexts with a team through git. Earlier proposals failed one by one: per-profile copies duplicate maintenance; workspace-only resources leak across profiles ("agents of this workspace shouldn't leak from one profile to another"); machine-only layering can't be committed for a team.

## Decision

Four layers *(amended 2026-08-20, surface grill: the personal profile+workspace layer was cut as over-engineering — a resource is either user-scoped or project-scoped)*, **additive** (base always sums), most specific wins on name conflict:

1. User layer — visible always, every profile, every workspace.
2. Personal profile layer — that profile, every workspace.
3. Project-committed shared base — that workspace, **all** profiles (git physics).
4. Project-committed per-profile-name folders — team-shared division: applies when the active profile's **name** matches the folder name.

- **Name-binding is the sharing mechanism**: layer 4 (and extension placements, ADR-002) bind by profile name; content naming an absent profile stays **dormant** with a visible "declares content for profile X — create it?" hint. Creating/renaming to the name wakes it.
- Personal material never writes inside the repo; repo-side profile folders are deliberate, committed team decisions.
- Machine-tier agent memory follows the same profile split (per-profile); repo-committed workspace memory stays shared like layer 4.

## Alternatives Considered

### Alternative 1: Profile owns copies of resources

- **Description**: creating a profile copies resources into it.
- **Pros**: true isolation; simple mental model.
- **Cons**: duplicate maintenance; updates fork; contradicts "nothing is copied" extension semantics.
- **Why rejected**: maintenance cost and drift.

### Alternative 2: Shared registry + per-profile selection lists

- **Description**: all resources global; each profile keeps an enablement list.
- **Pros**: reuse without copies.
- **Cons**: a second stateful mechanism (lists) beside folder layout; no git-committed team story; per-item toggling is exactly the noisy management UI the product avoids.
- **Why rejected**: folder-shaped layering covers the same need with the tools users already have (files + git).

## Consequences

### Positive

- The team story is "commit a folder"; the extension story reuses the same name-binding; conflicts resolve by one rule (most specific wins).

### Negative

- Name-binding means renames can strand content (mitigated: tiered rename handling — machine folders auto-rename, repo folders offered, placements go dormant with hints).

### Risks

- Shadowing surprises → the effective catalog must show which layer won and why (inspectability requirement carried to Part II).
