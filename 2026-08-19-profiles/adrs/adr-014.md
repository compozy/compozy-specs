# ADR-014: The remembered selection is daemon-owned state

## Status

Accepted

## Date

2026-08-20

## Context

ADR-003 makes the remembered profile per-workspace and shared by every surface ("switching in the UI or CLI updates the current lens's slot"). Today's only comparable state is client-side: the web's active-workspace store persists to browser storage (`compozy:active-workspace:v4`) — which the CLI cannot see. A selection only the browser knows cannot drive CLI resolution, and two browsers would drift.

## Decision

- The remembered choice lives in the daemon: `profile_selections(lens, workspace_id, profile_id)` in the global catalog, exposed via the selection routes in `_dx.md` (GET/PUT), consumed by the CLI resolver's third rung and by the web.
- The web treats it as server state: reads/writes through the API, keeps only a client-side cache for instant render (existing store pattern), never a divergent source of truth.
- **The remembered choice is not the active view.** Each client owns an ephemeral active view (current profile or aggregate mode, per lens); the daemon row is only the default applied when a client next enters a lens. `profile.selection_changed` invalidates the remembered-choice projection — it never force-switches an open client's active view (US-010.EC-4). A switch is: set the local active view, then persist the remembered choice; on persist failure the client rolls back and surfaces the error.
- Delete sweeps rows (`SweepProfile`); **archive deliberately leaves rows in place** — they resolve to a `default` fallback carrying `archived_remembered_fallback` provenance (the frozen US-033 distinction), and unarchive restores them untouched. Workspace deletion cascades via trigger. *(Amended round 5: sweeping on archive destroyed the required fallback provenance.)*
- Stores real profiles only — the aggregate state is per-client view state and is never persisted here (ADR-003).

## Alternatives Considered

### Alternative 1: Client-persisted (browser storage), CLI keeps its own file

- **Pros**: no schema, no routes.
- **Cons**: CLI and web drift; two terminals and a browser give three answers to "which profile is my-saas in?"; sweep on archive impossible.
- **Why rejected**: the selection is shared acting context by decision, not per-client preference.

### Alternative 2: Reuse the opaque `clientstate` store

- **Pros**: existing machinery, workspace-keyed, purge support.
- **Cons**: clientstate is per-client presentation state by contract (window manager); selection is cross-client runtime context consumed by the CLI resolver — wrong ownership semantics, and reads from the CLI would rummage another domain's documents.
- **Why rejected**: semantic mismatch; a two-column table is cheaper than bending a contract.

## Consequences

### Positive

- One answer per workspace everywhere; sweepable; inspectable via API/Settings.

### Negative

- One more tiny table + route pair.

### Risks

- Web cache staleness after CLI `profile use` → selection changes emit a catalog-adjacent event the web already listens for (settings/state refresh path); Playwright covers the cross-surface case.
