# ADR-010: A profile is organization, not access control

## Status

Accepted

## Date

2026-08-20 (decided in grill-me D12)

## Context

"Marketing can't see finance" is the natural multi-tenant reading of profiles — and it lands on vocabulary the product explicitly closed (the historical cross-workspace-access decision removed grants/toggles/trust-list surfaces; the glossary instructs against reintroducing them). The runtime is single-operator and local-first: there is no user/role/org model for ACLs to attach to. Market precedent agrees: Chrome documents profiles as separation, not security.

## Decision

- **Profiles carry no permission or grant vocabulary.** Any profile can be selected by the operator at any time; the aggregate view shows everything. Profile = organization and filtering.
- **The network stays shared**: peer registry and infrastructure are machine-level; conversations are work (stamped); agents in different profiles can talk — explicitly desired ("até é melhor porque agents se conversam").
- **Profile management is local-only in v1**: no create/switch/archive/delete from remote gateway surfaces; remote inherits read scoping only.
- **Worktrees stay visible in every profile** (owner-tagged): hiding-by-profile is capability gating, future scope.
- Product copy states the boundary plainly where operators might assume otherwise: separation, not security; multi-person access control is a future, separate program.

## Alternatives Considered

### Alternative 1: Profile-level access control (ACLs/grants)

- **Description**: profiles can be locked, granted, or hidden from each other.
- **Pros**: matches the SaaS multi-tenant instinct.
- **Cons**: reopens closed vocabulary; needs an identity/role model that doesn't exist; single operator means the "attacker" owns the machine anyway.
- **Why rejected**: wrong problem for a single-operator runtime; future multi-person spec owns it.

### Alternative 2: Per-profile network isolation

- **Description**: agents can only converse within their profile.
- **Pros**: symmetric with work scoping.
- **Cons**: kills desired cross-context collaboration; peers/infra are machine facts.
- **Why rejected**: operator decision — conversation across contexts is a feature.

## Consequences

### Positive

- No permission machinery to build, test, or explain; the closed-vocabulary ruling stays closed.

### Negative

- Operators wanting true confidentiality between contexts don't get it from profiles — the copy must keep saying so.

### Risks

- Future multi-person era will need real boundaries → the immutable stamp plus fail-closed server-side filtering are deliberately the right substrate for it.
