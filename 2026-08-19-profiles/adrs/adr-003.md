# ADR-003: Profile selection is remembered per workspace

## Status

Accepted

## Date

2026-08-20

## Context

D10 defined one resolution chain ending in a single machine-level sticky choice. Stage 1 market research converged from two independent directions on a different expectation: VS Code remembers the active profile per workspace ("opening folder X restores the profile you used there"), and Arc binds Spaces to profiles. The operator confirmed adopting per-workspace memory for v1: "voltar em um workspace deveria estar com o profile selecionado guardado".

## Decision

- The resolution chain keeps its shape and order: explicit `--profile` flag → `COMPOZY_PROFILE` environment variable → **remembered choice keyed by the resolved workspace** → `default`. One resolver, joined to the existing workspace-resolution boundary (L-033); resolution runs after the workspace resolves.
- The Global lens (no workspace) has its own remembered slot, same semantics.
- **Memory stores real profiles only** — never the "All profiles" aggregate state (an acting context must be a profile; aggregate is a way of looking, not of acting). Returning to a workspace restores the last real profile used there; "All profiles" is re-entered manually.
- A workspace with no remembered entry opens in `default`.
- A remembered entry pointing at an archived profile falls back to `default` (per ADR-001).
- Switching profiles in the UI or CLI updates the current lens's slot. Two concurrent terminals may still run different profiles via flag/env without touching memory.
- Machine-scoped commands ignore profile selection entirely (unchanged from D10).

## Alternatives Considered

### Alternative 1: Single machine-level sticky (original D10 reading)

- **Description**: one remembered choice for the whole machine.
- **Pros**: simplest state; predictable for operators who live in one context at a time.
- **Cons**: contradicts the strongest market convention for workspace-bound tools; operators juggling project-bound contexts must re-switch on every workspace change.
- **Why rejected**: operator confirmed contexts follow projects; two independent market precedents agree.

### Alternative 2: Remember the full switcher state including "All profiles"

- **Description**: per-workspace memory stores whatever was selected, aggregate included.
- **Pros**: exact restoration of the last view.
- **Cons**: silently re-entering the aggregate makes creation file to `default` without the operator noticing — the documented misfiling trap (Slack/Notion); violates "sticky accepts only real profiles" (D10).
- **Why rejected**: acting context must be explicit; the trap outweighs the convenience.

## Consequences

### Positive

- Returning to a project restores its working context — the profile follows the work.
- `default` stays the universal cold-start answer (no entry, archived entry, machine commands).

### Negative

- Selection state becomes a per-workspace map that management surfaces must be able to inspect; delete flows sweep it, while archive leaves rows in place as provenance for the `archived_remembered_fallback` resolution note (amended round 5).

### Risks

- Operators who want one profile everywhere now see per-workspace drift — mitigated by `COMPOZY_PROFILE`/flag pinning and by the switcher always displaying the active identity.
