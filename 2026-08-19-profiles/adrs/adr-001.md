# ADR-001: Profile lifecycle — archive instead of delete-with-work or transfer

## Status

Accepted

## Date

2026-08-20

## Context

Work entities carry an immutable owning-profile stamp set at creation (dossier decision D9); an administrative transfer verb is explicitly future scope. Deleting a profile that still owns work would therefore either orphan the stamps, silently mass-reassign work (a hidden transfer), or dead-end the operator (blocked until empty with no way to empty). Market evidence (grill round 1, Track B): Chrome/Arc document trust erosion when lifecycle semantics surprise users.

## Decision

- A profile that still owns work can only be **archived**: it leaves the switcher, selection surfaces, and day-to-day listings; its work remains stored and appears only in the labeled aggregate view ("All profiles"), always owner-labeled.
- Archive is reversible (**unarchive** restores the profile to the switcher). An archived profile keeps its name reserved.
- **True deletion is allowed only when the profile owns no work** (then the name frees immediately).
- The `default` profile is permanent: never archived, deleted, or renamed. Its color/icon may be customized (cosmetic only).
- Sticky selections pointing at an archived profile fall back to `default`.
- Archive is blocked while the profile's sessions are running (stop them first); it pauses the profile's automations and lists them in the confirmation.
- Archive is also blocked while any of the profile's task runs is leased/running; **queued (unleased) runs freeze with the profile**: the single claim query (`ClaimNextRun`, unchanged signature and sole claimer) additionally requires the owning profile to be `active`, evaluated inside the same claim transaction. Unarchive makes frozen queued runs claimable again; the archive confirmation reports their count.
- The archive state change, the running/leased checks, and the automation pause commit in one immediate transaction, so an archive can never race a claim, trigger, or spawn into creating work for an archived profile.
- Unarchive lists the paused automations for explicit reactivation — never a silent resume.

## Alternatives Considered

### Alternative 1: Block deletion until the profile is empty

- **Description**: refuse to delete while any owned work exists.
- **Pros**: trivially safe; no new states.
- **Cons**: dead end in v1 — no transfer verb exists, so a profile with history can never be removed from the switcher.
- **Why rejected**: punishes cleanup; the operator's stated goal is organization.

### Alternative 2: Delete reassigns owned work to `default`

- **Description**: deletion moves every owned row to the `default` profile.
- **Pros**: switcher stays minimal; single-step cleanup.
- **Cons**: it is the deferred transfer verb wearing a delete costume; violates stamp immutability (D9); silently rewrites attribution (spend, usage history).
- **Why rejected**: hidden mass mutation of history contradicts the immutable-stamp contract.

## Consequences

### Positive

- Zero data loss; attribution history stays truthful; switcher stays calm.

### Negative

- Archived profiles accumulate; Settings needs an archived-profiles list (management surface, not switcher).

### Risks

- Operator expects "delete" to free the name while work exists → mitigated by offering archive in the delete flow with plain copy, and true delete the moment the profile is empty.
