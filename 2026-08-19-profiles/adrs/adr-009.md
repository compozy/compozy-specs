# ADR-009: Machine credentials by default; per-profile provider overrides in the vault

## Status

Accepted

## Date

2026-08-20 (decided in grill-me D7)

## Context

Credentials are the sharpest isolation risk: today nothing segments (one vault, process-wide environment references, provider CLI logins in the operator home). Full per-profile credential isolation (the Hermes home model) forks provider state and contradicts the single-runtime decision (ADR-004). Zero separation makes "finance pays its own bill" impossible.

## Decision

- **Machine credentials are the default for every profile.** A profile may **override per provider** (e.g., its own OpenAI key for billing separation).
- Overrides live in the **credentials vault under a profile-scoped reference**, mirroring the existing global-vs-workspace reference pattern; resolution is scoped to the owning profile and fail-closed elsewhere.
- **Process-environment references are forbidden for profile-scoped secrets** — the process environment is machine-wide by nature and cannot carry a per-profile boundary.
- **Native provider CLI logins remain the machine's in v1**; per-profile provider homes are a recorded future rung. Surfaces state this plainly (no false login-separation promise).
- **Spend/usage attribution follows the owning profile's stamp regardless of which key executed** — attribution is ownership, not key accounting.

## Alternatives Considered

### Alternative 1: Strict per-profile credential isolation (Hermes home semantics)

- **Description**: every profile carries its own keys, logins, provider homes.
- **Pros**: cryptographic-grade separation; per-profile billing exact.
- **Cons**: forks refresh-token/login state per profile; requires per-profile provider homes (v1 non-goal); punishes the common case (one person, one set of keys).
- **Why rejected**: cost lands on every profile to serve the rare case; the override covers the real need.

### Alternative 2: No credential separation in v1

- **Description**: machine credentials only; billing separation organizational.
- **Pros**: zero vault changes.
- **Cons**: kills the finance/marketing billing story; copy would have to walk back a natural expectation.
- **Why rejected**: the override is cheap relative to its value and rides existing vault scoping precedent.

## Consequences

### Positive

- Default unchanged for existing use; billing separation possible per provider per profile; attribution stays truthful either way.

### Negative

- Two resolution sources (machine + override) must be inspectable ("which key would this profile use for provider P?").

### Risks

- Silent fallback confusion (override removed → machine key) → resolution surface names the source; removal warns when owned work exists.
