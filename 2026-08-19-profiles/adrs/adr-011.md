# ADR-011: No inbound routing table in v1 — entry points own their deliveries

## Status

Accepted

## Date

2026-08-20

## Context

The exploration named Hermes' provenance-based route table (platform/guild/channel/thread → profile, specificity-weighted) the single most genuinely new capability worth stealing — it is what turns profiles from "a filter a human switches" into "an operating mode". It was also the one exploration-level scope question never decided anywhere (peer-review blocker). Including it means shipping a real subsystem — match rules, specificity, fallback semantics, management surfaces, agent-operable CRUD, docs — inside the spec that already re-scopes the runtime.

## Decision

- **v1 ships no inbound routing table.** Unattended inbound work is owned by its entry point's profile: bridge deliveries belong to the bridge instance's owner (Business Rule 25), automation jobs/trigger runs belong to their stamped owner, and gateway-triggered local work belongs to its target's owner.
- **One entry point serves exactly one profile.** Serving two contexts from the same platform means one instance per profile (e.g., two bots).
- The provenance route table is **named future scope**. The retrofit is additive by design: it becomes a decision layer evaluated before the ownership stamp ("owner = route match, else entry-point owner"); the stamp, server-side filtering, and aggregate views are unchanged.
- Trigger to revisit: the operator needs one connection-bound endpoint (one bot, one inbox, one number) serving multiple contexts and duplicating instances is unacceptable.

## Alternatives Considered

### Alternative 1: Port the Hermes route table in v1

- **Description**: declarative provenance → profile rules with additive specificity, most-specific-wins.
- **Pros**: single-connection platforms can fan into many profiles; the "operating mode" vision lands immediately.
- **Cons**: a whole decision subsystem with its own config, UI, agent surfaces, and docs; zero usage evidence yet about which match keys matter; lands inside the largest-scope spec of the program.
- **Why rejected**: the static owner rule covers the common case (separate bots/channels per context is normal practice); the substrate v1 builds is exactly what the table plugs into later.

### Alternative 2: No rule (unattended inbound lands in `default`)

- **Description**: entry points carry no owner; deliveries file to the fallback profile.
- **Pros**: nothing to design.
- **Cons**: silently misfiles every unattended delivery; contradicts the stamped-bridge ruling of the scope contract.
- **Why rejected**: worse than both other options at no meaningful savings.

## Consequences

### Positive

- v1 stays focused; the ownership answer for inbound is one sentence; the future table needs no rework of the scoping substrate.

### Negative

- Single-connection platforms (one messaging number, one email inbox) bind to a single profile in v1.
- Work that lands in the wrong profile stays there (no transfer verb until future scope) — the mitigation is choosing the entry point's owner deliberately at creation.

### Risks

- Operators may assume channel-level routing exists because Hermes has it → docs and the bridge creation surface state the one-owner rule plainly.
