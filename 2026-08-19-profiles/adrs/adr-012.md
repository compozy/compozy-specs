# ADR-012: Profile identity — stable ULID stamp, unique name handle, rename rewrites daemon-owned artifacts

## Status

Accepted

## Date

2026-08-20

## Context

Approved behavior forces two properties that pull apart: renames never move work (US-003.AC-1), and team/extension binding is by **name** (ADR-006 layer 4, ADR-002 placement). A single identifier cannot be both stable under rename and the human-typed binding key. Vault references additionally need to stay readable (D7 wrote `vault:profiles/<p>/...`).

## Decision

- `profiles.id` is a generated ULID, immutable, and is the value stamped on the 17 work roots, used in selection rows, enablement rows, cache keys, and `@pf-<id>` extension-data segments.
- `profiles.name` is the unique public handle (grammar `^[a-z][a-z0-9-]{0,31}$`): CLI/API routes, folder names, repo layer binding, extension placement, and vault ref segments use the name.
- Rename updates the name and, under the lifecycle operation protocol, rewrites every **daemon-owned** name-bearing artifact: machine profile folders and `vault:profiles/<old>/…` refs — and nothing else. Selection rows are id-keyed and are deliberately **not** touched by rename. Repo folders are offered (operator commits); extension files are never touched (dormancy).
- `default` has a **fixed, documented constant id** — the zero ULID `00000000000000000000000000` — so the profiles migration can seed the row and backfill stamps before any application code runs, on fresh and upgrade paths alike (the `scheduler_pause (id=1)` singleton precedent). Every other profile id is a generated ULID; boot's ensure step only verifies the row exists. *(Amended 2026-08-20, peer-review round 2: a backfill cannot reference a row created only after migrations finish.)*

## Alternatives Considered

### Alternative 1: Name as the primary key everywhere

- **Pros**: one identifier; readable rows.
- **Cons**: rename becomes a mass rewrite of 17 tables plus caches, or renames get forbidden.
- **Why rejected**: contradicts approved rename semantics ("nothing moves").

### Alternative 2: ULID everywhere, including refs and folders

- **Pros**: nothing ever rewrites.
- **Cons**: unreadable vault refs and folders; name-binding (the sharing mechanism) still needs names anyway.
- **Why rejected**: ergonomics of hand-authored folders/refs are part of the product surface.

## Consequences

### Positive

- Rename is cheap and safe; history/attribution never rewrites; bindings stay human-readable.

### Negative

- Two identifiers to keep straight; the vault-ref rewrite must be transactional with the rename.

### Risks

- A missed name-bearing artifact goes stale on rename → the rename transaction owns an explicit rewrite list, tested.
