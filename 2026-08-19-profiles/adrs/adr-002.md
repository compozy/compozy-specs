# ADR-002: Extension-declared profiles are created automatically at install

## Status

Accepted

## Date

2026-08-20

## Context

D27 lets an extension place each contributed resource into a profile by name. The original D27 wording added a "profile template" kind: the extension ships a preset and the operator clicks "Create profile X" to instantiate it. During spec Stage 1 the operator rejected the button flow: an extension that declares a profile should just produce it — "ao habilitar ela, o profile é automaticamente criado e tudo é feito propriamente, sem essa de botão ou de sugerir" — while explicitly demanding two safeguards: no repeated creation, and sane behavior across extension updates.

## Decision

- An extension manifest may **declare profiles**: name, identity seed (color/icon), persona defaults (the D15 keys), and credential asks (per D7), alongside `profile: <name>` placement on its resources.
- **Install creates declared profiles automatically.** An update that introduces a newly declared profile creates that one at update time. No button, no suggestion step.
- **Create-once marker.** Creation is recorded durably per (extension instance, profile name). A marker means never create again for that installed instance — boot, enable/disable cycles, update, and repair never re-create. A full uninstall removes the instance and its markers; a later fresh install is a new installation and may create its declared profiles again — an existing name is still bound, never seeded.
- **Operator lifecycle wins.** If the operator archives or deletes a declared profile, the extension never resurrects it. Re-adoption path: the operator creates the name manually (placed resources re-bind by name — standard D5 per-profile-name-layer semantics (layer 4 as amended)).
- **Existing name = bind, never seed.** If a profile with the declared name already exists at install, no identity/defaults/credential seeding is applied; placed resources simply apply there. An extension never mutates an operator-owned profile — including via updates.
- **Uninstall/disable leaves the profile.** Extension-owned resources withdraw (D17 semantics); the profile, its work, its config, and its credentials remain.
- **No surprise:** the install/update confirmation summary names the profiles that will be created. Missing declared credentials put the profile in a visible needs-setup state; use fails closed with a plain message.
- **Nothing is copied**: resources stay extension-owned and update with the extension (unchanged from D27).

## Alternatives Considered

### Alternative 1: One-click template instantiation (original D27 wording)

- **Description**: extension contributes a preset; operator clicks "Create profile" on the extension page.
- **Pros**: explicit consent moment; zero surprise.
- **Cons**: a second manual step after install; the extension's declared division doesn't exist until someone finds the button; contradicts install-and-go distribution.
- **Why rejected**: operator decision — the extension determines the profile; enabling it must be sufficient.

### Alternative 2: Dormant-until-manually-created (pure per-profile-name-layer semantics for extensions)

- **Description**: placements naming a missing profile stay dormant with a "create?" hint.
- **Pros**: zero writes at install; symmetrical with repo folders.
- **Cons**: repo folders have no author present to act — extensions do (the manifest is the author's intent); dormancy turns every extension install into a scavenger hunt.
- **Why rejected**: defeats the distribution use case (installable working contexts).

### Alternative 3: Re-create on every enable/boot

- **Description**: reconcile declared profiles continuously.
- **Pros**: self-healing.
- **Cons**: resurrects profiles the operator explicitly removed; fights operator autonomy; hidden background mutation.
- **Why rejected**: violates the operator-lifecycle-wins safeguard the operator explicitly demanded.

## Consequences

### Positive

- Extensions become a real distribution vehicle for complete working contexts (1 machine-wide skill + 2 skills in profile X + 1 in Y just works after install).
- One mechanism serves marketplace, local, and dev-linked installs.

### Negative

- Creation markers add lifecycle state that must survive reinstall/update and be inspectable.
- A new profile appearing at install can surprise an operator who skims the summary — mitigated by the named list in the confirmation and the quiet-switcher default.

### Risks

- Marker lost/desynced → duplicate creation attempt; mitigated by name-existence check before create (existing name = bind, never seed).
- Malicious/greedy extensions declaring many profiles → visible in the install summary; count is part of review surface.
