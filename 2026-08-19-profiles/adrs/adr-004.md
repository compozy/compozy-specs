# ADR-004: Core ownership model — fixed workspaces, profile-stamped work, uniform default, one runtime

## Status

Accepted

## Date

2026-08-20 (decided 2026-08-19/20, grill-me session; recorded as ADR at spec Stage 1)

## Context

The exploration converged on one fork everything else hangs from: how a profile relates to workspaces and to the runtime. Hermes isolates by giving each profile an entire home directory (normally its own process); Compozy's differentiator is one runtime with one state model. The operator also rejected both a profile-owns-workspaces hierarchy ("I don't want to re-add workspace A in every profile") and workspace-shared content ("all profiles seeing the same workspace content is not good").

## Decision

- **Workspaces are fixed and host-global**: a registered folder, owned by no profile, listed identically for every profile.
- **Work is stamped with its owning profile at creation** — sessions, tasks, loop runs, automations and peers in that class. Children inherit through their parent relationship. The stamp is **immutable** (no mid-session switch; no transfer verb in v1).
- **No selection = `default`**, a real profile created at bootstrap, living uniformly like any other profile — no special-cased root home (Hermes' back-compat asymmetry is explicitly rejected; we have no users to protect).
- **Filtering is enforced in the daemon, fail-closed** — a view with indeterminate scope shows nothing. Never client-side.
- **One daemon, one database, one runtime.** Per-profile stores/processes are rejected.
- v1 audience is **operator-grade segmentation** (one person separating their own contexts); the data model is normie-ready but no non-technical claim is made (copy stays future-framed).

## Alternatives Considered

### Alternative 1: Profile owns workspaces (Hermes parent model)

- **Description**: a profile is a container; workspaces live inside it.
- **Pros**: cheapest data model (children inherit transitively); matches Hermes.
- **Cons**: the same project folder must be re-registered per profile — the operator explicitly refused this friction.
- **Why rejected**: operator decision; projects are machine facts, contexts are lenses.

### Alternative 2: Per-profile home/store (literal Hermes port)

- **Description**: each profile gets its own state root (and effectively its own runtime instance).
- **Pros**: strongest isolation; near-zero schema work.
- **Cons**: N daemons/sockets contradicts the "one runtime, one state model" product differentiator; fixed shared workspaces make per-profile stores impossible; cross-profile views need a control plane.
- **Why rejected**: breaks the product's core architectural promise.

### Alternative 3: Workspace content shared across member profiles

- **Description**: profiles are memberships; a workspace's work is visible to every member profile.
- **Pros**: no stamping.
- **Cons**: contexts don't actually separate — the operator rejected it outright.
- **Why rejected**: fails the feature's purpose.

## Consequences

### Positive

- Register a project once, use it from any context; the switch is a filter, not a migration.
- A fresh install is byte-identical in behavior to today (quiet `default`).
- Only creation-root entities carry the stamp; children inherit — the change surface stays bounded.

### Negative

- Every read surface must enforce the profile axis server-side (the enforcement sweep is the bulk of the work).

### Risks

- A missed surface leaks across contexts → mitigated by fail-closed defaults and by landing the shared enforcement point first (ADR-007).
