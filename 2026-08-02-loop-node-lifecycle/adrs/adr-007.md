# ADR-007: Target-health isolation — per-target breaker and quarantine with full repair context

## Status

Accepted

## Date

2026-08-01

## Context

Today's consecutive-failure breaker is loop-global with a fixed threshold: one unhealthy external dependency kills the whole run as stalled, punishing healthy nodes. Temporal's circuit-breaker design supplies the two rules worth copying: key the breaker per destination, and count only transport-class failures — an application-level "no" says nothing about target health, so it records as success. Temporal's dead-letter queue supplies the anti-lesson: its entries are opaque blobs with no error, attempt count, or timestamp, so operator repair means correlating logs by hand. Market analysis shows native quarantine/DLQ is mostly absent everywhere, with "failed-run inventory + controlled replay" the emerging expectation.

## Decision

1. **Breaker per (node family, target).** Health is tracked per external target — an external tool server, a tool identity, an agent runtime — not per loop. Only transport/infrastructure-class failures count toward tripping; semantic failures and handled (routed/absorbed) failures never do.
2. **An open target fails fast, into the normal failure flow.** While a target's breaker is open, nodes bound to it fail immediately with an explicit "target unavailable" cause that follows the standard precedence chain (route → escalate). The run is never killed globally because one target is sick; recovery probes close the breaker when the target heals.
3. **Quarantine replaces run death for repeat offenders.** A node that exhausts its handling for unexpected failures enters a quarantined terminal state instead of dragging the run down. The run continues on independent branches.
4. **Quarantine entries carry the full repair context:** the failure chain (classified causes, attempt history, timestamps), the remediation hints, the node's inputs reference, and the target involved. An operator or agent must be able to diagnose from the entry alone — no log archaeology.
5. **Quarantine is a workable inventory.** Quarantined nodes are listable across runs, inspectable, and requeueable after repair. Requeue re-enters through normal generation succession; all caps and budgets still apply.
6. **A required-but-quarantined producer never stalls silently.** If forward progress (including a gate-driven re-attempt) needs a quarantined node, the run surfaces as needing attention with the reason — visible on operator surfaces — rather than waiting invisibly or failing cryptically.

## Alternatives Considered

### Alternative 1: Keep the loop-global breaker, tune the threshold

- **Description**: Same arithmetic, configurable limit.
- **Pros**: No new keying.
- **Cons**: Still conflates "this loop is stuck" with "that server is down"; still kills healthy work.
- **Why rejected**: Wrong diagnosis axis; the fix is keying, not the number.

### Alternative 2: Count all failures toward the breaker

- **Description**: Any failure on a target trips it eventually.
- **Pros**: Simpler classification.
- **Cons**: A tool that correctly rejects invalid requests would be declared unhealthy; Temporal's documented rationale directly refutes this.
- **Why rejected**: Health is about the transport, not the answer.

### Alternative 3: No quarantine (run death or infinite handling)

- **Description**: Exhausted nodes terminate the run (today) or loop in repair forever.
- **Pros**: Fewer states.
- **Cons**: Run death loses all sibling progress; infinite repair burns budget. Both lose the "fix it and continue" story operators ask for by name.
- **Why rejected**: Quarantine is the only option that preserves both progress and bounds.

## Consequences

### Positive

- One bad dependency degrades one lane, not the whole run; the failure inventory becomes operable.
- Repair context on the entry makes quarantine actionable by agents, not just humans.

### Negative

- New states and verbs to learn (quarantined, requeue) and a health model to document.

### Risks

- Breaker keying must re-verify the bounds invariant: repair and requeue paths remain subject to caps identically (loops-paper-adoption Safety Invariant 10 posture, restated per target).
- Quarantine × gate re-attempt interaction is the subtlest seam; the techspec must define it against the succession planner explicitly.
