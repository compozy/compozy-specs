# ADR-002: Escalate-by-default failure posture with explicit absorption

## Status

Accepted

## Date

2026-08-01

## Context

Today a loop author has no failure vocabulary: no error routes, no allow-fail, no per-node retry (outside continuous goal nodes). When a node fails, the engine's only response is generation-level re-attempt with repair context, then the consecutive-failure breaker. Spec 1 introduces node-level handling (retry, error routes, reactions), which forces a decision: what happens when a node fails and the author declared nothing, and in which order do the handling layers apply?

The references disagree. Sim kills the run when a failure has no error edge. Previous-generation Compozy made a missing error transition a hard runtime failure after the task already ran (deep-dive correction: it was never a compile-time lint, and no allow-fail escape hatch ever existed). The briefing originally recommended adopting a mandatory-annotation rule. But the motivation behind those designs — failures dying silently or killing the run — does not exist in this engine: the default path is already escalation into a repair loop that carries the failure forward as context.

## Decision

1. **Unannotated failure escalates.** A node failure with no author annotation flows into generation succession with repair context — today's behavior, now the declared default of the contract.
2. **Absorption is always explicit.** A failure can only be swallowed by an authored error route or an explicit allow-fail declaration. Silent absorption is impossible by construction.
3. **Precedence chain (the contract's first rule):** node-level automatic retry → authored error route → failure reactions → escalation to generation succession. Only unhandled failures escalate; a routed failure is marked handled and does not trip run-level failure policy.
4. **Predicate failure policy (two deliberate defaults, from Sim):** a broken continuation predicate fails open — the loop exits rather than hangs; a broken routing predicate fails closed — it becomes a routable failure the error path can catch. Both outcomes are always recorded as diagnostics (improving on Sim, which records nothing for the first case). Predicate evaluation is cost-bounded; exceeding the bound is treated as a broken predicate under the same policy.
5. **Bounds are bounds.** Handled (routed or absorbed) failures still count toward iteration caps and budgets. No handling path is exempt from run-level limits (extends loops-paper-adoption Safety Invariant 10 posture).

## Alternatives Considered

### Alternative 1: Mandatory annotation (the briefing's original recommendation)

- **Description**: Every fallible node must declare an error route or allow-fail; validation rejects otherwise.
- **Pros**: Forces authors to think about failure node by node.
- **Cons**: Makes every loop verbose (agents authoring loops would boilerplate it); breaks all existing definitions; solves a problem this engine does not have — the default here is escalation into repair, not silent death.
- **Why rejected**: The v0 rule guarded against silent absorption; here absorption is already impossible without declaration.

### Alternative 2: Run dies on unrouted failure (Sim)

- **Description**: No error edge means the failure kills the run.
- **Pros**: Simple; failure is always loud.
- **Cons**: Throws away the engine's strongest asset — the generation repair loop with carried-forward failure context.
- **Why rejected**: Strictly worse than escalation for an engine that has repair.

### Alternative 3: Risk-scoped mandatory annotation

- **Description**: Annotation required only for node families with external effects.
- **Pros**: Middle ground.
- **Cons**: Creates two node classes authors must memorize; validation asymmetry.
- **Why rejected**: Complexity without a matching failure-mode gain.

## Consequences

### Positive

- Authoring stays light for humans and agents; nothing existing breaks.
- Every failure has exactly one well-defined path; "what happens if I do nothing" has a one-sentence answer.
- Broken predicates can neither hang a run nor pass silently.

### Negative

- Authors who want loud, immediate failure must declare it (route to a halting path) rather than getting it by omission.

### Risks

- Precedence must be enforced identically across all node families; a family that skips a layer breaks the contract's predictability. The techspec must state the chain once and derive per-family behavior from it.
