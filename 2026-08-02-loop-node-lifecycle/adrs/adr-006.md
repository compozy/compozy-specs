# ADR-006: Authorable reactions — trigger vocabulary, observe-only effects, fail-open contract, commit-gated dispatch

## Status

Accepted

## Date

2026-08-01

## Context

The engine has lifecycle hooks for extensions but no authorable per-node reaction surface in the loop definition — the single most-requested authoring gap in the corpus. The market's floor is a once-only failure hook (Inngest per-function `onFailure`, n8n error workflow); Sim contributes the safety contract (effects fire in isolation, failures swallowed and recorded, identifiers and resume links pre-bound before inputs resolve, effects see a copy of state); Mastra contributes the anti-lesson (its watch callbacks are not isolated — a throwing observer can fail the run). Temporal's effect-buffering contributes the ordering rule: effects that fire before the state they announce is durably recorded double-fire on retry and lie on rollback.

## Decision

1. **Trigger vocabulary.** Node-level reactions: `on_success`, `on_error`, `on_retry`, `on_pause`, `on_timeout`, `on_cancel`, `on_quarantine`. Loop-level reactions in the loop contract: one per terminal outcome (done, no-op, blocked, failed, exhausted, stalled, canceled) — "tell me when the run ends, however it ends" in one line. `on_error` fires once, after node-level handling (retries, routes) exhausts; `on_retry` fires per attempt. Deferred beyond v1: `on_resume`, authorable liveness reactions (engine events cover both).
2. **Effect vocabulary: emit and run.** A reaction entry can emit a typed event (feeding hooks, extensions, and the live event stream) and/or run a tool (channel message, webhook, anything the tool surface offers). No state-writing effect kind.
3. **Pre-bound context.** Effects resolve with the node's identifiers, the failure/pause context (including remediation hints), and ready-to-use resume/approval links — bound before input resolution, so "post the approval link" is authorable even though the node is paused.
4. **Fail-open, observe-only.** An effect failure is recorded on the run's record and never fails, delays, or retries the node. Effects observe state; they cannot mutate run state, verdicts, history, or outcomes. Reaction execution is isolated per entry — one dead webhook does not stop the next effect.
5. **Commit-gated dispatch.** Reactions and the lifecycle events they ride dispatch only after the state change they announce is durably recorded — never before. Crash-between-commit-and-dispatch resolves to at-least-once delivery of a truthful event, never announcement of a state that did not land. (Generalizes the existing durable-append-then-broadcast ordering invariant to all effects.)

## Alternatives Considered

### Alternative 1: Emit-only v1

- **Description**: Reactions emit events; delivery is wired externally via extensions/automation.
- **Pros**: Smallest surface; safest.
- **Cons**: The number-one use case ("notify my channel with the approval link") stops being a one-liner and requires external wiring the author must own.
- **Why rejected**: Kills the flagship value of the feature.

### Alternative 2: Emit + run + annotate (state-writing `set`)

- **Description**: Reactions may also write annotations visible to later generations.
- **Pros**: Most expressive.
- **Cons**: Breaks the observer/mutator boundary; conflicts with read-only history posture; reopens the re-entrancy hazard the fail-open contract closes.
- **Why rejected**: State flows through the graph and verdicts, not through side effects. Revisit only with concrete evidence of need.

### Alternative 3: Sim's trigger set (pause only)

- **Description**: Effects only at human-pause time.
- **Pros**: Proven minimal core.
- **Cons**: No failure notification — the market-floor use case — and no terminal-outcome hook.
- **Why rejected**: Too narrow for the contract Spec 1 defines.

## Consequences

### Positive

- Notification-with-context becomes a one-line authoring concern; extensions and event consumers get a uniform, truthful signal stream.
- The fail-open + observe-only pair makes reactions safe to add to any node without changing its semantics.

### Negative

- At-least-once dispatch means consumers must tolerate duplicate events after crashes (the event carries enough identity to dedupe).

### Risks

- Effect tools run with real capabilities; the techspec must state which execution context and permissions effect-invoked tools inherit, and reaction output must never leak secrets (redaction applies to pre-bound failure context).
