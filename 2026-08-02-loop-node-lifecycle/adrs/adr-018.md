# ADR-018: Web Visual Contract expansion — editor lifecycle authoring + hero path; start-binding held

## Status

Accepted

## Date

2026-08-02

## Context

The approved Visual Contract under `docs/design/opendesign/loops/` covers ten surfaces (finals +
labs): run page, node controls, quarantine sheet, inventories, **loop editor** (lifecycle grammar
+ chrome states), and the **hero path** (catalog → run form → loop detail). Spec 1's PRD,
user stories, TechSpec, and `_tests.md` originally only bound the run-page / inventories
subset to `task_08`. The editor authors the same DSL keys Spec 1 introduces (`retry`,
`deadline`, `result_contract`, `on_error`, node/loop `on_*`, `wait`, `on_parent_close`); shipping
the runtime grammar without truthful editor authoring leaves operators unable to declare the
contract they just gained. The hero path was redesigned in the same Visual Contract pass
(DESIGN-BACKLOG §2.3) with the `canceled` terminal and arrive-and-use run form — also absent
from the task tree.

Separately, DESIGN-BACKLOG §5 draws Start-binding authoring (`start[]` surfaces as Switch
allowlist, hands-free folds) in the editor artboard, but names a Spec 3 adjacency ship gate:
editor writes `start[]`, production sidebar gains the Start lane, docs drop "read-only" strip
language. Spec 1 is silent on ingress policy; folding Start-binding into this slate would either
smuggle Spec 3 scope or ship a Visual Contract without a durable write path.

## Decision

1. **Absorb editor lifecycle grammar + chrome states into Spec 1.** The web MVP includes
   truthful authoring of the Spec 1 failure contract in the loop editor: reliability envelope,
   six node triggers and seven contract terminals as effect lists, `wait` inspector,
   `on_parent_close`, lint dock (errors gate Publish; warnings never do; zero counts omit), and
   chrome states (built-in read-only with fork-before-publish; publish-rejected 422 strip).
   Owned by a dedicated frontend task (`task_09`), with WT + Playwright coverage.
2. **Absorb hero path Visual Contract into Spec 1.** Catalog (roster incl. `canceled`), run
   form (arrive-and-use, this form = `http`, no `stop`), and loop detail (reliability tiles +
   recent runs) ship as `task_10`, depending on run-page state pills/formatters from `task_08`.
   Parity evidence is `eng-ui-screenshot` + a content-addressed QA walk — not a new Playwright
   visual suite.
3. **Hold start-binding authoring.** `start[]` / Start lane / hands-free surface switches stay
   Spec 3 domain. Visual Contract rows for Start allowlist are out of Spec 1 task scope;
   production keeps current Start strip behavior until Spec 3 adjacency lands. Recorded as
   Non-Goal + MVP Boundary held item with the backlog §5 ship gate verbatim.
4. **Incremental delta, two frontend tasks.** Update existing artifacts in place; do not
   regenerate the PRD/TechSpec/task tree. Split editor (high) and hero path (medium) so each
   remains independently implementable with disjoint test IDs. Renumber docs → `task_11` and
   the QA pair → `task_12`/`task_13` so the QA tail stays last.

## Alternatives Considered

### Alternative 1: Single god-task for all new web surfaces

- **Description**: One frontend task owns editor + hero path + run-page reinforcement.
- **Pros**: Fewer renumbers; one Visual Contract owner.
- **Cons**: Mixes high-complexity form/PATCH/linter work with medium visual-parity work;
  violates cy-create-tasks "independently implementable" sizing; blocks parallel waves.
- **Why rejected**: Editor and hero path have disjoint files, tests, and risk profiles.

### Alternative 2: Regenerate the entire Spec 1 artifact tree

- **Description**: Re-run cy-create-prd / cy-create-techspec / cy-create-tasks from scratch.
- **Pros**: Clean numbering; fresh grill.
- **Cons**: Destroys accepted ADRs 001–017, peer-review corpus, and settled backend task
  boundaries for a web-only gap; high rewrite risk with no product change to the runtime slate.
- **Why rejected**: The gap is additive web scope; incremental delta preserves settled decisions.

### Alternative 3: Ship Start-binding authoring in Spec 1

- **Description**: Implement Start lane write path + allowlist UI from DESIGN-BACKLOG §5 now.
- **Pros**: Matches the full editor artboard; closes the docs "read-only" strip inconsistency.
- **Cons**: Ingress/`start[]` is Spec 3 domain; Spec 1 has no product rules for surface
  allowlists; ship gate explicitly requires Spec 3 adjacency.
- **Why rejected**: Scope smuggling. Held with an explicit ship gate until Spec 3.

## Consequences

### Positive

- Spec 1 web delivery matches the approved Visual Contract for lifecycle-relevant surfaces.
- Authors can declare Spec 1 DSL keys in the UI that already validates and persists them.
- QA pair stays at the graph tail with deps on all three web tasks + docs.
- Start-binding deferral survives DESIGN-BACKLOG deletion because it is recorded in MVP
  Boundary / Non-Goals / this ADR.

### Negative

- Task tree grows from 11 → 13; ~50 cross-task references need renumbering.
- Editor artboard still shows Start lane chrome that Spec 1 will not implement — authorized
  difference that implementers must not treat as a ship requirement.

### Risks

- **Risk**: Implementers treat Start allowlist rows as in-scope because they appear on
  `loop-editor.html`. **Mitigation**: Visual Contract tables in `task_09` exclude those rows
  and name the authorized difference; ADR-018 + Non-Goals cite the Spec 3 ship gate.
- **Risk**: Hero path drifts from run-page state chrome. **Mitigation**: `task_10` depends on
  `task_08` and reuses shared formatters/pills.
