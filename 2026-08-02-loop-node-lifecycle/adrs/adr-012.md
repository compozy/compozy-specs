# ADR-012: Scheduling of future work — durable due-times on the 15s scheduler cycle, one cell epoch kills stale wakes, opportunistic in-memory timers

## Status

Accepted

## Date

2026-08-01

## Context

The daemon has no durable timer service. Everything time-based rides `Scheduler.RunOnce`
(`internal/scheduler/scheduler.go:266`) at `defaultInterval = 15s` (`internal/scheduler/types.go:14`):
lease sweep, block expiry, the loop coordinator backstop
(`internal/daemon/scheduler_loop_coordinator.go:12`), watch-events gap wakes, starvation
escalation. The loop plane advances event-first (post-commit wakes, hook-observer wakes) with the
15s cycle as backstop; there is no `next_attempt_at`, no delayed enqueue, no in-loop ticker. The
contract adds four future-time needs: retry backoff (US-008), authored deadlines (US-010), timer
waits (US-021), and escalation-ladder steps (US-022). Idea 27 (epoch fencing) guards all of them:
scheduled work belonging to a superseded state must never fire (US-010 EC-4, Business Rule 15).

## Decision

1. **Durable truth is a due-time column scanned by the existing 15s cycle.** The loop backstop
   gains a due-scan: `loop_generation_outputs.next_attempt_at <= now` (retries),
   `loop_node_waits.resume_at <= now` (timers), `loop_node_waits.next_escalation_at <= now`
   (ladders), and authored-deadline expiry — each due hit enqueues the corresponding coordinator
   wake through the existing `EnqueueLoopCoordinatorWake` path. No new ticker, no rival timer
   service; restart safety is inherited because due-times are rows.
2. **Retries are coordinator-mediated, not in-process sleeps.** A failing attempt ends its task
   run; the coordinator boundary classifies, appends the attempt-ledger row, sets
   `status = retrying` + `next_attempt_at` under a bumped cell epoch, and yields. When due, a fresh
   deterministic task run (`…node.<id>.<item>.a<attempt>`) is enqueued. `internal/retry` is reused
   only *inside* an attempt for sub-second transport retries internal to an executor call, never
   to hold a lease across backoff.
3. **One cell epoch invalidates stale future work.** The authoritative fence is
   `loop_generation_outputs.epoch` — a single per-cell counter (round-1 review B-004). Every
   scheduled future action persists the epoch it was issued under (`loop_node_waits.issued_epoch`
   for timers/ladders; the retry row compares against its own cell); every superseding lifecycle
   mutation (pause, cancel request, resume, manual reset, quarantine, requeue, route) increments
   the epoch of every affected cell in the same transaction that mutates control/wait state; a
   due-scan hit whose issued epoch differs from the current cell epoch is dropped with a
   `stale_schedule_dropped` diagnostic. `loop_node_controls.revision` fences verb CAS only and
   never gates schedules. This is idea 27 as a product guarantee: no ghost timers.
4. **Opportunistic fast path, durable slow path.** The daemon-side loop action runtime may arm an
   in-memory `time.AfterFunc` for a due-time it just persisted (sub-15s precision for short
   backoffs); the timer is best-effort and lost on restart — the due-scan is the guarantee. Both
   paths converge on the same wake, deduplicated by idempotency key.
5. **Paused and canceled cells never fire.** The due-scan predicate excludes rows whose control
   row is paused/quarantined and rows in terminal states; pause additionally suspends declared
   clocks by shifting anchors on resume (Business Rule 14).

## Alternatives Considered

### Alternative 1: In-process retry inside the claimed run (hold the lease across backoff)

- **Description**: The executor retries with `internal/retry` sleeps while the task run stays
  claimed.
- **Pros**: Sub-second precision; no coordinator round-trip; simplest to build.
- **Cons**: A crash during backoff loses the retry state (lease sweep marks it failed with the
  wrong attempt count); pause/cancel during backoff needs polling inside a foreign goroutine;
  attempt visibility requires side-channel writes; a long backoff blocks a lease slot.
- **Why rejected**: The contract promises visible, durable, pause-aware retries (US-008 AC-3,
  EC-1/EC-2); only durable scheduling delivers that.

### Alternative 2: New dedicated loop timer service with a due-time index and its own goroutine

- **Description**: A `loopTimerWheel` component firing exact due-times.
- **Pros**: Millisecond precision.
- **Cons**: A rival ticker beside the scheduler contradicts the established single-cycle design;
  another component with boot/shutdown/recovery semantics; precision beyond 15s buys nothing the
  defaults need (backoff base 1s, cap 30s — user accepted the slop).
- **Why rejected**: The seams survey's conclusion stands: join the cycle, don't rival it.

### Alternative 3: Delay column on `task_runs` (`available_at`) with claim-predicate change

- **Description**: Enqueue the retry run immediately, claimable only after `available_at`.
- **Pros**: Queue-native delayed delivery.
- **Cons**: Changes claim semantics for every consumer of the single queue (L-003 blast radius);
  loop-domain policy leaks into `internal/task`; stamps would need to live on the queue too.
- **Why rejected**: The loop coordinator owns node scheduling; the queue stays policy-free.

## Consequences

### Positive

- Zero new runtime components; restart heals by construction (worst case one 15s tick, same as
  today's coordinator convergence).
- One epoch mechanism covers retries, timers, deadlines, and ladders identically.

### Negative

- Worst-case +15s latency on any scheduled fire when the fast-path timer is lost — accepted in
  the defaults grill (TIMER GRANULARITY row).

### Risks

- Due-scan cost grows with parked rows — bounded by partial indexes on the due columns and the
  existing per-cycle page limits (mirror `EnqueueWatchEventsGapWakesPage`'s cursor pattern).
