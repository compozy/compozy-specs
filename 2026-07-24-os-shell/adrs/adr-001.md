# ADR-001: Single responsive OS shell replaces the AppShell grid (hard cut)

## Status

Accepted

## Date

2026-07-19

## Context

The web SPA today renders one active route inside a fixed chrome grid: `AppShell` (56px rail + nav panel sidebar, global 48px `TopbarShell`, single `Outlet`). The AGH OS v2 concept (`docs/design/opendesign/os/agh-os-v2.html`) replaces that chrome with a desktop metaphor: menubar, wallpapered desktop with floating windows, dock, and sessions rail. AGH is greenfield alpha with a zero-legacy posture (SD-002, L-006): dual shells and compat layers are forbidden. The current web app is desktop-first with no dedicated mobile shell; the prototype blocks viewports under 960px outright, which regresses usability on small screens.

## Decision

The OS shell is the **single** shell for the web app and it is **responsive**:

- The `AppShell` grid, global `TopbarShell` mount, and navigation `AppSidebar` are deleted, not kept as fallback.
- The window manager separates **logical state** (open windows, focus, per-window location) from **presentation mode**: `floating` (≥960px: draggable/resizable windows on a desktop) and `compact` (<960px: the same windows rendered as a full-viewport stack with the dock adapted). Rect geometry is a floating-mode concern only.
- The compact presentation's visual design is delivered by a dedicated prototype (in progress by Pedro) and lands under Visual Contract Mode; the architecture ships ready for it from day one.

## Alternatives Considered

### Alternative 1: Hard cut + "viewport too small" notice under 960px

- **Description**: Prototype behavior — desktop-only shell, blocking notice below 960px.
- **Pros**: Smallest scope; matches the prototype exactly.
- **Cons**: Regresses small-viewport usability the current app technically has; bakes a dead end into the shell.
- **Why rejected**: Product decision — Pedro wants the OS shell itself to be responsive.

### Alternative 2: OS shell + current AppShell kept as small-viewport fallback

- **Description**: Two shells selected by viewport width.
- **Pros**: No compact design work needed.
- **Cons**: Two chromes to maintain in parity forever; contradicts SD-002 zero-legacy; doubles QA surface.
- **Why rejected**: Dual-shell maintenance is exactly the compat-bridge posture the repo forbids.

## Consequences

### Positive

- One shell, one interaction model, one QA surface.
- Presentation-mode split forces clean WM state design (logical vs geometric), which also serves persistence and sync.

### Negative

- Compact mode adds design + implementation scope to v1 (accepted by explicit MVP decision).
- Every existing route chrome behavior (topbar slots, breadcrumbs) must be reimplemented per-window before the old chrome can be deleted.

### Risks

- Compact prototype arrives later than shell implementation → sequence compact-mode implementation as the trailing phase gated on the prototype; architecture (presentation switch) is not blocked.

## Implementation Notes

Delete targets are enumerated in `_techspec.md` §Delete Targets. Breakpoint: 960px (matches prototype floor and existing `min-[880px]/min-[1100px]` desktop-first grid history; single canonical constant in `systems/os`).

## Amendment (2026-07-19, peer-review round 1 — B-009)

The compact prototype is no longer pending: the current working-tree prototype ships a complete `<960px` mode (`os-v2.css` `@media (max-width:959px)` block + `os-v2.js` `mqMobile`): windows render as a stacked fullscreen stack (no border/radius/shadow/resize, zoom control hidden, enlarged traffic-light hit areas), the dock becomes a bottom tab bar (56px `--tabbar-h`, horizontal scroll, no magnification/tooltips/separators, safe-area insets), menubar menus collapse, and overlays clamp to the viewport. **This is the compact visual reference for v1** — the compact implementation phase is a normal Visual Contract Mode task against it, not gated on a future prototype. The Context sentence about the prototype blocking small viewports describes the pre-amendment prototype and is superseded.
