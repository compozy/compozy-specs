# ADR-009: Window snap layer on floating windows — persisted fractional zones, locally derived rendering

## Status

Superseded by `.compozy/tasks/window-management/adrs/adr-001.md` on 2026-07-22.

The independent fractional-zone model, opaque `win:*` writes, and public
`desktop-state` surface described below are no longer implementation contracts. The replacement is a
daemon-authoritative semantic topology with persistent virtual desktops, structural split/stack nodes,
revisioned commands, and validated layout documents. This file remains only as decision history.

## Date

2026-07-20

## Context

ADR-007 deferred edge snapping / half-screen tiling as a named post-MVP follow-up ("no prototype design; drop zones/preview/persistence are real scope"). Both blockers have since dissolved: `.resources/hermes/apps/desktop` provides a production-grade reference — a verbatim FancyZones port with resolved drag/overlay/motion constants (digested in `analysis/02_analysis_hermes-window-arrangement.md`) — and the desktop-state service (tasks 01–02, shipped) makes persistence a payload-field change because the daemon treats `os_shell` payloads as opaque JSON (ADR-008): adding a field to the `win:*` doc touches zero Go, zero wire contract, zero CLI.

Hermes itself is a **tiling** pane shell (guillotine tree, tabbed zones, sashes). Porting that paradigm would contradict ADR-003 (rect-per-window state) and ADR-006 (floating macOS-style desktop is the product identity) and would demand a new state model, renderer, and multi-client convergence semantics. The owner decision is to match Hermes's **interaction quality**, not its paradigm.

## Decision

1. **Snap layer on floating windows** (FancyZones-class, Windows-11-style): dragging a window near a desktop edge/corner previews a zone overlay; release snaps the window to that zone. v1 zones: left/right halves and four corner quarters. The top edge stays unbound — zoom already owns "fill the desktop"; a top-edge zone would create a second maximize path.
2. **`snap` is a persisted field on the `win:<windowId>` payload**: `snap: {fx, fy, fw, fh} | null` — normalized fractions (0..1) of the desktop work area. Fractions were chosen over a zone enum so thirds, spans, custom layouts, and agent-authored zones need no schema change, and so agents get a strictly larger surface than the six pointer zones.
3. **Derived rendering authority**: while `snap` is set, each client renders the window's geometry as `work area × fractions`, computed locally (the same non-Rnd absolute path maximized windows use), clamped to window minimums. Viewport resize re-derives and **never commits** — this eliminates cross-client commit oscillation between different viewport sizes and makes proportional reflow free. `rect` keeps the last committed px (the snapping client's derivation) for thumbnails and non-rendering readers.
4. **Whole-doc atomicity**: `snap` always travels inside the whole `win:*` doc (KV put semantics). A rect-only write is by construction a write with `snap: null` — `snap` and `rect` can never disagree because they never travel separately. No partial-update rules, no special agent contract.
5. **Exclusivity + restore**: `snap` and `maximized` are mutually exclusive (setting either clears the other). `snapWindow` stores the pre-snap rect in `prevRect`; dragging away or any `commitRect` clears `snap`; restore returns `prevRect` exactly. Safety Invariant 19 captures this.
6. **Scope (owner-selected)**: v1 = basic snap (halves/quarters, overlay, drag-away restore) + keyboard/palette (palette commands for every zone + restore; Rectangle-style chords ⌃⌥←/→ halves, ⌃⌥U/I/J/K quarters, ⌃⌥↓ restore; palette is the a11y-guaranteed path). Compact presentation: snap actions are no-ops.
7. **Constants as the parity contract**: the Hermes/FancyZones numbers (4px drag threshold, 20px sensitivity radius, 80ms linear overlay fade, 150ms ease-out zone morph on insets/colors/opacity only, active-target-only backdrop blur, reduced-motion collapse) are adopted verbatim as the normative motion contract, with file provenance in the analysis. Evidence is Storybook + `eng-ui-screenshot` captures + designer review — **no rendered-reference bundle**: Hermes's paradigm differs, so its pixels are provenance, not a Visual Contract reference.

## Alternatives Considered

### Alternative 1: Port the Hermes tiling paradigm (zone tree + tabs + sashes)

- **Pros**: The full power-user experience; the reference implementation exists.
- **Cons**: Rewrites the state model (tree, not rects), persistence payloads, convergence semantics, and the renderer; contradicts ADR-003/006; weeks of scope inside a closing program.
- **Why rejected**: Wrong paradigm for the product identity. Recorded follow-up: an optional "tiled space" mode as its own program, reusing this layer's zone resolver.

### Alternative 2: Pure-gesture snap (no persisted field; snap just produces rects)

- **Pros**: Zero payload change; snap is invisible to every reader.
- **Cons**: A snapped half degrades to a fixed px rect — no proportional reflow on viewport resize, and other clients can't distinguish snapped from hand-placed.
- **Why rejected**: The opaque-payload discovery made the persisted field nearly free (web codec + docs only), and fractions buy reflow + agent expressiveness. This was the initial recommendation; the owner chose the persisted field once the true cost was established.

### Alternative 3: Named-zone enum (`"left-half" | "tl" | …`)

- **Pros**: Closed set, trivial validation.
- **Cons**: Every follow-up (thirds, span, custom zones) is a schema change; agents limited to pre-baked zones.
- **Why rejected**: Fractions subsume the enum at equal validation cost (range + minimum checks).

## Consequences

### Positive

- Proportional reflow ships in v1 (a snapped half stays half across viewport changes) — free consequence of fractions + derived rendering.
- Agents can arrange desktops in fractional zones through the existing `agh desktop-state` surface — no new endpoint, verb, or tool.
- Zero Go/wire/CLI change; the daemon remains ignorant of window semantics (ADR-008 held).
- The zone resolver and constants are reusable verbatim by the future tiling program.

### Negative

- The `win:*` client schema grows; codec validation must salvage invalid `snap` to `null` without dropping the window (US-001.EC-2 posture).
- Two geometry authorities per window (committed rect vs derived) — bounded by invariant 19's exclusivity and no-commit-on-resize rules.

### Risks

- Derived geometry intentionally differs across clients with different viewports (same fractions, different px) — documented so convergence tests assert fractions, not px (E2E-026).
- Quarter zones on short viewports can derive below window minimums — derivation clamps to minimums, accepting fraction overflow; asserted in unit coverage.

## Implementation Notes

Owned by task_09. Store action `snapWindow(id, zone)`; pure zone resolver (pointer → zone hint) tested without DOM; overlay renders from a single published hint per frame (Hermes pattern); snapped windows bypass react-rnd exactly like maximized ones. Follow-ups named here so nobody re-litigates: tiling window mode, snap-layout editor / custom zones, multi-zone span (Shift), linked seam resize (snap groups), thirds presets, auto-arrange ("tidy", still ADR-007's).
