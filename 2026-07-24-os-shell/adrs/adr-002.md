# ADR-002: Window = app subtree with internal navigation; the URL reflects the focused window

## Status

Accepted

## Date

2026-07-19

## Context

TanStack Router has no parallel/named-outlet routes (upstream Discussion #605; the Parallel Routes docs page is a TODO stub), so N simultaneously visible windows cannot be N active routes. The codebase is already layered as thin route files → router-glue wrappers (`-*-route.tsx` + `use-*-route.ts`) → pure prop-driven `systems/*` views, which makes views portable into window bodies. Deep links, back/forward, and loader-based cache warming must keep working. Route masking has a known unmount/remount flicker bug when search params change inside masked routes (Discussion #1966), which rules out URL-encoded window layouts.

## Decision

- A **window hosts one app's route subtree** with internal navigation: e.g. the `tasks` window navigates internally between `/tasks`, `/tasks/$id`, `/tasks/$id/runs/$runId`; the window breadcrumb deepens accordingly.
- **Sessions are multi-instance** — one window per session, id `session:<sessionId>`. All other apps are **single-instance** (`app:<appId>`); opening an already-open app focuses it.
- **The URL is the focused window's current location.** Every open/focus/internal-navigation flows through `router.navigate()`; route leaves become sync-controllers that reconcile URL → window manager and render `null`. Focus changes mirror window location → URL. Back/forward traverse focus + location history. Deep links open/focus the owning window at the target location.
- Window geometry (rect/z/minimized) never appears in the URL; it lives in the window-manager state (ADR-004).
- Unfocused windows keep their location in WM state and render outside the router `Outlet`; on mount they warm caches by calling the same preload modules route loaders use (`-*-preload.ts` → shared `queryOptions`).
- TanStack Router remains the **single navigation authority**; the WM is the single window-arrangement authority (L-005 exclusivity applied to the frontend).

## Alternatives Considered

### Alternative 1: Every route (including details) opens its own window

- **Description**: List and detail become sibling windows.
- **Pros**: Maximally "OS-like"; free multitasking of details.
- **Cons**: Window explosion; no prototype design; ambiguous URL/focus semantics; single-instance guards become incoherent.
- **Why rejected**: Complexity without a designed interaction model.

### Alternative 2: Serialize the window set into search params (URL = whole desktop)

- **Description**: `?windows=...` encodes open windows/layout.
- **Pros**: Shareable desktop layouts.
- **Cons**: Route-masking flicker bug (#1966); noisy URLs; conflicts with daemon-side persistence.
- **Why rejected**: Fragile on a known upstream bug and redundant with ADR-004 persistence.

### Alternative 3: Wait for TanStack parallel routes

- **Why rejected**: Deprioritized upstream with no timeline; blocks the program indefinitely.

## Consequences

### Positive

- Deep links, loaders, and `<Link>` usage across `systems/*` keep working unchanged (windows render under the same `RouterProvider`; any in-window click focuses the window first, so navigation lands on the focused window).
- Route files survive as sync-controllers — no route inventory rewrite.

### Negative

- Per-app router glue (`use-*-route.ts`) must be rewritten as window controllers that read location from WM state instead of `useSearch`/`useParams`.
- The `network` domain (deep router coupling, `$workspaceId` in path) is the most expensive port.

### Risks

- Search-param validation for unfocused windows bypasses route `validateSearch` → controllers validate window locations with the same shared zod schemas from `systems/*/lib`.

## Implementation Notes

Focus-change → `navigate({ to: window.location })` uses `replace: false` so focus history is real history. Closing the focused window navigates to the next-top window's location, or `/` (desktop) when none remain.

## Amendment (2026-07-19, peer-review round 1 — B-006)

The naive bidirectional sync (sync-controller → `openOrFocus` → focus → `navigate`) forms a feedback cycle: a `route-pop` (browser Back) would re-push the location it just popped, and a pointer-focus followed by an in-window link would write two history entries. The decision is refined: a single **routing coordinator** mediates URL↔WM with explicit causes — `user-open`, `user-focus`, `route-pop`, `hydrate`, `workspace-switch`. Rules: (1) the WM store is side-effect-free — no store action navigates; (2) route-originated reconciliation (`route-pop`, deep link) updates the store only and never pushes history; (3) user-originated transitions produce exactly one history write; (4) hydration completes before the initial URL is applied as the final focus intent (deep link wins over restored focus); (5) keyboard activation inside an unfocused window focuses it exactly as pointer interaction does. `_techspec.md` §Routing Model and Safety Invariants 11–12 carry the normative text.

## Amendment 2 (2026-07-19, owner decision — modal policy)

Modal surfaces follow the window model rather than fighting it: dialogs/sheets are **window-scoped** (portal into the owning window via `OverlayContainerContext`, centered, clamped, blocking only that window), route-backed modal flows (`/tasks/new`, `/tasks/$id/edit`, network threads) become **in-window locations** of their app's subtree — which this ADR's window↔route model already covers — and the desktop-level overlay set is a closed list (palette, spaces, toasts, onboarding gate, context-destroying confirms). Normative text: `_techspec.md` §Modal & Overlay Policy, Safety Invariant 18.
