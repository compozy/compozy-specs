# ADR-004: Operator deep links to foreign-workspace sessions prompt before switching the active workspace

## Status

Accepted

## Date

2026-07-28

## Context

The web SPA scopes session lookup and cache identity to the active workspace: a deep link (`/agents/:agent/sessions/:session` or `/session/:session`) to a session owned by another workspace renders `Session not found` and never changes the active workspace (`docs/qa/scenarios/ET-web-session-deep-link-isolation.md`, in-flight on branch `xstate-refac`). The daemon intentionally allows operator-scope global reads (`GET /api/sessions` without a workspace filter), so this is a client-side UX decision, not a security boundary — the frontend is explicitly not one. Pedro flagged the dead-end as the wrong UX and chose the confirm-first variant over silent auto-switch.

## Decision

When a session deep link misses in the active workspace, the route loader resolves the owner via the operator-scope global sessions surface. If the session exists in another workspace, the UI shows a confirmation ("This session belongs to workspace B — switch?"). On confirm, the SPA activates the owning workspace and opens the session; on cancel, it stays put and shows the existing not-found state. Sessions that exist nowhere keep today's `Session not found` behavior. This is operator UX only — agent actors are governed by the `workspaceaccess` policy (ADR-001/002) and never by web routing.

## Alternatives Considered

### Alternative 1: Silent auto-switch

- **Description**: Deep link activates the owning workspace immediately, like a file link opening the right project.
- **Pros**: Zero friction; one less dialog.
- **Cons**: Workspace switch swaps desktops, windows, and runtime context — an invisible jump disorients and can interleave with in-progress arrangement work.
- **Why rejected**: Pedro chose the explicit variant; the switch is a heavyweight context change worth one click.

### Alternative 2: Keep the block

- **Description**: Preserve `Session not found` for foreign sessions.
- **Pros**: No work; strongest client-side scoping story.
- **Cons**: Punishes the product's own permalinks; the "protection" defends nothing the daemon doesn't already allow the operator to read.
- **Why rejected**: It is friction without a threat model.

## Consequences

### Positive

- Permalinks from notifications, terminals, and docs work regardless of the currently active workspace.
- No daemon changes required; the operator global read surface already exists.

### Negative

- The QA scenario `ET-web-session-deep-link-isolation` must be rewritten: "never changes workspace" becomes "never changes workspace *without confirmation*", and foreign-session data must stay unrendered until confirm.
- Touches route loaders currently being refactored on `xstate-refac`; coordination with that in-flight work is required.

### Risks

- Leaking foreign session content pre-confirmation: the loader must fetch only the minimal owner projection (workspace id + name) before the user confirms.

## Implementation Notes

**Amended by peer review round 1 (B-006): phase 0 includes a backend deliverable.** The existing global sessions catalog returns full `SessionPayload` objects, so a client-side projection cannot satisfy the pre-confirm minimal-fetch contract. Phase 0 ships `GET /api/sessions/:session_id/owner` — contract type, core handler, HTTP + UDS registration, OpenAPI/TS codegen — returning exactly `{session_id, workspace_id, workspace_name}` (404 for unknown sessions). The loader fetches only this projection pre-confirm, cached under a dedicated `session-owner` query key that is never merged into session catalogs or detail caches.

Affected web modules: `web/src/routes/_app/-agent-session-route-loader.ts`, `-session-permalink-route.ts`, `web/src/systems/workspace/stores/active-workspace-store.ts`, the new `session-owner` query key module. The confirmation is a routed dialog, not a toast, so it is deep-link-replayable and E2E-addressable.
