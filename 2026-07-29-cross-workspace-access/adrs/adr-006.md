# ADR-006: Beta posture — instructional enforcement via system prompt; the technical operator boundary is deferred

## Status

Accepted (supersedes ADR-005; amended by ADR-007, 2026-07-28 — the beta posture, audit-as-detection, and deferred containment ADR all stand. The dedicated standing system-prompt rule and the toggle/grant surfaces it guarded were removed: with no self-grantable state left, the remaining gap is the pre-existing `permissions.*` config-file-edit exposure, covered by audit + docs)

## Date

2026-07-28

## Context

Three peer-review rounds progressively hardened the operator/agent boundary (token file → process-ancestry classification + nonce-bootstrapped web authority + CAS'd consent + dispatch-scoped permits), and round 3 showed even that design has an escapable core (`setsid`/double-fork erases lineage) — with the counter-observation that an escaped same-UID process already has direct filesystem access to every workspace root and to `compozy.db`, so no daemon-side mechanism adds real security against it. Pedro's product call: this is over-engineering for a beta. Simplify, accept the gap openly, and enforce the rule where ACP runtimes demonstrably comply — the system prompt.

## Decision

1. **The technical operator boundary is deferred.** No process-ancestry classifier, no nonce/cookie web authority, no operator token, no CAS'd grant generations, no dispatch-scoped consent permits. Mutation and read surfaces use the **existing** guards, exactly like tool-approval grants today: loopback `privilegedMutationGuard()` on HTTP mutations, UDS peer-cred, trusted `scope.Operator` on native mutation tools, and the fail-closed `agentMutableConfigKinds` classifier on `compozy__config_set`.
2. **Enforcement is instructional + audited.** Every managed agent session's daemon-assembled base instructions (system prompt) gain a standing rule: *cross-workspace access is governed by the operator's toggle and grants; the agent must never enable the toggle, grant itself or other agents access, or circumvent workspace isolation even where technically able; when blocked, surface the denial and ask the operator* (the deny hint names the command). The official `skills/compozy/` skill and docs carry the same rule. Every cross-workspace allow/deny still emits an audit event, so violations are visible.
3. **The accepted gaps are enumerated, not hidden** (spec "Accepted Beta Gaps" section): a supervised agent could technically reach grant/toggle mutation surfaces through loopback HTTP/UDS or direct config-file edits; prompt/manual grant races are last-write-wins (tool-approval parity); global read surfaces are loopback-open. Closing them is a named future security ADR (OS-enforced session containment), to be written when the product leaves beta or evidence demands it.

## Alternatives Considered

### Alternative 1: Ship the round-2/3 boundary machinery

- **Description**: Ancestry classifier + nonce web authority + CAS consent + dispatch permits, with round-3's fixes (positive proof / containment).
- **Pros**: Strongest daemon-side story; three review rounds of design already done.
- **Cons**: Still escapable without OS containment (round-3 B-001); large platform-specific surface (peer-cred gaps on Windows/Darwin-nocgo); weeks of work defending against an adversary that already owns the filesystem.
- **Why rejected**: Cost/benefit indefensible for a beta with zero production users; the real fix (containment) is a separate project.

### Alternative 2: Hold the feature until OS-enforced containment exists

- **Pros**: No gap ever ships.
- **Cons**: Blocks a wanted product capability behind an unstarted sandbox project.
- **Why rejected**: The feature's default is deny; the gap only matters after the operator opts in, and the operator is the only user.

### Alternative 3: Instructional enforcement (chosen)

- **Pros**: Matches the actual threat (prompt-injected but compliant agents follow their system prompt; ACP runtimes respect it broadly); ships now; keeps the clean policy core, audit trail, and UX; honest documentation.
- **Cons**: A deliberately malicious agent ignores instructions — accepted and documented.

## Consequences

### Positive

- The spec shrinks to its essence: central policy + toggle + grants + prompt + audit + web UX, all on proven machinery (tool-approval template).
- No platform-specific peer-credential work; Windows parity concerns disappear.
- The system-prompt rule also covers surfaces no technical guard reaches (e.g., an agent editing config files through its own shell tools).

### Negative

- Security posture is trust-based for the beta window; the audit trail is detective, not preventive.
- The future containment ADR inherits the full hardening scope.

### Risks

- An operator may over-trust the toggle in multi-agent setups with untrusted third-party agent definitions. Mitigation: docs/site security page states the beta posture in plain language; default remains off; reject grants and audit events give a ban-and-detect loop.

## Implementation Notes

The base-instruction assembly point for ACP sessions is daemon-owned (verify exact surface at implementation; sessions already receive daemon-injected env/instructions at start). The rule text ships in one place and is covered by a unit test asserting its presence in the assembled instructions and an `acpmock` E2E asserting the mock runtime receives it. ADR-005's artifacts (classifier, nonce store, `workspace_access_state` table, CAS revisions, DispatchID permits) are not built; ADR-005 is superseded, kept for the design record.
