# ADR-009: Task Worktree Policy — Profile Block Mirroring SandboxPolicy, Per-Run Materialization at the Session Bridge

## Status

Accepted

## Date

2026-08-11

## Context

ADR-003 decided the task surface: a worktree policy with modes `inherit | none | ref | per_run` on the task execution setup, decided before enqueue, with fan-out offering per-run isolation. The entry-points analysis mapped the complete precedent to mirror: `SandboxPolicy{Mode, SandboxRef}` spans 11 layers — domain type (`internal/task/profile.go:115-118`), normalization, config-backed validation gates, flat columns + CHECK on `task_execution_profiles` (`71_task_profiles.sql:19-22,36-39`), whole-profile-replace service with the active-run lock (`manager_profile.go:74-81`), HTTP/UDS routes, CLI (`task profile inspect|update|delete`), native tool (`compozy__task_execution_profile_set`), config default (`task.orchestration.profile.default_sandbox_mode`), daemon application (`session_policy_gate.go:42-71` → `task_session_bridge.go:121-123`), and the session-reuse fingerprint (`task_role_sessions.go:286-301`).

Two open mechanics remained: **where** a `per_run` worktree materializes, and **who** guards session reuse against wrong-directory execution. The reference products bind materialization to the interactive first-send (synara `ChatView` lazy creation) — but task runs are non-interactive; there is no composer to host a pending state, and Business Rule 21 demands: materialization failure fails the run and leaves no orphan.

## Decision

1. **`WorktreePolicy{Mode WorktreeMode; WorktreeRef string}` joins `ExecutionProfile`**, modes `inherit | none | ref | per_run`, mirroring SandboxPolicy at every one of the 11 layers: normalizer (empty ⇒ `inherit`), validation (`ref ⇔ non-empty WorktreeRef`, ref must resolve to an attached worktree of the task's workspace at write time), flat columns + CHECK constraint, PUT-replace semantics unchanged, config default `task.orchestration.profile.default_worktree_mode = "inherit"`.
2. **The policy is resolved once at enqueue and snapshotted onto the run row** (peer-review B-002): the enqueue transaction writes `task_runs.resolved_worktree_mode/_ref` (the same discipline as the immutable `resolved_network_participation` snapshot), and the profile→session bridge (`applySessionWorktreePolicy` beside `applySessionSandboxPolicy` in `internal/daemon`) consumes **only the claimed run's snapshot** — the live profile is never re-read after claim. Resolution: `none`/empty → workspace root; `ref` → re-resolve the snapshotted ref at worker start (removed/missing ref fails the run with `worktree_ref_invalid` — never a silent root fallback, BR-19); `per_run` → materialize now.
3. **Per-run materialization is synchronous inside worker-session preparation and lease-fenced**: `MaterializeForRun` is a thin wrapper over the same phased creation primitive manual creation uses (L-004 — one creation path). It runs inside the active claim: heartbeats continue throughout materialization, every run/session binding and run-fail write goes through `task.Service` guarded by the claim token, a claimant whose lease lapsed mid-materialization cannot bind (the worktree unwinds via the standard rollback), and the worktree domain never receives the raw claim token — it sees task/run identifiers only. Any failure fails the run with the materialization error and rolls back per the creation contract (no directory, no branch, no row) — BR-21. Run-created worktrees persist after terminal states with `origin = per_run` and the owning `run_id` recorded.
4. **Session-reuse fingerprint includes the worktree axis**: worktree mode + resolved ref join `taskRoleProfileFingerprint`. `per_run` never reuses a pooled session — every run gets a fresh session bound to its fresh worktree, making BR-23 (a reused session never executes in a different worktree than its binding) structural rather than checked.
5. **Claim eligibility is untouched**: the worktree policy shapes *where* the worker session runs, never *which* run is claimed. No claim-filter SQL is added; `task.Service.ClaimNextRun` remains the only claim authority (L-005).
6. **Fan-out per-run isolation is the same policy, not a parallel mechanism**: the fan-out flow sets `per_run` semantics for the spawned runs; each run materializes independently, partial failure attributes to its run (US-016 EC-2).

## Alternatives Considered

### Alternative 1: Run-level worktree table / per-run policy overlay

- **Description**: A `task_run_worktree_policies` side table letting individual runs override the task policy.
- **Pros**: Maximum flexibility.
- **Cons**: The profile is the established task-owned overlay; no story needs per-run divergence beyond `per_run` itself; a second policy home reintroduces the parallel-queue smell (L-003).
- **Why rejected**: `per_run` as a profile mode covers the need with zero new authority surfaces.

### Alternative 2: Materialize at enqueue time

- **Description**: Create the worktree when the run is enqueued, before any claim.
- **Pros**: Run starts faster once claimed.
- **Cons**: Queued-but-never-claimed runs orphan worktrees; cancellation before claim needs cleanup machinery; violates "no orphan" cheaply.
- **Why rejected**: Materialize-on-worker-start makes the failure domain equal the run's own lifecycle.

### Alternative 3: Lazy materialization at first prompt (synara/t3code model)

- **Description**: The session starts at the root and the worktree appears on first send.
- **Pros**: Matches the interactive-composer references.
- **Cons**: Task runs are non-interactive; a session that starts in one directory and moves is exactly the in-place mutation ADR-003 forbids; the pending state has no host surface.
- **Why rejected**: Wrong execution model for the queue path.

## Consequences

### Positive

- Agents manage the policy through the exact surfaces they already know (`task profile update`, `compozy__task_execution_profile_set`), and the PUT-replace caveat is already documented behavior.
- BR-20 (decided before enqueue) is enforced by the existing active-run lock for free.
- The claim path stays lock-free of worktree concerns; scheduler and lease semantics are untouched.

### Negative

- Worker-session start absorbs bootstrap latency for `per_run` (copy list + setup command, up to the configured timeout). Accepted: runs are asynchronous, and the pending worktree is visible in navigation while it materializes.
- The whole-profile PUT keeps its replace semantics, but the worktree block gains a dedicated patch primitive (`task.Service.SetWorktreePolicy` → `PATCH /tasks/:id/execution-profile/worktree`, `compozy task profile set-worktree`, `compozy__task_worktree_policy_set`) so setting the worktree policy alone preserves every other block — required by US-014 AC-3 (peer-review B-010); the PUT footgun caveat remains documented for whole-profile writers.

### Risks

- Concurrent runs of one task must never collide on name/branch: run suffixes derive from the run id (unique by construction); creation collision still refuses cleanly (US-015 EC-2).
- Fingerprint omission would silently reuse a wrong-directory session (correctness bug class flagged in the entry-points analysis); the fingerprint change ships in the same task as the policy application and is test-pinned.

## Implementation Notes

Loop-side environment control (`run-agent`/`goal` Environment absorbing `params.cwd`) follows ADR-003's decision and is specified in `_techspec.md` — it reuses this ADR's resolution semantics (`ref` re-resolution, per-run materialization, no silent fallback) at the loop action bind seam.
