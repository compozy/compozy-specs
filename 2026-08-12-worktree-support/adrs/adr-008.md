# ADR-008: Git Execution — A Capturing Runner Inside `internal/worktree`, Serialized Per Repository

## Status

Accepted

## Date

2026-08-11

## Context

No code in `internal/` reads or mutates git state for workspaces or sessions today. Exactly one package shells out to git — `internal/registry/gitsrc`, scoped to extension/registry sources — and its runner is deliberately hostile to this feature's needs: it discards stdout (`client.go:246-256`), and its `isolatedGitEnvironment()` forces `GIT_CONFIG_GLOBAL=/dev/null` + `GIT_CONFIG_NOSYSTEM=1` (`git_runtime.go:92-122`), which would strip the user's commit identity, credential helpers, and worktree-relevant settings. What it does prove out: an injectable `lookPath`/runner/version-probe seam, a hard version floor (git ≥ 2.37, `git_runtime.go:12`), explicit timeouts, and `GIT_TERMINAL_PROMPT=0`.

The feature needs read paths that parse porcelain output (`worktree list --porcelain -z`, `status --porcelain=v2 --branch -z`, `rev-parse`, `rev-list --left-right --count`) and mutation paths (`worktree add/remove`, `branch`, `add`/`commit`/`push`, `update-ref -d`) that are safe under concurrent invocation from UI + CLI + agents (PRD High-Level Constraint: per-repository mutations serialize rather than corrupt). synara ships the strongest concurrency pattern in the reference set: every mutation acquires a per-repository semaphore keyed on the canonicalized `git rev-parse --git-common-dir` (`.resources/synara/apps/server/src/git/Layers/GitCore.ts:781-834`), so all linked worktrees of one repo serialize against one lock.

## Decision

1. **One new package, `internal/worktree`, owns the worktree domain and its git execution.** No separate `gitutil` package ships in v1: the runner, porcelain parsers, and command builders are files inside `internal/worktree` (respecting the 500-line file split: runner, porcelain parsing, discovery, status, mutations each in their own file). `gitsrc` is untouched.
2. **The runner copies gitsrc's posture and fixes its two gaps**: `execabs.LookPath("git")` (CWD-safe), version probe with floor **git ≥ 2.37** (same floor as `gitsrc` — one documented git requirement for the whole product), per-call `context` timeouts, `Stdin = nil`, `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`; but it **captures stdout/stderr** (bounded) and **preserves user git config** — commit identity, credential helpers, and `core.*` settings are the operator's, and commit/push must run under them. Only `GIT_*` override variables that would redirect the repo (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`) are stripped.
3. **Capability gating, not raw errors**: git missing or too old degrades the entire worktree surface to a deterministic diagnostic (`worktree_git_unavailable` / `worktree_git_version_unsupported`) carried in list/inspect payloads and tool availability diagnostics; a non-git workspace shows no worktree affordance at all (US-001 AC-4).
4. **Per-repository mutation lock** keyed on the canonicalized git common dir (resolved once per workspace, cached): every create, adopt-side write, remove, branch reclamation, and exit action (commit/push) acquires it; discovery and status reads do not. Lock scope is in-process (single daemon owns the runtime); a bounded queue rejects pileups with `worktree_operation_in_progress` rather than deadlocking.
5. **Discovery is read-only by construction**: the discovery/status file exposes no mutating command; `git worktree prune` and `git fetch` are never invoked implicitly (ADR-002; explicit refresh gestures may fetch only where the PRD allows a user-asked network action).

## Alternatives Considered

### Alternative 1: Reuse/extend `internal/registry/gitsrc`

- **Description**: Add capturing output and config passthrough to the existing client.
- **Pros**: One git package; hardening already reviewed.
- **Cons**: gitsrc's isolation *is its contract* — registry installs must not see user config or credentials; loosening it per-call forks the security posture inside one package; registry scope would import-couple worktree needs.
- **Why rejected**: Two callers with opposite trust requirements should not share one env builder.

### Alternative 2: go-git (in-process library)

- **Description**: Use `go-git` instead of shelling out.
- **Pros**: No binary dependency; typed API.
- **Cons**: Linked-worktree support is incomplete (add/remove/porcelain parity gaps); behavior drift vs the git the user runs in the same tree; every competitor studied shells out; hooks/credential helpers would not run.
- **Why rejected**: The worktree feature's whole truth model is "what git says"; a reimplementation that disagrees with the user's git is untruthful by construction.

### Alternative 3: Standalone `internal/gitexec` shared package now

- **Description**: Extract the runner into a neutral package for future consumers (forge ext, future VCS features).
- **Pros**: Ready for reuse.
- **Cons**: Exactly one consumer exists; a premature shared surface invites the generic-infrastructure anti-pattern the playbook refuses; extraction later is mechanical.
- **Why rejected**: Add a file to a package before adding a package (design minimalism); revisit when a second consumer is real.

## Consequences

### Positive

- One git requirement (≥ 2.37) across the product, one diagnostic vocabulary, one place to audit command construction.
- Per-repo serialization makes UI+CLI+agent races corruption-free by construction, and the lock key (common dir) is exactly the parent-identity key adoption validates against.
- Runner injectability keeps unit tests hermetic (fake runner) while integration tests use real git.

### Negative

- A binary dependency on system git remains (accepted: PRD constraint "git as an external dependency" with graceful degradation).
- The in-process lock does not guard against the *user* running git concurrently in a terminal — status reads must tolerate torn reads and surface them as explicit read errors, never as clean.

### Risks

- Windows path canonicalization (case-insensitivity, `\` vs `/`, symlink quirks) affects lock keys and containment checks — all common-dir and path comparisons go through one canonicalization helper, tested per-platform (PRD cross-platform constraint).
- Long-running exit actions (push over slow network) hold the repo lock; timeouts per command class keep the queue moving.
