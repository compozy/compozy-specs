# ADR-011: Branch Namespace `run/`, Readable Generated Names, and Compare-and-Delete Reclamation

## Status

Accepted

## Date

2026-08-11

## Context

Three naming contracts needed final values. (1) BR-16 requires automatically created (per-run) branches to live in "a recognizable CompozyOS namespace"; the shipped design set uses `run/` (e.g. `run/fix-flaky-e2e`) and the UI/UX review validated that reading, while the market records complaints about long tool prefixes colliding with team conventions (Claude Code's `worktree-`). (2) The PRD left generated worktree names (manual creation with the name omitted) as an open question between readable words and task-derived slugs; herdr generates `worktree/<adjective>-<noun>-<hex>` (`.resources/herdr/src/worktree.rs:21-32`), synara/t3code generate opaque `<tool>/<hex>` then rename via an LLM on first turn. (3) BR-17 permits automatic reclamation only of namespaced, auto-created branches, and only when "verifiably unchanged since creation" — synara implements the strongest verification primitive in the reference set: `git update-ref -d refs/heads/<branch> <expectedHead>`, git's atomic compare-and-delete (`.resources/synara/apps/server/src/git/Layers/GitCore.ts:2822-2894`), plus content `stateHash` markers for its gateway trees.

Operator decisions (grill, 2026-08-11): namespace `run/`, configurable; generated names use readable words.

## Decision

1. **Run-branch namespace default is `run/`**, configured by `[worktrees] run_branch_namespace` (global, per-workspace overridable via the workspace config overlay). Per-run branches are `<namespace><task-slug>-<run-suffix>` where the suffix derives from the run id — unique by construction across concurrent runs (US-015 EC-2). Only branches created by Compozy inside the configured namespace are ever reclamation-eligible; changing the configured namespace affects future creations only and never re-classifies existing branches (eligibility is recorded per-branch at creation, not re-derived from the current config).
2. **Manual creation never forces a prefix** (BR-15): the branch is the user's explicit name, or derived from the worktree name by slugging. Generated worktree names (name omitted) are readable `<adjective>-<noun>` pairs from embedded wordlists, with a numeric suffix only on collision. No LLM renaming pass exists in v1 — the name is the record label from birth (ADR-001 rule 4).
3. **Reclamation is compare-and-delete against the recorded creation head**: at creation, the worktree row records `created_branch = true` and `created_head` (the commit the branch was cut at). A branch is *verifiably unchanged* iff `refs/heads/<branch>` still equals `created_head`. Reclamation executes `git update-ref -d refs/heads/<branch> <created_head>` — atomic at the git layer, so a concurrent commit makes the delete a no-op and the commits survive. Reclamation runs only during removal of a run-created worktree (or acceptance of a cleanup suggestion); a failed compare-and-delete downgrades to an informational note, never an error.
4. **Everything else is preserved**: worktree removal never deletes user branches (BR-17); detached checkouts have no branch to reclaim; a run-created branch that received commits is treated exactly like a user branch from then on.

## Alternatives Considered

### Alternative 1: `compozy/run/` (vendor-prefixed) namespace

- **Description**: Double-segment namespace making the tool of origin explicit.
- **Pros**: Zero ambiguity about who created the branch; no collision with a team's own `run/` convention.
- **Cons**: Longer everywhere branches render (rows, chips, PR headers); the configurability escape hatch already resolves collisions; design set is authored with `run/`.
- **Why rejected**: Operator chose `run/` + configurability; per-branch recorded eligibility removes the mis-reclamation risk that vendor-prefixing would otherwise guard.

### Alternative 2: Opaque hex branches + LLM rename on first turn (synara/t3code model)

- **Description**: Generate `run/<8-hex>`, then a model renames it semantically after the first message.
- **Pros**: Names end up describing the work.
- **Cons**: A model call in the critical path of branch identity; rename-vs-ownership races (synara must delay renames until creation durability); per-run branches are already semantically named by the task slug.
- **Why rejected**: The task slug gives semantics for free; the rename machinery is complexity without a payer.

### Alternative 3: Content-hash ownership markers (synara `stateHash`)

- **Description**: Record a working-tree content hash at creation; verify before any automated deletion.
- **Pros**: Proves the whole tree untouched, not just the branch pointer.
- **Cons**: Solves a different problem — tree content is guarded by the two-step dirty removal (ADR-006), while branch reclamation only needs pointer identity; hashing every file at creation taxes every per-run start.
- **Why rejected**: `created_head` comparison is exact for the branch question; the dirty check owns the tree question.

## Consequences

### Positive

- `run/fix-flaky-e2e-r9b02c1`-style branches are recognizable, greppable, and safe to reclaim by construction.
- Teams with conflicting conventions set one config key; recorded eligibility keeps history consistent across config changes.
- Generated names are legible in every navigation surface without pretending to know the work's purpose.

### Negative

- Two naming systems coexist (readable pairs for manual, task-slug for per-run) — deliberate, since their audiences differ.
- Wordlist names carry no semantics; operators who want meaning type a name.

### Risks

- Slugging must be deterministic and cross-platform (case-insensitive filesystems): one shared sanitize function (lowercase, `[a-z0-9-]`, collapse, trim, cap length) feeds branch and directory derivation, with the derived pair previewed before confirmation (US-001 EC-2).
- `update-ref -d` with an expected value can race a *ref rename*; treated as reclamation-skipped (informational), consistent with never-delete semantics.

## Implementation Notes

Wordlists embed in `internal/worktree` (no network, no external files). The sanitize function and namespace matching are pure helpers with table-driven tests. `created_head`/`created_branch` columns are specified in ADR-007 / `_techspec.md` Data Models.
