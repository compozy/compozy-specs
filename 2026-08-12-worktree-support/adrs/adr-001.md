# ADR-001: Worktree as a Nested Sub-Context of Its Parent Workspace

## Status

Accepted

## Date

2026-08-11

## Context

Compozy workspaces are flat runtime scope objects: no parent/child relation, no VCS awareness, no kind discriminator anywhere in the entity, storage, wire contract, or navigation (analysis `04_analysis_compozy-workspace-baseline.md`). The feature requires worktrees that are (a) created from a git-backed workspace, (b) discovered when created externally, (c) selectable the same way a workspace is selected, and (d) nested under the parent workspace in navigation.

The references ship two opposite models. Synara and t3code attach a worktree to a *session/thread* as an attribute (`.resources/synara/packages/contracts/src/orchestration.ts:275`; `.resources/t3code/packages/contracts/src/environment.ts:22-28`) — which makes nested, selectable worktrees unimplementable because there is no worktree identity to render or select. herdr makes the worktree a *full workspace* plus a provenance record (`.resources/herdr/src/workspace.rs:34-41`), which gives selection parity for free but collides with four Compozy invariants: cross-workspace access is exact-string workspace-identity equality (a parent agent touching a child would be denied), workspace-scoped memory would reset to empty per worktree, OS-shell topology is owned per workspace (a child would boot with an empty desktop set), and the durable workspace identity file lives inside the working tree, so every checkout of the repo carries the parent's identity.

Market evidence says users think of a worktree as "the same project, different task" and expect the selection gesture to match the parent's (analysis `05_analysis_market-worktree-ux.md`, Transferable Patterns 2-3).

## Decision

A worktree is a **first-class nested sub-context of exactly one parent workspace**, and the canonical product term is **Worktree** (the parent term remains Workspace; the market's use of "workspace" for the child unit is explicitly rejected).

- Worktrees appear **nested under their parent workspace** in every navigation surface that lists workspaces, and selecting a worktree is the same gesture as selecting a workspace.
- Selecting a worktree scopes the working views: sessions and task runs bound to that worktree are what the surface shows, and new work started while a worktree is selected runs inside it by default.
- A worktree **inherits its parent's brain**: memory, agents, skills, configuration, permissions, and trust boundary all come from the parent workspace. Work executed in a worktree belongs to the parent workspace's scope, bound to the worktree.
- A worktree has stable identity minted by Compozy at creation/adoption time; its filesystem path is mutable metadata, never identity. The identity file checked out inside a worktree's tree is the parent's and is never read as the worktree's own identity.

## Alternatives Considered

### Alternative 1: Full child workspace (herdr model)

- **Description**: The worktree is a real workspace row with its own scope (sessions, tasks, memory, config), plus a provenance record linking it to the repo group (`.resources/herdr/src/workspace.rs:34-41`, `.resources/herdr/src/workspace/git/discovery.rs:71-99`).
- **Pros**: Selection, session ownership, and every workspace feature work with zero new concepts; herdr proves the UX.
- **Cons**: Project memory fragments (agents in a worktree lose everything learned in the parent); parent↔child agent collaboration becomes cross-workspace and is denied by policy; empty window topology per worktree; identity-file collision across checkouts; destructive registry prune on out-of-band removal would cascade-delete runtime history.
- **Why rejected**: Every one of those costs lands on the product's core promise — agents with durable project memory operating safely across parallel work.

### Alternative 2: Session attribute (synara/t3code model)

- **Description**: The worktree is a nullable field on the session/thread record; navigation shows at most a badge.
- **Pros**: Smallest data-model change; proven in two shipped products.
- **Cons**: No selectable identity — the nesting and selection requirements are unimplementable; path-as-identity forces fragile normalization everywhere; no per-worktree views.
- **Why rejected**: Contradicts the stated requirement ("selected the way a workspace is selected, nested in navigation").

### Alternative 3: Market vocabulary ("workspace" for the child)

- **Description**: Call the child unit a workspace, as Conductor/Superset/Sculptor do.
- **Pros**: Familiar to users arriving from those products.
- **Cons**: Inverts Compozy's hierarchy — the parent is already the Workspace; glossary discipline forbids the collision.
- **Why rejected**: One word for two nested concepts guarantees confusion in UI, docs, CLI, and agent tooling.

## Consequences

### Positive

- Agents working in a worktree keep the parent's memory, skills, and permissions — parallel work without amnesia.
- Selection parity with workspaces satisfies the market expectation ("same gesture as the parent") without duplicating workspace machinery.
- The cross-workspace access boundary is untouched: parent and worktrees are one trust domain.
- Runtime/agent state per worktree (which has a running session, which is idle) is renderable from state the daemon already owns — the market gap no competitor fills.

### Negative

- A new product concept exists between workspace and session; every surface that lists or filters work must learn the worktree dimension.
- Session and task views need worktree-aware scoping and filtering.

### Risks

- Identity handling must be explicit: the worktree's checkout contains the parent's identity file, and treating it as the worktree's own identity would collide registrations. Mitigation: worktree identity is always minted and stored by the runtime, derived from (parent workspace, worktree), never read from the checked-out tree.
- "Inherits the parent's brain" must not silently become "shares mutable state unsafely" — concurrent sessions in different worktrees still need per-session isolation guarantees already provided by the session model.

## Implementation Notes

Deliberately thin at PRD stage. The binding constraints the TechSpec must resolve are catalogued in `analysis/04_analysis_compozy-workspace-baseline.md` (identity file, session cwd containment, policy equality, destructive prune-on-list) and `analysis/06_analysis_worktree-entry-points.md` (session-reuse fingerprint, profile PUT-replace semantics).
