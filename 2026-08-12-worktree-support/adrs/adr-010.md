# ADR-010: Forge Provider — New `forge.provider` Extension Surface; Bundled GitHub Extension Authenticates via Secret Binding + Opportunistic `gh`

## Status

Accepted

## Date

2026-08-11

## Context

ADR-004 fixed the architecture direction: the runtime core owns everything answerable from local git plus zero-credential fallbacks; forge specifics (PR state, idempotent PR creation, merged detection) ship as extensions, GitHub first as a bundled one. The TechSpec must fix the concrete extension surface and the credential model.

Verified platform facts: the extension provide surface is a closed set of six (`internal/extensionprotocol/capabilities.go`), each mapping to required daemon→extension service methods with a consumer registry and conformance tests; bundled extensions follow the `dev-cycle` pattern (`extensions/dev-cycle/` — `embed.go`, `install.go`, manifest, self-hosted subprocess via `compozy __internal extension-provider <name>`); extension secret bindings (Vault-backed, manifest-declared `requires_env`) already exist (`internal/extensionenv/bindings.go`). Separately, Compozy's MCP runtime supports **remote HTTP MCP servers with OAuth** (`internal/mcp/executor_auth.go`, tokens in `global_db_mcp_auth.go`), and the marketplace models remote MCP entries (`internal/marketplace/entry_mcp_launch.go`, `launch.type = "remote"`) — the GitHub remote MCP (`https://api.githubcopilot.com/mcp`) is an already-modeled shape (settings fixtures `github-remote`). The operator asked whether the extension should bundle the GitHub MCP to reuse its OAuth.

## Decision

1. **`forge.provider` becomes the seventh member of the closed provide set**, with required service methods:
   - `forge/capabilities` — the forge-agnosticism contract (grill decision 2026-08-11): given normalized remote URLs, the extension declares which it can serve, and for each served remote returns the **provider vocabulary** (request noun + action labels — "pull request" vs "merge request", satisfying US-032 AC-3), **`supports_draft`**, a **`compare_url_template`**, **template path conventions** for body prefill, and `credential_source` (`binding | gh | absent`). Core and web render from this payload — no forge terminology or URL shape is hardcoded in core paths that have a serving extension. Two extensions claiming one remote resolve deterministically by enable-order with the winner surfaced (US-032 EC-2).
   - `forge/status` — for (remote, branch): PR existence/number/state (normalized to `open|closed|merged`), merged evidence, fetched-at.
   - `forge/pr_create` — idempotent create (existing open PR for the branch is returned as `opened_existing`, never duplicated), inputs: base, title, body, draft.
   Consumer registry, manager wiring, and conformance-matrix coverage follow the existing per-capability pattern.
2. **Core keeps a minimal URL-shape table for well-known public hosts** (github.com, gitlab.com, bitbucket.org) used **only** to build the browser compare link when **no** extension serves the remote — this keeps US-022 AC-4 ("browser path works with no forge extension") true without leaking any forge API into core. An unknown host with no extension falls back to the remote's web URL (honest, still a working browser path). An enabled extension's `compare_url_template` always wins over the table.
3. **The bundled GitHub extension serves github.com only in v1** (grill decision): enterprise/custom hosts are a post-v1 extension-side increment (a configured extra-hosts list) requiring zero core change, because remote matching is already extension-owned.
4. **Bundled GitHub extension at `extensions/forge/github/`** (embed + install + manifest + self-hosted subprocess rpc), enabled through the same managed-install path as `dev-cycle`.
5. **Credential model — secret binding canonical, `gh` CLI opportunistic**: the manifest declares `requires_env = ["GITHUB_TOKEN"]`; the operator binds it via the existing extension secret-binding surface. When no binding exists, the extension probes the local `gh` CLI (`gh auth token`) and uses that credential, reporting `credential_source = "gh"` in `forge/capabilities`. With neither, forge affordances are absent and the zero-credential fallbacks (browser compare page, local merged evidence) carry the exit — always present regardless (ADR-004). A GitHub device-flow login is a post-v1 increment that would only change how the stored token is minted.
6. **The extension bundles no MCP sidecar, and agent-facing GitHub tools stay with the marketplace remote MCP entry.** The two surfaces stay independent: MCP OAuth tokens belong to the MCP connection and never cross into extension subprocesses.
7. **No forge credential ever transits logs, payloads, events, or the wire** — the binding resolves inside the extension launch env exactly like every other extension secret; `gh`-sourced tokens live only in the extension process.

## Alternatives Considered

### Alternative 1: Reuse the GitHub remote MCP OAuth token for forge calls

- **Description**: When `github-remote` MCP is authorized, the forge provider reads its token from `global_db_mcp_auth`.
- **Pros**: Zero additional setup for operators already using the GitHub MCP.
- **Cons**: MCP auth tokens are in the absolute redaction set (`internal/CLAUDE.md` Security Invariants) — handing them to an extension subprocess creates a new egress path for a fenced token class; the token is minted by GitHub's MCP OAuth app with that app's scopes and works against the REST API only incidentally today (audience-binding is where the ecosystem is heading); forge availability would couple to an unrelated tool-server connection; and no third-party forge gets an equivalent ride, making the bundled extension architecturally special — the exact asymmetry ADR-004 forbids.
- **Why rejected**: Breaks a security invariant and the uniform provider contract for a setup convenience the `gh` fallback already delivers.

### Alternative 2: Bundle the GitHub MCP sidecar in the extension kit

- **Description**: The extension ships `resources.mcp_servers.github` so one install covers agent tools + forge.
- **Pros**: One-extension story.
- **Cons**: Duplicates the marketplace remote entry (which already has first-class OAuth); the command-based sidecar would require the `github-mcp-server` binary locally and authenticate by PAT anyway; two GitHub MCP paths would coexist with different auth.
- **Why rejected**: The marketplace remote MCP is strictly better for agent tools; the extension should own only what is uniquely its job.

### Alternative 3: `gh` CLI as the only credential path

- **Description**: No binding; shell out to `gh` for everything (the synara/t3code model).
- **Pros**: Zero token management in Compozy.
- **Cons**: Breaks in environments without `gh`; departs from the extension secret model every other extension uses; headless/agent-driven setups have no bind-a-secret story.
- **Why rejected**: Fine as a fallback, wrong as the contract.

### Alternative 4: Device-flow OAuth in v1

- **Description**: The extension implements GitHub device flow, storing the minted token via the binding surface.
- **Pros**: Best first-run UX.
- **Cons**: OAuth app registration/ownership, token refresh lifecycle, and a login UX land in v1 for a convenience the binding + `gh` path already covers.
- **Why rejected for v1**: Deferred; it layers cleanly on the same binding later.

## Consequences

### Positive

- "Add GitLab support" is now literally an extension implementing three service methods — no core change, no credential special-casing.
- Truthful UI is enforceable at the data layer: no matching extension (or no credential) ⇒ `forge/capabilities` says so ⇒ PR affordances are absent, not disabled (BR-30).
- The redaction story is uniform: one secret class (extension env binding), one resolution path, plus a process-local `gh` token that never leaves the extension.

### Negative

- Operators without `gh` must create a token and bind it — more friction than OAuth until the device flow ships.
- `gh` probing adds an availability axis the extension must report honestly (`credential_source`, plus its absence).

### Risks

- Forge data is a network-derived cache: staleness must be marked per BR-14/US-024 EC-2, and per-workspace scoping of cached forge rows must be leak-proof (covered by the `worktree_forge_status` side table keying in ADR-007).
- Rate limits / token expiry mid-session degrade to the absent-credential behavior with the cause named (US-032 EC-1/EC-3) — the service-method error contract carries a machine-readable cause.

## Implementation Notes

Service-method payload shapes, the manifest, and the `__internal extension-provider` wiring live in `_techspec.md`. Base-branch intent recording (`git config branch.<name>.gh-merge-base` at creation, t3code precedent) is core-side and feeds `forge/pr_create` inputs — the extension never resolves bases itself.
