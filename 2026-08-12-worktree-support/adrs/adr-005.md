# ADR-005: Central-Home Placement; the Session Boundary Extends to Attached Worktrees

## Status

Accepted

## Date

2026-08-11

## Context

Placement of created worktrees splits the market three ways: hidden inside the repo (Claude Code `.claude/worktrees/`), a central per-tool home (Conductor `~/conductor/workspaces/...`, Superset `~/.superset/worktrees/...`, and all three local competitor repos), and the hand-rolled sibling convention (`../repo-feature-x`). Conductor migrated from in-repo to central — a signal about how the trade-off resolves at scale. What has converged: the product picks the default and derives the path; the user never types one (analysis `05_analysis_market-worktree-ux.md`).

Compozy has a binding constraint the market doesn't: every session working directory is validated against the workspace root at creation, at loop-action bind, and on every prompt/resume; anything outside is rejected (analysis `06_analysis_worktree-entry-points.md`, Risk 1). A central-home worktree is outside the parent root by definition.

## Decision

- **Default placement is a central location under the Compozy home**, grouped per workspace, with product-derived directory names. The user never types a path during normal creation.
- The default location is **configurable** (global and per-workspace), and a per-creation override exists for power users and agents.
- **The session working boundary is extended by definition**: a session may run inside its workspace root *or inside any attached worktree of that workspace*. This is an explicit consequence of ADR-001 — worktrees are part of the parent workspace's trust domain — not a relaxation of the containment rule's purpose. Everything outside {workspace root + attached worktree roots} remains rejected exactly as today.
- Directory names derive from the worktree name; renames of the branch never silently rename the directory (display labels come from the worktree record, never from the path basename).

## Alternatives Considered

### Alternative 1: In-repo placement (`<workspace>/.compozy/worktrees/`)

- **Description**: Claude Code's model; worktrees live hidden inside the parent checkout.
- **Pros**: The only option requiring zero boundary change; discoverable next to the code.
- **Cons**: Pollutes the user's repo unless every repo gitignores the directory; known symlink-escape hazards; nested-checkout weirdness (a repo containing checkouts of itself confuses tooling — JetBrains warns against exactly this); inflates the project directory users sync/back up.
- **Why rejected**: Pushes a per-repo hygiene obligation onto every user repo; the boundary extension is a one-time, explicit product decision instead.

### Alternative 2: Sibling directories (`../repo-<name>`)

- **Description**: The classic manual convention.
- **Pros**: Visible in the file manager; matches long-standing user habit.
- **Cons**: Pollutes the directory *containing* the repo (which Compozy does not own); discovery scoping becomes fuzzy; same boundary extension needed as central home, with none of its tidiness.
- **Why rejected**: All of central home's costs, fewer of its benefits.

## Consequences

### Positive

- User repositories stay clean; `git status` in the parent never sees Compozy's worktrees.
- One predictable place on disk for everything Compozy created — inspectable, quotable, and cleanable.
- Grouping by workspace keeps per-workspace listing and cleanup trivial and leak-free.

### Negative

- Worktrees are not visible next to the repo in a file manager; the product's navigation and "open in editor/terminal" affordances must carry that discoverability.
- The boundary extension touches a security-shaped invariant enforced in multiple paths; it must be specified precisely (attached worktrees only — never arbitrary discovered paths) and tested as such.

### Risks

- Disk growth is real (market reports of tens of GB accumulating silently). The per-workspace grouping plus the assisted-exit cleanup suggestions (ADR-004, ADR-006) are the counterweight; the worktree list must make footprint legible.
- An adopted external worktree may live anywhere on disk (sibling, custom path); the boundary extension covers it because attachment — not location — is what grants session eligibility.

## Implementation Notes

The containment enforcement points and their exact behavior are catalogued in `analysis/06_analysis_worktree-entry-points.md` (Risk 1). The extension is "root OR attached worktree root", evaluated against the worktree registry — never a path-prefix heuristic.
